# development/audit-ledger Specification

## Purpose
缺陷台账供多个开发者各自使用的 AI（Claude Code、Codex）共同维护：AI 通过命令行工具按需读取和写入，写明谁用什么方式处理了每个问题，合并与发布状态由版本记录自动推导，减少通读与手改、避免互相覆盖。

## Requirements

### Requirement: 只读取需要的条目
台账 SHALL 提供命令让 AI 只读取需要的部分：列出未关闭的条目（每条一行：ID、标题、优先级、当前状态、当前负责人、最后更新），或读取单个 ID 的完整信息（基本信息、推导出的当前状态、全部处理记录、任务记录开头的「结论 / 下一步」）。AI 开始或接续缺陷任务时 SHALL 先列出未关闭条目，不需要通读全部历史。

#### Scenario: 开工先看未关闭的
- **WHEN** 台账共 255 条，其中 18 条未关闭，AI 运行列出未关闭条目的命令
- **THEN** 只输出这 18 条，每条一行

#### Scenario: 查看单个问题
- **WHEN** AI 查看 BUS-046
- **THEN** 输出它的标题、优先级、当前状态、当前负责人、全部处理记录，以及关联任务记录开头的「结论 / 下一步」

#### Scenario: ID 不存在
- **WHEN** AI 查看一个不存在的 ID
- **THEN** 提示该 ID 不存在，并以非零退出码结束

### Requirement: 处理记录写明谁用什么方式处理
每次写入 SHALL 追加一条处理记录，包含：时间（北京时间）、动作、开发者、方式、会话或任务 ID、Git 分支，以及说明或证据。开发者取本机 Git 用户名；方式与会话 ID 在 Claude Code 中自动识别，其他方式（Codex、手工）由调用方传入；分支取当前分支。缺少开发者或方式时 SHALL 拒绝写入。历史处理记录 SHALL 只追加、不修改、不删除。

#### Scenario: Claude Code 中认领
- **WHEN** 开发者 Ezio 在 Claude Code 会话中认领 UI-104，当前分支为 `fix/ui-104`
- **THEN** 处理记录写明开发者 Ezio、方式 Claude Code、该会话 ID、分支 `fix/ui-104`、时间

#### Scenario: Codex 中接手
- **WHEN** 另一位开发者在 Codex 任务中接手 UI-104，并传入方式 Codex 与任务 ID
- **THEN** 追加一条接手记录，当前负责人变为该开发者（Codex），原认领记录保留

#### Scenario: 缺少方式
- **WHEN** 在无法识别方式的环境里写入且没有传入方式
- **THEN** 拒绝写入并提示需要说明方式

### Requirement: 当前负责人与他人条目的保护
当前负责人 SHALL 取最近一次认领或接手记录中的开发者与方式；条目关闭或判为不适用后不再有负责人。没有负责人的条目任何人可以认领，已关闭的条目任何人可以重开（重开者成为负责人）。迁移前的历史负责人无法确认具体开发者，按「不同开发者」处理。对已有负责人的条目进行认领、关闭、暂缓、判为不适用、重开时：

- 同一开发者、同一方式：直接执行。
- 同一开发者、换了方式或会话（例如从 Claude Code 换到 Codex）：工具 SHALL 先自动写入一条接手记录（注明从哪个方式、会话转来），再执行原操作，不需要调用方额外操作。
- 不同开发者：SHALL 拒绝，只允许追加备注；只有该开发者明确同意转交后，才可以用接手命令接手（需写明同意来源）。

#### Scenario: 同一开发者换工具自动接手
- **WHEN** UI-104 由 Ezio 在 Claude Code 中认领，之后 Ezio 在 Codex 任务中关闭它
- **THEN** 先自动写入一条接手记录（从 Claude Code 会话转到 Codex 任务），再写入关闭记录，条目关闭

#### Scenario: 不能关闭别人负责的条目
- **WHEN** UI-104 当前负责人是另一位开发者，Ezio 的 Claude Code 会话尝试关闭它
- **THEN** 拒绝，提示当前负责人是谁、可以追加备注，以及只有对方同意后才能接手

#### Scenario: 对方同意后接手
- **WHEN** 对方开发者同意转交，Ezio 的会话用接手命令接手 UI-104 并写明同意来源
- **THEN** 写入接手记录，之后可以正常关闭

### Requirement: 提示信息说明下一步
命令被拒绝或缺少参数时，提示 SHALL 用中文说明原因，并给出可直接执行的下一步命令，或说明需要向谁确认，使 AI 不依赖人工提醒即可继续。所有命令 SHALL 提供简短帮助，列出用法与示例。

#### Scenario: 缺少方式时给出命令
- **WHEN** 在 Codex 中写入且没有传入方式
- **THEN** 提示无法识别使用的工具，并给出带 `--via Codex --session <任务ID>` 的完整命令示例

#### Scenario: 关闭缺证据时给出格式
- **WHEN** 关闭时没有提供验收方式与证据
- **THEN** 提示缺少的项目，并给出带 `--method` 与 `--evidence` 的完整命令示例

### Requirement: 合并与发布状态自动推导
条目的当前状态 SHALL 由记录与版本信息共同得出，不手工记录合并与发布阶段：

- 已关闭、暂缓、不适用：取最近一次对应的处理记录（重开之后以重开为准）。
- 否则按关联的 PR 与提交推导：还没有关联 PR 或提交为「处理中」；PR 未合并为「待合并」；提交已进入 `develop` 但不在任何发版标签中为「已合并待发布」；提交已在某个发版标签中为「已发布待验收」，并给出最早包含它的版本。
- 能查询发版运行结果时，部署失败的版本显示为「部署失败」；查询不到时显示版本并注明「部署结果未核实」。

推导 SHALL 只读取本地 Git 与可选的 GitHub 查询，不修改台账数据。

#### Scenario: 合并后自动变为待发布
- **WHEN** UI-104 关联的 PR 已合并进 `develop`，还没有发版
- **THEN** 查看时状态为「已合并待发布」，台账数据没有被改动

#### Scenario: 发版后自动变为待验收
- **WHEN** 包含该提交的 `v1.33.0` 已发布且发版运行成功
- **THEN** 状态为「已发布待验收」，并显示版本 `v1.33.0`

#### Scenario: 查不到部署结果
- **WHEN** 本机没有可用的 GitHub 查询
- **THEN** 状态仍按标签推导，并注明「部署结果未核实」

### Requirement: 写入校验
写入 SHALL 校验，不通过时拒绝并说明原因，台账保持不变：

- 关闭需要验收方式（本机、生产、自动化测试等）与证据；
- 暂缓需要原因与回顾日期；
- 判为不适用需要理由与确认人；
- 已关闭的条目只能重开或追加备注；
- 新问题 SHALL 由工具按类别分配下一个未使用的编号，已有 ID 不重排、不复用。

#### Scenario: 关闭缺少证据
- **WHEN** AI 关闭 UI-104 但没有提供证据
- **THEN** 拒绝写入并提示需要验收方式与证据

#### Scenario: 暂缓缺少回顾日期
- **WHEN** AI 暂缓 DEP-012 但没有提供回顾日期
- **THEN** 拒绝写入并提示需要回顾日期

#### Scenario: 新问题分配编号
- **WHEN** UI 类已用到 UI-103，AI 新建一个 UI 类问题
- **THEN** 分配 UI-104

### Requirement: 多人并发维护
台账数据 SHALL 每个 ID 独占一行，写入只改动对应 ID 的行，使不同开发者同时修改不同条目时版本合并不冲突。写入 SHALL 先重新读取最新数据；一次命令只写一次，写入失败时数据保持原样。

#### Scenario: 两人改不同条目
- **WHEN** 两位开发者分别在各自分支关闭 UI-104 与 BUS-090，先后合并
- **THEN** 两次合并都没有冲突，两条都关闭

### Requirement: 使用规范随仓库提供
`audit/` 的使用规范 SHALL 写在仓库里，任何开发者的 AI（Claude Code、Codex）开工时都能自动获得，不依赖某个 AI 自己的记忆或人工提醒。规范分三处，内容一致：

- `AGENTS.md`（Claude Code 与 Codex 都自动加载）：完整但简短的操作规则，覆盖什么情况用 `audit/`、开工第一步、只经工具写入、发现新问题如何编号、负责人规则、何时可以关闭、汇报范围、不写 Wiki。
- 工具的 `guide` 命令：输出同一份操作规则，供任务中途查阅；`open` 的输出末尾附一行提示可运行 `guide`。
- `audit/09-remediation/README.md`：命令说明、状态含义、证据要求与示例。

#### Scenario: 新会话自动知道怎么用
- **WHEN** 另一位开发者的 Codex 在新任务中处理一个用户反馈的缺陷，没有人提醒台账规则
- **THEN** 它从自动加载的 `AGENTS.md` 得知先运行 `open`、新建 ID、经工具认领与关闭，并在写入时带上 `--via Codex --session <任务ID>`

#### Scenario: 中途查阅
- **WHEN** AI 在任务中途不确定是否可以关闭某个条目
- **THEN** 运行 `guide` 得到与 `AGENTS.md` 一致的操作规则

### Requirement: 使用规范的内容
使用规范 SHALL 写明：缺陷、审查发现、用户反馈的问题记在 `audit/`，新功能走 OpenSpec；修复时发现未登记的问题先查重再新建 ID 并一并处理；整改进度只记在 `audit/`，不写进知识库；别人负责的条目由其自行验收；汇报时只讲自己负责的条目，暂缓项不重复列出。

#### Scenario: 修复中发现新问题
- **WHEN** AI 修复 UI-104 时发现另一个没有登记的界面缺陷
- **THEN** 先查是否已有 ID，没有就新建 ID、认领并一并修复，不只写「未处理」

#### Scenario: 汇报台账
- **WHEN** 用户问台账还有什么要处理
- **THEN** AI 只列自己负责、需要处理的条目，别人负责的最多一句说明归属，暂缓项不列出

### Requirement: 台账自检
台账 SHALL 提供自检命令供本机与 CI 使用：格式正确、ID 唯一且符合编号规则、处理记录字段齐全、引用的任务记录文件存在。暂缓条目超过回顾日期时 SHALL 列出提醒但不判为失败。

#### Scenario: 引用的任务记录不存在
- **WHEN** 某条记录引用的任务记录文件已被删除
- **THEN** 自检失败并指出该 ID 与缺失的文件

#### Scenario: 暂缓到期提醒
- **WHEN** DEP-005 的回顾日期已过
- **THEN** 自检通过，并列出 DEP-005 需要重新评估

# system/data-encryption Specification

## Purpose
规定敏感数据（加密的系统参数、供应商收款人身份证号、AI 服务的 API Key 等）加密存储与解密的方式，保证数据库与备份中只有带认证的密文。

## Requirements

### Requirement: 带认证的加密存储
需要加密存储的敏感数据 SHALL 使用 AES-256-GCM 加密：密钥由部署配置 `AES_KEY` 经 HKDF-SHA256 派生为 32 字节，不在数据库中保存；每次加密使用新的随机 12 字节初始向量，附 128 位认证标签。存储格式为 `v2:` 加 Base64(初始向量 ‖ 密文 ‖ 认证标签)。空值不加密，按原样存储。

#### Scenario: 同一明文两次加密结果不同
- **WHEN** 同一个值先后加密两次
- **THEN** 两个密文都以 `v2:` 开头且互不相同，各自都能解密回原值

#### Scenario: 数据库中只有密文
- **WHEN** 保存一个加密的系统参数或收款人身份证号后查看数据库字段
- **THEN** 字段以 `v2:` 开头，不包含明文

#### Scenario: 空值
- **WHEN** 加密的值为空字符串
- **THEN** 按空字符串存储，读取时返回空字符串

### Requirement: 密文被篡改时拒绝解密
解密 SHALL 校验认证标签；密文、初始向量或标签被改动，或用不同的 `AES_KEY` 解密时，系统 SHALL 报错，不返回任何部分明文。非空密文没有 `v2:` 前缀时，系统 SHALL 直接报错，不尝试按其他格式解密。

#### Scenario: 密文被改动
- **WHEN** `v2:` 密文中任意一个字节被改动后解密
- **THEN** 解密失败并报错，不返回内容

#### Scenario: 换了 AES_KEY
- **WHEN** 用另一个 `AES_KEY` 解密原来的 `v2:` 密文
- **THEN** 解密失败并报错

#### Scenario: 没有 v2 前缀
- **WHEN** 解密一个非空且不以 `v2:` 开头的值（例如旧的 AES/ECB 密文）
- **THEN** 解密失败并报错，不返回内容

## Context

- 报价单行（`quotation_item`）引用成本来源询价记录 `cost_quote_id`，询价记录有回价时间 `quoted_at`；报价行已有一组橙色提示（`hints`，建议主管核价等），显示在型号下方。
- 标为已发送有三个入口：详情页顶部的发送方式下拉、文件下载后询问、文字报价弹窗，最后都走详情页的 `markSent(channel)` 和后端 `QuotationServiceImpl.markSent`。
- 供应链第一期：需求对象（品牌 + 归一化型号）有覆盖状态四档、证据有效天数设置、系统处理记录（`sc_followup_log`，按「租户 + 来源类型 + 来源 ID」唯一）和系统提醒（`reminder_type` + 下一步）；询价回价已经通过事件联动（`QuoteLinkage`）。
- 采购：采购订单有预计发货日 `expected_ship_date`、状态（草稿 / 已下单 / 已取消）、取消原因；供应商发货记录（在途 / 已入库 / 已作废）；到货差异（少发 / 不良 / 多发）。
- 模块关系：supply 只通过自己的 Mapper 用 SQL 读其他模块的表，quotation 与 supply 互不引用。

## Goals / Non-Goals

**Goals:**

- 销售在报价单上直接看到哪些型号的成本旧了、货源不稳，发送前必须确认。
- 采购延期、取消、少发、不良第二天出现在该型号的时间线和负责人的今日待办上，「可直接报价」自动降为「需确认」。

**Non-Goals:**

- 不从供应链跟进直接发起询价任务（见 proposal「不在本期」）。
- 不做供应商评分和分级，不统计供应商履约率（第四期）。
- 不阻止销售报价：确认后照样能发，系统只要求看过、留痕。
- 不改报价单给客户看的内容。

## Decisions

1. **提示实时计算，不入库。** 报价详情在草稿或修改中的版本上计算提示，随详情返回（`QuotationItemVO.supplyHints`）。
   - 备选是生成报价行时写进 `hints`。不采用：覆盖状态、证据天数每天都在变，存下来会过时。
   - 一张报价单的计算：批量读询价记录回价日期 1 次，按品牌 + 型号批量读需求对象 1 次。

2. **依赖方向：quotation 定义接口，supply 实现。** quotation 包里放接口 `QuoteSupplyHints`（入参：行 ID、品牌、型号、成本询价记录 ID；出参：行 ID → 提示文字列表），supply 提供实现。没有实现时（例如单元测试）视为没有提示。
   - 这样 quotation 不引用 supply 的实体，supply 也只多依赖一个接口。

3. **发送确认前后端都校验。**
   - 前端：`markSent` 发送前看当前版本里有提示的行，有就先弹确认窗，勾选后带 `supplyConfirmed=true` 调接口。三个发送入口都走这个函数，不用分别改。
   - 后端：`markSent` 在锁住报价单后重新计算当前要发送版本的提示，有提示且 `supplyConfirmed` 不为 true 时抛业务异常，消息「有 N 个型号的成本或货源要先确认」。
   - 「记一次发送」（已发送的当前版本再发）不校验：内容和上次一样，已经确认过或发送时还没有这项功能。

4. **确认留痕走提交后事件。** 发送确认后 quotation 发布 `QuoteSupplyConfirmedEvent`（租户、报价单号、发送人、各行的品牌 / 型号 / 提示）。supply 用 `@TransactionalEventListener`（提交后）在当前请求线程另起事务写处理记录，失败只记日志，与品类细分补齐的做法一致。
   - 处理记录为人工记录（发送人），来源类型 5「报价发送确认」，来源 ID 为报价行 ID（每个版本的行 ID 不同，一行只记一次）。
   - 报价单操作日志另记「发送前确认供应：N 个型号」。

5. **履约异常每天扫描一次，接在每日任务里。** 在 `SupplyDailyJob` 里每个租户导入信号、补齐品类之后，重算优先级与覆盖之前，执行 `FulfillmentFeedback.scan(today)`。
   - 备选是在采购、仓库的保存事务或提交后事件里实时回写。不采用：要在采购下单、取消、到货差异、供应商发货多个入口埋点，而延期本来就只能靠每天比较日期发现。一天的延迟可以接受。
   - 来源类型：6 采购延期（来源 ID 为采购行 ID）、7 采购取消（采购行 ID）、8 到货差异（差异 ID）。唯一键已有，重复扫描靠插入冲突跳过。
   - 延期判断用订单级发货：订单有任何一条未作废的供应商发货记录或入库记录就不算延期。预计发货日改后又延期的，同一采购行不再重复记录。
   - 只看预计发货日在近 30 天内的订单，并排除从飞书迁移的历史订单（`migrated = 1`）。本机数据里迁移订单有 1000 多张早已过了预计发货日、却没有发货记录（迁移时没有补发货记录），不排除会一次产生大量误报。
   - 取消、到货差异看近 30 天；第一次运行同样只看近 30 天，不回溯更早的历史。
   - 型号匹配与询价证据一致：型号行品牌用 `BrandResolver` 识别，型号用 `MpnNormalizer` 归一化；品牌识别不到的跳过。

6. **降级与提醒复用第一期规则。**
   - 只降「可直接报价」到「需确认」，用 `CoverageService.change(…, "履约异常")`，操作日志记为系统。其他状态不动。
   - 提醒类型 5「履约异常」，文字「采购 PO… 延期 / 取消 / 少发 / 不良，确认渠道是否可靠」。写提醒沿用 `DemandRecalc` 的规则：人定的下一步还没到期时不覆盖，只在时间线留一条。把这段规则从 `DemandRecalc` 提成可复用的方法。
   - 每条异常一个事务；一条失败只记日志，其他照常。

7. **处理记录不显示供应商名称。** 内容只写采购单号、日期和数量；供应商在采购单里，看得到采购单的人自然能看到。这样不用按「查看货源信息」权限处理记录内容。

8. **数据库只改注释。** `sc_followup_log.source_type`、`sc_demand.reminder_type` 增加取值，迁移 V1.5.37 只更新这两列的注释，可回退。

## Risks / Trade-offs

- [提示太多，销售习惯性勾选] → 只提示两类、每行最多两条，确认弹窗逐行列出；时间线留下是谁确认的，主管能抽查。
- [延期误报：供应商其实发了货，采购没登记发货记录] → 处理记录写明「没有供应商发货记录」，提醒负责人核实；同时促使采购补登发货。
- [每日扫描有一天延迟] → 可以接受；到货差异、取消第二天就能看到。
- [品牌写法不统一导致匹配不上] → 与询价证据同一套识别，识别不到的跳过，不误改别的型号。

## Migration Plan

- 迁移 V1.5.37：只改两列注释，回退脚本恢复原注释。
- 后端、前端一起发布；编排服务无改动。
- 上线后第一次每日任务只处理近 30 天的取消、到货差异和预计发货日在近 30 天内的延期，提醒数量有限。

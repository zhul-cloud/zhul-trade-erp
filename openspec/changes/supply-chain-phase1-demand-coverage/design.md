## Goals / Non-Goals

**Goals:**

- 一个地方看到全部需求信号，同一型号不重复。
- 一眼看到无货有多少、集中在哪些品牌和品类，并能指定人限期解决。
- 每个重点需求有一个明确、有证据、会过期的覆盖状态。
- 打开供应链跟进就知道今天该处理哪几条。

**Non-Goals:**

- 不让用户在 25 个节点之间手动推进状态。节点只用来对照 SOP，系统里表现为信号、需求、覆盖这三样东西各自的状态。
- 不做供应商能力分级（A/B/C/D）、渠道搜寻与验证任务、试单——第二期。本期的专项只管范围、负责人和进度。
- 不在报价时强制校验覆盖状态——第三期。
- 不做平台关键词自动抓取、不做评价抓取。
- 不存金额，不做毛利潜力、客户价值的金额打分。

## Decisions

1. **覆盖状态用四档**（用户 2026-11-13 确认）：可直接报价、需确认、有线索未验证、无渠道。地图上的「已覆盖 / 弱覆盖 / 缺口」分别对应第一档、第二三档、第四档。另有「暂不覆盖」不是覆盖状态，是需求对象的状态（决定不做的需求不进矩阵）。

2. **需求信号独立成表，自动来源每天汇入一次。** 定时任务每天凌晨按租户读取前一天新增的询盘型号行、销售订单行、无货的询价记录、标为未成交的报价单型号行，各写一条信号。幂等键为「来源类型 + 来源行 id」，重复执行不重复写。
   - 备选是在询盘、订单的保存事务里实时写信号。不采用：会把新模块的故障带进核心单据的事务。
   - 事务边界：每个租户、每种来源一个事务；某个租户失败不影响其他租户，下次执行补上。
   - 来源单据后来被取消或删除，信号保留（需求真实出现过），但带「来源已取消」标记，不计入近 90 天次数。
   - 「丢单」取报价单未成交。商机输单没有型号，不汇入。

3. **需求对象以「品牌 + 归一化型号」为键**，归一化规则与询价记录、商品主数据相同。没有型号的信号（搜索词、调研常见）归到「品牌 + 二级品类」级的需求对象。自动汇入的信号品牌和型号都能识别时自动归类；识别不到品牌、或人工录入时没填全的，进「待归类」由人处理。

4. **需求等级由系统按信号推出，不能手改：**
   - 观察：只有搜索词或同行调研。
   - 重复：观察类信号来自两个以上来源，或出现两次以上。
   - 已验证：有询盘。
   - 商业：有销售订单或报价单（含未成交）。

5. **优先级系统给建议，人可以改，改时必须写理由。** 建议规则只用次数（近 90 天、不含来源已取消的）：
   - 高：询盘 3 次及以上；或有成交且出现过无货；或因货源类原因未成交（未成交原因属于「交期/物流」分类）2 次及以上。
   - 中：询盘 2 次；或有成交。
   - 低：其余。
   人工改过的优先级不再被系统覆盖，系统建议与它不一致时进入「需求情报」板块的「待复核」。阈值先写死，用一段时间后再决定要不要做成可配置。

6. **高、中优先级的需求自动进入覆盖矩阵；低优先级的可以手动加入。** 进入时系统给建议状态：

| 条件（按顺序判断） | 建议状态 |
|---|---|
| 有效期内有该型号的有价询价记录，或有效期内有已下单的采购订单行 | 可直接报价 |
| 有该型号的有价询价记录或采购订单行，但都已过期 | 需确认 |
| 没有该型号的价格记录，但有供应商主营该品牌（及品类） | 有线索未验证 |
| 以上都没有 | 无渠道 |

   有效期 = 系统设置「供应证据有效天数」，默认 30 天，按证据日期（询价日期、下单日期）算。品牌 + 品类级的需求对象没有型号，只在后两档里判断。

7. **状态由人确认，但系统守两条底线：** 没有有效期内证据不能标「可直接报价」；已标「可直接报价」的条目证据过期后，定时任务自动降为「需确认」并记操作日志。其余改动（如把系统建议的「可直接报价」改成「需确认」）随意，需写说明。

8. **主渠道、备选渠道存为覆盖渠道表**（需求对象 + 供应商 + 主 / 备），供应商来自供应商库。证据不复制，页面按「该供应商 + 该型号」读最近一条有价询价记录或采购订单行，显示价格、币种、货况、货期和日期。只有一个渠道或没有备选的「可直接报价」「需确认」条目算「单一渠道依赖」。

9. **数据范围：只按租户隔离，不受个人数据范围限制**（与询价记录一致）。供应商名称和渠道只对有「查看货源信息」的人显示，没有该权限时覆盖矩阵仍可看状态和数量，看不到是哪家供应商。

10. **页面结构照客户跟进**（用户 2026-11-13 确认）。原来设计的「供应链工作台」「需求池」两个页面合成「供应链跟进」一个页面：今日待办 + 五个板块 + 阶段导航 + 分组列表 + 作战卡 + 记一次处理 + 我的 / 团队。理由：两个模块思路一致，用户学一次就够；地图（板块与阶段）和方法（作战卡）直接出现在干活的地方，不用另做说明页。差别只有两处：
    - 分组的对象从「客户」换成「品牌 · 品类」，下面挂的从单据换成型号；
    - 数字按型号统计，不按组统计（「无货 14 个型号」比「无货 5 个品牌品类」有用）。

11. **阶段不是手动推进的状态，而是由数据推出来的位置。** 需求情报的三个阶段取自信号与优先级，供应覆盖的四个阶段就是四档覆盖状态。每个阶段对应作战地图上的节点，用来取作战卡内容（映射见 `supply-chain/followup`「板块内按阶段导航」）。作战卡内容首次从五份 SOP 分册导入，存成系统数据，不写死在代码里。

12. **系统提醒只在四种情况产生**：出现询价无货、证据过期、新进入矩阵待确认、重点缺口没有下一步。由每天的定时任务在汇入信号、重算建议状态之后一并生成，写到需求对象的下一步行动与行动日期上（来源标为系统）；人定的下一步未到期时不覆盖，只在详情时间线上留一条提醒。事务边界：与同一租户的重算在同一个事务里。

13. **无货的口径**（用户 2026-11-13 确认）：默认近 30 天，可切换近 90 天；按型号去重算「无货型号数」，同时显示次数；无货率 = 无货型号数 ÷ 同期询过价的型号数，保留一位小数，四舍五入。板块卡片上的「无货 n」只算还没解决的（当前不是「可直接报价」）。无货数据直接来自「询价无货」信号，不另建表。

14. **专项是原定第二期「缺口开发任务」的简化版，提前到本期**（用户 2026-11-13 确认）。只有范围（品牌 + 品类）、目标、负责人、截止日期和型号清单，进度由型号的覆盖状态自动算，不做审批、不做子任务。第二期的供应商开发与验证接上后，专项下再挂验证任务。

15. **处理记录单独成表**，一条记录可以涉及多个型号（记录表 + 涉及型号用 JSON 数组存 id，按需求对象查时间线走关联查询）。记处理在一个事务内完成：写记录 → 改所选型号的覆盖状态 → 更新下一步与负责人 → 写操作日志；改状态前在事务内重新校验证据。

## Risks / Trade-offs

- [自动汇入量大，信号表增长快] → 只汇入能识别出型号或品牌的行；按来源行幂等；列表默认只看近 90 天。
- [建议状态不准，用户不信任] → 建议与确认分开显示，页面上写明依据是哪条记录；人工确认优先。
- [覆盖矩阵建好后没人维护] → 证据过期自动降级 + 今日待办提醒；第二期的验证任务接上后有明确的责任人。
- [优先级阈值不合适] → 先写死并在页面上显示命中了哪条规则，上线后按实际数据调整。
- [品牌识别不到的询盘行很多，待归类积压] → 待归类支持批量归到同一需求对象、批量忽略。

## Migration Plan

- 新增六张表与菜单、按钮资源、一项系统设置，并导入作战卡内容；加进含「采购管理」菜单的套餐，授给内置租户管理员，其他角色由管理员授权。
- 上线后首次执行汇入时回溯近 180 天的询盘、订单、无货、未成交，之后每天增量。
- 回退：删六张表、资源与系统设置；不影响其他模块。

## 后三期路线（各自另开变更）

- **第二期 供应商能力验证与可报价供应池**（V1–V5、M5）：缺口开发任务、渠道搜寻与资格审查、货源与条件验证、按品牌 / 品类分别评 A/B/C/D。覆盖状态的依据从「有没有价格记录」升级为「有没有验证通过的供应商」。
- **第三期 报价与履约协同**（Q1–Q5）：报价时提示覆盖状态，证据过期强制先确认；采购延期、缺货、错型等异常回写覆盖状态。
- **第四期 供应商评分与复盘**（G1–G5）：按响应、交期、质量、异常算供应商表现，赢丢单与履约复盘，升降级与淘汰，新缺口回到需求情报。

## 已确认的默认值（用户 2026-11-13 确认先按建议来）

- 「供应证据有效天数」默认 30 天，现货与期货先不分开；用一段时间后按实际情况再调。
- 优先级规则的阈值（3 次、2 次、近 90 天）先按决策 5 写死。
- 不新建内置角色。菜单与按钮先授给内置租户管理员，由管理员在角色管理里授给采购负责人等角色。

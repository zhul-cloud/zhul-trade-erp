# Design

## Context

- **生产存储与网站入口**：生产用阿里云 OSS（`STORAGE_TYPE=oss`），网站经 Cloudflare 访问，单个请求上限 100MB；`application.yml` 的 multipart 上限按此设为约 95MB。
- **现有上传**：询盘附件由后端整份接收（`InquiryConstants.ATTACHMENT_MAX_BYTES` 10MB），再写入存储；下载走后端签发的存储签名链接，不经过 Cloudflare 转发文件。
- **现有解析**：
  - 后端把 Excel 转成文字放进 `rawContent`（`SpreadsheetText`），图片和 PDF 以签名链接传给编排服务；
  - 编排服务整份读入内存，转为 base64，放进**一次**模型请求（`server.py` 的 `_attachment_block`）；
  - 订阅方式另有 25MiB、20 页的硬限制（`subscription.py`）。
- **期限**：编排服务每个任务总期限 900 秒（`AI_ORCHESTRATOR_TIMEOUT_SECONDS`）；后端超时扫描 20 分钟（`AI_TASK_TIMEOUT_MINUTES`），从任务创建时间算起。

## Goals / Non-Goals

**Goals:**

- 直传做成通用能力，询盘是第一个接入的场景；其他业务以后只需登记场景、换用组件。
- 能放进一次模型请求的小询盘，解析路径与结果不变，避免回归。
- 大文件解析不受单次请求、页数、订阅附件上限影响，进度可见，未解析的部分不丢失、可追溯。

**Non-Goals:**

- 不迁移其他模块的现有上传：商品视频、收货视频、供应商附件等保持原样，以后各自接入。
- 不做跨页面刷新的断点续传：上传会话在当前页面内可以继续；刷新页面后需要重新上传。
- 不改铭牌图片的规则，不支持压缩包。
- 不改商机页面自己的附件规则（单个 10MB、最多 10 个）；只是带入询盘时按询盘的合计上限判断。
- 不改下载方式。

## Decisions

### D1 直传方式：后端逐片签名，浏览器直传 OSS

- **选择**：后端用现有 OSS 凭据发起分片上传（InitiateMultipartUpload），为每个分片生成签名的 UploadPart PUT 地址。浏览器只拿到这些地址，拿不到任何凭据。
- **签名锁定分片大小**：签名时把这一片的 `Content-Length` 一并签入（V4 签名的附加签名头），上传的字节数与签名不符时 OSS 直接拒绝（403），不能借一个分片地址传超大内容。2026-11-10 用开发桶实测：多 1 字节、少 1 字节都返回 403，长度正确的照常上传。
- **不选临时凭证 + 浏览器 SDK**：要新建 RAM 角色、授权策略和一组新密钥，运维更重；凭证的权限范围也比逐个签名的地址宽。
- **不选分片经后端中转**：服务器要转手 500MB 的数据，对现有服务器的带宽和磁盘都不划算。

### D2 上传会话

- **存储**：Redis 键 `zhul:erp:upload:{tenantId}:{uploadId}`，TTL 1 天，与 OSS 临时文件的清理期限一致。
- **会话内容**：租户、用户、场景、原文件名、声明大小、临时对象键、OSS uploadId、状态（上传中 / 已完成 / 已使用）、完成后的正式文件键。
- **生命周期**：
  - **准备上传**：校验场景、权限、扩展名和声明大小，创建会话，返回分片大小和第一批签名地址；
  - **续签**：按需领取后面分片的签名地址；
  - **完成上传**：后端合并分片，再做完成校验；
  - **取消上传**：后端中止分片上传并删除会话；
  - **业务保存时认领**（2026-11-10 改回认领方案）：完成上传、校验通过后，文件仍留在临时位置，返回临时文件键 `tmp/{租户}/{uploadId}.{ext}`。业务单据保存时凭这个键认领：必须是本租户、本人、该场景上传并通过校验的文件，认领时才转到正式文件键；同一文件再次认领（保存失败后重试）返回同一个正式键。传完却没保存到单据的文件留在 `tmp/`，和其他未完成的上传一样 1 天后被清理，不会在正式位置留下没人引用的大文件。其他附件（如从商机带入的、普通上传的铭牌图片）仍按 `FileStorageService.locate` 校验。上传过程中的每一步（续签、传分片、完成、取消）只能由发起上传的本人操作。

### D3 分片参数

- **分片**：每片 16MB，500MB 共 32 片；同时传 4 片；每片失败自动重试 3 次，间隔递增。
- **签名地址**：每次签发 8 片，有效期 15 分钟，快用完时续签。
- **断网后继续**：前端记住已完成分片的 ETag，从未完成的分片接着传。

### D4 完成校验与正式位置

1. CompleteMultipartUpload 合并分片；
2. HeadObject 核对实际大小不超过场景上限；
3. 按范围读取文件开头 8KB，用现有 `UploadRules` 的文件头判断类型；
4. 通过后文件留在临时位置（图片压缩后写回临时位置），等业务单据保存时认领；认领时用 CopyObject 在 OSS 内部复制到正式键（按「存储目录」规则，如 `tenant/{租户}/inquiry/{年月}/{随机名}.{ext}`），再删除临时对象。500MB 在单次 CopyObject 的 1GB 限制以内，复制不经过服务器。
5. 不通过就删除临时对象，并返回原因。

### D5 本地存储

存储方式为本地（`STORAGE_TYPE=local`）时，前端和上传流程与 OSS 完全一样，只是每片的上传地址换成后端自己的接口，文件写在服务器的私有上传目录。

- **上传地址**：「准备上传」返回的每片地址是 `PUT /api/v1/uploads/{id}/parts/{n}`，带这次上传会话的一次性令牌，令牌只对这次上传、这一片有效，15 分钟过期，和 OSS 签名地址一样续签。
- **经过网站入口也能用**：每片 16MB，远小于 Cloudflare 单次 100MB 和 Nginx `client_max_body_size 100m`。所以本地存储即使部署在 Cloudflare 后面，大文件也能传，不只限于开发环境。
- **写盘方式**：
  - 分片按请求体的流直接写入同一个临时文件的对应位置，即第 n 片写在 (n−1)×16MB 处，不把整片读进内存；
  - 乱序、重复上传同一片都正确；
  - 不先存成多个分片文件再拼接，避免临时占用两倍磁盘。
- **临时目录**：放在私有上传目录下的 `tmp/{租户}/{上传 ID}`，和正式目录在同一个文件系统上。
- **完成上传**：
  1. 检查每一片都已收到，按实际大小和文件头校验；
  2. 通过后用文件系统重命名移到正式路径（规则和 OSS 相同，如 `tenant/{租户}/inquiry/{年月}/{随机名}.{ext}`），只是改名，不复制；
  3. 不通过就删除。
- **清理**：本地没有 OSS 的生命周期规则，改由后端定时任务每小时扫描 `tmp/`，删除超过 1 天的未完成上传及其 Redis 会话。定时任务没有登录上下文，按多租户规范用 `TenantScope.platform` 执行，删除时只按目录和会话判断，不读业务表。
- **下载和 AI 解析**：和现在一样走后端签名链接（`LocalFileStorage.signedUrl`）。AI 编排服务按 D7 流式下载到自己的临时目录，不直接读共享目录（沿用 audit AI-003：编排服务只接受 http 链接）。
- **磁盘与内存**：
  - 默认 Compose 的 `private-uploads` 是 tmpfs，文件放在内存里，重启就没了。存储方式为本地、又要收大附件时，必须先按[数据持久化与备份](../../../docs/06-部署运维/03-数据持久化与备份.md)把它换成磁盘目录；
  - 后端启动时如果发现存储方式为本地、私有上传目录又在 tmpfs 上，在日志里明确警告「大附件会占用内存，重启后丢失」；
  - 「准备上传」时检查目录所在磁盘的剩余空间，不够「声明大小 + 1GB」时拒绝并提示「服务器存储空间不足」，不会传到一半才写满磁盘。

### D6 OSS 配置由部署方完成

- **跨域规则**：允许网站域名 PUT，允许任意请求头，暴露 ETag。
- **生命周期规则**：`tmp/` 前缀 1 天删除；未完成的分片上传 1 天后中止。
- 应用不改存储桶配置（不需要更大的 RAM 权限）。后端启动时只读检查跨域规则是否存在，缺少时在日志里给出明确警告，不阻止启动。

### D7 编排服务取附件改为流式写盘

`_read_attachment` 从整份读进内存，改为分块写入任务的临时目录；单个附件超过 500MB 时直接失败，任务结束后删除临时目录。

### D8 预处理统一放在编排服务

- **PDF（pymupdf）**：逐页提取文字，可提取文字足够的页按文字处理，否则按 150dpi 渲染、长边最大 2000 像素。加密文件、损坏的页记入「未解析」。
- **图片（Pillow）**：长边最大 2000 像素，转 JPEG 或 PNG。
- **Excel**：xlsx 用 openpyxl 只读流式读取，xls 用 xlrd，csv 按流读取；每行转成文字时带上表头。
- **逐个文件处理**：附件按顺序一个一个下载、预处理，处理完的原文件和渲染页面立即删除，只保留预处理后的文字和压缩后的图片。所以临时磁盘只取决于最大的单个文件（500MB）加上工作空间，与附件个数无关。
- **后端改动**：不再把 Excel 转成文字放进 `rawContent`，改为和 PDF 一样以链接传给编排服务。避免后端为 500MB 的 Excel 占用大量内存，小 Excel 的解析结果不变。
- **新增依赖**：编排服务加 openpyxl、xlrd。

### D9 分批与合并

- **预处理单元**：文字页、渲染页、一组 Excel 行。
- **每批上限**：不超过 8 张图片或渲染页、约 2 万字文字、18MB 数据，API 与订阅方式用同一套上限，在订阅方式单次调用的 25MiB、20 页以内。原定 20 张图 / 6 万字，2026-11-10 用 Codex 订阅实测一批要 14–15 分钟，贴着单次调用 900 秒的期限，改为约三分之一，让单批在 5 分钟左右完成。只需一批的小询盘仍按原来的 18MB、20 页、6 万字判断。
- **单次期限**：每次调用（含重试）都重新计算单次调用期限；单次调用到期只算这一批失败一次，按规则重试，只有整个任务的期限到了才让任务失败。
- **只需一批时**：沿用现在的单次请求，带联网搜索，行为不变。
- **需要多批时**：
  1. **提取**：各批并行，每个任务同时 3 批，只提取型号，不联网搜索；失败的批重试 2 次。
  2. **合并**：确定性代码按确认型号合并去重。型号转大写、去掉空格后比较，保留连字符。数量单位相同时相加，单位不同时保留第一行并标「待核实」；纠正说明附上出现位置（文件与页码或行号）。
  3. **核验**：去重后的型号每批 50 个，用文字请求并开启联网搜索做核验。
     - **搜索上限的口径**：租户设置的「最大搜索次数」改为按每次模型调用计算，每个核验批各自适用。整次解析的搜索次数 = 设置值 × 核验批数，随型号数量线性增长。
     - **只需一次调用的小询盘**：行为不变，上限就是整次解析的上限。
     - **为什么放宽**：这个上限是 2026-10-15（`1e7cc85e`）从 Claude Code CLI 改用 Anthropic API 时加的。API 没有「单次最多花多少钱」的开关，只能限制搜索次数来间接控制费用；订阅方式也靠它保护额度。按整次解析合计时，几百个型号的大清单大部分得不到核验，所以改为按调用计算，控制费用的作用仍在，只是不再随清单变大而失效。
- **回调结果**：新增 `unparsed`，列出文件、页码或行号范围和原因，用于确认页提示。

### D10 逐项容错：一处失败不影响其他

- **容错单位**：附件、页、Excel 行组、提取批、核验批各自独立。
  - 附件下载或预处理失败：记入 `unparsed`（文件名与原因）；
  - 页损坏：记入 `unparsed`（文件与页码）；
  - 提取批失败：重试 2 次，仍失败的记入 `unparsed`（页码或行号范围）；
  - 核验批失败或达到搜索上限：这批型号不核验、标「待核实」，不进 `unparsed`。
- **订阅方式达到搜索阈值**：仍按原规则终止这次调用（保护额度），但不再让整个任务失败，而是对同一批不联网重新提取，型号标「待核实」。
- **任务失败的唯一条件**：所有附件和文字都没能提取出任何型号，失败原因汇总 `unparsed` 里的前几条。
- **合并只用成功批次的结果**。所有批次的成败都写进编排服务日志（批次编号、范围、耗时、原因），不写业务内容。

### D11 进度与超时

- **编排服务**：每完成一批，就带当前的已完成批数和总批数报一次进度；超过 60 秒没有新完成的批也会报一次，作为心跳。
- **后端**：收到进度时只更新 `ai_task` 的进度和最后一次进度报告时间（迁移给 `ai_task` 增加这几个字段），不改变任务状态；任务结束后到达的进度报告忽略。
- **超时扫描**：
  - 从「最近一次回调或进度报告」与创建时间中较晚的一个开始计时；
  - 另设最长处理时长：新增配置 `AI_TASK_MAX_MINUTES`，默认 180。
- **编排服务的期限**：
  - 单次模型调用沿用 900 秒；
  - 整个任务的期限改为新增配置 `AI_ORCHESTRATOR_MAX_SECONDS`，默认 10200 秒，比后端最长处理时长短 10 分钟，留给回调重投。
- **询盘详情**：「解析中」显示「已解析 x / y」。

## Risks / Trade-offs

- [OSS 跨域规则漏配，浏览器上传在跨域这一步失败] → PR 和部署文档写明配置方法；后端启动时自检并告警；前端把跨域失败提示为「上传服务未配置好，请联系管理员」。
- [大文件解析费用高、时间长、订阅额度消耗快] → 上传完成后提示预计批数；进度可见；批数按页、行线性增长，没有放大。
- [每单附件合计可到 2GB、不限个数，编排服务临时磁盘吃紧] → 附件逐个下载、预处理，处理完即删（D8），临时目录留 2GB 空闲即可，写进部署文档。
- [附件个数不再限制后，一张询盘挂很多文件] → 每单合计 2GB 封顶；接口另有一次最多 1000 个文件键的技术兜底，防止一次请求触发上万次存储查询，正常使用碰不到，不作为业务上限。
- [整次解析的搜索次数随型号数线性增长，费用随之增加] → 上传完成后提示预计批数；编排服务日志记录每次解析的总搜索次数，便于核对费用；租户仍可调低每批上限。
- [跨批合并把不同型号误合并] → 只按规范化后的完整确认型号合并，不做模糊匹配；合并结果都会进确认页，由业务员确认。
- [D8 的 Excel 后端改动影响小询盘的现有结果] → 用现有带 Excel 的解析用例做回归，确认型号一致。
- [本地存储时大附件写满服务器磁盘，或默认 tmpfs 占满内存] → 准备上传时检查剩余空间；启动时发现 tmpfs 就告警；部署文档写明本地存储收大附件前必须改成磁盘目录。
- [直传后小文件也多了一次「准备 / 完成」往返] → 小文件只有一片，多两次请求，可以接受，换来所有场景只有一条上传路径。

## Migration Plan

1. **数据库迁移**：给 `ai_task` 增加进度和最后一次进度报告时间字段，只增不改，可以回退（回退脚本删除这几列）。
2. **新增配置项**：`AI_TASK_MAX_MINUTES`（后端）、`AI_ORCHESTRATOR_MAX_SECONDS`（编排服务）。写进 `.env.example`，PR 里写明生产取值；都有默认值，不填也能启动。
3. **OSS 配置**：发版前由有阿里云权限的人配置跨域规则和生命周期规则，详见 D6 和 `docs/06-部署运维/12-大附件直传与解析配置.md`。
4. **上线验收**：先在本机本地存储模式验收，再在生产用一个 200MB 以上的 PDF 验收上传和解析。
5. **回滚**：重新部署上一版即可。新增字段和临时文件不影响旧版本；已经直传上来的附件是普通存储文件，旧版本照常可以读取。

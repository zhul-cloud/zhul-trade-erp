## Context

采购需求（`purchase_requirement`）按销售订单型号行生成，一个型号行可拆成多条需求。可下单数量 = 需求数量 − 草稿中 − 已下单。型号行的自动进度在 `OrderPurchaseProgress` 里按「已下单数量 ≥ 型号数量」「合格入库数量 ≥ 型号数量」判断；型号行没有任何有效需求时视为「系统外采购」，不按采购推进。货物状态、到齐知会、订单成本也以型号数量为基准。

## Goals / Non-Goals

**Goals:** 删除需求里还没下单的数量；删掉的数量在订单进度、货物状态、到齐知会里按「不需采购」处理；可追溯原因和操作人。

**Non-Goals:** 不恢复已删除的数量（删错了可由业务员在销售订单重新安排，或后续另开变更）；不处理已下单的数量（走取消采购订单）；不改订单成本口径（还没下采购订单的数量本来就按报价成本估算）。

## Decisions

1. **字段**：`purchase_requirement` 增加 `removed_qty int NOT NULL DEFAULT 0`（删除的数量）、`remove_reason varchar(200) NULL`。部分删除时 `quantity` 减去删除数量、`removed_qty` 累加；整条删除时同样记 `removed_qty`，并写 `deleted_at`（软删除）。备选「只写 deleted_at、不记数量」无法支持部分删除，也无法在订单上显示删了多少。
2. **需采购数量 = 型号数量 − 该型号行所有需求（含已软删除）的 removed_qty 之和**。`OrderPurchaseProgress` 的「全部已下单」「全部入库」改为与需采购数量比较；需采购数量为 0（全部删除）时型号行没有有效需求，沿用系统外采购的处理。货物状态的「待采购」= 需采购数量 − 已下单数量；到齐知会同样按需采购数量。以型号行汇总 removed_qty，而不是对有效需求的 quantity 求和，避免存量数据（部分取消、拆分）口径不一致带来的进度跳变。
3. **草稿行**：删除时先把这条需求在草稿采购订单上的数量移出（复用拆分时扣草稿行的逻辑：扣到 0 删除该行，草稿没有行时删除草稿），再改需求。已下单采购订单上的数量不动。
4. **事务边界**：一次删除在一个事务内完成（需求、草稿行、型号行进度重算、两处操作日志），对需求加行锁，防止与下单、拆分并发。
5. **权限**：新按钮权限 `purchase:requirement:delete`；迁移时授予已有 `purchase:requirement:split` 的角色。数据范围与列表一致（只能删自己能看到的需求）。
6. **原因**：前端三选一 + 说明，后端存为「仓库有库存：说明」这样的一段文字（≤200 字）；选「其他」时说明必填。

## Risks / Trade-offs

- 删错无法撤销 → 弹窗列出将删除的数量与受影响的草稿，二次确认；日志可查。
- 进度口径改动影响已有订单 → 只有删除过的型号行 removed_qty > 0，其余型号行的需采购数量等于型号数量，结果不变；用契约测试覆盖。

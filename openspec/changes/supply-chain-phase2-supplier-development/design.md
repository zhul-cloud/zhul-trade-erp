## Context

- 第一期（`supply-chain-phase1-demand-coverage`，PR #304、#309）已有：
  - 需求对象（品牌 + 二级品类 + 型号，带优先级）
  - 覆盖状态与证据索引 `EvidenceIndex`：证据取自询价记录 `sourcing_quote` 和采购订单行 `purchase_order_item`
  - 专项 `sc_gap_project` / `sc_gap_project_item`
  - 处理记录 `sc_followup_log`
  - 每日定时任务、回价事件联动
  - 供应链跟进的五个板块，前两个已开放
- 供应商主营产品表 `supplier_product_scope` 记录「供应商 × 品牌 × 二级品类」，品类为空表示该品牌全部品类。
- 第一期设计里，第二期原定是 V1–V5 的完整验证与分级。用户 2026-11-14 把重点调整为「公司还需要开发哪些品牌品类的供应商」，分级和验证延后。动机见 proposal.md。

## Goals / Non-Goals

**Goals:**

- 合格家数、要求家数、缺口实时算，不存快照，与第一期证据口径一致。
- 开发任务复用专项，用户不用多学一个概念。
- 候选从线索到合格全程可追踪，合格由数据自动判定，不靠人报。

**Non-Goals:**

- 不做供应商 A/B/C/D 分级、资格审查表单、样品与试单（第三期）。
- 不做外部渠道的自动搜寻（平台抓取、搜索引擎）。
- 不改供应商库：候选不自动在供应商库建档。
- 热度与要求家数不做配置页面。

## Decisions

1. **开发任务复用专项，不另建实体。** 专项本来就是「一个品牌 + 品类、一个负责人、一个截止日期」，第一期设计也预留了「专项下再挂验证任务」。
   - 做法：专项加一个可空字段 `supplier_target`（目标家数），有值就表示带开发目标。
   - 备选是独立的开发任务表。不采用的原因：同一个品牌品类会同时出现「专项」和「开发任务」两样东西，负责人、截止日期各维护一份，用户要分清两者的区别。
   - 代价：第一期「至少一个型号」和「品类可不选」的规则对带开发目标的专项要放宽或收紧，见 `supply-chain/gap-project`。

2. **合格供应商实时计算，复用第一期的证据规则。**
   - 在第一期的证据读取上加一个按范围汇总的方法：读近 90 天的有效询价记录和已下单的采购订单行，得到「品牌 × 二级品类 → 供应商集合」。
   - 证据归到哪个范围，按以下顺序判断：
     1. 型号已有需求对象的，取需求对象的品牌与品类；
     2. 询价记录和采购订单行都取商品主数据的品牌与品类（询价记录按型号匹配商品主数据，与采购订单行同一口径），商品主数据的品类不是二级品类时按未分类处理；
     3. 都取不到品类的，归到「品牌 · 未分类」，取不到品牌的丢弃。
   - 供应商须为启用且未删除。
   - 不存快照：每个租户的数据量在万级以内，一次请求内建好索引就够用。第一期 `EvidenceIndex.Snapshot` 已经按这种方式工作。
   - 90 天写成常量，与第一期 30 天的「供应证据有效天数」是两个口径：
     - 30 天判断一个型号现在能不能直接报价；
     - 90 天判断一家供应商算不算在这个品牌品类里活跃。

3. **热度只由需求对象的优先级推出，不新增打分。** 规则见 `supply-chain/supplier-development`。
   - 第一期的优先级已经综合了询盘次数、成交和无货，再叠一层分数会让两套规则对不上。
   - 要求家数 3 / 2 / 1 先写死，与第一期阈值的处理方式一致，用一段时间后再决定是否配置化。

4. **新增三张表**，都带 `tenant_id`，在 `TenantTables` 归为私有，软删除：
   - `sc_expansion_scope`（主动拓展范围）：品牌、二级品类、热度、理由、负责人。同一租户、同一范围只能有一条有效记录：用生成列 `active_scope`（未删除时为「品牌-品类」，删除后为空）加唯一键实现。
   - `sc_dev_candidate`（候选供应商）：
     - 字段：专项 id、供应商 id（可空）、名称、联系人、联系方式、来源、阶段、放弃原因、合格依据（证据类型 + 证据 id + 日期）、下一步行动与日期、负责人；
     - 同一专项、同一供应商 id 唯一。
   - 候选的处理记录不另建表，直接写入第一期的 `sc_followup_log`：
     - 新增「对象类型」字段 `object_type`（1 型号 / 2 候选）和 `candidate_ids`（候选 id 的 JSON 数组）；候选记录的 `demand_ids` 为空，第一期按 `demand_ids` 查询的时间线不受影响；
     - 专项详情把型号记录和候选记录按时间合并显示。
   - 第一期 `sc_gap_project` 加 `supplier_target` 字段。

5. **候选自动合格走两条路**，与第一期回价联动的方式相同：
   - **回价事件**：第一期 `QuoteLinkage` 在询价记录生效后、事务提交时触发处理。在这里加一步：查该供应商在同范围、进行中专项下的候选，若有则标为合格。
   - **每日定时任务**：兜底处理采购订单、漏掉的事件，以及证据过期后从合格退回「已报价」。
   - 事务边界：
     - 事件处理在新事务里执行，用 `TenantContext.runAs(事件所属租户)`，失败不影响回价；
     - 定时任务每个租户一个事务，用 `TenantContext.runAs`；
     - 合格依据的写入与阶段变更在同一事务里完成。
   - 新的线程池回调入口按项目规则补一个跨线程的租户契约测试。

6. **供应商开发板块的数据接口按范围分页。**
   - 后端一次算出全租户所有范围的热度、合格家数、缺口，在内存里筛选、排序后分页返回组行；候选按专项 id 批量取。
   - 板块卡片与阶段导航的数字由同一次计算得出，保证数字和列表一致。

7. **记一次处理复用第一期弹窗**：对象类型为候选时，换成候选阶段的选项。不能手动选「合格」，原因见 spec。一次记处理在一个事务里完成：写处理记录 → 改候选阶段 → 更新候选与专项的下一步 → 写操作日志。

8. **权限**：
   - 新增按钮权限「维护供应商开发」(`supply:dev:edit`)，管理主动拓展和候选；
   - 建开发任务仍用第一期的「维护专项」；
   - 候选与供应商名称沿用「查看货源信息」(`inquiry:supplier:view`)，没有该权限时接口不返回名称和联系方式。
   - 菜单不变。

9. **系统提醒不落库**：今日待办里的三种系统提醒在请求时按当时数据算出，不写入下一步字段。这样不会覆盖人定的下一步，也不需要额外的定时任务和去重；代价是提醒不出现在时间线上。高热度缺口提醒只发给主动拓展的负责人，见 `supply-chain/followup`。

## Risks / Trade-offs

- **商品主数据的品类与需求对象的品类不一致，同一家供应商被算到两个范围。** → 判断时以需求对象为先；只有没有需求对象的型号才看商品主数据。
- **合格口径过宽：只报过一次价也算合格。** → 用户已确认按近期真实报价或下单判断，分级放第三期。页面显示合格依据，方便人工判断。
- **全量实时计算在数据量大时变慢。** → 先按需求对象和证据的租户量级评估，单次计算预期在百毫秒级；超过 1 秒再加缓存（按租户的列表缓存，5 分钟）。
- **复用专项后，第一期专项的「品类可不选」与开发目标冲突。** → 只有带开发目标的专项要求必选二级品类；只管型号的保持原规则。
- **候选只登记名称、迟迟不关联供应商库，无法自动合格。** → 阶段到「已报价」时提示关联；今日待办把「已报价未关联超过 7 天」列为提醒。

## Migration Plan

- **迁移**：
  - 新增 `sc_expansion_scope`、`sc_dev_candidate`；
  - `sc_gap_project` 加 `supplier_target`，`sc_followup_log` 加对象类型；
  - 新增按钮资源「维护供应商开发」，授给内置租户管理员；
  - 导入 M5、V1、V2 的作战卡内容（第一期已导入的跳过）。
  - 版本号在开发时按 develop 最新版本顺延，当前为 V1.5.34 之后。
- **上线顺序**：第一期合并上线后再合并本期。
- **回退**：删除两张新表、两个新字段和按钮资源。第一期的数据不受影响，带开发目标的专项退化为普通专项。回滚脚本放 `sql/build/rollback/`。

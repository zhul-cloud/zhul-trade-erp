## Context

见 `proposal.md - Why`。技术前提：

- 已有一套跑在 Claude Code 环境下的"烛龙询盘助手"（`inquiry-parser` → `order-splitter` → `report-generator` → `feishu-pusher` 四个 skill），逻辑成熟（联网搜索验证型号、按品牌+品类拆单、生成中英文询价话术），当前产出写入飞书多维表格。参考文档：`/Users/mac/Documents/00-福州福唯科技有限公司/99-AI智能体/烛龙询盘助手_v1.2.1/`（skill 内容，飞书 App 凭证在其中，不随本次迁移带入 zhul-erp 仓库）与 `/Users/mac/Documents/04-烛龙外贸业务中台/04-数据模型/飞书表结构设计(询盘单).md`（原三层表结构设计，原表名为"客户询盘/询盘单/询盘单明细"，不含"采购"字样）。
- zhul-erp 当前只有用户域（v1.0.0），customer/supplier 等主数据、inquiry 等业务域表均不存在（见 `.claude/context/data-model.md` 的后续版本规划：v1.1 主数据域、v2.0 业务域 inquiry 原计划在此）。
- 项目金额字段规范（`.claude/rules/finance-rules.md`）要求所有金额存原币金额+汇率+本位币金额三元组，禁止在未确认币种时存储金额字段。
- 项目现有编码规范是"前缀+自增主键"（如 `DP10000`），但业务单据编号（询盘号）沿用飞书原有的"日期+当日流水号"惯例，两者并存，互不冲突。
- 真实业务流程：客户原始询盘录入后，AI 解析拆单产出的分组**这时候还只是"客户要什么"的一部分，尚未指定由谁去对接供应商**；"分配给某个采购员"是拆单完成之后单独发生的一个动作，分配之后这个分组才成为某个采购员手头要去问供应商的工作项。

## Goals / Non-Goals

**Goals：**
- 承接"烛龙询盘助手"已有的 AI 解析/拆单能力，迁移落地为 zhul-erp 的正式业务模块
- 建立客户询盘（原始诉求全貌）与询盘单（按品牌+品类拆分的可分配单元）两个独立但关联的模块，并显式建模"分配给采购员"这一步
- 建立 Java 后端与外部 AI 编排服务之间的**通用**异步任务契约，为未来接入更多 skill（不仅是询盘）打地基
- 补齐 customer / supplier 最小可用主数据表，支撑询盘模块的真实外键关联

**Non-Goals：**
- 不在本次实现 AI 编排服务本身（不写 Python/Node 代码、不部署）——本次 zhul-erp 侧只对接契约，AI 编排服务的落地是独立的技术栈、独立的工作
- 不接入 `report-generator`（PDF 解析报告）
- 不设计询盘之后的报价单（quotation）/销售订单（sales_order）模块，也不设计两者与 `inquiry_order` 的具体衔接方式——只确保当前表结构不会阻碍未来衔接
- 不做客户/供应商的完整 CRM/SRM 能力（信用评级、账期、多联系人等），只建最小可用字段
- 不设计"分配"动作本身的权限规则（谁有权分配、是否需要审批）——本次只提供 `assignee_id` 字段和状态位，分配动作的操作权限留给实现阶段按项目现有的角色权限体系处理

## Decisions

### 1. AI 集成架构：独立的 AI 编排服务，而非 Java 直接调用某个模型 API

**决策**：新增一个独立部署的 AI 编排服务（技术栈不限于 Java，初期建议 Python/Node 以贴近 Claude Agent SDK 生态），Java 后端与它之间只通过一份通用 JSON 契约通信，不感知具体用的是 Claude、DeepSeek 还是其他 Agent 平台。

**理由**：`inquiry-parser` 对每个型号都要联网搜索，这是 Claude Messages API 的托管 `web_search` 工具原生支持的能力，但不是跨供应商通用的——换模型平台时，搜索这一环大概率要重新实现（自己接搜索 API、自己写工具调用循环）。把这部分易变的"AI 供应商细节"隔离在独立服务背后，Java 主干代码和数据库结构在换供应商时零改动。

**备选方案**：Java 直接调用 Anthropic Messages API，在 Spring Service 内处理 tool_use 消息。更简单，但把 AI 供应商的调用细节和持久化逻辑耦合在同一个类里，换供应商成本高，且与团队现有的 Claude Code skill 迭代习惯（改 `.md` 文件即生效）脱节。已否决。

### 2. Skill 文件的加载方式：独立 `skills/` 目录，运行时加载，与服务代码同仓库同提交

**决策**：AI 编排服务的仓库下建 `skills/{skill-name}/` 目录（每个 skill 一个子目录，文件互不干扰），服务在启动或收到 reload 信号时读取这些文件作为 prompt 内容，而不是编译进代码。但这些文件与服务代码提交在同一个仓库、同一次 commit 里。

**理由**：纯粹"打包进编译产物"会让日常 prompt 调优（这是高频操作，参考现有 `MEMORY.md` 里那种细粒度调整）绑架一次完整部署；纯粹"读一个完全独立、不受版本控制关联的外部路径"会导致 skill 输出结构和服务解析代码悄悄失配、难以追溯。两者结合：改 skill 内容是轻量操作（改文件+reload，不需要完整发布流程），但 git 提交历史保证 skill 版本和服务代码版本始终可追溯到同一次提交。

### 3. Java ↔ AI 编排服务契约：通用 `ai_task` 表 + skill_id 路由 + webhook 回调

**决策**：不为询盘解析单独设计一套集成方式，而是设计一个通用契约：

```
POST {AI服务}/skills/{skill_id}/run
  body: { input: {...}, callback_url: "https://zhul-erp/api/v1/ai-tasks/{task_id}/callback" }
  → 202 { job_id }

AI服务处理完成后：
POST {callback_url}
  body: { status: "success"|"failed", output: {...}, error: null|string }
```

对应 zhul-erp 侧新增通用表 `ai_task`（`skill_id`、`status`、`output` JSON、`error_message`、`requested_by`、时间戳），本次询盘解析是第一个使用它的场景。未来接入新 skill 时，AI 服务侧加一个 `skill_id`，Java 侧加一个对应的结果处理器（解析 `output`、落对应业务表），两边都不需要改对方已有代码。

**理由**：用户明确说明后续还要接入更多 skill；如果这次为询盘量身定制一套专属集成方式，下次接入新 skill 时大概率要推倒重来。通用契约的代价是 Java 侧需要一个"按 skill_id 分发到对应 handler"的轻量路由层，成本可控。

**部署与鉴权**：AI 编排服务与 zhul-erp-backend 初期部署在同一台机器/同一内网，webhook 走内网直连；回调端点需要独立鉴权（如共享密钥或内网信任），不走用户态 JWT（回调方不是登录用户）。

### 4. 客户询盘 与 询盘单：两个独立模块 + 显式的"分配采购员"步骤

**决策**：拆成 `customer_inquiry`（客户询盘，原始诉求全貌）与 `inquiry_order`（询盘单，AI 按品牌+品类拆出的可分配单元）两个可独立管理、独立列表页的模块，通过外键关联（`inquiry_order.customer_inquiry_id`，可空，见决策 6）。

`inquiry_order` **不叫"采购询盘单"**——拆单刚完成时，它依然只是客户诉求的一部分，还没有指定任何人去对接供应商。新增 `assignee_id`（采购员，FK → `user_basic`，初始为空）字段和一个"待分配"状态，把"分配给采购员"显式建模为一个独立的动作：

```
AI 拆单确认 → 待分配（inquiry_order 已创建，assignee_id 为空）
                  │
                  │  指定采购员（谁有权限做这一步，留给实现阶段按现有角色权限处理）
                  ▼
              已分配/待处理（assignee_id 有值，采购员开始处理）
                  │
                  ▼
              已发供应商 → 已收报价 → 已报客户 → 已成交/已取消
```

**理由**：飞书原设计三层嵌套（客户询盘→询盘单→明细）本身没有"采购"这个词，是本设计早期讨论中误加的标签，把"拆单"和"分配给采购员"这两个本该分开的动作混成了一个。拆分成两个模块、并显式加入分配状态后：AI 拆单结束时产出的记录仍然是中性的、面向"客户想要什么"的分组；"这是某个采购员的工作项"这个语义，只在分配动作发生之后才成立，与真实业务流程一致。团队自己在 `04-烛龙外贸业务中台` 的目录规划里也已经把"客户询盘单"和"采购询盘单"列为两个平级模块，本设计的两表拆分与此保持一致，只是纠正了中间表的命名和语义时机。

**已否决的备选方案**：
- 拆单结果仍存成多条 `customer_inquiry`（同表自引用）——`customer_inquiry` 的字段（询盘来源、原始内容、原始附件、总产品数等汇总统计）和拆单分组需要的字段（品牌、品类、assignee_id、供应商关联）属性形状完全不同，塞进一张表会有大量按行类型才有意义的可空列，查询和理解成本高。已否决。
- 不设中间分组层，`customer_inquiry` 直接挂多个型号明细——会丢失"按品牌+品类分组"这个天然的分配粒度：分配动作找不到自然的挂载对象，只能退化成按型号逐条分配（太碎）或用无实体支撑的临时标签打批次（难追溯）。已否决。

### 5. AI 拆单结果的落库时机：确认时才落库，预览阶段不写业务表

**决策**：AI 处理完成后，结果整个存在 `ai_task.output`（JSON），`customer_inquiry.status` 置为"待确认"；预览页直接渲染这份 JSON（前端本地可编辑），不触碰 `inquiry_order`/`inquiry_order_item`。业务员点击"确认拆单"后，才把（可能已被编辑过的）JSON 提交给一个专门的确认接口，此时才真正创建 `inquiry_order` 及其明细记录（初始状态为"待分配"）。

**理由**：避免"AI 生成的低置信度数据已经是正式记录"的问题（原飞书设计的已知短板），同时不需要额外设计一张草稿/暂存表——`ai_task.output` 本身就是暂存区。

### 6. 询盘单可独立存在（`customer_inquiry_id` 可空）

**决策**：`inquiry_order.customer_inquiry_id` 允许为空，支撑"跳过 AI，纯手动创建"的入口——业务员遇到简单询盘（如老客户一句话要几个型号）时，可以不经过客户询盘录入，直接建一张询盘单。手动创建的询盘单同样从"待分配"状态开始。

### 7. 一张询盘单可对应多个供应商：拆出关联表 + 明细报价交叉表

**决策**：不把供应商和报价直接挂在 `inquiry_order`/`inquiry_order_item` 上，而是拆两张表：
- `inquiry_order_supplier`：这张询盘单发给了哪些供应商（发出日期、回复截止、该供应商整体回复状态、报价单附件）
- `inquiry_order_item_quote`：型号 × 供应商的报价交叉表（原币金额+汇率+本位币金额、该供应商这个型号的货期、报价状态）

**理由**：外贸询价常见做法是同一批型号问多家供应商比价，若报价字段直接挂在明细上（1个型号只能对应1个报价），无法表达"这个型号 A 供应商报 100 元、B 供应商报 95 元"这种真实场景。拆出交叉表后，询盘单详情页可以直接做"同一型号跨供应商报价对比"，这是外贸询价的核心诉求之一。

**代价**：比原设计多两张表、多一层查询复杂度，但结构上可以承载真实业务场景，避免后续因为"发现要问多家供应商"而被迫做破坏性表结构迁移。

### 8. 供应商报价金额字段遵循项目金额规范（原币+汇率+本位币三元组）

**决策**：`inquiry_order_item_quote` 的报价字段按 `finance-rules.md` 规范存 `quote_price_original` / `currency_code` / `exchange_rate` / `quote_price_cny` 四个字段，不简化为单一人民币字段。

**理由**：海外供应商（如问品牌海外官方）报价常见美元等外币，虽然询价阶段的报价还不是正式入账的财务凭证，但提前按规范存储可以避免后续报价单/订单模块复用这批数据时再做一次数据修复。

### 9. 单据编号规则：沿用飞书方案的日期+流水号逻辑，去除分隔符

**决策**：
```
客户询盘编号：   IQ{YYYYMMDD}{NNN}         示例：IQ20260425001
询盘单编号：     {客户询盘编号}{字母}         示例：IQ20260425001A
                （手动创建、无父级客户询盘时，直接以当日流水号生成：IQ{YYYYMMDD}{NNN}{字母}）
明细编号：       {询盘单编号}{NN}            示例：IQ20260425001A01
```
流水号（`NNN`）生成策略沿用原设计：查询当日已有编号最大序号 +1；查询失败时用随机数兜底并在备注中标记待人工核实。字母后缀超过 26 个时使用 AA/AB/AC……

**理由**：业务单据编号（询盘号、报价单号、订单号）惯例上是日期+流水号，与部门/岗位这类内部管理编码（前缀+自增主键）性质不同，不强行统一。

### 10. `inquiry_order.status` 由人工推进，不从供应商子状态自动计算

**决策**：`inquiry_order.status`（待分配→已分配/待处理→已发供应商→已收报价→已报客户→已成交/已取消）的每一步流转都由人工显式触发（"待分配→已分配"由分配动作触发，其余由采购员手动推进），不根据 `inquiry_order_supplier` 里各供应商的独立状态自动聚合计算。

**理由**：一张询盘单可能同时问了 3 家供应商，"2 家回复了算不算已收报价"这类聚合判断规则本身没有唯一正确答案，交给人工判断比设计一套自动聚合逻辑更简单可靠，也避免了自动状态机在边界场景下的不可预期行为。

### 11. `inquiry_order_supplier` 的报价来源不强制绑定正式供应商主数据，区分"正式供应商"与"电商询价渠道"两种来源类型

**背景**：实际业务里，相当一部分询价来源是淘宝/1688/闲鱼这类电商平台的随手比价——很多时候只问一次、卖家不会再联系第二次，把每一次都当成正式供应商建档，会让 `supplier` 主数据很快被大量一次性、低质量记录淹没（联系人/主营品牌这些字段对匿名网店卖家也填不出来）。

**决策**：`inquiry_order_supplier.supplier_id` 改为可空，新增 `source_type`（1=正式供应商 2=电商询价渠道）区分报价来源：
- `source_type=1`：`supplier_id` 必填，关联 `supplier` 主数据，字段行为与原设计一致
- `source_type=2`：`supplier_id` 为空，改用三个新字段承载电商渠道信息：`channel_platform`（枚举：淘宝/1688/闲鱼/其他）、`channel_name`（店铺/卖家名称）、`channel_link`（商品或店铺链接，可空）

同时，`inquiry_order_item_quote` 不再直接存 `supplier_id`，改为存 `inquiry_order_supplier_id`（关联 `inquiry_order_supplier.id`）——这样报价对比功能对"正式供应商"和"电商询价渠道"两种来源一视同仁，不需要在报价表里再区分一次来源类型；同时消除了原设计里 `inquiry_order_supplier` 和 `inquiry_order_item_quote` 各自独立存一份 `supplier_id`、两者可能不一致的隐患。

预留一个"转为正式供应商"的操作入口（P05 详情页，电商询价来源的卡片上）：业务确实成为稳定合作对象后，可基于 `channel_name` 等信息一键创建 `supplier` 记录并回填 `supplier_id`、把 `source_type` 改回 1，原有报价记录不受影响。

**理由**：与决策 4（客户询盘/询盘单拆分）同一类问题——"一次性比价"和"稳定供应商关系"是两个生命周期完全不同的概念，不应该用同一张主数据表硬凑。这样设计既保留了电商询价参与"同型号跨来源比价"的核心诉求（决策 7），又不污染供应商主数据；"转为正式供应商"这个晋升动作让两者之间有一条自然的迁移路径，而不是二选一之后就回不了头。

**代价**：`inquiry_order_supplier` 表增加 1 个类型字段 + 3 个条件字段，且需要应用层校验"根据 `source_type` 决定必填哪一组字段"（不使用数据库层 CHECK 约束，与项目现有的"业务校验放应用层、数据库不做业务判断"惯例一致）；`inquiry_order_item_quote` 的外键从 `supplier_id` 改为 `inquiry_order_supplier_id` 属于原设计的一处修正，不涉及新增表，不影响 Migration Plan 的新增表数量（仍为 8 张）。

### 12. 手动新建询盘单选择客户时，`inquiry_order` 新增独立的 `customer_id` 字段直接承载，不经过 `customer_inquiry`

**背景**：PRD 6.6（P06 手动新建询盘单）写的是"客户：Select+搜索，可留空（不关联客户询盘）"——这句话暗示选了客户就应该"关联客户询盘"，但 `inquiry_order` 表只有 `customer_inquiry_id` 外键，没有独立的 `customer_id` 字段，字面上没有地方存这个客户选择。

**决策**：给 `inquiry_order` 表新增一个独立的可空 `customer_id BIGINT NULL` 字段（关联 `customer.id`，加索引），与 `customer_inquiry_id` 是两个互不干扰、语义清晰的外键：
- `customer_inquiry_id` 有值 → 这张询盘单来自 AI 拆单确认
- `customer_id` 有值（`customer_inquiry_id` 必为空）→ 手动创建时选了客户
- 两者都为空 → 手动创建且未选客户

手动创建询盘单**恒不产生、也不关联任何 `customer_inquiry` 记录**，无论是否选择了客户；编号统一走"无父级"的独立编号规则（`IQ{YYYYMMDD}{NNN}{字母}`），不再区分"选没选客户"两种编号路径。

**已否决方案：手动创建时若选了客户，自动创建一条最小化 `customer_inquiry` 作为挂载点，再让 `inquiry_order.customer_inquiry_id` 指向它**。这是本决策最初的实现方案，上线前评审阶段被否决，理由：
- `customer_inquiry` 这张表的语义是"客户的原始诉求全貌"（决策4的核心前提），一条自动生成、没有 `raw_content`、`source`="其他"的空壳记录会直接出现在 P01 客户询盘列表里——业务员点开会看到一条看不出任何实际内容的"询盘"，这正是决策4（客户询盘/询盘单拆分）和决策11（电商询价渠道不进供应商主表）反复强调要避免的"语义混淆"：不该为了挂一个外键就生造一条与该表本意不符的记录。
- 该方案权衡的"避免给 `inquiry_order` 加冗余字段"这个代价，相比"列表页出现看不懂的空壳记录"这个代价小得多；况且这是预上线阶段、还没有真实数据的表，加一列的成本很低，不构成需要规避的理由。
- 该方案还导致 `CustomerInquiryServiceImpl` 和 `InquiryOrderServiceImpl` 之间的编排逻辑复杂化（两次非原子写入、Controller 层跨两个 Service 编排、潜在孤儿记录），而独立字段方案不涉及任何跨模块编排，`InquiryOrderServiceImpl` 单独完成一次写入即可。

**理由**：独立字段让"这张询盘单的客户信息从哪来"始终有唯一、明确的答案（要么来自 `customer_inquiry_id`，要么来自 `customer_id`，不会两个都有值），不需要为了塞进已有外键而制造额外的、名不副实的数据；也不需要跨模块编排或事务协调。

## Risks / Trade-offs

- **[风险] `inquiry-parser` 对每个型号都执行联网搜索，一条含 10~20 个型号的询盘处理耗时可能是分钟级，且有真实的 API 调用成本** → 缓解：已确定为异步流程（业务员提交后可离开，处理完成后回来查看待确认状态），不做同步等待
- **[风险] webhook 回调依赖 Java 后端与 AI 编排服务网络互通** → 缓解：现阶段两者同机/同内网部署，风险可控；未来若拆分部署需重新评估（记入 Open Questions）
- **[风险] skill 文件运行时加载，若忘记 reload，AI 服务可能用旧版本 prompt 处理新请求** → 缓解：skill 与服务代码同仓库同提交，理论上"部署服务=更新到最新 skill"应该是同一个动作；具体的 reload 触发机制留给 AI 编排服务自己的实现细节
- **[权衡] 多供应商报价对比（决策 7）比原设计多两张表** → 已接受：一次性把结构做对，避免后续破坏性迁移
- **[风险] "待分配"状态下的询盘单如果长期没人分配，容易被遗漏** → 未在本次设计中缓解，建议实现阶段在工作台"待办事项"里加一条"待分配询盘单"提醒（复用已有的工作台待办模式），具体记入 Open Questions

## Migration Plan

本次全部为新增表和新增模块，不修改任何现有表结构，风险面小：

1. 新增 8 张表（`customer`、`supplier`、`customer_inquiry`、`inquiry_order`、`inquiry_order_item`、`inquiry_order_supplier`、`inquiry_order_item_quote`、`ai_task`），追加进 `sql/build/sql/schema_v1.sql` 或新开 `schema_v1.1.sql`（沿用项目既有的版本化 SQL 文件惯例，具体由实现阶段决定）
2. 回滚仅需 `DROP` 这 8 张新表，不影响既有功能

# Design

## Context

- 完整度由 10 个模块组成，列表按当前页的商品 ID 分模块批量查询后在内存里算（`ProductCompletenessMapper`），所以前端只能在当前页排序。
- 「缺图片 / 缺物流 / 缺海关」筛选和缺项统计已用 `CompletenessSql` 的同一组 SQL 片段，保证数量与筛选结果一致。
- `product_media` 有媒体类型（1 图片、2 视频）与主图标记。

## Goals / Non-Goals

**Goals:**
- 完整度排序在全部商品范围内正确，口径与列表显示的完整度一致。

**Non-Goals:**
- 不把完整度落成冗余列、不加定时重算。
- 不改变完整度的组成与完成条件。

## Decisions

1. **排序用 SQL 表达式现算。** 按完整度排序时，在列表查询里把 10 个模块的完成条件拼成「各模块 EXISTS / 条件成立记 1」相加的表达式排序，模块条件全部取自 `CompletenessSql`，与内存计算共用片段，保证排序结果与列显示一致（为此把内存计算里还没抽出的模块条件也收进 `CompletenessSql`）。
   - 备选：商品表冗余完整度列，在各模块写入时更新 —— 写入点有十几处（规格、FAQ 审核、媒体、物流……），漏一处就不一致，现阶段商品量用现算足够。
   - 只在用户选择按完整度排序时拼这个表达式，默认列表查询不变。
2. **有图片复用「缺图片」的条件取反。** 「有图片」= `EXISTS(主图)`，「缺图片」= `NOT EXISTS(主图)`，同一片段，两个筛选数量相加等于全部商品。有视频 = `EXISTS(未删除的视频)`。
3. **列表项返回主图地址。** 当前页商品 ID 批量查主图（一次查询），返回主图的文件地址；商品媒体目前没有缩略图规格，前端按 40×40 显示并懒加载。
4. **商品编号就是商品 ID。** 不新增编码字段，与商品候选页「商品编号」一致；列固定在左侧，可复制。

## Risks / Trade-offs

- [完整度排序要对每个商品跑 10 个子查询，商品多时慢] → 生产只读实测（11,164 个已建档商品）：物流、海关、参考价三张表只有 (tenant_id, product_id) 唯一键，子查询不带租户条件用不上，排序约 5.9 秒；模拟用上商品 ID 索引后约 0.15 秒。迁移 V1.5.61.9 给三张表补 `product_id` 单列索引（现有缺项统计同样受益）。
- [主图原图较大拖慢列表] → 图片懒加载；上传时图片已限制在 5MB 以内。之后如需缩略图另开变更。

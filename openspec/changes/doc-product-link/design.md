## Context

- 商品库 `product` 是平台级共享库（`tenant_id = 0`，`owner_tenant_id` 标归属，写入由 `ProductWriteGuard` 校验），唯一键 `uk_tenant_brand_mpn (tenant_id, brand_id, mpn_normalized)`，`brand_id NOT NULL DEFAULT 0`。
- 商品候选池 `product_candidate` 也是平台级，按「品牌键 + 归一化型号」唯一（品牌键：识别到的为 `#品牌ID`，否则为小写去空格的品牌原文），已有 `product_id` 列，但只在建档或并入后才填。
- 询盘型号的匹配和进池由 `ProductArchiver.sync` 做（幂等，在调用方事务内）。历史补齐由启动任务 `CandidateBackfill` 做。
- 单据明细中只有 `inquiry_item` 和 `sales_order_item` 有 `product_id`。报价、PI、销售订单的显示靠 `DocItemProducts` 按「行 → 询盘型号 → 品牌 + 型号」现查。其余明细（采购、仓库、售后）只有型号、品牌文字和 `so_item_id`。
- 本机数据：候选约 9.6k 条，商品 98 条。采购订单行约 1.08 万行，其中包含没有来源订单行的飞书迁移数据。

## Goals / Non-Goals

**Goals:**
- 每个「像型号」的业务型号从询盘确认起就有稳定的 product_id，并一路传到采购、仓库、售后的明细上。
- 候选审核前后 ID 不变；重复的用商品合并收拢，合并有记录，能追溯。
- 商品库原有功能（列表、发品、内容、SEO、完整度、热度）不受候选商品影响。
- 历史单据尽量补齐，补不上的有清单，可以人工处理。

**Non-Goals:**
- 不做库存（仓库档案、批次、流水、余额、成本、月结），另开变更。商品合并在那个变更里扩展为库存转移。
- 不支持两个已建档商品之间的合并（第一期只有候选并入已建档）。
- `sourcing_quote`、`sc_demand`、素材、AI 任务这类非单据数据，仍按型号键关联，不加 product_id。
- 不改单据上显示的品牌和型号文字（仍是单据当时保存的）。

## Decisions

1. **商品表加建档状态，候选进池时生成商品。**
   - `product` 增加三列：
     - `archive_status tinyint`：1 候选、2 已建档、3 已并入、4 已驳回。现有商品回填为 2。
     - `brand_key varchar(80)`：规则同候选池。
     - `merged_into_id bigint NULL`。
   - 唯一键改为 `(tenant_id, brand_key, mpn_normalized)`：品牌没识别的候选商品 `brand_id = 0`，用品牌原文区分。识别出品牌或审核选定品牌后，同步更新 `brand_id` 和 `brand_key`。
   - `ProductArchiver.upsert` 新建候选时，在同一事务里插入候选商品，回写 `product_candidate.product_id`，询盘型号同时关联它。
   - 备选方案：用候选 ID 当库存键。不采用，因为这样会出现两套 ID，单据和库存都要区分「这是候选 ID 还是商品 ID」。
2. **审核和改正。**
   - 建档：在原商品上更新品牌、品类、系列、名称、生命周期，`archive_status = 2`，ID 不变。
   - 审核时改了品牌或型号，先按新的品牌键和归一化型号查重：不重复就直接改；与一个已建档商品重复，就返回「将并入」的预览（受影响单据数），用户确认后走第 3 点。
   - 候选状态的商品豁免「被引用后不可修改品牌和型号」。
3. **商品合并。**
   - 新表 `product_merge`（平台级）：原商品、主商品、各明细表受影响条数（JSON）、原因、操作人、时间。
   - 明细表清单集中登记在 `DocumentProductTables` 里。新增带 `product_id` 的明细表必须登记，否则 `DocumentProductTablesContractTest` 失败，做法同 `TenantTables`。
   - 合并时：锁住两个商品；对每张登记的表执行 `UPDATE … SET product_id = 主 WHERE product_id = 原`。这一步跨租户，用 `TenantScope.platform`，代码里显式写条件。
   - 然后原商品改为已并入、记下 `merged_into_id`，候选改为已并入，写合并记录和操作日志。全部在一个事务里。
   - 读取时按 `merged_into_id` 跳到主商品。主商品必须是已建档的，第一期不会出现链式合并，只需要跳一次。
4. **驳回限制。**
   - 驳回前检查候选商品是否被销售订单及之后的明细引用（采购需求、采购订单、发货、入库、差异、出库、售后、退货、采购退货）。有引用就拒绝驳回。
   - 没有引用的：商品改为已驳回，询盘型号、报价、PI 行的 product_id 置空。现有的 `unlinkRejected` 扩展到这几张表。
   - 重新打开时，按候选池规则重新关联。
5. **product_id 的传递。** 在各单据的生成处复制上一张单据的 product_id，不再查商品库：
   - 报价生成、PI 生成、PI 转订单
   - 需求生成、拆分
   - 下单（草稿行）
   - 发货单、入库单、到货差异
   - 出库通知
   - 售后单、销售退货、退货入库、采购退货

   `DocItemProducts` 改为直接读行上的 product_id，再按 `merged_into_id` 跳转，去掉按文字匹配。询盘型号改型号或回填真实型号后，`ProductArchiver.sync` 同步更新它还没转订单的报价和 PI 行。
6. **转订单校验。** PI 转销售订单时，所有行都必须有 product_id，否则抛出 `BizException` 并列出型号。手动建单本来就从选择器选商品。
7. **商品库功能过滤。**
   - 加一个工具 `ProductScopes.archived(wrapper)`（`archive_status = 2`）。
   - 逐一检查约 25 个直接查 `product` 的文件，按用途分三类：
     - 只要已建档：列表、发品、内容、SEO、完整度、热度、素材、参考价、`supply` 的品类同步。
     - 已建档 + 候选：选择器、型号匹配。
     - 按 ID 读、需要跳转主商品：单据显示。
   - 用契约测试固定商品列表、发品任务候选范围、选择器这三处的结果。
8. **候选商品的租户可见性。**
   - 候选商品属于平台级数据，但它的来源是各家公司的询盘。选择器只返回已建档商品，以及「`product_candidate_source` 里有当前租户来源」的候选商品。
   - 精确匹配对所有租户都匹配候选商品，保证同一型号只有一个 ID，但只回传 ID 和型号，不回传名称、描述等由别家公司询盘带来的资料。
9. **历史回填。**
   - 迁移只加列，不回填数据。
   - 回填扩展 `CandidateBackfill` 这个启动任务，用 `sys_config` 标记只跑一次，分批处理，每批 200，`TenantScope.platform`：
     1. 已有候选全部补生成候选商品。
     2. 各明细沿来源链补：报价、PI 按 `inquiry_item_id`；订单行按询盘；采购和仓库按 `so_item_id` 或采购订单行。
     3. 剩下的按「品牌 + 归一化型号」匹配；匹配不到、又像型号的，进池生成候选商品。
   - 处理完仍为空的行，进入「待关联」清单。这个清单按需查询各明细表 `product_id IS NULL` 的行，不另建表。
10. **事务边界。**
    - 询盘确认：候选商品的生成和询盘型号的关联在询盘确认事务内。
    - 审核建档、并入、驳回：各自一个事务。合并对两个商品加行锁，防止与审核并发。
    - 回填：每批一个事务，失败的批次跳过并记日志，下次启动继续。

## Risks / Trade-offs

- **商品表行数涨 10 倍左右。** 风险是漏加过滤，导致候选混进商品列表或发品。应对：用 `ProductScopes` 集中过滤，加契约测试；`archive_status` 加索引，与 `tenant_id` 组成联合索引。
- **合并要改多张租户表，耗时可能较长。** 一个型号被引用的行通常只有几十到几百行，可以接受。合并操作只在候选审核时由运营触发。
- **唯一键变更可能和已有数据冲突。** 迁移前先查重（同 `brand_key + mpn_normalized` 有多行的），有冲突就停止迁移，人工处理。
- **转订单校验会挡住少数历史上能转的 PI**（行里写的不是型号）。这是有意的，提示里写清楚原因和处理办法。
- **别家公司的询盘资料可能泄露。** 由第 8 点的可见性规则限制，用契约测试覆盖。

## Migration Plan

- **V1.5.53**：
  - `product` 加 `archive_status`、`brand_key`、`merged_into_id`；回填现有商品的状态为 2 和对应品牌键；查重通过后替换唯一键。
  - 新增 `product_merge` 表。
- **V1.5.54**：给报价、PI、采购需求、采购订单、供应商发货、采购入库、到货差异、销售出库、售后、销售退货、退货入库、采购退货的明细表加 `product_id`（NULL，带索引）。
- **数据回填**：由启动任务完成，见第 9 点。
- **回退脚本**：删除新增的列、表和唯一键调整；回填生成的候选商品按 `archive_status = 1` 软删除。
- **上线前**：在生产只读统计候选数量、各表待回填行数和预计的待关联条数，写进 PR 说明。

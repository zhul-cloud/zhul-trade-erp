# Design

## Context

- 询盘型号 `inquiry_item` 和订单型号 `sales_order_item` 上原本都有 `remark` 字段，都没有被读写：前者只有历史迁移写过「成色：…」，后者只在由 PI 生成订单时复制 PI 行的备注（PI 行都有询盘来源，这些型号的备注读询盘型号，不读它），手动订单从未写过。
- PI 行的 `remark` 会打印到 PI 文件上，是给客户看的，不能复用。
- 下游单据都能追溯回询盘型号：报价、PI、订单行直接带 `inquiry_item_id`，采购需求与采购单行经 `so_item_id` 关联。

## Decisions

1. **唯一来源、实时读取，不往下游复制**：备注只存在询盘型号上（手动订单的型号存在订单型号上），各单据返回时按关联查询，所以各处始终是最新内容，也不需要同步逻辑。备选方案「复制到每张单据再同步」改动多、容易不一致，所以不采用。
2. **复用原有的 `remark` 字段**，只增加修改人与时间两列；`purchase_order_item` 增加 `remark_alert` 存「下单后备注有更新」。
3. **标红范围**：只标「已下单」的采购单行，草稿直接显示最新内容；标红在采购单维度一次清除（「我已核对」），写采购单日志。
4. **订单上修改**：有询盘来源的型号改询盘型号的备注（唯一来源）；没有的改订单型号自己的。
5. **只在系统内显示**：所有给外部的文件（报价单、PI、CI / PL、采购单）都不读这个字段，模版占位符不增加。

## Risks / Trade-offs

- **列表多一次批量查询**：报价、PI、订单、采购需求、采购单的详情与列表，各按 ID 批量多查一次，开销可以接受。

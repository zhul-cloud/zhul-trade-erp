## Context

动机见 proposal.md。现状：

- 收款记录属于 PI（手动订单属于订单），PI 收款状态由「已到账毛额 + 手续费差额」与合计比较得出；多收只提示「将记为预收」，没有后续处理。
- 订单收入在「已到账」时按各笔到账毛额折人民币计算，所以多收的钱被算进了收入。
- 外币到账的人民币由结汇单先进先出确定，每次结汇后重算所有未结完的到账。
- 退款单 `fin_customer_refund` 必须挂订单，冲减订单收入，经营统计按退款日期单列。
- 供应商侧已有「供应商欠款」（应付单超付后可抵扣、退款），可作为客户余额的参照，但两者不共用表：方向、对象和报表口径都不同。
- 订单、PI、退款、结汇都有归属事业部，结汇按事业部分别先进先出。

## Goals / Non-Goals

**Goals:**
- 客户余额只通过流水变化，任何时点的余额都能由流水重放得到，月度核对表恒等平衡。
- 订单收入只含真实货款；代收、多收、余额抵扣都能在订单上看清来源。
- 后续的缺货部分取消、售后退货只需调用「转入」即可接入。

**Non-Goals:**
- 退款申请与审批：放在变更 ②。本变更的售后退款仍由财务直接登记。
- 余额跨币种兑换、跨事业部转移。
- 历史代收的追溯识别（上线前的 PI 没有代收款标记，不补）。
- 平台订单售后退款转余额（暂时只能原路退回）。

## Decisions

### 1. 余额用「流水表 + 先进先出消耗」，不存余额字段

新表 `fin_customer_credit_entry`，每条流水一行；转出类流水（抵扣占用、提现、负数调整）另有消耗明细表 `fin_customer_credit_consumption`（转出流水 id、被消耗的转入流水 id、原币金额、人民币价值），用来记录先进先出消耗了哪几笔转入、各取多少锁定价值。释放、作废时按消耗明细原样退回。

- 可用余额 = 转入合计 − 未释放的转出合计，按「租户 + 客户 + 币种 + 事业部」聚合查询，不落地余额字段，避免和流水不一致。
- 并发：转出前按 `zhul:erp:lock:credit:{tenantId}:{customerId}:{currency}:{buId}` 加 Redisson 锁，锁内重新计算可用余额再写流水。
- 备选「余额表 + 流水表」：读快，但要维护两处一致，回退和作废都要同步改；余额规模小（按客户），聚合足够，不采用。

### 2. 人民币价值在流水生成时锁定

结汇会改变到账的人民币，但余额一旦转入就固定价值。这样核对表的人民币价值能平衡，提现时的汇差也有明确的口径（价值 − 实际转出 → 汇兑损益）。代价见风险 1。

### 3. 余额抵扣是一条收款记录，付款方式 `CREDIT`

PI 抵扣和手动订单抵扣都落成 `payment_receipt` 里的一条记录，付款方式 `CREDIT`，同时带上它对应的「抵扣占用」流水。好处是收款状态、订单收款面板、订单收入的计算都沿用「遍历收款记录」的逻辑，只在三处特殊处理：不参与结汇、人民币取锁定价值、不计入报税统计和到账登记工作列表。

- PI 草稿保存时先生成占用流水（状态「草稿占用」），这时还不生成收款记录；PI 发送时生成收款记录，计入已到账。草稿占用同样计入「已占用」，防止两张草稿重复用同一笔余额。
- 备选「PI 上存抵扣金额，状态计算时加上」：收款状态、订单收入、成本明细各处都要单独加这一项，容易漏，不采用。

### 4. 代收款是 PI 费用行的一种类型

费用行加 `fee_type`（`NORMAL` / `COLLECTION`）。导出时代收款和普通费用一样显示业务员填的名称，系统内从销售额、净利润、红线测算里排除。PI 收款状态变为「已到账」时，在同一事务内生成代收转入流水；收款状态由「已到账」退回（作废到账）时，撤回还没被使用的代收转入。

手续费分摊：代收承担的平台手续费 = 平台手续费合计 × 代收款 ÷ 合计，按 PI 币种计算，尾差不单独处理（只有这一项）。订单成本里的平台手续费扣掉这部分。

### 5. 多收在订单收入里扣除，处理前后口径一致

订单收入 = 现金到账毛额（人民币）+ 手续费差额 + 余额抵扣价值 − 代收转入价值 − 多收价值。多收价值在「待处理」时按 PI 现金收款的加权到账汇率估算，随结汇变化；处理（转余额）时锁定。这样多收无论处理与否都不进入收入，处理只是把它从「待处理预收」挪到客户余额。

### 6. 退款单加 `refund_type`，余额提现不挂订单

`fin_customer_refund` 增加 `refund_type`（`AFTER_SALES` / `CREDIT_WITHDRAW`）与 `destination`（原路退回平台 / 银行汇款 / 转客户余额），`order_id` 改为可空（余额提现为空）。经营统计、订单收入只取 `AFTER_SALES`。余额提现退款单与汇兑损益其他收入互相引用，作废时一起作废。

- 备选「余额提现单独成一张新单据」：报表上又多一类要汇总；退款单本来就是「钱退给客户」的凭证，按类型区分更简单。

### 7. 汇兑损益放其他收入，类别内置、金额可负

其他收入表增加 `source_type` / `source_id`（来源退款单）；内置类别「汇兑损益」不出现在手动登记的下拉中。金额 > 0 的校验只作用于手动登记。

### 8. 余额按事业部隔离

转入取来源单据的归属事业部，抵扣和提现只能在同一事业部内进行，与「事业部财务独立、结汇按事业部先进先出」一致。如果以后需要跨事业部转移余额，再加一类「事业部间调拨」流水。

### 9. 事务边界

以下每一组都在同一个本地事务内完成，由 Service 层的 `@Transactional` 声明：
- 售后退款登记（转客户余额）+ 余额转入流水；
- PI 发送 + 余额抵扣收款记录生成；PI 关闭 / 作废 + 抵扣记录作废 + 释放流水；
- 到账登记 + PI 收款状态重算 + 代收转入；作废到账 + 代收撤回；
- 转给客户：余额提现退款单 + 提现流水 + 消耗明细 + 汇兑损益其他收入；
- 多收「退回客户」：多收转入 + 提现（同上）。

## Risks / Trade-offs

- [代收和多收按估算汇率锁定，结汇后真实人民币与锁定价值不同] → 差额留在订单收入里（订单收入 = 现金人民币 − 锁定价值）。金额小，且订单「已结算」要求结汇完成，届时差额已经确定；在设计和手册中说明这一点。
- [历史多收的订单收入变少，经营统计历史月份变化] → 上线前用脚本列出所有「已到账 + 差额 > 合计」的 PI 与订单及影响金额，给用户确认后再上线。
- [余额被占用后，来源退款单不能作废，操作上要先改 PI] → 拒绝时提示占用的 PI 编号，引导到对应 PI。
- [PI 过期不释放，余额长期被占用] → 「余额管理」页面显示「已占用」及占用的 PI，业务员可以关闭 PI 释放；工作台的过期 PI 提醒会顺带覆盖。
- [聚合计算余额，客户多时变慢] → 流水表按「租户 + 客户 + 币种 + 事业部」建联合索引；余额列表分页。

## Migration Plan

1. 迁移：新建 `fin_customer_credit_entry`、`fin_customer_credit_consumption`；`proforma_invoice_fee`、`sales_order_fee` 加 `fee_type`，默认 `NORMAL`；`fin_customer_refund` 加 `refund_type`（存量设为 `AFTER_SALES`）、`destination`（按原退款方式映射）、`order_id` 改为可空；`fin_other_income` 加 `source_type`、`source_id`；字典新增付款方式「余额抵扣」、其他收入类别「汇兑损益」、菜单「余额管理」与按钮权限「调整客户余额」，授给财务角色。
2. 上线前：运行多收影响清单脚本，确认影响范围。
3. 回退：新表与新增字段不影响旧版本运行；回退前确认没有余额流水（有流水时先导出核对表留档），把 `order_id` 为空的余额提现退款单和系统生成的汇兑损益作废，再部署旧版本。`order_id` 改回非空需要先处理这些行，所以回退 SQL 只删除新增的表和字段，不恢复 `order_id` 的非空约束。

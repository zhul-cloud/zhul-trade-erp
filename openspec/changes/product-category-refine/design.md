## Context

- 品类两级：一级品类 16 个（含兜底「其他」，「其他」下没有细分品类），细分品类 140 个。商品可挂一级或细分（见 `product/category`「品类支持两级结构」）。
- 商品数据全平台共享，按 `owner_tenant_id` 维护（见 `product/product`「商品数据平台共享，按归属维护」）；`product` 表不走租户拦截器，写入由归属校验把关。生产上待处理的 1416 个商品都属于正式租户。
- 商品候选已有批量 AI 解析品类（`CandidateAiFill`，技能 `candidate-classify`）：提交时快照、编排服务 50 条一批调用模型、一次回调、回调按条件更新；同一账号同时只能跑一个；前端轮询并把任务 ID 存 localStorage。本变更照搬这套做法。
- 商品没有逐单操作日志，修改只记更新人、更新时间。
- 供应链需求对象（`sc_demand`）的品类在信号导入时由来源行或其商品决定，之后只有新信号带品类才补（`DemandRegistry.findOrCreate`）。第二期已有按「归一化型号」批量查商品品牌和品类的查询（`SupplySourceMapper.productScopes`）。需求对象的操作日志用 `DocumentType.SC`。

## Goals / Non-Goals

**Goals:**

- AI 只给建议，商品品类以人确认为准；人改过的不被 AI 覆盖。
- 复用候选 AI 解析的任务、回调、进度模式，不新造一套。
- 供应链跟随商品主数据，不需要人在供应链里再补一遍。

**Non-Goals:**

- 不做定时自动跑 AI；每批都由人发起。
- 不给商品补逐单操作日志。
- 需求对象已有品类时不按商品纠正。

## Decisions

1. **建议存在商品表上，不另建表。** 迁移 V1.5.36 给 `product` 加三个字段：
   - `ai_category_id bigint NOT NULL DEFAULT 0`：AI 建议的细分品类，0 为没有；
   - `ai_category_state tinyint(2) NOT NULL DEFAULT 0`：建议状态（0-无、1-待确认、2-已忽略），加索引；
   - `ai_category_at datetime NULL`：建议时间（已忽略时为忽略时间）。
   一个商品只有一个归属公司，同一时间只需要一条建议。备选是建议表（可存多次历史），本期用不到历史，放弃。

2. **「品类未细分」= 商品品类是一级品类**（`category_id` 指向 `parent_id` 为空或 0 的品类，含「其他」）。缺项统计接口增加 `refine` 一项及三档子数量；列表查询参数 `missing=refine`，再加 `refineState=todo|pending|ignored`。租户账号的行业范围与其他缺项相同。

3. **AI 用新技能 `product-category-refine`，编排服务复用候选的分批调用。**
   - 结果处理器按技能 ID 分派，与候选共用 `candidate-classify` 会冲突，所以新起技能 ID；编排服务里映射到同一个 50 条一批的调用函数，只换提示词：说明对象是已建档商品，给出「当前品类」，品类清单只列当前账号可见的启用细分品类，判断不出填 0。
   - 输入条目：`key` = `p{商品ID}#{提交时 category_id}`、品牌名、型号、商品名称、描述、当前品类名。
   - 回调在任务所属租户下执行，逐条条件更新：`category_id` 仍为提交时的值、`ai_category_state = 0`、返回的 ID 是启用的细分品类 → 写 `ai_category_id`、`state = 1`、时间；否则不写，按「判断不出 / 跳过」汇总到任务输出。
   - 本地桩服务 `scripts/ai-orchestrator-stub` 加同名技能的假结果。

4. **提交接口支持「勾选」和「按筛选」两种来源。** `POST /api/v1/products/category-refine` 带 `ids` 或带当前筛选条件；按筛选时后端在「待 AI 细分」里按更新时间倒序取前 200 个。逐个检查能否维护（复用商品写入的归属校验），不能的跳过计数。提交前检查当前用户有没有未结束的同技能任务，有则拒绝。进度查询 `GET /api/v1/products/category-refine/{taskId}` 只能查自己提交的。

5. **采纳、改选、忽略。**
   - `POST /api/v1/products/category-refine/accept {ids}`：一个事务，逐个条件更新 `ai_category_state = 1` 且能维护 → `category_id = ai_category_id`，清空建议，记更新人和时间；不满足的跳过并返回原因。跨一级品类的数量由前端按列表数据先提示，后端不拦。
   - `ignore` / `unignore {ids}`：只改 `ai_category_state`（1 或 0 → 2，2 → 0），清空建议品类；忽略时 `ai_category_at` 记为忽略时间，供「已忽略」列表显示。
   - 改选走现有的商品编辑接口。商品编辑保存时品类有变化，就清空 AI 建议和忽略标记，这样过期的建议不会再被采纳。
   - 权限都要求 `product:product:edit`，不新增权限码。

6. **供应链按商品主数据补齐，用事件解耦。**
   - 商品侧在采纳或编辑改品类的事务内发布「商品品类已变」事件（带商品 ID）；供应链用事务提交后监听，在当前租户下另起事务补齐对应需求对象。商品模块不依赖供应链模块。补齐写的操作日志操作人为系统（操作人 ID 0，显示「系统」）。
   - 供应链新增补齐步骤：查本租户 `category_id = 0` 且有型号的需求对象，用 `productScopes` 按型号批量查商品（每批 500 个型号），取同品牌、细分品类的商品，条件更新 `category_id = 0 → 新品类`，写 SC 操作日志。
   - `SupplyDailyJob` 在导入信号后、证据联动前对每个租户执行一次（`TenantContext.runAs`），兜底其他公司改的商品和事件处理失败的情况。
   - 事务边界：商品采纳一个事务；供应链补齐在事件监听里另起事务，失败只记日志、不影响采纳结果，第二天由定时任务补上。

## Risks / Trade-offs

- [AI 给错细分品类] → 只写建议，必须人采纳；跨一级品类醒目提示；采纳前可改选。
- [「其他」里的商品可能不属于任何细分品类] → AI 可以判断不出，不强行归类；这些商品仍在「待 AI 细分」，可以忽略。
- [AI 用量] → 一次最多 200 个、50 个一批调用，按公司 AI 配置计量；不联网搜索。生产首批约 1416 个，分 8 次左右。
- [采纳后需求对象换了「品牌 · 品类」] → 已在进行中专项里的型号仍留在原专项；供应商开发清单和矩阵是实时计算的，自动反映。
- [按筛选提交时列表与后端取数有时间差] → 后端按提交时刻的状态重新筛，跑完的提示以后端汇总为准。

## Migration Plan

- 迁移 V1.5.36：`product` 加三个字段和 `ai_category_state` 索引，默认值不影响现有数据。
- 回退：回滚脚本删除三个字段和索引；未采纳的建议丢失，已采纳的品类保留。供应链补齐的需求品类保留（本来就是正确的品类）。
- 无 `.env` 配置项变化；编排服务需随版本一起部署（新技能 ID）。
- 上线后：用正式租户先跑一批 200 个，抽查建议质量，再跑余下的。

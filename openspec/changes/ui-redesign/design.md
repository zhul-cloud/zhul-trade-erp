# Design

## Context

动机见 proposal.md「Why」，行为要求见 `specs/`。下面只列影响实现方式的现状：

- **技术栈**：前端是 Umi Max 4、antd 6、ProComponents 3。
- **主题**：集中在 `src/theme/`，包括 `palette.ts`（令牌）、`antd.ts`、`shell.ts`、`AppTheme.tsx`、`store.ts`。页面取色走 `useAppTheme().palette` 或 CSS 变量 `var(--z-*)`。代码已默认浅色，但设计规范仍写「深色默认」。
- **样式**：页面文件约 270 个（不含测试），其中 260 个有内联样式；页面里写死的颜色约 100 处（十六进制与 rgba）。页头有多种写法：`PageTitle`、`SalesPageTitle`、`PurchasePageTitle`、`WarehousePageTitle`、`QuotationPageTitle`、`PageHeader`。
- **面包屑**：不在外壳里，由 `crm/opportunity`、`customer`、`inquiry/shared`、`supplier` 的页面级组件渲染，共 32 个文件传了 `crumbs`。
- **渐变散落多处**：
  - `palette.ts` 的三个渐变常量；
  - `src/utils/appearance.ts` 的 `LOGO_GRADIENT_STOPS`，供 `BrandLogo` 在 canvas 上画标签图标；
  - `public/logo.svg` 的 linearGradient；
  - 兜底用的 `public/favicon.ico`；
  - `AuthLayout` 的 radial-gradient 光晕。
- **等宽大写小标签**：4 处直接写了 `IBM Plex Mono`（3 个页面与 `product/theme.tsx`）。
- **develop 动态**：近 30 天有 270 个提交改了前端，来自两位开发。用户说明后续新增页面不会很多，所以同步的工作量主要来自别人对已有页面的修改。
- **CI**：只在发往 develop、main、release、hotfix 的 PR 和 develop 推送时运行；只要改了代码就跑完整后端测试。

## Goals / Non-Goals

**Goals:**
- 新视觉由主题令牌和骨架组件一次定义，页面不再自己写颜色和页头结构。
- develop 同步进来的旧模板代码能被自动检查出来，不靠人工逐页翻。
- 规范文档只有一份最新版本；过期的旧规则移入备份目录，不和新规则混放。
- 每个任务都经独立复审，减少错误和效果不理想的情况。

**Non-Goals:**
- 不改后端、接口、数据库和业务规则。
- 不做手机端适配，最低按 1366×768 的电脑屏幕验收。
- 不新增统计：快捷筛选和汇总行只沿用页面已有的统计。
- 以下现有规定保持不变：单据页的列顺序（`system/navigation`「单据页统一显示」）、金额显示、标签页与返回、来源单号。详情页布局与明细固定列按本变更的 `system/navigation` 增量修改。

## Decisions

### 1. 分支：独立长期分支，完成后一次合并

- **分支**：`feat/ui-redesign` 从 develop 拉出，独立维护，期间不并入 develop。用户已否决按批次合并：新旧界面不能混着上线。
- **推送与检查**：开发期间不开 PR，所以不跑 CI。每次推送前在本机跑 `npm run lint`、`npm run lint:ui`（已迁移目录，清单由脚本维护）、`npx antd lint ./src`、`npm test`、`npm run build`。
- **同步 develop**：用 merge，不用 rebase，因为 rebase 会改写已推送的长期分支历史。同步时机有三个：开始改代码（第 4 组）之前一次；之后每完成一个批次一次；develop 有较多前端合并时随时一次。
- **冲突处理**：业务逻辑（接口参数、字段、校验、状态流转）以 develop 为准，界面按新规范重做。
- **同步记录**：每次同步写进本变更目录的 `sync-log.md`，记合入的提交范围、受影响页面和处理状态。这个文件只记同步。
- **规范例外**：`docs/06-部署运维/11-分支与版本规范.md` 规定「不要新建其他长期分支」。本分支是用户批准的例外，最终合并时把例外写进该规范，期间不单独改 develop。

**已知取舍**：琥珀与警告色、红与错误色同属一个色系。用户选这两种主题色时，主按钮和警告、错误标签会更接近。状态标签始终是浅底加文字，主按钮是实色块，靠形态区分。默认主题色是琥珀，所以这个问题人人都会遇到：琥珀的链接色 `#FDA92D` 和警告标签字色 `#FFAB00` 几乎一样，靠「链接是纯文字、警告是带浅底和图标的标签」来区分，原型里要专门核对这一点。快捷筛选的选中态（主题色浅底）也和警告标签接近，靠全圆角、勾选图标和所在位置区分（原型 A1c、A2c）。
- 其他相近的组合：天蓝与信息色同为蓝绿系、青绿与成功色同为绿系，状态标签都有浅底，链接是纯文字，靠形态区分。选「红」时，红色单号和链接会和涨跌色里的红挨在一起（如销售订单列表的毛利）。原计划在主题设置里提示换涨跌颜色，复审指出换了以后另一个方向仍是红色，只是换了方向撞色，2026-11-20 用户决定删掉提示，接受这一撞色。
- 深色链接色在原色基础上略微提亮，使它在卡片、选中底（原色 16%）、父级菜单底（`#2C2C2C`）上都不低于 4.5:1，同一颜色兼作深色下的选中文字；紫、宝蓝、红的深色选中底仍按原色计算。
- 图表：主题色作为第一个系列时，从 6 个系列色里去掉色相最接近的一个，其余顺延（D51 后按新系列的序号去：琥珀、红去橙红 `#FF5630`，青绿去青 `#00B8D9`，天蓝、宝蓝去蓝 `#1877F2`，紫去紫 `#8E33FF`；原写法「琥珀去 `#B87A14`…」已作废）。第一个系列取令牌 `palette.chart`（`chartSeries()` 的第一个），跟主题色走（照 PrimeDash）：浅色为原色，深色为深色链接色。琥珀原色在白底只有 1.93:1，低于图形 3:1，是用户看过对比图后选定的例外（2026-11-22，深一档琥珀显脏），所以用到它的图表都要在旁边或悬停提示里写数值，不只靠颜色传达。
- 焦点框：浅色为 2px 主题色加外侧 2px `#637381`（对白底 4.88:1，琥珀原色只有 1.93:1，单靠主题色不满足焦点指示 3:1）；深色为 2px 深色链接色。

**浅色风格**也学 PrimeDash：页面底色为浅灰，卡片为白色加轻阴影、不加边框，选中项用主题色浅底配主题色文字，图标放在主题色浅底的小方块里。**暗黑底**仍按用户 2026-11-20 的要求用中性近黑（见上表），不用 PrimeDash 偏蓝紫的 `#151521`、`#1E1E2D`。PrimeDash 的皮肤切换不采用，多一套卡片样式就多一份维护，也会破坏统一。

**曾考虑的主色**：近黑主按钮（用户不要浅色下的大块黑色）、`#0761D1` 蓝（用户觉得丑）、ClickHouse 电光黄（浅色下对比度只有 1.07）、墨蓝等 4 种低饱和色（被 PrimeDash 的 6 种预设取代），都不用。

PrimeDash 的组件尺寸、字体与本变更的取舍见 `reference-primedash.md`。

**其他令牌**：
- 圆角（同 PrimeDash）：按钮和输入框 8，卡片 10，状态标签 4。
- 阴影：卡片、侧栏、顶栏、主按钮按 PrimeDash 带柔和阴影（浅色）；深色模式不用阴影，靠边框分层。
- 字体：中文用系统字体；数字和英文用 Public Sans（与 PrimeDash 一致，OFL 开源，作为前端依赖打包，不走外网）。表格数字等宽。2026-11-20 前写的是 Inter，与参考站和已定稿原型不符，已改。

### 3. 公共骨架组件

复用 develop 上 `doc-list-unify` 已建的 `src/components/ListLayout/`（`FilterCard`、`FilterField`、`MainCard`），在同一目录扩展，不另建一套：

- `FilterCard` 增加「更多筛选」：常显项之外的条件收进去，按钮显示生效数量；
- 新增 `PageHeader`（一行页头）、`SummaryBar`（页头下方的指标汇总行）、`QuickFilters`（搜索条件区下方的快捷筛选行）、`Section`（详情分区）、`HelpTip`（帮助图标）；
- 状态下拉沿用 `doc-list-unify` 的写法：选项带数量，切换立即查询。
- **SummaryBar**：每项是「名称 + 数字」，可带一行副文字（如分项金额）。口径不能从名称看出来的，名称旁加帮助图标写口径。宽度不够时副文字整段隐藏，不截断、不换行；只有在页面别处也能看到的副文字才可以这样隐藏（如销售订单「进行中」的各阶段数量，在订单状态下拉里能看到）。
- **QuickFilters**：照 PrimeDash Chips，高 30、全圆角。未选中为中性浅底，选中为主题色浅底、主题色字，前面加勾选图标。

这些组件替代现有的多种页头写法。2026-11-20 用户确定的取舍：状态沿用下拉框；统计卡片拆成状态类、条件类、指标类；搜索条件区只露常用项，其余放「更多筛选」；`doc-list-unify` 后续批次继续在 develop 上做，同步过来后在本分支按新设计改。

- **面包屑**：随新页头一起去掉。各业务域迁移时删除 `crumbs` 和 4 个页面级组件里的面包屑渲染，界面检查规则把 `Breadcrumb`、`crumbs` 列为禁止项。
- **HelpTip**：用 antd 自带的标签提示，表单项用 `Form.Item` 的 `tooltip`，标题旁用同一个图标组件。只在鼠标悬停时显示；按用户决定，豁免「可交互元素都要有可见焦点」这条要求。
- **antd API**：写 antd 代码前，先用 `npx antd info <组件>` 核对。

另一方案是只换主题令牌、不动页面结构。这样改不掉「页面靠说明文字撑结构」和「各页页头不一致」，所以不选。

### 4. 界面检查规则

新增检查命令 `npm run lint:ui`，可以按目录运行。检查以下内容：

- 渐变和发光写法；
- 页面文件里写死的颜色值；
- 旧页头组件、页头说明属性、`Breadcrumb` 和 `crumbs`；
- 直接写 `IBM Plex Mono` 的地方；
- 常识性套话；
- 单行输入框过长的提示文字。

确认弹窗和警告条的内容不检查。「保存后生效」一类有时带有用信息的说法，只提示人工判断，不判错误。确有必要的例外，在代码行上写明原因后放行。

在业务域迁移完之前，`lint:ui` 只对已迁移的目录强制通过（目录清单由脚本维护，每迁完一个域加进去），所以不会卡住每次推送的 `npm run lint`。全部迁移完成后（任务 7.8），再把它并入 `npm run lint`。

同步 develop 后对全仓库跑一次 `lint:ui`，报出的位置就是要按新设计改的地方。

**工作台布局与涨跌颜色**（2026-11-20 用户提出，按技能与资料评估）：
- 同一行卡片等高会把空白移进卡片内部（UI-041 记录里也写过「强行等高只会把空白移到卡片内部」）。工作台改为两列瀑布流：按模板顺序放进当前较矮的一列，卡片保持自身高度。业务员看板因此自然分成「要处理的」（待办、过期 PI）与「看数字的」（业绩、询价进度、商机）两列。不采用拉高指标格或按高度重新配对：前者只是换个地方留白，后者模板一改就失效。这会取代 UI-041 对看板「同一行等高」的处理。
  - 实现：在组件注册表 `widgets/index.tsx` 给每个组件写一个预估高度，按预估高度贪心分列（`dashboard/index.tsx` 的 `assignColumns`），只依赖模板顺序和预估高度，所以加载完成、`useOnReactivate` 刷新都不换列；只在切换看板或跨过单列与两列的断点时重算。两列各自从上往下叠放。原定用 antd 6 `Masonry` 并以 `column` 固定，2026-11-21 实测它按测量结果绝对定位，卡片加载后长高会叠到下一张上，而列已经由我们自己定好、用不到它的测量，改为两个普通的竖排列。不用 CSS `columns`：它先填满左列再填右列，顺序和分组都控制不了，高度一变还会重排。写代码前用 `npx antd info Masonry` 核对。
- 涨跌颜色每人可选：涨红跌绿（默认，2026-11-20 用户改定，选项排在前面）或涨绿跌红，纯按方向着色，盈亏同理（盈利同涨、亏损同跌），告警色不变。2026-11-20 先按「变好 / 变坏」着色，结果「费用」上涨显示红色、同一设置下上涨有红有绿，用户指出和选项名字矛盾，改为按方向。代价是越低越好的指标（费用）上涨也显示「涨」色，好坏由使用者判断，与股票软件的习惯一致。现有代码的 `higherIsBetter` 不再参与着色。纳入的地方：`BlockWidget` 的较上月、`OpportunityCard` 的较上一周期（原来增加绿、减少橙、无箭头），以及订单、成本、报价、PI、利润统计、经营报表、砍价统计、采购订单列表与详情的砍价金额（`purchase/components.tsx`、`purchase/orders/detail.tsx`，详情顶部数字卡用 `MetricCard` 的 `toneBy`）里按正负着色的金额；成本调整的调增、调减金额（`finance/costingParts.tsx` 的 `SignedMoney`，原来固定增绿减红，2026-11-26 用户确认纳入）。不纳入：余额、已入账这类正数高亮（余额管理与流水、报销、收款台、客户详情的可用余额），低于红线、还能让多少这类按阈值判断的颜色，库存流水的数量增减（2026-11-21 随 develop 新增，是出入库方向，不是金额涨跌），以及告警色。实现为 `src/theme/delta.tsx` 的 `useDeltaColor().of(值)` 和 `DeltaText`（变化配上下箭头），零值和空值用正文色。

## Risks / Trade-offs

- **[同步冲突多]** develop 前端改动频繁，主要是改已有页面。→ 按第 1 节的时机同步，不攒；用 `lint:ui` 定位要改的地方；冲突时业务逻辑以 develop 为准。
- **[开发期间没有 CI]** 问题可能到最后才暴露。→ 每次推送前在本机跑完整前端检查；develop 上的后端改动已在 develop 通过 CI。
- **[删改文案导致 Jest 断言失败]** → 测试随页面一起改，断言改为针对行为，不针对说明文字。
- **[去掉面包屑后，直接打开的详情页没有返回列表的入口]** → 从侧边栏回到列表，站内跳转仍用返回条，已写进导航规范增量。
- **[快捷筛选少了数字]** 原来没有统计的页面不显示数字。→ 不为此加后端；确有需要另立变更。
- **[页面级主规范描述了外观]** 已知 `purchase/purchase-order`、`inquiry/sourcing-task` 的统计卡片，`crm/customer-followup` 的渐变箭头。→ 改到对应页面时在本变更补增量，归档前用 `openspec validate --strict` 校验。
- **[最后一次同步引入未经复审的改动]** → 最后同步之后再复审一次，并用 BrowserOS neo 回归受影响的页面。
- **[用户手册截图过时]** → 放到合并前一批统一更新。

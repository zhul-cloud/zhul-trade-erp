# Design

## Context

动机见 proposal.md「Why」，行为要求见 `specs/`。下面只列影响实现方式的现状：

- **技术栈**：前端是 Umi Max 4、antd 6、ProComponents 3。
- **主题**：集中在 `src/theme/`，包括 `palette.ts`（令牌）、`antd.ts`、`shell.ts`、`AppTheme.tsx`、`store.ts`。页面取色走 `useAppTheme().palette` 或 CSS 变量 `var(--z-*)`。代码已默认浅色，但设计规范仍写「深色默认」。
- **样式**：页面文件约 270 个（不含测试），其中 260 个有内联样式；页面里写死的颜色约 100 处（十六进制与 rgba）。页头有多种写法：`PageTitle`、`SalesPageTitle`、`PurchasePageTitle`、`WarehousePageTitle`、`QuotationPageTitle`、`PageHeader`。
- **面包屑**：不在外壳里，由 `crm/opportunity`、`customer`、`inquiry/shared`、`supplier` 的页面级组件渲染，共 32 个文件传了 `crumbs`。
- **渐变散落多处**：
  - `palette.ts` 的三个渐变常量；
  - `src/utils/appearance.ts` 的 `LOGO_GRADIENT_STOPS`，供 `BrandLogo` 在 canvas 上画标签图标；
  - `public/logo.svg` 的 linearGradient；
  - 兜底用的 `public/favicon.ico`；
  - `AuthLayout` 的 radial-gradient 光晕。
- **等宽大写小标签**：4 处直接写了 `IBM Plex Mono`（3 个页面与 `product/theme.tsx`）。
- **develop 动态**：近 30 天有 270 个提交改了前端，来自两位开发。用户说明后续新增页面不会很多，所以同步的工作量主要来自别人对已有页面的修改。
- **CI**：只在发往 develop、main、release、hotfix 的 PR 和 develop 推送时运行；只要改了代码就跑完整后端测试。

## Goals / Non-Goals

**Goals:**
- 新视觉由主题令牌和骨架组件一次定义，页面不再自己写颜色和页头结构。
- develop 同步进来的旧模板代码能被自动检查出来，不靠人工逐页翻。
- 规范文档只有一份最新版本；过期的旧规则移入备份目录，不和新规则混放。
- 每个任务都经独立复审，减少错误和效果不理想的情况。

**Non-Goals:**
- 不改后端、接口、数据库和业务规则。
- 不做手机端适配，最低按 1366×768 的电脑屏幕验收。
- 不新增统计：快捷筛选和汇总行只沿用页面已有的统计。
- 以下现有规定保持不变：单据页的列与布局（`system/navigation`「单据页统一显示」）、金额显示、标签页与返回、来源单号。

## Decisions

### 1. 分支：独立长期分支，完成后一次合并

- **分支**：`feat/ui-redesign` 从 develop 拉出，独立维护，期间不并入 develop。用户已否决按批次合并：新旧界面不能混着上线。
- **推送与检查**：开发期间不开 PR，所以不跑 CI。每次推送前在本机跑 `npm run lint`、`npm run lint:ui`（已迁移目录，清单由脚本维护）、`npx antd lint ./src`、`npm test`、`npm run build`。
- **同步 develop**：用 merge，不用 rebase，因为 rebase 会改写已推送的长期分支历史。同步时机有三个：开始改代码（第 4 组）之前一次；之后每完成一个批次一次；develop 有较多前端合并时随时一次。
- **冲突处理**：业务逻辑（接口参数、字段、校验、状态流转）以 develop 为准，界面按新规范重做。
- **同步记录**：每次同步写进本变更目录的 `sync-log.md`，记合入的提交范围、受影响页面和处理状态。这个文件只记同步。
- **规范例外**：`docs/06-部署运维/11-分支与版本规范.md` 规定「不要新建其他长期分支」。本分支是用户批准的例外，最终合并时把例外写进该规范，期间不单独改 develop。

### 2. 配色令牌

色值整合自 awesome-design-md 收录的 Vercel、Supabase、ClickHouse、Raycast、Resend、Wise、IBM、PostHog 等后台类设计规范，对比度按 WCAG 计算。具体取值以原型确认为准，确认后如有调整同步修订本节和 specs。

| 用途 | 浅色 | 深色 |
|---|---|---|
| 页面底色 | `#FAFAFA` | `#0A0A0A` |
| 卡片 | `#FFFFFF` | `#1A1A1A` |
| 浮层 | `#FFFFFF` + 阴影 | `#242424` |
| 分隔线 | `#EBEBEB` | `#2A2A2A` |
| 控件边框（≥3:1） | `#8F8F8F` | `#6E6E6E` |
| 主文字 | `#171717` | `#F5F5F5` |
| 正文 | `#4D4D4D` | `#CCCCCC` |
| 弱文字（≥4.5:1） | `#6B6B6B` | `#8F8F8F` |
| 主按钮 | `#171717` 底白字 | `#FFFFFF` 底黑字 |
| 链接、可点单号、焦点框 | `#0761D1` | `#3B9EFF` |

状态与提醒的语义色（文字 / 浅底）：

| 语义 | 浅色 | 深色 |
|---|---|---|
| 成功 | `#16794A` / `#E8F6EE` | `#4ADE80` / `#10261A` |
| 警告 | `#A35200` / `#FFF4E0` | `#F5A623` / `#2B2010` |
| 错误 | `#C50000` / `#FDECEC` | `#FF6161` / `#2E1517` |
| 信息 | `#0761D1` / `#EAF2FE` | `#3B9EFF` / `#0F2038` |
| 中性 | `#4D4D4D` / `#F2F2F2` | `#B4B4B4` / `#262626` |

各状态归哪个语义色，不在这里凭印象定。按任务 1.1 从代码现有的 `Pill`、`Tag` 着色整理成对照表，有分歧的由产品负责人定。

**图表系列色**：6 个，在浅色和深色底上的对比度都不低于 3:1。依次为 `#3B82F6`、`#2F9E99`、`#B87A14`、`#E8664A`、`#2E9A62`、`#7A8794`。

**现有 palette 键的去向**：键名保留下来，从 develop 同步进来的旧页面会自动换上新颜色。语义已不存在的键直接删除，引用处会编译报错，借此逐一改掉。

| 现有键 | 去向 |
|---|---|
| `canvas`、`card`、`hairline`、`control`、`ink`、`sub`、`mute`、`link`、`hover` | 保留，换新色值 |
| `green`/`greenSoft`、`orange`/`orangeSoft`、`red`/`redSoft` | 保留，对应成功、警告、错误 |
| `faint` | 保留，只用于禁用、占位，不作正文 |
| `sidebar`、`inset` | 保留：侧栏与页面底色相同，凹底用浅灰 |
| `accentSoft`、`accentLine` | 改名为信息浅底、信息描边，旧名删除 |
| `violet`、`violetSoft`、`cyan` | 删除，引用处按语义改用状态色或中性色 |
| `PRIMARY_GRADIENT`、`ACCENT_GRADIENT`、`LOGO_GRADIENT` | 删除 |

**编译抓不到的渐变**：`LOGO_GRADIENT_STOPS`、`public/logo.svg`、`public/favicon.ico`、`AuthLayout` 的光晕，以及 4 处 `IBM Plex Mono`，在任务 4.3 里逐个改掉，并由界面检查规则兜底。

**品牌强调色**：不设，彩色只用于功能。ClickHouse 的电光黄 `#FAFF69` 作为深色工作台大数字的备选，在原型里对比。如果采用，需要先在 `interface-style`「颜色只表达功能」里加一条例外。黄色在白底上对比度只有 1.07，浅色主题不能沿用。系统里绿色已表示成功，橙色已表示警告和型号备注，所以不用这两个颜色做主色。

**其他令牌**：
- 圆角：按钮和输入框 6，卡片 12，只有标签用胶囊形。
- 阴影：只用于浮层和弹窗。
- 字体：中文用系统字体；数字和英文用 Inter（OFL 开源，作为前端依赖打包，不走外网）。表格数字等宽。

### 3. 公共骨架组件

在 `src/components/Page/` 下新增 `PageHeader`、`SummaryBar`（页头下方的指标汇总行）、`QuickFilters`、`FilterBar`（含「更多筛选」）、`Section`、`HelpTip`，替代现有的多种页头写法。

- **面包屑**：随新页头一起去掉。各业务域迁移时删除 `crumbs` 和 4 个页面级组件里的面包屑渲染，界面检查规则把 `Breadcrumb`、`crumbs` 列为禁止项。
- **HelpTip**：用 antd 自带的标签提示，表单项用 `Form.Item` 的 `tooltip`，标题旁用同一个图标组件。只在鼠标悬停时显示；按用户决定，豁免「可交互元素都要有可见焦点」这条要求。
- **antd API**：写 antd 代码前，先用 `npx antd info <组件>` 核对。

另一方案是只换主题令牌、不动页面结构。这样改不掉「页面靠说明文字撑结构」和「各页页头不一致」，所以不选。

### 4. 界面检查规则

新增检查命令 `npm run lint:ui`，可以按目录运行。检查以下内容：

- 渐变和发光写法；
- 页面文件里写死的颜色值；
- 旧页头组件、页头说明属性、`Breadcrumb` 和 `crumbs`；
- 直接写 `IBM Plex Mono` 的地方；
- 常识性套话；
- 单行输入框过长的提示文字。

确认弹窗和警告条的内容不检查。「保存后生效」一类有时带有用信息的说法，只提示人工判断，不判错误。确有必要的例外，在代码行上写明原因后放行。

在业务域迁移完之前，`lint:ui` 只对已迁移的目录强制通过（目录清单由脚本维护，每迁完一个域加进去），所以不会卡住每次推送的 `npm run lint`。全部迁移完成后（任务 7.8），再把它并入 `npm run lint`。

同步 develop 后对全仓库跑一次 `lint:ui`，报出的位置就是要按新设计改的地方。

### 5. 依据先行，不凭印象写

画原型、改页面之前，先把三类依据整理成表，放在本变更目录（任务第 1 组，只读代码，不依赖原型）：

- **`status-colors.md`**：从代码现有的着色整理出「状态 → 语义色」，有分歧的由产品负责人定。
- **`search-scope.md`**：一次性读完所有带关键字搜索的列表的后端查询条件，逐行写明页面、可搜字段、匹配方式、后端代码位置。查不到的标「待核实」，问用户。
- **`stat-cards.md`**：列出每个列表的统计卡片、口径、与页签的关系、属于条件类还是指标类及去向，以及涉及的主规范条款；分类由产品负责人确认。已知的有：
  - `purchase/purchase-order` 的「逾期未发」；
  - `inquiry/sourcing-task` 的顶部统计卡片。

  统计页的口径同样以代码为准。

文案清理参考 Impeccable 的 clarify、distill 和 unslop 的 AI 痕迹清单，只改措辞，不增删业务事实。

### 6. 文档清理

- **重写规范**：`.claude/context/ui-design-patterns.md` 整份重写，只保留新规则。仍然有效的内容按新结构重新编排，不保留新旧并存的段落，包括：
  - 列表页统一规范、金额显示、菜单分组与命名、标签页与返回、来源单号、单据页统一规范；
  - 表单弹窗结构、图标（Lucide）、可访问性要求（焦点色换新令牌，帮助图标的悬停例外写明）；
  - OpenPencil 作图注意、复用方式。

  `AGENTS.md` 和 `.claude/rules/coding.md` 按节名引用的地方，节名保留或同步改引用。
- **旧规范备份**：旧版规范全文，以及 `docs/03-产品原型/02-商品域/_备选方案存档/`，移入 `docs/_backup/ui-v3/`，首页写明「已作废，仅供追溯，不是现行规则」。
- **其他文档**：
  - `AGENTS.md`、`.claude/rules/coding.md`，以及相关 PRD 和路线图里描述旧视觉的句子，改成指向新规范；业务内容不动。
  - 不改 `openspec/changes/archive/`、其他人的变更目录、PRD 的修订历史行。
- **业务原型**：各功能已确认的 `.op` 原型是业务确认记录，留在原处。在 `docs/03-产品原型/` 首页写明「视觉以 `ui-design-patterns.md` 为准，旧原型只作业务确认」。本次的新原型放在 `docs/03-产品原型/界面改造/`。

### 7. 原型先行

- **样板页**：用 OpenPencil 先画 4 张：工作台、销售订单列表、销售订单详情、登记表单弹窗。浅色全部画；深色另画工作台两版（纯黑白、电光黄大数字）用来对比，其余样板页各一版。
- **确认后**：用户确认原型后，同步修订 specs、design、tasks，重跑 `openspec validate --strict`，然后才开始重写规范和改代码。
- **后续批次**：有新结构的页面（如工作台各岗位看板、客户跟进页），先补原型再开发。
- **工具**：pencil MCP 连不上时改用 `op` 命令行；无界面服务用完后执行 `op stop`。

### 8. 审核角色：完成的任务都要复审

每个任务做完，先交独立审核者复审，通过后才勾选完成。用户验收仍是最终把关。

- **审核者**：没有参与这项任务编写的 AI 代理，新开、不继承编写过程的上下文。它只读不改，避免自己审自己。
- **依据**：确认的原型、`specs/system/interface-style` 逐条对照、`ui-design-patterns.md`、第 5 节的三张依据表、改造前的页面行为。
- **内容**：
  - 视觉：截图与原型对照，浅色和深色都看；
  - 文案：有没有常识性套话，说明放的位置对不对，业务字段和匹配规则有没有代码依据；
  - 行为：对比改造前后的提交，确认只改了展示，接口调用、字段、校验、状态流转没有变化；
  - 代码：用 `/code-review` 查缺陷、重复实现、遗漏的写死颜色；
  - 效果：用 Impeccable 的 critique、audit 给页面打分，指出层次、留白、对齐不理想的地方。
- **记录**：结论分「通过」和「需修改」两种，写进本变更目录 `review-log.md`，记任务编号、依据、问题和处理结果。「需修改」的改完后重新复审，直到通过。
- **人工复审**：原型、文档清理清单、每个业务域完成后，再交用户看一次。

### 9. 导航规范增量的写法

「页面标题跟随菜单管理」原有三个场景，其中两个以面包屑命名。OpenSpec 的修改块要求场景名称不变，所以改用「删除旧条款 + 新增『页面名称跟随菜单管理』」，并在删除说明里写明承接关系。

## Risks / Trade-offs

- **[同步冲突多]** develop 前端改动频繁，主要是改已有页面。→ 按第 1 节的时机同步，不攒；用 `lint:ui` 定位要改的地方；冲突时业务逻辑以 develop 为准。
- **[开发期间没有 CI]** 问题可能到最后才暴露。→ 每次推送前在本机跑完整前端检查；develop 上的后端改动已在 develop 通过 CI。
- **[删改文案导致 Jest 断言失败]** → 测试随页面一起改，断言改为针对行为，不针对说明文字。
- **[去掉面包屑后，直接打开的详情页没有返回列表的入口]** → 从侧边栏回到列表，站内跳转仍用返回条，已写进导航规范增量。
- **[快捷筛选少了数字]** 原来没有统计的页面不显示数字。→ 不为此加后端；确有需要另立变更。
- **[页面级主规范描述了外观]** 已知 `purchase/purchase-order`、`inquiry/sourcing-task` 的统计卡片，`crm/customer-followup` 的渐变箭头。→ 改到对应页面时在本变更补增量，归档前用 `openspec validate --strict` 校验。
- **[最后一次同步引入未经复审的改动]** → 最后同步之后再复审一次，并请用户补看受影响的页面。
- **[用户手册截图过时]** → 放到合并前一批统一更新。

## Migration Plan

1. 全部批次完成，复审通过，用户逐页验收。
2. 和其他开发约定前端改动冻结一到两天。
3. 最后同步一次 develop，复审同步带进来的改动，跑本机全量前端检查，再用 BrowserOS neo 逐页截图回归。用户补看受影响的页面。
4. 在分支规范里补上长期分支例外，然后发 PR 到 develop，跑完整 CI 后合并。
5. 按发版流程拉 `release/X.Y.0` 上线，升次版本号。
6. **回滚**：本次没有数据迁移。生产出问题时回退到上一个版本的镜像，develop 上 revert 这次合并提交。

## Open Questions

- 深色工作台的大数字用纯白还是电光黄，在原型里对比后由用户定。如果选电光黄，按第 2 节在 specs 里加例外。

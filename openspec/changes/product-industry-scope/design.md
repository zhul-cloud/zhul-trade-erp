## Context

- 品牌、品类、系列、商品都存为平台数据（tenant_id = 0），所有租户读同一份；写入只限平台账号，例外是租户审核候选、确认资料包。
- 读取入口集中在商品模块：品牌、品类、系列、商品的列表与选项接口（带 `OptionsCache` 缓存），商品搜索与型号匹配（`ProductLookupService`），以及被询盘、商品候选、供应商主营产品、资料导入复用的 `BrandResolver`（品牌识别）和 `CategoryMatcher`（品类匹配）。
- 字典表 `dict_type` / `dict_item` 已有平台级字典与字典管理页面。
- 当前只有工业控制一个行业，所有数据都属于它。

## Goals / Non-Goals

**Goals:** 数据模型支持多行业；租户只读到本行业数据；平台能为品牌、一级品类指定行业；新租户选行业即可用。

**Non-Goals:**
- 不复制数据给租户，商品主数据仍是平台一份。
- 不做租户多行业（一个租户一个行业，以后需要再扩）。
- 不按行业过滤按 ID 的详情和单据渲染（已开单据要能正常显示）。
- 不新增第二个行业的数据（等真正开新行业时由平台在字典里加，再给数据打标签）。

## Decisions

1. **行业用字典维护。** 字典类型 `industry`，首项 `INDUSTRIAL_CONTROL`「工业控制」。新增行业只需平台在字典管理里加一项，不改代码。
   - 备选：单独建行业表。不选：只有编码和名称，字典已满足，且已有管理页面。
2. **行业挂在一级品类和品牌上。**
   - `product_category.industry_code`：一级品类必填，细分品类留空、跟随上级（避免上下级不一致）。
   - `product_brand_industry(brand_id, industry_code)`：品牌与行业多对多（Siemens、ABB 等跨行业品牌只维护一条品牌）。
   - 系列跟随品牌、商品跟随一级品类，不另存行业，避免冗余数据不一致。
3. **过滤放在读取入口统一处理。** 新增 `IndustryScope`：从当前登录账号解析租户行业（平台账号返回「不限」），各读取入口据此加条件；`BrandResolver`、`CategoryMatcher` 的候选范围也按它过滤，询盘、候选、供应商主营产品、资料导入因此自动生效，不逐个模块改。品牌、品类选项缓存仍存全部行业的一份，读取时在内存里按可见范围过滤，缓存失效逻辑不变。
4. **租户行业为空时不限制。** 正常情况下不会为空（迁移设为工业控制，创建时必选）；万一为空按「不限」处理，保证不会因为配置缺失导致业务页面没有数据。
5. **行业的默认值。** 页面上新建租户、品牌、一级品类都必须选行业；接口没传行业时（旧的调用方、候选审核、测试），租户审核候选新建的品牌继承租户行业，其余新建用默认行业（字典中排第一的启用行业），修改时保持原值。传了停用或不存在的行业一律拒绝。
6. **界面。**租户表单加「行业」下拉、列表加行业列；品牌列表加行业列与筛选、编辑弹窗多选行业；品类列表加行业列与筛选、一级品类编辑弹窗选行业（细分品类显示「跟随上级」）。先出 OpenPencil 原型再实现。

## Risks / Trade-offs

- [遗漏某个读取入口，导致跨行业数据泄露] → 过滤集中在 `IndustryScope` 与两个识别组件；契约测试按入口逐个覆盖（选项、列表、搜索、匹配、询盘识别、候选识别）。
- [品牌跨行业时，一个行业的租户看到该品牌下其他行业的系列] → 当前可接受（系列没有行业）；需要时再给系列加行业。
- [多一层过滤带来查询开销] → 品牌、品类数据量小（百级），走缓存；商品查询加一个按品类 ID 集合的条件。

## Migration Plan

- Flyway：新增行业字典、`tenant.industry_code`、`product_category.industry_code`、`product_brand_industry`；现有租户、一级品类、品牌全部设为工业控制；附反向 SQL。
- 上线后数据可见范围与现在相同（只有一个行业）。
- 与 `tenant-data-init` 的关系：初始化结果显示租户行业与本行业品牌、品类、系列数量；租户没有行业时提示先在编辑租户里选择行业。建议先实现本变更，再实现 `tenant-data-init`。

# Design

## Context

- 连接方式的顺序与开关存在 `sys_ai_provider_config`（每个租户每种 `mode:provider` 一行，`sort_order`、`status`）。
- 现在 `sort_order` 按组各自编号：API 组 1、2，订阅组 1、2。
- 没保存过的卡片没有行，排序值取 `10 + 服务商次序`。
- `AiConfigServiceImpl.ordered()` 先排 API 组、再排订阅组。`chain()` 把订阅统一附在 API 后面。只有在没有可用 API Key 时才查询订阅登录状态：每查一次都要编排服务运行一次 CLI，所以不放在每个任务上。

## Goals / Non-Goals

**Goals:**
- 一个统一顺序，API Key 与订阅可以互相穿插；任务按这个顺序使用。
- 升级后各公司的实际顺序不变。

**Non-Goals:**
- 执行中切换、暂停与恢复的规则不变。
- 订阅授权、订阅设置只读等规则不变。
- 编排服务不改。

## Decisions

1. **统一排序值，迁移只平移订阅行**
   - 新规则：
     - 保存时整个列表按顺序写 1..n。
     - 没保存过的卡片排序值：API 为 `10 + 次序`（10、11），订阅为 `30 + 次序`（30、31）。
   - 迁移 `V1.5.48`：订阅行 `sort_order + 20`（旧值 1～3 变为 21～23），API 行不动。
   - 平移后的大小关系：已保存 API（1、2）< 未保存 API（10、11）< 已保存订阅（21～23）< 未保存订阅（30、31）。这与旧规则「API 组在前、各组内按旧值」完全一致，不需要窗口函数重排。
   - 回退：`sort_order - 20`。
   - 备选方案是按 `ROW_NUMBER()` 重排为 1..n。它会让「只保存过订阅、API 从没保存」的公司把订阅排到 API 默认卡片之前，改变页面顺序，所以不采用。
2. **排序**
   - `ordered()` 把全部卡片放在一起，按排序值排，同值时按默认次序（Claude API、OpenAI API、Claude 订阅、OpenAI 订阅）。
   - 未获授权的公司不列订阅卡片。
   - 保存时提交的列表只含看得见的卡片。未授权公司残留的订阅行编号可能与 API 重复；之后获得授权时，按「同值看默认次序」排序，订阅仍在 API 后面。
3. **`chain()` 保持列表顺序**
   - 按列表顺序逐个处理：API 需要 Key 且不在暂停中，订阅需要已开启且不在暂停中，满足的放入候选序列。
   - 候选序列里一个 API Key 都没有时，才查询订阅登录状态并剔除未登录的订阅（规则与现在相同）。
   - 有 API Key 时，订阅不查登录状态。订阅排在前面却未登录时，由编排服务调用失败后切换并暂停，与现在 API 之后的订阅一样。
4. **保存校验**：去掉「平台订阅只能排在 API Key 之后」，其余校验（重复、未授权不能提交订阅）不变。
5. **前端**
   - 两个 `SortableContext` 合成一个，去掉 `moveWithinGroup` 改用 `arrayMove`。
   - 删除两个分组标题、分隔说明，以及「不能跨组」的放回逻辑。
   - 列表上方加一行说明。卡片标题已带「API Key / 平台订阅」，不再另加标签。

## Risks / Trade-offs

- **排在前面的订阅未登录时，每个任务的第一次调用都会失败一次再切换**：失败后进入 10 分钟暂停，新任务会跳过它，所以影响有限，与现在相同。
- **费用**：订阅排在前面时，订阅出问题会自动改用付费 API Key。这是公司自己排的顺序，页面说明里写明，不另加确认弹窗。

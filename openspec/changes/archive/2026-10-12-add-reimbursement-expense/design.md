## Context

依据供应链单据模型第 7.2 节「付款与报销」与第 6.1 节「费用行」。③a 已经有：
- **应付单**（`fin_payable`，来源为采购单、货代对账单）；
- **付款记录**（`fin_payment`）：员工垫付标为待报销（`reimburse_status = 1`），进报销单后为 2，且不能作废；
- **退款**：财务登记供应商退款，退到公司账户。

垫付的其他来源：
- **国内快递**：`courier_waybill`，有运费和垫付人 `payer_id`，没有截图；
- **退货运费**：`receiving_discrepancy`，有运费 `return_freight`，没有垫付人。

**用户已定**：
- 员工勾选自己的待报销项提交；
- 财务在报销单上登记已付（账户、日期、截图）；
- 快递费和退货运费在提交报销时补传截图；
- 费用单既记成本也走付款：公司对公生成应付，员工垫付进报销。

## Goals / Non-Goals

**Goals**
- 员工能看到并一次提交自己全部的垫付，补齐截图；财务能看到谁该报多少、什么时候付的。
- 供应商退款退到员工手里的，能冲减报销，欠款不会挂着没人管。
- 偶发成本有地方记，并能分摊到订单型号，供 ③c 算实际成本。

**Non-Goals**
- 不做报销审批流（「暂不审核」）、不要发票。
- 不做个人借款、备用金。
- 不在本变更里算订单实际成本（③c）。

## Decisions

**1. 待报销项不建表，按来源实时汇总**
- 待报销 = 各来源里「垫付人是本人、有效」的记录，减去已进入有效报销单的。
- 五种来源与金额：

  | 来源类型 | 取自 | 金额 |
  |---|---|---|
  | 1 采购货款 | `fin_payment`（kind 1、method 2、有效） | `amount_cny` |
  | 2 国内快递 | `courier_waybill`（`payer_id`、`freight > 0`、没撤销） | 运费 |
  | 3 退货运费 | `receiving_discrepancy`（新增 `return_payer_id`、已处理、`return_freight > 0`） | 运费 |
  | 4 费用单 | `fin_expense`（method 2、有效） | 人民币金额 |
  | 5 收到退款 | `fin_payment`（kind 2、method 2、有效） | 负的实收人民币 |

- 垫付人统一按用户 ID 比较；付款记录存的是登录名，查询时按账号换成用户 ID。
- **备选**：待报销项建表，在各来源登记时写入。来源有五处，删改、撤销、作废都要同步，容易不一致，所以不采用。

**2. 报销单与明细**
- `fin_reimbursement`：
  - 编号 BX、申请人（用户 ID、登录名）、提交时间、项数、合计；
  - 状态：1 待付款、2 已报销、3 已撤回；
  - 撤回原因；付款账户、付款日期、付款人、付款时间、说明。
- `fin_reimbursement_line`：来源类型、来源 ID、来源编号、日期、说明、金额（人民币，负数为退款）、`release_seq`。
- **防重复报销**：唯一索引（`tenant_id`, `source_type`, `source_id`, `release_seq`）。
  - 有效明细的 `release_seq` 为 0；
  - 报销单撤回时，把各行的 `release_seq` 改成自己的行 ID，释放唯一位；
  - 并发提交同一项时，后到的触发唯一冲突，返回「有的项已经在其他报销单里」。
- 付款记录的 `reimburse_status`：提交时设为 2，撤回时改回 1，保持 ③a 的「进报销单后不能作废」。
- 来源单据作废或撤销时：
  - 待付款报销单里的那一行由来源侧拦下：已进报销单的快递不能撤销，费用单不能作废，付款不能作废；
  - 已报销的同样不能改。

**3. 截图**
- 补传的截图挂在来源上，而不是报销明细上，这样撤回后截图还在。复用通用附件表，新增两个归属类型：
  - `COURIER_PROOF`：快递，owner 为快递 ID；
  - `RETURN_PROOF`：退货运费，owner 为差异 ID。
- 采购货款、收到退款用付款记录的截图（`PAYMENT`）；费用单用费用单凭证（`EXPENSE`）。
- 报销付款的转账截图挂在报销单上（`REIMBURSE`）。

**4. 已收到退款**
- 复用 ③a 的退款：付款记录 kind 2、method 2（员工垫付）、`advance_user` 为本人、没有账户、`reimburse_status = 1`。
- 核销明细 `from_credit = 2` 冲减应付单欠款，计算逻辑不变。
- 只能对「本人垫付过（有本人的 method 2 付款核销进来）且有欠款」的应付单登记。

**5. 报销付款进付款记录**
- 财务登记已付时生成一条付款记录：kind 3 报销付款，收款方类型 5 员工、收款方名称为员工姓名，method 1，账户、日期、截图同登记。
- 这条记录不核销应付，不进入原「付款合计 / 公司对公 / 员工垫付」统计，以免和员工垫付重复计算；付款记录页的统计另加「报销付款」。
- 撤销已付时作废这条付款记录。

**6. 费用单**
- `fin_expense`：编号 FE；名称、发生日期；收款方（类型 1 供应商、2 线上店铺、3 货代、4 其他，供应商 ID 或平台 + 店铺名或名称）；币种、金额、汇率、人民币金额；method、垫付人 ID；说明；状态（1 有效、2 已作废）；作废原因。
- `fin_expense_allocation`：`expense_id`、`so_id`、`so_item_id`、金额、人民币金额。③c 按订单型号行汇总。
- **公司对公**：应付来源类型 3 费用单，`PayableSyncService.syncExpense` 生成或重算，一期，到期日为发生日期；作废时应付关闭。收款方类型 4「其他」只有名称，同名同币种视为同一收款方（可以合并付款）。
- **员工垫付**：不生成应付，待报销来源 4。

**7. 权限与菜单（迁移 V1.2.59）**
- **菜单**：财务管理下新增「报销单」`/finance/reimbursements`、「费用单」`/finance/expenses`。
- **按钮**：
  - `finance:reimburse:pay`（报销付款），挂在报销单下；
  - `finance:expense:edit`（费用单维护），挂在费用单下。
- **授权**：
  - 有采购单、出库打包或收款管理菜单的角色，得到报销单菜单；
  - 有收款管理的角色，得到报销付款、费用单菜单与费用单维护；
  - 内置租户管理员得到全部。
- 数据范围：没有报销付款权限的人只看本人的报销单。

**8. 前端**
- `pages/finance/reimbursements`：
  - 「待报销」页签：本人；
  - 「报销单」页签：列表与详情抽屉；
  - 待退款提醒与「登记已收到退款」弹窗；
  - 财务的「登记已付」抽屉。
- `pages/finance/expenses`：列表、录入抽屉（收款方选择、分摊行选订单型号）、详情、作废。
- 到货差异处理弹窗：填退货运费时出现「垫付人」（默认本人）。
- 付款记录页：类型增加「报销付款」，统计增加报销付款。

## Risks / Trade-offs

- **[实时汇总的性能]** 每次打开待报销都要查五个来源。
  → 只查本人、只查未进报销单的；数据量很小。
- **[来源被改]** 待付款报销单里的快递费、退货运费如果来源被改金额，报销单金额就对不上。
  → 已进报销单的来源禁止修改金额或撤销，提示「已在报销单 BX… 里，请先撤回」。
- **[「其他」收款方按名称合并]** 名称写法不一致会被当成两家。
  → 录入时下拉提示已有的名称。

## Migration Plan

- Flyway `V1.2.59__reimbursement_expense.sql`：
  - 报销单、报销明细、费用单、费用分摊表；
  - 到货差异加 `return_payer_id`，存量有退货运费的回填为处理人；
  - 菜单与按钮并授权。
- 单据类型 BX、FE 加入 `DocumentType`。
- 回滚：菜单下线；已生成的报销、费用数据保留。

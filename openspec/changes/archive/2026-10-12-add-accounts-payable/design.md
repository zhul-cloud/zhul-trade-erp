## Context

**依据**：供应链单据模型第③期（`docs/02-产品PRD/04-供应链域/供应链单据模型-设计-V1.0.md` 第 7 节资金层、第 9 节事务边界）。本变更是 ③a：应付与付款；员工垫付的报销单、费用单是 ③b，订单实际成本与砍价报表是 ③c。

**已有基础**：
- **采购单**（`purchase`）：分期付款条件（比例 + 时点：下单后、发货前、入库后、入库后 N 天）、其他费用、原币 / 汇率 / 人民币合计、确认下单、修改留痕、取消；发货进度「已入库」表示全部入库。
- **到货差异**（`purchase`）：少发不补、退货不补减少订购数量并重算合计；折价接收记录折价金额，还没进应付。
- **货代对账**（`logistics/StatementService.confirm`）：确认后对账单不可改。
- **公共能力**：
  - `DocumentNumberService`：单据编号；
  - `AttachmentService`：附件存储，用于付款截图；
  - 「收款账户」（`BankAccountDO`，按币种）：作为公司付款账户；
  - 收款管理（`sales`）：可参照的「登记 + 截图 + 作废」写法。

**用户已定**：
- 拆成三个变更依次做；
- 公司对公付款由财务登记，登记即生效；
- 线上店铺付款支持公司对公和员工垫付两种；
- 外币按原币核销，记录实付人民币和实际汇率。

## Goals / Non-Goals

**Goals**
- 欠谁多少、什么时候到期、付了没有，都能在系统里一眼看清，付款能对到采购单和对账单。
- 应付金额随采购单、到货差异自动同步，不用人手维护。
- 员工垫付能被记录下来，给 ③b 报销单提供数据。

**Non-Goals**
- 不做报销单、费用单（③b），不做订单实际成本、砍价报表（③c）。
- 不做付款审批、请款流程，不做供应商发票。
- 不生成会计凭证；汇兑差异只显示。
- 退货运费、国内快递运费这些员工垫付的费用放到 ③b 处理，不进应付。

## Decisions

**1. 新模块 `finance`，应付与付款独立于采购和物流**
- 包结构：`com.zhul.erp.modules.finance.{controller,service,repository,dto,entity}`。
- 采购、物流只调用 `PayableSyncService` 的同步接口（`syncPurchaseOrder(poId)`、`createForStatement(statementId)`），不直接写应付表。
- 应付表记录来源类型和来源 ID，财务查询不反向依赖采购的内部结构。
- **备选**：放进 `purchase` 模块。但货代应付来自物流，以后还会有费用单、报销单，放进采购会越来越杂，所以不采用。

**2. 一张来源单据一张应付单，金额按「来源当前状态」重算，而不是记增减流水**
- 应付金额 = 采购单合计 − 已处理折价合计；采购单取消时为 0。
- 每次相关动作后，`syncPurchaseOrder` 在调用方事务内：锁定应付单，按采购单现状重算金额和付款计划，再把已付金额重新分配到各期。
- 好处是任何修改路径（改价、差异、重新打开、取消）都不会漏算，结果可以重放。
- **备选**：按动作记录应付调整流水。可以追溯每次变动，但每条修改路径都要写对应流水，容易漏，所以不采用。变动原因在采购单操作日志里已经有了。

**3. 存储**

| 表 | 主要字段 |
|---|---|
| `fin_payable` 应付单 | `tenant_id`、`payable_no`、`payee_type`（1 供应商、2 线上店铺、3 货代）、`supplier_id`、`shop_platform`、`shop_name`、`source_type`（1 采购单、2 货代对账单）、`source_id`、`currency_code`、`amount`、`exchange_rate`、`amount_cny`、`paid_amount`、`paid_cny`、`credit_amount`（欠款）、`status`（1 未付、2 部分付款、3 已付清、4 已关闭）、`next_due_date`、`deleted_at` |
| `fin_payable_installment` 付款计划 | `payable_id`、`seq`、`ratio`、`trigger_type`（1 下单后、2 发货前、3 入库后、4 入库后 N 天）、`offset_days`、`amount`、`due_date`（可空，表示待入库）、`paid_amount`、`status` |
| `fin_payment` 付款记录 | `payment_no`、`kind`（1 付款、2 供应商退款）、收款方字段同上、`method`（1 公司对公、2 员工垫付）、`bank_account_id`、`advance_user`（垫付人）、`pay_date`、`currency_code`、`amount`、`amount_cny`、`actual_rate`、`credit_used`（本笔抵扣的欠款）、`remark`、`reimburse_status`（垫付：0 待报销，③b 使用）、`void_at`、`void_by`、`void_reason`、`idempotency_key` |
| `fin_payment_allocation` 核销明细 | `payment_id`、`payable_id`、`amount`（原币）、`amount_cny`、`from_credit`（0 实付、1 欠款抵扣）、`credit_payable_id`（抵扣来源应付单） |
| 付款截图 | 复用通用附件表 `biz_attachment`，归属类型 `PAYMENT`，不另建表 |

- 所有表都是业务表：带 `tenant_id`、`deleted_at`，金额 `DECIMAL(18,2)`，汇率 `DECIMAL(18,6)`。
- 索引：`tenant_id`、来源、收款方、`status`、`next_due_date`、`deleted_at`。
- 同一来源只有一张有效应付单，用唯一索引（`tenant_id, source_type, source_id, deleted_flag`）保证。

**4. 付款计划的金额与已付分配**
- 各期金额 = 应付金额 × 比例，两位小数 HALF_UP，尾差给最后一期。
- 已付分配：把应付单的已付合计按期次顺序填满：先按到期日排，「待入库」排后，同日按期序。分配结果只是派生值，每次重算都会刷新。
- 期次状态和「已逾期 / 即将到期」在读取时按当天计算，不存。
- 应付单只存 `next_due_date`（最早一期有未付金额的到期日），用于筛选和排序；同步时更新。
- 到期日推算在同步时完成：
  - 下单日期、预计发货日期取自采购单；
  - 全部入库日期取发货进度变为「已入库」的入库单日期；
  - 入库确认会调用同步。

**5. 核销与欠款**
- 已付金额 = 有效核销明细（含欠款抵扣）合计。
- 欠款 = max(0, 已付 − 应付 − 已退款合计 − 已抵扣出去的金额)。
- 抵扣是一种核销：在付款记录里，`from_credit = 1` 的明细从来源应付单的欠款转到目标应付单；两张应付单在同一事务内更新，按 ID 顺序加锁，避免死锁。
- 供应商退款是 `kind = 2` 的付款记录，冲减来源应付单的欠款。退到公司账户的在这里登记；退到员工手里的，在 ③b 的报销单里冲减。

**6. 并发与幂等**
- 登记付款：先按 ID 升序 `SELECT … FOR UPDATE` 锁住涉及的应付单，再校验未付和欠款，最后写入。
- 前端每次打开登记抽屉生成一个 `idempotency_key`；后端按（`tenant_id`、`key`）唯一，重复提交返回第一次的结果。
- 作废同样加锁，状态检查和恢复在同一事务内完成。

**7. 权限与菜单（迁移 V1.2.58 插入 `sys_resource` 并授权）**
- **菜单**：「财务管理」下新增「应付管理」`/finance/payables`、「付款记录」`/finance/payments`，排在收款管理之后。
- **按钮**：
  - `finance:payment:register`（付款登记）；
  - `finance:payment:advance`（垫付登记）；
  - `finance:payment:void` 不单独设：作废由「登记人本人」或「有付款登记权限的人」完成。
- **授权**沿用以往迁移的做法：
  - 有「收款管理」菜单的角色，得到应付管理、付款记录和付款登记；
  - 有「采购单」菜单的角色，得到垫付登记；
  - 内置租户管理员得到全部。
- 采购单详情的付款面板跟随采购单权限，不需要应付菜单。

**8. 存量数据**
- 迁移只建表、插菜单；不在 SQL 里生成应付，因为分期和到期日计算在 Java 里。
- 上线后由启动任务 `PayableBackfill` 补齐：已下单、还没有应付单的采购单，已确认、还没有应付单的货代对账单，逐张调用同步生成。
- 有应付单的不再处理，所以重复启动不会重复生成；每张单据一个事务，失败只记日志，下次启动再补。
- 测试库由集成测试覆盖这段逻辑。

**9. 前端**
- `pages/finance/payables`：列表 + 详情抽屉。
- `pages/finance/payments`：列表 + 登记付款抽屉，可从应付管理、采购单面板、对账单详情打开，按入口带出收款方和应付单。
- 采购单详情加「付款」卡片；采购单列表加付款列；货代对账单列表和详情加付款状态。
- 列表遵循列表页统一规范：更新时间倒序，固定四列。金额统一用 `formatAmount`。

## Risks / Trade-offs

- **[重算覆盖历史]** 应付金额总按采购单现状重算，不保留「当时欠多少」的快照。
  → 采购单操作日志已记录每次修改；付款记录本身不变，可以追溯。
- **[待入库期次的催付]** 「入库后」的期次在全部入库前没有到期日，分批入库时，已入库部分不会提前到期。
  → 和业务约定一致（按整单入库算）；有特殊情况可以先付，系统允许提前核销未到期的期次。
- **[欠款计算复杂]** 欠款、抵扣、退款交织。
  → 集中在 `PayableSyncService` 一处计算，契约测试覆盖少发欠款抵扣、取消后退款、作废恢复。
- **[员工垫付进入报销前的状态]** ③b 上线前，垫付只是记为「待报销」，没有报销流程。
  → 付款记录页可以按垫付人筛选，临时手工报销。

## Migration Plan

- Flyway `V1.2.58__accounts_payable.sql`：建表、单据编号类型 AP 和 PY、菜单与按钮权限，按上面的规则授权。
- 发布后首次启动自动补齐存量应付；在应付管理核对补齐的数量。
- 回滚：菜单下线即可，存量采购、物流数据不受影响。

# Design

## Context

- **货代现状**：货代就是供应商表里类型为「服务商」（`supplier_type = LogisticsConstants.SUPPLIER_SERVICE`）的记录。
  - 以下都按供应商 ID 引用货代：发货通知与出库单（`forwarder_id`）、出运单、运费账单（`forwarder_statement.forwarder_id`）、应付与付款（收款方类型「货代」+ `supplier_id`）、供应商收款账户。
  - 发货通知的下拉来自 `GET /logistics/forwarders`（`LogisticsSupport.forwarders`），列出全部启用的服务商，排除历史迁移的占位。
- **客户负责人现状**：`customer.owner_id` 为 0 表示未分配；数据范围「仅本人」的用户看不到未分配客户，「全部」的能看到。转移走 `CustomerServiceImpl.transfer`：写操作日志，并把未结束的跟进对象转给新负责人（`followupSync.ownerChanged`）。
- **新增菜单的做法**：参照 V1.5.34。插入菜单与按钮资源；追加到已含相关菜单的租户套餐；授权给已有相关菜单的角色。

## Goals / Non-Goals

**Goals:**
- 货代在界面上独立管理，供应商管理里不再混着货代；原有单据、付款、账单的引用一行都不用改。
- 客户自有货代在发货时优先出现、能默认选中，不会被其他客户误用。
- 公海客户的放入、认领规则简单明确，并发认领不出错。

**Non-Goals:**
- 不把货代迁到新表。
- 不做公海的自动规则（如超过 N 天没跟进自动放入）和认领数量上限。用户这次只要手动放入、自由认领；以后需要再加。
- 客户自有货代不区分运费由谁付；付款仍按现有应付规则走。

## Decisions

1. **货代数据仍放在供应商表**：
   - 新增「货代管理」接口 `/api/v1/logistics/forwarders`（分页、详情、新增、修改、停用），只处理 `supplier_type = 服务商` 的记录。新增时类型固定为服务商，编码沿用供应商编码规则。
   - 收款账户复用供应商收款账户的表与组件。
   - 供应商管理的列表、导出、选择器、新增与编辑都排除服务商：请求带服务商类型时拒绝；前端类型选项去掉「服务商」。
   - 不建新表的理由：引用货代的单据、账单、付款、收款账户都按供应商 ID 关联。拆表要改多张表和历史数据，风险大，用户感知不到区别。
2. **归属客户**：`supplier.customer_id`（bigint，可空，加索引），只对服务商有意义。
   - 发货通知取下拉时带上订单的客户。后端返回启用的公司货代（`customer_id` 为空）加这个客户的货代，并标记 `customerOwned`。
   - 排序：客户指定的在前，再按名称排。
   - 默认选中：客户指定只有一家时选它；否则全部可选只有一家时选它；其余不默认。保留 UI-095 的「先选货代」提示。
   - 提交发货通知时后端再校验：所选货代要么是公司货代，要么属于这张订单的客户。
   - 客户合并时把被合并客户的货代改归保留客户（加进合并搬迁的表清单）。客户软删除时归属保留，货代仍可在货代管理里改，显示「（客户已删除）」。
   - 客户详情的「客户指定货代」用 `/logistics/forwarders/by-customer/{客户ID}`：查看要求客户在数据范围内，新增要求客户编辑权限（归属固定为这个客户）；修改已有货代走货代管理接口，要求货代编辑权限。
   - 货代管理里选「归属客户」时按自己的数据范围搜索客户。
   - 费用单收款方选「货代」时改为从货代列表选（供应商搜索已不含货代）。
3. **公海字段**：`customer` 新增 `in_pool`（tinyint，默认 0）、`pool_at`、`pool_by`、`pool_reason`（varchar 200）、`last_owner_id`，并加索引 `(tenant_id, in_pool)`。
   - **放入**：逐个加行锁检查。必须是负责人本人，或者有转移权限且客户在自己数据范围内。然后设 `owner_id = 0`、`in_pool = 1`，记下放入信息和上一任负责人；跟进对象改为无人负责（`followupSync.ownerChanged(id, 0)`）；写操作日志。
   - **公海列表** `GET /masterdata/customers/pool`：只要求有客户管理菜单权限，不套数据范围，只查 `in_pool = 1`。
   - **认领** `POST /masterdata/customers/{id}/claim`：用条件更新 `... WHERE id = ? AND in_pool = 1` 防止并发；更新 0 行时查出当前负责人，提示「已被 xxx 认领」。认领后事业部取认领人所在事业部（`businessUnitService.unitOfUser`），为空时不变；跟进对象转给认领人；写操作日志。
   - **详情**：查看类接口（客户详情、画像、联系人列表、RFM 明细）改用 `requireReadable`：数据范围内的客户或在公海的客户都能看。其余修改、新建询盘与单据走原来的数据范围校验，并对公海客户一律拒绝（「在公海，认领后才能操作」），转移也要先认领。
   - 前端：客户详情对公海客户显示公海提示与「认领」，隐藏跟进、信用、客户指定货代和编辑类操作；客户列表与详情在有编辑或转移权限时显示「放入公海」入口，是否允许由后端判断。
   - 「全部客户」列表、导出、第一批的建档统计（`profile-counts`）和客户选择器都排除 `in_pool = 1`。
4. **菜单与权限**：
   - 新增菜单「货代管理」，按钮包括新增、编辑、停用。追加到已含「出运管理」菜单的套餐；授权给已有供应商菜单或出运管理菜单的角色。
   - 公海不新增权限：放入用「负责人本人或客户转移权限」，认领与查看用客户管理菜单权限。

## Risks / Trade-offs

- [货代仍在供应商表，以后若要和供应商彻底分开还要再迁一次] → 这次的接口与前端已经按货代独立组织，以后拆表只改后端存储层。
- [公海客户的详情对所有业务员可见] → 这是公海的本意。资料修改与新建单据仍要先认领。
- [认领后事业部随认领人变化，已有单据的事业部不变] → 与「转移」勾选同步事业部的规则一致。

## Migration Plan

- 迁移（版本号在合并前按 develop 的最新版本确定）：
  - `supplier.customer_id`；
  - `customer` 的 `in_pool / pool_at / pool_by / pool_reason / last_owner_id` 与索引；
  - 菜单「货代管理」及按钮资源、套餐追加、角色授权。
- 回退：删除新增的列、索引与资源（迁移文件里写明回退语句）。回退前要先确认没有公海客户（`in_pool = 1`），否则这些客户会变成未分配。
- 没有配置变化。

## Context

系统目前没有站内通知，交接靠各页面的待办列表（询价超时、今日待办）和工作台看板。生产租户 1000 的现状（2026-11-10 只读核对）：
- 「采购员」「供应链主管」「仓库」「财务」角色都没有账号；
- 询价分配、采购下单、登记发货、收货主要由两位「阿里国际站事业部合伙人」完成；
- 「收货」权限业务员、合伙人、总经理、租户管理员都有。

所以不能按权限找收件人，要用「单据负责人 + 可配置的岗位接收人」。用户确认的规则：
- 采购负责验收入库，业务员负责打包，采购登记发货；
- 采购员没处理不升级、不催办，只在采购需求列表标红；
- 今日待办不进通知；
- 第一期只做站内通知，第二期接飞书。

## Goals / Non-Goals

**Goals：**
- 第一期 16 个节点的站内通知；待办型通知随单据状态自动处理；
- 收件人按负责人和岗位接收人确定，按人合并；
- 发送渠道可扩展，第二期接飞书时不改各节点的代码。

**Non-Goals：**
- 飞书推送、邮件推送；
- 超时升级、催办；
- 用户自己按节点开关通知；
- WebSocket 实时推送（第一期用每分钟轮询）；
- @提及、评论类通知。

## Decisions

### 1. 数据模型

`notification`（业务表，带 `tenant_id`、`deleted_at`）：
- `recipient_id`：收件人用户 ID；
- `node_code`：节点编码，如 `SOURCING_POOL`；
- `kind`：类型（1-待办、2-知会）；
- `merge_key`：合并键，同一收件人、同一节点、同一合并键的待处理通知只有一条；
- `biz_no`：相关单据编号；`biz_ids`：这条通知涉及的记录 ID（JSON 数组，如任务、需求、发货单），用于判断待办是否已处理；`item_count`：涉及的数量；
- `content`：一句话内容；标题不落库，按节点模板和 `biz_no`、`item_count` 生成；
- `link`：前端路由；
- `urgent`：是否紧急；
- `read_at`：已读时间；
- `done_at`：已处理时间，只有待办型才有；
- 必填审计字段。

索引：`(tenant_id, recipient_id, done_at, read_at)`、`(tenant_id, node_code, merge_key)`。

`notification_receiver`（基础表，带 `tenant_id`）：
- `post_code`：岗位（`PURCHASE_LEAD`、`RECEIVER`、`FINANCE`）；
- `user_id`：接收人；
- `status`：1-有效、0-已移除；
- 收货人岗位另用一条 `user_id = 0` 的记录表示「采购订单的采购员」；保存为空时留一条 `user_id = -1`、已移除的记录，表示「保存过」。

两张表在 `TenantTables` 都归为私有。

**为什么不放进系统配置：** 接收人是多选的用户，需要按用户停用过滤、查名字，用独立表更直接。

### 2. 发送流程

```
业务 Service（事务内）
  └─ XxxNotices（各模块自己的通知拼装类）→ Notifier.send(Notice)
        │  Notice：节点、合并键、单据编号、链接、涉及的 ID、数量、内容、紧急、负责人
        │  有事务时先登记在事务资源里；没有事务时立即发送
        ▼ TransactionSynchronization.afterCompletion（只在 STATUS_COMMITTED 时）
TenantContext.runAs(登记时的租户) → NotificationService.deliver（新事务 REQUIRES_NEW）
  ├─ 解析收件人：负责人 → 岗位接收人 → 去掉操作人、停用用户
  ├─ 按 (节点, 合并键, 收件人) 合并：有待处理的待办或未读的知会就合并 ID、更新内容和时间，ID 有增加时清掉 read_at；没有就新增
  └─ 写库即送达（第一期只有站内）
```

- 业务回滚不发；发送时捕获异常只打日志，不影响业务。
- afterCompletion 时业务事务已结束，登记时记下租户和操作人，发送时用 `TenantContext.runAs` 还原租户。定时任务入口用 `TenantScope.platform` 逐租户执行，单个租户内再用 `TenantContext.runAs`。
- 「订单货已到齐」每个合并键只发一次。

**备选方案：** `@TransactionalEventListener(AFTER_COMMIT)` 发事件。效果相同，但要额外定义事件类；直接用事务同步更简单。直接在业务事务里写通知的方案会让通知失败拖垮业务、回滚时通知已写入，不选。

**依赖方向：** 发送类（`XxxNotices`）依赖 `Notifier`；判断待办是否处理的类（`XxxNotificationChecker`）只依赖 Mapper，被 `NotificationService` 注入。两者分开，避免业务 Service ↔ 通知服务的循环依赖。

### 3. 待办自动处理：读取时按需检查

各模块实现 `NotificationTodoChecker`：给定节点、收件人和 `biz_ids`，返回其中仍未处理的 ID。查询列表或角标前，`NotificationService.refreshOpen(收件人)` 取出本人未处理的待办，按节点交给对应的检查类：
- 全部已处理 → 写 `done_at`；
- 部分已处理 → 更新 `biz_ids` 与 `item_count`，标题跟着变成剩余数量。

| 节点 | 涉及的 ID | 仍未处理的条件 |
| --- | --- | --- |
| 询价任务待分配 | 任务 | 任务仍在待分配 |
| 询价任务分配给我 | 任务 | 任务在询价中，且收件人仍是有效处理人 |
| 付款水单待登记 | 水单 | 水单有效，且还没有用这张水单登记的有效到账 |
| 有型号需要你采购 | 需求 | 需求有效、采购员是收件人、已下单数量小于需求数量 |
| 有型号没指定采购员 | 需求 | 需求有效、没有采购员、还没全部下单 |
| 供应商已发货 / 到期还没收货 | 发货单 | 发货单仍在途 |
| 到货有差异 | 差异 | 差异仍待处理 |

**为什么不在各业务点调 resolve：** 能让待办「完成」的入口很多（分配、改派、取消、作废、下单、关闭、拆分……），逐个挂钩容易漏，漏了待办就一直挂着。按需检查只需要每个节点写一个判断，列表一打开就是准的。检查只针对本人未处理的待办（通常几条），每次一条查询，开销可控。

### 4. 节点定义集中在一处

`NotificationNode` 枚举定义每个节点的编码、名称、类型、岗位、标题模板。链接与一句话内容由各模块的 `XxxNotices` 拼好放进 `Notice`；标题统一由节点模板生成，方便第二期飞书复用同一套内容。

### 5. 订单货已到齐

收货成功后（验收、直接收货、直发货代确认都走同一个入库方法），按订单货物状态的口径（`PurchaseLinks`）计算有采购的型号「待采购 + 待发货 + 在途」是否为 0；为 0 就发送。`merge_key = 订单 ID`，该键已有通知时不再发，保证只发一次。

### 6. 到期未收货定时任务

每天 9:00 运行（`@Scheduled`）：找出预计到货日不晚于今天、还没收完、不是直发货代、该节点还没有通知的发货单，按收货人规则发送。会被 `BackgroundEntryTenantContractTest` 自动检查。

### 7. 前端

- `TopBar` 增加铃铛：用 antd `Badge` 显示数字，点击打开 `Drawer`，抽屉里用 `Segmented` 切换「待处理 / 全部」，列表滚动到底时加载下一页（每页 20 条）。
- 每 60 秒轮询一次角标（`GET /api/v1/notifications/count`）；页面不在前台时暂停，回到前台立即刷新。列表底部「加载更多」，每页 20 条。
- 业务设置增加「通知接收人」页：三个岗位卡片，接收人以头像标签显示，「添加」从本租户有效账号中搜索选择，改动即保存；收货人卡片用分段控件切换「采购订单的采购员 / 指定的人」；卡片下面列出该岗位接收哪些通知。
- 采购需求列表：顶部加「超时未下单」统计卡，点击切换只看超时；超时的行浅红底，型号旁标「超时 N 小时」；按订单视图的订单行标「N 个超时」。

### 8. 接口

| 接口 | 说明 |
| --- | --- |
| `GET /api/v1/notifications?tab=todo\|all&page&pageSize` | 通知列表 |
| `GET /api/v1/notifications/count` | 角标数字：未处理待办、未读知会、合计 |
| `POST /api/v1/notifications/{id}/read` | 标为已读 |
| `POST /api/v1/notifications/read-all` | 全部已读，只处理知会型 |
| `GET /api/v1/system/notification-receivers` | 查询岗位接收人 |
| `GET /api/v1/system/notification-receivers/candidates` | 可选的接收人（本租户有效账号） |
| `PUT /api/v1/system/notification-receivers/{post}` | 修改岗位接收人，需要「通知接收人」编辑权限 |

通知接口只要登录，只能看和改自己的；接收人接口按「通知接收人」菜单与按钮权限控制。

### 9. 采购需求超时

- 系统配置新增 `purchase.requirement.overdue-hours`，默认 24。
- 超时 = 需求有效、还没全部确认下单（排入草稿也算没下单）、生成时间早于「现在 − 时限」。
- 列表查询返回 `overdueHours`（超出时限的小时数，没超时为空）；按订单视图返回 `overdueCount`；统计接口增加 `overdue`；筛选增加 `overdue=true`。
- 标红在查询时实时计算，不落库。

## Risks / Trade-offs

- [检查条件写错，待办一直挂着或提前消失] → 待办节点在集成测试里覆盖「完成后通知变为已处理」；通知列表 90 天后自动不显示，兜底。
- [岗位默认接收人取错] → 按权限实时计算、排除有系统设置权限的管理角色，上线后请用户在设置页确认；生产会默认两位合伙人，财务为空（页面提示）。
- [收件人列表与检查都在读取时做，列表接口变慢] → 只检查本人未处理的待办，按节点批量查询。
- [每分钟轮询的压力] → 角标接口只走 `(tenant_id, recipient_id, done_at, read_at)` 索引做计数，开销很小。
- [事件监听不在业务事务里，极端情况下业务提交成功但通知没发] → 可以接受，只记日志；通知不是业务数据。

## Migration Plan

1. 迁移 `V1.5.22__system_notification.sql` 新增两张表；岗位接收人不初始化数据，没保存过时按权限实时取默认值。
2. 新增系统配置 `purchase.requirement.overdue-hours = 24`（平台模板），菜单「业务设置 → 通知接收人」与编辑按钮，授权给已有「快递时效」菜单的角色，并加进租户套餐。
3. 发布后不补发历史通知，只对上线后发生的事件发通知。
4. 回退：后端回到上一版本即可；两张表与新菜单保留不影响旧版本，也可以按迁移文件头部的回退 SQL 删除。

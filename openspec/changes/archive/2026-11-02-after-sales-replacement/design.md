## Context

售后第一期（V1.4.3）已有售后单、退货单、退款申请。销售订单有两种来源：PI 生成（source=1）与手动建单（source=2，pi_id=0）。订单成本由 `OrderCostService` 按型号行汇总采购、运费、费用与售后退货冲减；CI/PL 由 `DocGroupService` 按订单型号单价出金额；销售统计、利润统计、经营统计都按销售订单取数。

## Goals / Non-Goals

**Goals:** 售后单一键生成 0 元补发订单，复用现有采购到出运全链路；补发成本归原订单；单证有申报货值；统计不虚增销售。

**Non-Goals:** 用闲置库存补发、补发订单的独立利润、时限提醒、退回供应商与应付打通。

## Decisions

1. **补发订单就是销售订单（source=3），不新建单据。** 采购需求、排单、入库、出库、出运、订单进度、部分取消全都按订单型号行工作，复用成本最低。备选「补发单」独立单据需要把整条采购物流链路再接一遍，否决。
2. **新增字段**：`sales_order.after_sales_id`、`sales_order.original_so_id`（加索引）；`sales_order_item.declared_price DECIMAL(18,2)`（原币，仅补发订单有值，其余为 NULL）。单价、金额、本位币金额写 0，合计 0，汇率仍取原订单汇率（金额字段原币与本位币同时存 0）。
3. **收款**：收款状态新增「无需收款」值（沿用 receipt_status 字段，补发订单建单即为该值）；收款登记、余额抵扣、退款、多收计算按 source=3 拒绝或跳过。PI 相关逻辑本来只对 source=1 生效。
4. **成本归属**：`OrderCostService` 计算原订单时，查出 `original_so_id = 本单` 且未取消的补发订单，对每张补发订单按原逻辑算出实际成本（Item 列表），合计成一个「售后补发」数（不进型号行，单独一行明细与 sources 里 type=REPLACEMENT）。补发订单自己的成本卡片仍算出明细，但收入、毛利不显示。结算状态：原订单要求补发订单也已结算。利润统计、经营统计调用同一个计算，自动带上。
5. **统计排除**：销售统计、利润统计（列表）、经营统计（收入、订单数）的查询加 `source <> 3`。
6. **单证**：`DocGroupService` 取价处：补发订单型号用 `declared_price`；单证组含补发订单时备注追加固定英文。
7. **结案校验**：`AfterSalesService.close` 检查该售后单下补发订单是否存在未取消且进度早于「已出运」的，提示单号。
8. **事务边界**：发起补发在一个本地事务内：锁售后单行 → 校验 → 建订单与型号行 → 生成采购需求（复用手动建单后的需求生成）→ 写售后日志。成本、统计是读时计算，无跨模块写入。

## Risks / Trade-offs

- 订单列表、收款、多收等按 source 判断的地方多（现有十余处 `SO_MANUAL` 判断）→ 逐处检查，补测试覆盖「补发订单不能收款」「不计入多收」。
- 原订单已结算后再补发，原订单会回到未结算 → 符合实际（成本变了），在成本卡片提示原因。
- 精度：申报金额 = 申报单价 × 数量，HALF_UP 两位；成本口径沿用现有。

## Migration Plan

迁移 V1.4.4：加三个字段与索引、字典「订单来源」与「收款状态」新值（如有字典）。回退：删除三个字段，source=3 的订单需先处理（回退 SQL 写在注释里）。

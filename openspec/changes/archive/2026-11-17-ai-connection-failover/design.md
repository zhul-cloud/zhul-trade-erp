# Design

## Context

- **配置**（`modules/aitask`）：
  - `sys_ai_config`：每租户一行，`mode` + `provider` 记「当前使用的连接方式」。
  - `sys_ai_provider_config`：每租户 × 用法 × 服务商一行，存 Key 密文、模型、思考强度、搜索次数。
  - 租户的订阅设置读平台（租户 0）那一行，租户自己没有订阅行。
- **提交**：`AiConfigServiceImpl.resolveForCurrentTenant()` 在请求线程里取出唯一一个 `AiCallConfig`，`AiTaskServiceImpl` 把它放进提交编排服务的请求体 `ai` 字段。
- **编排服务**（`scripts/ai-orchestrator/server.py`）：
  - 每个技能的模型调用都经过 `call_api(cfg, …, model=, effort=)`。调用方从 `cfg.parse_model` / `cfg.translate_model` 等字段取模型。
  - `_with_retries` 在同一连接方式上，对连接错误、408/409/429、5xx 做退避重试。
  - 订阅调用走 `subscription.py`，错误以 `RuntimeError` / `SubscriptionError("auth")` 等抛出。
- **回调**：进度回调（`send_progress`）在长任务中周期发送；结果回调（`send_callback`）在结束时发送一次，带 `model` 与用量。

动机见 proposal.md；行为要求见 specs。

## Goals / Non-Goals

**Goals:**
- 一次提交携带「按顺序挑好的可用连接方式列表」，编排服务在同一任务内逐次调用级别切换。
- 暂停状态在第一次失败时就生效，不等长任务结束。
- 上线后已有租户的实际使用方式不变，尤其是原来只用订阅的租户不会突然改用付费 Key。

**Non-Goals:**
- 不做按调用量、费用或延迟的智能选路，顺序完全由用户决定。
- 不改订阅的登录、授权和模型设置规则。
- 测试连接与模型列表接口的协议不变。
- 不让同一次调用并发打多家服务商（不做竞速）。

## Decisions

### 1. 顺序与开关存在 `sys_ai_provider_config`，单选字段停用但保留

- **新增字段**：`sort_order`（组内序号）。是否参与沿用原有的 `status` 列（0-关闭、1-启用），只改列注释，不另加 `enabled` 列。
- **租户的订阅行**：要记顺序和开关，所以租户也可以有订阅行。这些行只用 `sort_order`、`status`，模型字段忽略，仍然读平台那一行。没有订阅行时视为启用，按 Claude、OpenAI 排序。
- **单选字段**：`sys_ai_config.mode/provider` 不再作为调用依据，但保留不删。这样回退到旧版本时，旧代码仍能按原来的单选工作。
- **否决的方案**：新建一张「顺序表」。它与配置行一一对应，拆开只会多一次关联和一致性问题。

### 2. 组的先后由代码固定，只存组内顺序

- API 组永远在订阅组前面，所以 `sort_order` 只在同一用法内比较。
- 保存接口的入参是两组各自的有序列表。提交的列表里出现用法与所在组不符的项时，直接拒绝。
- 这样「订阅不能排到 API 前面」由结构保证，不需要额外校验跨组序号。

### 3. 后端挑选列表：`resolveChainForCurrentTenant()`

- **挑选规则**：按「API 组顺序 + 订阅组顺序」逐个检查，可用的放进列表，不可用的跳过。不可用的情况：
  - 未启用；
  - API 方式没有 Key；
  - 订阅未授权或未登录；
  - 处于暂停中。
- **列表为空时**：沿用原有的两种异常：
  - 没有任何「已配置且启用」的方式时，抛 `AiNotConfiguredException`；
  - 有配置但都因订阅不可用或暂停而跳过时，抛 `AiUnavailableException`。

  `isConfiguredForCurrentTenant()` 用同一套判断，保证顺带触发的任务和主动操作结论一致。
- **登录状态**：提交任务时，API 组里已有可用方式就直接把订阅接在后面，不查登录状态（避免每次提交都多一次请求）；未登录的订阅真轮到时由编排服务按「订阅未登录」切换并暂停。只有 API 组一个可用的都没有时，才查一次 `orchestratorClient.status()`：确认未登录的订阅跳过；查不到状态时，平台租户照常使用自己保存过的订阅，其他租户和从没保存过的订阅跳过。从没保存过的订阅在登录状态查不到时不算「已配置」，这样什么都没配过的公司仍提示「AI 未配置」。设置页展示时同样只查一次。

### 4. 暂停状态存 Redis，按「谁的连接」分键

- **键**：
  - API：`zhul:erp:ai:pause:{tenantId}:api:{provider}`，只影响本租户；
  - 平台订阅：`zhul:erp:ai:pause:0:subscription:{provider}`，所有租户共用，因为是同一个登录。
- **值**：`{reason, until}`，TTL 600 秒，到期自然恢复，不需要定时任务。
- **解除**：保存该方式（包括更换 Key）或测试连接成功时删除对应键。
- **为什么用 Redis 而不是数据库字段**：暂停只是提示性的短期状态，丢了最多多试一次。Redis 的 TTL 正好表达「10 分钟后恢复」，也不需要清理任务。这属于读多写少、可丢失的数据，符合缓存使用原则。

### 5. 编排服务：`call_api` 改为按列表切换，调用方按「角色」取模型

- **请求体**：新增 `connections`，为有序数组，每项与原 `ai` 字段结构相同。
- **兼容旧请求**：只有 `ai` 字段时，当作只有一项的列表。这样升级发布时，在途的旧请求仍能处理。
- **调用方式**：
  - `call_api(chain, role, …)`，`role` 为 `parse` / `translate` 等。每次调用时从当前连接方式取对应的模型与思考强度，不再由调用方传具体模型名。
  - 所有技能的调用点一起改，共约 10 处：`call_parse`、`call_translate`、背调、跟进、报价解析、候选分类、品类细化等。
- **调用流程**：
  1. 在当前连接方式上照旧执行 `_with_retries`。
  2. 抛出异常后按下面的「错误分类」判断。属于「换方式」的，把该方式记入本任务的失败集合，并发一条切换事件，再用下一个未失败的方式重做这一次调用。
  3. 本任务后续的调用（包括并行批次）都跳过失败集合里的方式。失败集合加锁，分批解析的线程共用。
- **错误分类**（集中在一个函数里，便于测试）：

| 换方式 | 不换方式（按原规则处理） |
| --- | --- |
| 鉴权失败（401/403）、额度不足（402、余额或配额类错误码） | 400 类参数或输入错误 |
| 429、5xx、连接错误，在 `_with_retries` 用完后仍失败 | 返回结果不符合 schema、拒答、搜索达到上限（`SearchLimitError`） |
| 单次调用超时，且任务剩余时间至少 120 秒（否则换了也来不及） | 整个任务到期（`JobTimeout`） |
| 订阅：未登录（`SubscriptionError("auth")`）、用量上限、CLI 进程超时 | 订阅模式的附件限制（大小、页数）：换另一家订阅限制相同，按原错误失败 |

- **只有一个方式时**：没有可换的，仍记下切换（后端据此暂停），但抛出原来的错误，保留原有的失败说明（如「AI 处理超过 N 秒未完成」）；有多个方式且都失败时，才报「AI 连接方式都不可用」并列出各方式的原因。
- **否决的方案**：整个任务换方式重跑。用户已选择只重做失败的那一次调用，避免重复计费。

### 6. 切换事件实时上报，结果回调再汇总

- 编排服务每发生一次切换，就向同一个回调地址发一条 `status = failover` 的事件（与进度报告一样只发一次、不重投），内容为原方式、原因分类、时间。后端收到后立刻写暂停键，这样长任务（最长 180 分钟）中途的失败，几秒内就能让新任务避开。
- 结果回调增加两个字段，后端写入 `ai_task`：
  - `connection`：完成最后一次成功调用的用法与服务商，写入 `ai_task.used_connection`；
  - `failovers`：本任务全部切换记录，写入 `ai_task.failovers`，并补写暂停（实时事件可能丢失）。
- 原因只用分类码：`auth`、`quota`、`rate_limit`、`provider_error`、`timeout`、`not_logged_in`、`usage_limit`。不转发服务商返回的原文，避免带出 Key 或账号信息。
- **为什么不只靠结果回调**：长任务结束前的这段时间，其他任务会继续撞同一个坏掉的方式。

### 7. 任务记录

- `ai_task` 新增两列：
  - `used_connection`：varchar，如 `api:openai`（不用 `connection` 作列名，避免撞 SQL 保留字）；
  - `failovers`：JSON，存切换记录数组。
- 原有的 `model` 列照旧记实际使用的模型。
- 任务详情接口返回这两项，前端在 AI 任务相关的展示处显示「已自动切换」提示。

### 8. 前端：两组卡片，组内拖拽

- **拖拽库**：新增 `@dnd-kit/core` 与 `@dnd-kit/sortable`，版本固定。两组各是一个独立的 SortableContext，跨组拖动天然不被接受。
- **为什么不用浏览器原生拖拽**：原生拖拽没有键盘操作和触屏支持，体验不及现有页面标准。
- **否决的方案**：只给上移、下移按钮。用户明确要求拖拽。可以额外给键盘方向键排序，保证可访问性。
- **右侧编辑区**：沿用现有的「模型与用量」面板，按选中的卡片切换内容。底部保存条保存全部修改，包括顺序、开关、Key、模型。

## Risks / Trade-offs

- **[风险] API 组内切到另一家付费 Key，产生用户没预期的费用** → 设置页 API 组标题下写明「排在前面的出问题时，会自动改用下一家」。不想被用到的 Key 关闭开关即可。任务记录里能看到每次切换。
- **[风险] 一次调用在 A 方式上已部分计费后才失败，换 B 重做，等于付了两份钱** → 只在连接方式本身的问题上切换，内容错误不切换。重试次数沿用 `_with_retries` 的上限，不增加。
- **[风险] 同一任务的不同批次来自不同模型，结果风格不一致** → 用户已接受「只重做失败的那一次」。任务记录里的 `failovers` 能看出发生过切换。
- **[风险] 错误分类误判（把内容错误当成方式故障），导致频繁切换和暂停** → 分类集中在一个函数，并按服务商异常类型与状态码逐一写单元测试。拿不准的错误一律归为「不换」，宁可失败也不乱切。
- **[风险] Redis 丢失暂停状态** → 最多是新任务多试一次已坏的方式，再由运行时切换兜住，不影响正确性。
- **[取舍] 暂停时长固定 10 分钟，不可配置** → 先满足需求。真有需要再加配置，属于额外功能，本次不做。

## Migration Plan

1. **迁移 `V1.5.43`**（V1.5.42 已被占用；实施时仍以最新号为准）：
   - `sys_ai_provider_config` 增加 `sort_order int NOT NULL DEFAULT 0`，`status` 列注释改为「是否参与使用（0-关闭、1-启用）」。
   - `ai_task` 增加 `used_connection varchar(32) NOT NULL DEFAULT ''`、`failovers json NULL`。
2. **数据转换**（同一个迁移脚本内）：
   - 组内顺序：`sys_ai_config` 当前选中的方式排在所在组第一位，组内其余按 Claude、OpenAI 排序。
   - 原来选中订阅的租户（含平台租户）：把该租户的 API 行设为 `status = 0`，行为保持不变。
   - 租户的订阅行：选中订阅的非平台租户插入订阅行，记录所选服务商排第一。
3. **发布顺序**：后端与编排服务随同一版本发布。编排服务兼容只有 `ai` 字段的旧请求，所以发布期间在途的任务不受影响。
4. **回退**：
   - 新增的列可以直接删除，迁移脚本里写好回退语句；被关闭的 API 行回退时恢复 `status = 1`（旧版本不读这一列做单选判断）。
   - `sys_ai_config.mode/provider` 一直保留，所以回退到旧版本后仍按原单选工作。
   - 回退前无需清理 Redis 的暂停键，它们会在 TTL 到期后自然消失。

# Design

## Context

- 销售出库单（`outbound_order`）一张对应一张销售订单（`so_id`），由发货通知生成。状态：1 待打包、2 已打包、3 已交货代、4 已撤回。
- 箱子 `outbound_box` 只有 `outbound_id`。箱内明细 `outbound_box_item` 按 `outbound_item_id` 指到具体出库单的型号行，所以箱内混装不同出库单的型号，在明细层面已经能表达。
- 按 `outbound_id` 取箱子的地方：
  - `OutboundService`：打包 `writeBoxes`、列表与详情 `toVos`；
  - `FreightService.boxes`：运费分摊；
  - `DocGroupService`：PL 按箱输出；
  - `LogisticsShipmentService`：出运单的箱数与计费重。
- 运费分摊 `FreightAllocator`：
  - 国内：`byOutbound` 先按出库单汇总计费重，再在出库单内按箱、按货值分；
  - 国际：`toLines` 先按箱，再按货值分。
- 交国内快递（`handOver`）已经支持多张同一货代的单合成一票。出运单按客户与货代组单。
- 原型须先经用户确认（OpenPencil），再开发页面。

## Goals / Non-Goals

**Goals:**
- 合并打包、整组处理与拆开的规则只在后端集中判断一次；前端只做提示和整组勾选。
- 不合并的出库单行为不变，历史数据不用迁移。

**Non-Goals:**
- 不做跨客户或跨货代的合并。
- 不改发货通知的生成方式：一张通知仍对应一张订单。
- 不新增菜单或按钮权限，沿用「打包出库」。
- 不给合并打包组单独编号或做独立的列表页。

## Decisions

1. **新表 `outbound_pack` 表示合并打包组，出库单和箱子都挂 `pack_id`**
   - `outbound_pack` 的列：`id`、`tenant_id`、`customer_id`、`forwarder_id`、`status`（1 有效、2 已拆开）、`packed_by`、`packed_at`、`split_reason`、`split_by`、`split_at`，以及标准审计列。
   - 业务表带 `tenant_id`，在 `TenantTables` 里归为私有（PRIVATE）。
   - `outbound_order.pack_id`、`outbound_box.pack_id`：可空，加索引。
   - 合并时，箱子的 `outbound_id` 记组内第一张单（id 最小），只为兼容旧查询；取箱一律按「单 → 组 → 组内全部箱子」。
   - **备选**：
     - 箱子去掉 `outbound_id`：改动面太大，历史数据也要迁移，不采用。
     - 不建新表、只在出库单上记同组单号：拆开、并发加锁和日志都不好做，不采用。

2. **取箱统一走一个支持类 `OutboundBoxes`**
   - 输入一组出库单 ID，返回这些单相关的全部箱子和箱内明细；合并的单会按 `pack_id` 带出整组的箱子，且每箱只返回一次。
   - 上述四处消费方都改用它。
   - 箱号在组内从 1 连续编号；单独打包时仍按单编号。
   - 每张单的「箱数 · 计费重」：单独打包时是自己的箱子；合并时显示整组的，并标「合并打包」，避免看起来箱子不够。

3. **运费分摊统一为「先按箱、再按货值」**
   - `FreightAllocator.byOutbound` 不再使用，国内运费也走 `toLines`。
   - 箱的货值按「出库单 + 订单型号行」分组，分摊结果每行带 `outbound_id`。
   - 出库单分到的运费 = 它的行之和，`byOutbound` 查询照旧按行汇总。
   - 不合箱时，每张单的运费仍等于它各箱之和，与原来先按单分的结果只差尾差位置。
   - 运费分摊表的 `outbound_id` 已有，不用新增列。
   - **备选**：合并的箱子按货值比例「拆」给各单后再走旧算法。逻辑重复，不采用。

4. **合并打包、重新打包、拆开都在一个事务里，按 ID 顺序加行锁**
   - 合并：锁定全部勾选的出库单（按 ID 升序），校验同客户、同货代、都是待打包。
   - 合并时调用改造后的 `writeBoxes`：先校验每张单每个型号的装箱数量，再作废这些单原有的箱子（包括它们原所属组的箱子），然后新建 `outbound_pack` 和箱子，各单写入 `pack_id`，状态改为已打包。
   - 重新打包：从组内任一张单进入时锁定组内全部单，替换整组箱子。
   - 拆开：组内全部单须为已打包。作废组的箱子，组状态改为已拆开，各单的 `pack_id` 置空、状态回到待打包。
   - 交快递：请求里的单展开到各自所在的组，展开后的集合必须等于请求集合，否则提示同组的单号。
   - 撤销交货代：撤销组内一张时，整组都撤销。
   - 出运单增减出库单：同样展开到组后校验。

5. **单证组「每张订单各一组」时用并查集合并**
   - 把出运单里的订单按合并打包组连起来，连在一起的订单合成一组，其余订单各一组。
   - PL 按组取箱，每箱只列一次；箱内的行带订单号。CI 照旧按订单行取数。

6. **前端**
   - 「待打包」页签加多选列和「合并打包」按钮：勾选不满足同客户、同货代时，按钮置灰并给出提示。
   - 合并打包抽屉复用现有打包抽屉的装箱编辑组件：型号池按出库单分组；新箱默认放入第一张单剩余的型号，箱内型号的下拉显示「OB 号 · 型号」。
   - 详情页显示「合并打包 · 同组 OB…」，提供「拆开」（填写原因）。
   - 「待交快递」、出运单的选择表格：勾选组内一张时，同组的单自动勾选。

## Risks / Trade-offs

- [旧代码仍按 `outbound_id` 直接查箱，合并时会漏掉组内其他单的箱子] → 开发前用 CodeGraph 列出 `OutboundBoxMapper` 的全部调用方，逐一改为 `OutboundBoxes`，并为每个消费方补合并场景的测试。
- [国内运费改为按箱分摊后，与历史单的尾差位置不同] → 只影响新分摊；已分摊的结果不重算。规范写明不合箱时结果相同、只是尾差位置可能不同。
- [合并后业务员不能直接撤回自己的发货通知] → 列表和详情显示同组单号，撤回时提示要先由仓库拆开。
- [并发：两个仓库人员同时合并有重叠的单] → 按 ID 顺序锁行，后到的请求重新校验状态（已不是待打包时拒绝）。

## Migration Plan

- 新迁移（版本号在合并前按 develop 的最新版本确定）：
  - 建表 `outbound_pack`；
  - `outbound_order`、`outbound_box` 加 `pack_id` 列与索引。
- 只新增，历史数据 `pack_id` 为空，行为不变。
- 回退：删除两列和新表。回退前确认没有有效的合并打包组（`outbound_pack.status = 1`），否则组内的单会各自显示同一批箱子，可能重复计数。
- 没有配置变化。

## Context

- **候选写入**：现在只有询盘一条路。`ProductArchiver.sync` 按询盘型号重算来源，它的流程是：
  1. 按 `brandKey + mpnNormalized` 加锁；
  2. 找到或新建候选；
  3. 写来源；
  4. `refresh` 重算来源数、可信度、出现时间，待审核且没有来源的候选会被软删除。
  
  删来源只删「这个询盘型号」的来源，不会动其他类型的来源。
- **来源表** `product_candidate_source`：`source_type`、`tenant_id`、询盘与订单 ID，没有文件名列。来源类型 5（手动）、6（导入）已经预留，但没有使用。
- **品类建议**：`CategoryMatcher.match(text, categories)` 返回唯一品类或「有歧义」。match-sub-category 之后优先细分品类。
- **品牌识别**：`BrandResolver.resolve(text)` 按名称和别名识别，识别不到时候选只存品牌原文和 `brandKey`。
- **可见范围**：租户只看到「至少有一条来源属于本公司」的候选。所以导入来源要记导入人的 `tenant_id`。
- **上传预览**：内容任务已有一套「前端读文件文本 → 预览接口重新解析 → 确认接口再解析一次写入」的做法，可以照搬。
- **wiki 文件**：frontmatter 有 `brand`、`category`、`model` 等；正文第一个一级标题形如 `# Siemens 6EP3437-8SB00-0AY0 — 中文说明`；「基本信息」表格两列，即「字段 | 内容」。目录里还有 `index.md`、索引追踪表等非商品文件。

## Goals / Non-Goals

**Goals**
- 上传 wiki 商品文件得到待审核候选，和询盘来源共用同一条候选、同一套审核。
- 预览和确认按同一份解析和查重逻辑，确认时重新解析，不信任前端结果。

**Non-Goals**
- 不做输入型号的 AI 解析（入口置灰）。
- 不导入规格、系列、HS 编码、物流、图片、发布状态。
- 不更新已在商品库的商品。

## Decisions

**1. 解析器是纯函数，放在 `product/candidate/support`**
- `WikiProductParser.parse(text)` 返回草稿：
  - 品牌、型号、品类文字、名称、中文描述、英文描述；
  - 错误列表，如缺 frontmatter、缺 `model`、缺 `brand`。
- 取值规则：
  - 「基本信息」表格按第一列字段名找行，「品类」「中文产品名」「英文产品名」都可缺；
  - 品类文字 = frontmatter `category` 加「品类」单元格，例如「PowerSupply（开关电源，新品类首次入库）」，拼成一段交给 `CategoryMatcher`；
  - 驼峰写法拆成单词，如 `ServoAmplifier` 变成 `Servo Amplifier`，便于和英文品类名匹配；
  - 中文描述取一级标题里「—」或「-」之后的文字；
  - 值为空、`—`、`[待确认]` 视为没有。
- 长度按候选字段截断：名称 128、描述 500。实现时以表结构为准。
- **备选方案：** 复用内容任务的 `ContentMarkdownParser`。它按章节解析内容包，wiki 文件的基本信息表格不在它的章节体系里，硬套反而复杂，不采用。

**2. 查重与处理结果**

对每个文件依次判断：
1. 解析错误 → 不能导入；
2. 同批里品牌加归一化型号已出现 → 重复；
3. 商品库已有（`tenant 0`、未删除、品牌 ID 与归一化型号相同；品牌未识别时不判断商品库）→ 已在商品库；
4. 候选池有同键候选：
   - 待审核 → 已在候选池；
   - 已驳回 → 曾被驳回；
   - 已建档或已并入 → 已在商品库；
5. 其余为新候选。

候选键与询盘一致，即 `brandKey`（品牌名小写去空格）加 `mpnNormalized`，所以同一型号无论从询盘还是导入进来都落在同一条候选上。

**3. 写入复用 `ProductArchiver` 的锁和重算**
- 新增 `ProductArchiver.importSource(draft, fileName)`：
  1. 按键加锁，和询盘同一把锁；
  2. 找到或新建候选。新建时状态待审核，建议品类用 `CategoryMatcher` 的结果，有歧义时为空；
  3. 已有候选只补空字段；
  4. 写一条来源：类型「导入」、`tenant_id` 取当前账号、文件名；
  5. 调 `refresh` 重算。
- 每个文件一个事务。确认接口逐个调用并汇总结果，与内容任务确认的做法一致。
- **可信度**：`levelOf` 对导入返回最低档。候选列表的可信度标签当前写作「询盘出现」，导入来的候选会显示这个标签，但来源列表里能看到类型是「导入」。这里不改可信度定义，以免影响热度统计。
- 询盘的 `sync` 只删询盘型号自己的来源，不会删导入来源；`refresh` 看所有来源，所以导入候选不会因为没有询盘来源而被软删除。

**4. 来源表加文件名**
- Flyway `V1.2.54`：`product_candidate_source` 加 `file_name varchar(255) NOT NULL DEFAULT ''`，注释写明「导入来源的文件名」。
- 候选详情的来源列表中，导入来源显示「导入 · 文件名 · 导入人 · 时间」，其他公司的来源仍只计次数。

**5. 接口**
- `POST /api/v1/product/candidates/import/preview`：输入 `{files: [{fileName, content}]}`，最多 200 个，每个不超过 1MB，返回逐个文件的预览。
- `POST /api/v1/product/candidates/import/confirm`：输入相同，服务端重新解析，返回成功、跳过、失败的汇总。
- 两个接口都只要商品候选菜单权限。

**6. 前端**
- 商品候选页标题区加「添加候选」按钮，打开抽屉。抽屉顶部用分段控件：「上传商品文件」可用；「输入型号（AI 解析）」不可用，提示「即将推出」。
- 上传区可多选或拖入文件夹里的文件，前端读成文本后调预览。预览是表格，列为：文件、品牌、型号、建议品类、名称、处理结果。处理结果用颜色标签，不能导入的显示原因。
- 底部显示「将新建 N 条、追加 M 条来源、跳过 K 个」，确认后显示结果并刷新列表。
- 先用 OpenPencil 出入口和预览两张原型。

## Risks / Trade-offs

- **[品类匹配率]** wiki 的品类是英文驼峰写法，如 DriveBoard、ASiModule，可能匹配不上细分品类。→ 留空，由审核人选择；预览里显示建议品类，可以先估计匹配情况。
- **[可信度标签]** 导入候选显示为最低档。→ 审核人从来源列表看类型；以后如有需要，再单独给导入定一档。
- **[品牌未识别]** wiki 里有少见品牌，如 QUEEN、JAKON、FANOX，会以原文进入候选。→ 和询盘一样，审核时新建品牌或选择已有品牌。

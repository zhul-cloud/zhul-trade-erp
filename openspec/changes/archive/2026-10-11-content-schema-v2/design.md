## Context

**现有上传流程**（`product/content`）：
- 一个文件解析成一个 `ContentDraft`，对应一个（包类型、平台、语言）；
- 预览一个文件一项，确认时一个文件一个事务；
- 写入后在 `product_content_import` 记一条记录（包类型、平台、原文）。

**现有存储**：
- **关键词**：按平台存在 `product_platform_keyword`。商品运营详情的关键词库是读取时合并出来的。
- **平台内容**：`product_platform_content` 按列存阿里国际站、中国制造网、社媒的内容。社媒每个渠道只有一列。
- **独立站**：`product_seo` 存标题、描述、长描述、首屏定义块，`product_seo_faq` 存问答。
- **规格**：`product_specification` 有名称、值、单位、来源（写死「内容包」）、是否已核实。

**AI 技能**：`fouwell-product-content` 维护在 zhul-skills 仓库，格式写在 `references/output-format.md`。它的实际输出见提案里的 VFD015M21A 样例，结构已经接近 v2，只是标题名、表格列、选用关键词的写法还不固定。

## Goals / Non-Goals

**Goals**
- 一份规范，ERP 和技能都照它来；技能输出的文件不用手改就能上传。
- 尽量复用现有的预览、确认、上传记录流程，不另起一套。
- 旧格式（v1 任务包、wiki 商品文件）继续可用。

**Non-Goals**
- 不导入价格与采购参考，留给业务回填。
- 不做关键词的在线编辑，也不做跨型号的关键词总览。
- 不做发布状态，不按平台官方规则校验字段长度（长度只作编辑提示）。

## Decisions

**1. 规范文档是唯一标准，技能引用它**
- 规范写在 `docs/02-产品PRD/02-商品域/商品内容规范-v2.md`，内容包括：
  - frontmatter；
  - 每个章节的标题名、表格列、取值规则、长度提示；
  - ERP 字段对照表；
  - 一份完整的资料包示例和一份营销包示例（以 VFD015M21A 为例）。
- 技能的 `references/output-format.md` 改写成同样的章节与列，并在文件开头写明「以 zhul-erp 仓库的《商品内容规范 v2》为准，两边不一致时以规范为准」。
- 技能仍可写自己的研究过程，但都放进「## 内部附录」。

**2. 合并营销文件在解析时拆成「虚拟文件」，复用现有流程**
- v2 营销文件解析后拆成多项：
  - 一项「关键词库」：平台为空，只写总库；
  - 每个平台章节一项：平台为该平台，包含该平台的块和选用关键词。
- 预览里每项显示为「文件名 · 关键词库」「文件名 · 阿里国际站」，可分别跳过块；块键为「部分:章节名」（如 `alibaba:FAQ`），预览修改、跳过都用它；每项带 `fileIndex` 对应上传的第几个文件。
- 确认时按「关键词库 → 各平台」的顺序，每项一个事务；上传记录每项一条，原文保存整份文件。
- 这样平台启用校验、走错入口校验、同批去重、按平台写入、按平台记写入时间、上传记录都不用改模型。
- **备选方案：** 让一个预览项包含多个平台的块，写入时在一个事务里写多个平台。这要改预览的数据结构、去重键、启用校验和上传记录，牵动面大，而且某个平台失败会拖累整份文件。不采用。

**3. v2 解析器独立，产出现有的 `ContentDraft`**
- 新增 `ContentV2Parser`：frontmatter 有 `schema: 2` 时走它，否则走现有的 `ContentMarkdownParser`（含 wiki 转换）。
- `ContentDraft` 增加以下字段：
  - `schema`；
  - 营销项的 `platform`；
  - 新块类型：识别信息、未知字段、冲突、来源、关键词总库、选用关键词、备选标题、产品属性、引导语、H1 与 URL 别名、图片说明、帖子、视频。
  
  新块都加进 `ContentSection`，并标明所属包类型和平台。
- 「## 内部附录」以及之后的同级章节一律跳过，不提示；其他不认识的章节跳过并提示。

**4. 存储**

| 内容 | 存储 |
|---|---|
| 规格的条件、证据状态、来源说明 | `product_specification` 加 `condition_text`（256）、`evidence`（64）、`source_note`（256）。来源说明把「S02、S03」换成「S02 台达 VFD-M 手册；S03 铭牌照片」，按来源索引查名称 |
| 资料待确认项 | 新表 `product_fact_note`：`tenant_id = 0`、商品、类型（1 关键未知字段、2 冲突与待确认）、项目、当前状态、影响、顺序、`import_id`。每次确认 v2 资料包时，先软删除旧的再插入 |
| 来源索引 | `http(s)` 链接按地址合并进技术资料，标题取「发布者及范围」；相对路径（照片等）不导入 |
| 应用需求 | 写入应用场景：标题为「场景」，描述为「产品作用；选型前提：…」 |
| 产品识别 | 商品只有一个名称字段：为空时补中文名称（没有中文用英文），英文名称不单独保存；系列复用 wiki 导入的系列匹配，只补空 |
| 关键词总库 | 新表 `product_keyword`：公司、商品、语言、关键词、小写键、档位、分类、意图、依据、顺序、`import_id`、软删除。替换时在商品锁内软删除旧词再插入，不靠唯一键 |
| 平台选用 | 新表 `product_keyword_use`：公司、商品、`keyword_id`、平台、顺序、软删除 |
| 平台新字段 | `product_platform_content` 加 `title_alternates`、`attributes`、`faqs`、`posts`、`videos`（都是 JSON 文本）和 `cta`。阿里国际站和中国制造网的详情都存在 `detail`；阿里、中制的 FAQ 存 `faqs`，独立站的营销问答仍存 `product_seo_faq` |
| 独立站新字段 | `product_seo` 加 `h1`、`url_slug`、`alt_texts`（JSON 文本） |

- JSON 文本由服务层用 Jackson 读写，前端拿到的是结构化字段。
- 社媒旧的三列保留用于显示旧数据：`posts` 为空时回退到旧列。
- **迁移**：`product_platform_keyword` 按公司、商品合并进总库（同词不分大小写合并，档位取最高，按原档位和顺序排序），平台关系写成选用。旧表保留，注释改为「已停用」，不再读写。
- **备选方案：** 平台新字段各建子表（属性表、FAQ 表、帖子表）。它们只是整块显示、整块替换，没有按条查询的需求，子表只会增加写入和读取的代码量。不采用。

**5. 关键词写入规则**
- **「关键词库」项**：
  1. 整份替换总库；
  2. 去掉不在新库里的词的选用；
  3. 关键词按 P1/P2/P3 分档，也认核心、主要、长尾；
  4. 同库内重复的词只留第一个，并提示。
- **平台项的选用关键词**：
  - 按小写键在总库里找；找不到的按主要档补进总库并提示；
  - 整份替换该平台的选用。
- **旧格式平台包的关键词库**：合并进总库（同词档位取最高，新词追加），并整份替换该平台的选用。
- 商品内容接口的 `keywordLibrary` 改为读总库加选用，返回结构不变，另加分类、意图、依据；平台内容里的 `keywords` 改为该平台选用的词。

**6. 下载模版**
- **资料包**：新模版 `facts-v2.md`。生成输入里加上已有规格的证据列和已有待确认项。
- **营销包**：
  - 由 `marketing-v2-head.md`（关键词库）、`marketing-v2-alibaba.md` 等平台片段和 `marketing-v2-appendix.md` 拼成；
  - 默认拼本公司启用的全部平台；
  - 指定平台时只拼该平台；
  - 独立站俄文只拼独立站，`lang: ru`。
  
  生成输入里加上已有关键词总库。
- **接口**：`GET /marketing/package` 的 `platform` 改为可选，不传表示全部启用平台；`site-ru` 表示独立站俄文。

**7. 前端**
- **上传预览**：
  - 文件列表显示拆出的项（文件名 · 平台）；
  - 新块的展示方式：表格类（属性、未知字段、来源、关键词、备选标题、图片说明）用列表，帖子和视频按 Markdown 排版显示。
- **商品运营详情**：
  - 关键词库页签加分类、意图列，标出未选用的词；
  - 阿里和中制页签加备选标题、属性表、FAQ、引导语；
  - 独立站加 H1、URL 别名、图片说明文字；
  - 社媒改为按篇显示帖子，视频方案折叠显示。
- **商品详情**：规格表加条件、证据、来源列；资料状态条加「待确认 N 项」，可展开。
- **营销包下载**：下拉第一项为「全部启用平台（推荐）」，其次是各平台和「独立站俄文」。

**8. 技能修改**
- 在 zhul-skills 仓库修改 `SKILL.md`（交付验收与新格式对齐）和 `references/output-format.md`，然后运行 `install.sh`。
- 用技能重新生成 VFD015M21A 的两份文件，作为验证样例。这一步是真实 AI 调用，执行前先告知用户。

## Risks / Trade-offs

- **[技能输出不严格]** AI 可能改动标题名或表格列。
  → 解析时标题按开头匹配，并兼容常见写法（Buyer benefits / 卖点、Product details / 产品详情）；对不上的章节在预览里提示，可以手改后再确认。
  → 规范附完整示例，降低偏差。
- **[虚拟文件让上传记录多条]** 一个合并文件确认后在上传记录里有多条（每平台一条），各自都存了整份原文。文件很小，可以接受；记录里显示同一个文件名，按平台区分。
- **[关键词迁移]** 合并会丢掉「同一个词在不同平台的不同档位」，只保留最高档。这正是总库的目的，可以接受。
- **[社媒旧列]** v1 和 v2 的社媒数据并存。显示时优先 v2，旧列只回退显示，不再写入。

## Migration Plan

- Flyway `V1.2.57__content_schema_v2.sql`：
  1. 规格加三列；
  2. 新建 `product_fact_note`、`product_keyword`、`product_keyword_use`；
  3. 平台内容表与独立站表加列；
  4. 迁移关键词；
  5. 修改旧关键词表的注释。
- 发布后通知运营：任务包按 v2 重新下载；技能更新后生成的文件可以直接上传。

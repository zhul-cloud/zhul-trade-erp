# Design

## Context

- 手动订单（`source` = 手动）和费用订单的收款记在 `sales_order` 上，收款状态、已到账、差额都在订单上。PI 转成的订单收款记在 PI 上，售后补发订单不收款（见 `SalesConstants.ORDER_RECEIPT_SOURCES`）。
- 销售日期的修改已有现成写法：`POST /sales/orders/{id}/sales-date`，菜单权限 + 数据范围，锁订单后改，写操作日志。约定付款日照这个写法做。
- 老板看板的资金卡（`BossWidgets.cashWidget`）：
  - 「应收未收」在 BUS-080 / BUS-081 后已计入手动订单和费用订单；
  - 「其中过期未收款」来自 `PiService.overdue()` 的各币种合计，只看 PI。

## Goals / Non-Goals

**Goals:**
- 约定付款日存在订单上，可空；逾期由查询时按「今天」算，不存逾期状态，避免再加定时任务。
- 看板的过期未收款金额与订单详情的逾期标记用同一个判断条件。

**Non-Goals:**
- 订单列表不加约定付款日列和逾期筛选，留到有需要时再做。列表页固定列规范不受影响。
- 不改 PI 过期规则、「过期未收款的 PI」卡片和风险提醒里的数量，它们链到 PI 列表，含义是「PI」。
- 不按付款条件推算付款日，也不支持分期约定。

## Decisions

1. **字段**：`sales_order.payment_due_date DATE NULL`，注释写明只用于收款记在订单上的订单。
   - 不另建表：一张订单只有一个约定日，不需要历史。修改历史记在操作日志里。
   - 已有订单取值为空，不回填。
2. **逾期判断（唯一口径）**：同时满足以下条件即为逾期。
   - 订单有效，来源属于收款记在订单上的订单；
   - `payment_due_date < 今天`，收款状态不是「已到账」；
   - 剩余未收 = 合计 − 已到账 − 差额，且大于 0。

   后端放一个小的判断方法供详情（逾期天数）复用；看板按同样的条件查询。前端只显示后端返回的 `overdueDays`，不自己算，避免时区和口径不一致。
3. **接口**：
   - 手动建单、新建费用订单的请求加可选的 `paymentDueDate`。
   - 新增 `POST /sales/orders/{id}/payment-due-date`，请求体 `{paymentDueDate: 日期或 null}`，权限同修改销售日期。
   - 校验：订单有效、来源收款记在订单上、日期不早于销售日期。
   - 改销售日期时，如果改后晚于已有的约定付款日，拒绝并提示「销售日期不能晚于约定付款日」，保持约束成立。
4. **看板金额**：
   - 过期 PI 仍取 `piService.overdue()` 的各币种合计；
   - 再按上面的条件查逾期订单，按订单币种累加剩余未收；
   - 两部分按币种合并后显示，任一币种有金额即标红。
   - 订单查询带数据范围，与应收未收一致。
5. **精度**：剩余未收是原币，`DECIMAL(18,2)` 相减，没有舍入。显示按 `money()` 两位小数 HALF_UP 加千分位，与现有副标题一致。看板不涉及折算。
6. **事务边界**：
   - 修改约定付款日是单表单行更新（锁订单行），和操作日志在同一个事务里。
   - 建单时随订单一起写入，事务与现有建单相同。
   - 看板只读。

## Risks / Trade-offs

- [约定付款日不填就不算逾期，可能漏] → 建单弹窗里字段放在销售日期旁边，详情可随时补填。是否改成必填由用户日后决定，不影响结构。
- [「今天」跨零点] → 统一用北京时间的 `LocalDate.now()`。数据库和容器的时区都是 Asia/Shanghai，与 PI 过期判断一致。
- [看板「其中过期未收款」与「过期未收款的 PI」卡片的数字不同] → 卡片标题明确是 PI，资金副标题是全部过期未收款。规范里已写明两者口径。

## Migration Plan

- 新迁移 `V1.5.38__sales_order_payment_due_date.sql`：只加一个可空列，不改数据。
- 回退：先回退应用，再执行 `ALTER TABLE sales_order DROP COLUMN payment_due_date`。这一列只有新功能写入，删掉后不影响其他功能。
- 前后端需要一起部署：前端新字段依赖后端返回值，后端单独部署时旧前端不受影响。

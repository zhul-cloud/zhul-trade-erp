## Context

询盘解析由 `scripts/ai-orchestrator` 调 Claude Code 执行（异步任务 + 回调），每个型号输出一个中文 `description`，写入 `inquiry_item.description`。报价行、PI 行、订单行都有一个 `description`，依次复制；报价单与 PI 的导出把它放进模版的描述列（福唯模版里叫「Inquiry Info」）。AI 任务框架按 `skill_id` 分发结果（`AiTaskResultHandler`）。

原则：系统内看到的都是中文，发给客户的都是英文。

## Goals / Non-Goals

**Goals:**
- 新解析的询盘直接有中英文两份描述，一路带到报价单、PI；页面显示中文，导出与文字报价用英文。
- 旧数据能在报价单、PI 上一键补英文，补过的询盘型号以后再报价也直接有英文。

**Non-Goals:**
- 不批量翻译存量数据。
- 订单的页面显示与内部单据不变（订单行只留存英文描述）。
- 询价任务、询价包继续使用中文描述。

## Decisions

1. **各层都存两份**：`description`（中文，系统内显示）与 `description_en`（英文，给客户）。
   - 字段加在询盘型号、报价行、PI 行、订单行。
   - 复制链路：询盘型号 → 报价行 → PI 行 → 订单行，两份一起带。
   - 报价单出新版本、复制为新报价单，PI 出新版本，也一起复制。
   - 存量的报价行、PI 行描述多半是中文，迁移时不改。存量里业务员手改成英文的描述也留在 `description`；英文描述为空的行在编辑页提示，可一键生成。
   - 备选：报价行只存一份英文描述。放弃原因：违背「系统内看中文」的原则，业务员在报价单上看不懂型号是什么。

2. **渲染时取英文**：报价单与 PI 的渲染模型里，`item.description` 取英文描述，为空时退回中文。模版不用改，旧模版直接生效。

3. **解析输出 `descriptionEn`**：提示词里给出写法：英文品名与关键规格，品牌用英文名，保留型号与参数，不超过 300 字。草稿行、确认请求、型号明细 VO 都带上它。

4. **通用的「生成英文描述」**：
   - 新 skill `translate-item-descriptions`，输入 `[{key, text}]`，输出 `[{key, text}]`。编排服务用 `claude -p` + `--json-schema`，不放行任何工具（不联网）。
   - 后端接口与具体单据无关：
     - `POST /api/v1/translations/item-descriptions`，请求带 `[{key, text, inquiryItemId?}]`（最多 300 条，每条不超过 300 字），返回任务 ID；
     - `GET /api/v1/translations/item-descriptions/{taskId}`，返回状态与结果（只能查自己提交的任务）。
   - 结果处理器在成功回调时，把译文补到带了 `inquiryItemId` 的询盘型号上（只补英文描述为空的，不覆盖人工填写的）。
   - 报价行、PI 行不在后端直接改：前端轮询拿到结果后，只填英文描述仍为空、或仍是生成前内容的行，再由业务员保存。这样不会覆盖生成期间的修改，也不绕过草稿与编辑中版本的保存流程。
   - 报价单与 PI 共用一个前端 Hook（提交、轮询、合并结果）。

5. **缺英文描述的判断**：英文描述为空，或含中日韩文字（与品牌提示同一个正则）。

## Risks / Trade-offs

- [AI 翻译不准，如型号被改写] → 提示词要求原样保留型号、参数和单位；结果写回后标「请检查后保存」，业务员可改。
- [任务长时间不回调] → 沿用 AI 任务的超时看门狗，超时后状态为失败，按钮恢复可重试。
- [占位脚本（stub）不会真翻译] → stub 对新 skill 返回「EN: + 原文」，只用于联调；对解析返回固定的英文描述。
- [编辑页多一个输入框，表格更高] → 英文输入框默认一行、随内容增高；紧凑模式（预览展开）下英文放在展开行里。

## Migration Plan

- 新迁移脚本：四张表各加 `description_en varchar(300) NOT NULL DEFAULT ''`。
- 编排服务需要重启以加载新提示词与新 skill。没有重启时，解析结果没有英文描述，导出退回中文并在编辑页提示，可用「生成英文描述」补；但「生成英文描述」要求编排服务已更新，否则任务失败并提示。

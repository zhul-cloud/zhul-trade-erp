## Context

- 业务规则来源：本地知识库 `/Users/mac/Documents/inquiry-wiki`（`BUSINESS.md` 定义询盘生命周期与 Excel 询盘文件结构，`schema/` 下是解析与报价脚本），询价包模板以 `raw/日期/采购员/已询价/*.xlsx` 为准（①询盘单单列结构 + ②询价单按淘宝、1688、闲鱼分区，右侧附填写规范）
- 现有实现（`add-inquiry-management`）：`customer_inquiry`、`inquiry_order`、`inquiry_order_item`、`inquiry_order_supplier`、`inquiry_order_item_quote`、`ai_task`；AI 编排服务在 `scripts/ai-orchestrator/`，以 `claude -p --json-schema` 产出结构化结果，经 webhook 回调；附件经 `AttachmentStorageService` 存公开目录。开发库只有几条测试询盘
- 可复用的基础：`PrivateFileStorage`（非公开存储 + 文件头校验）、`DataScopeResolver`、菜单与按钮权限（`@perm.has` / `@perm.canAccessMenu`）、平台级内置角色（`role.tenant_id=0`、`is_built_in=1`）、POI（`poi-ooxml`）
- 商机已能「创建客户询盘」（`customer_inquiry.opportunity_id`、S1/S2 自动推进到 S3），本变更必须保持这个入口可用

## Goals / Non-Goals

**Goals:**
- 一个客户询盘的型号明细只存一份，询价任务、询价记录、选定价格都挂在明细上，报价变更（`add-quotation-pricing`）只读明细即可出单
- 分配、回价进度、超时都能在系统内看到，不再依赖文件目录
- 兼职采购用 Excel 也能闭环，且看不到客户名称与联系方式

**Non-Goals:**
- 定价、报价单、正式报价单导出（下一个变更）
- 消息推送（站内信、企业微信等）：本次的「提醒」只体现为列表标记与工作台计数
- 自动分配的复杂策略（技能矩阵、轮询、按时段排班）：只做品牌、品类两类规则加推荐兜底
- 把 `inquiry-wiki` 的历史 Excel 批量导入历史询价（可以作为后续一次性脚本）

## Decisions

### 1. 数据模型：明细为中心，任务只是引用

```
customer_inquiry 1 ── n inquiry_item ── n sourcing_quote（历史询价记录）
       │                     │  selected_quote_id ─┘
       │                     │  sourcing_task_id（待询价时）
       └── 1 ── n sourcing_task 1 ── n sourcing_task_assignee（多人比价）
                                     sourcing_import（导入的 Excel 文件记录）
sourcing_assign_rule（预留自动分配）
```

- `inquiry_item`：确认后的型号明细（品牌、`brand_id` / `brand_key`、品类、原始型号、确认型号、`model_key`、`product_id`（命中商品主数据时）、置信度、纠正说明、数量、单位、描述、生命周期、替代型号、难度、询价话术、搜索关键词、价格来源〔复用历史价 / 询价〕、`selected_quote_id`、`sourcing_task_id`、回价状态〔待询价 / 已回价 / 无货〕）
- `sourcing_task`：编号、客户询盘、品牌、品类、紧急、状态（待分配、询价中、已回价、已取消）、退回原因、首次分配时间
- `sourcing_task_assignee`：任务 × 采购人员，含分配时间、是否当前有效（改派时旧记录置为无效，不删除）、提交时间
- `sourcing_quote`：一条询价结果，即历史询价的一行（品牌键、`model_key`、渠道、店铺 / 供应商、单价、币种、汇率、本位币单价、是否含税、货况、货期、备注、是否无货、询价人、询价日期、草稿 / 已提交、来源明细与任务）

**为什么不沿用「询盘单带明细」**：现有模型里明细属于询盘单，报价时要从多张询盘单反向合并；多人比价、复用历史价（明细不进任何询盘单）也都塞不进去。以明细为中心后，「拆」只是给明细打上任务号，「合」天然成立。

**替代方案**：保留 `inquiry_order` 名称只改结构——否决，名称和语义都变了（它不再拥有明细），继续叫「询盘单」会让代码和页面里的两套概念混在一起。页面上对采购的称呼统一为「询价任务」，询价包 Excel 文件名沿用「询盘单A · 品牌 · 品类」以照顾现有习惯。

### 2. 旧表处理

`customer_inquiry` 保留并改造（商机、AI 任务都在引用它）：加 `urgent`、`quote_deadline`（报价截止日期）、`customer_type`（新客户 / 老客户，创建时按该客户此前是否有「已成交」询盘计算的快照，不随后续变化重算）、`progress_*` 计数，状态码重排，来源枚举改为渠道（WhatsApp、邮件、阿里国际站…）而非「文本 / Excel / 图片」——输入形式由附件本身体现。`inquiry_order*` 四张表停止使用，代码删除，表保留到下一个版本再由清理迁移删除（遵守「不物理删除业务数据」，期间可回查）。开发库的旧测试询盘在迁移中标记为「已取消」。

### 3. 历史询价匹配键：品牌 + 归一化型号，与商品主数据同一套规则

型号归一化直接复用商品模块的 `MpnNormalizer`（全角转半角、转小写、去掉所有非字母数字字符），存为 `model_key`；品牌用商品模块的 `BrandResolver` 按品牌及别名解析出 `brand_id`，解析不到时存规整后的品牌名 `brand_key` 兜底。历史价复用以 `(brand_id 或 brand_key, model_key)` 精确匹配；只有归一化型号相同、品牌不同的记录作为参考，不默认复用——与商品主数据「同品牌下归一化型号唯一、不同品牌允许相同」保持一致。`model_key` 与品牌键建联合索引。

确认解析时顺带按同一规则查商品主数据，命中则在 `inquiry_item.product_id` 记下商品，报价变更可以从商品带出重量、尺寸、HS 编码、原产地；未命中不影响询价。

**替代方案**：只忽略大小写和空白、保留连字符——否决，与商品主数据规则不一致会导致同一型号在两处判断结果不同，且询盘原文的空格、连字符写法差异很大。

### 4. 金额

询价单价按人民币录入，仍按项目规范存三元组：原币单价、汇率、本位币单价（人民币时汇率为 1）。`DECIMAL(18,2)`，汇率 `DECIMAL(18,6)`，HALF_UP。含税标记单独存，选价与比价时不做含税换算（换算口径留给报价变更中的定价策略）。

### 5. 推荐与超时都在查询时计算

- 推荐：`近 180 天该品牌 已回价 任务数`（按 `sourcing_task_assignee` 统计）降序，再按进行中任务数升序。一次查询算出工作台所有待分配任务的推荐，不建统计表。
- 超时：`首次分配时间 + 时限 < now` 且状态不是已回价 / 已取消。时限（普通 24 小时、紧急 4 小时）放系统设置。不做定时任务，避免为提醒引入调度。

### 6. 询价包 Excel：模板 + 隐藏标识

- 生成：POI 按现有模板生成 ①询盘单 与 ②询价单；另加一个隐藏且保护的工作表 `_meta`，写入租户、任务编号、每个明细的 ID 与型号、模板版本。②询价单每个型号行的隐藏列也写明细 ID。
- 导入：先读 `_meta` 定位任务并校验归属，再逐分区读取行，优先按隐藏明细 ID 匹配，ID 被删时按型号文本匹配；分区标题（【淘宝】【1688】【闲鱼】）决定渠道；分区「备注：」行写入该分区本次记录的备注。
- 预览不落库：上传后文件存入 `PrivateFileStorage`（模块 `sourcing-import`），返回解析结果与问题行；确认时提交修正后的行，同时写一条 `sourcing_import` 记录（文件、任务、上传人、入库行数）用于追溯。

**替代方案**：按文件名或单元格位置识别——否决，兼职采购会改文件名、插行删行。

### 7. 兼职采购：平台级内置角色 + 统一隐藏客户信息

新增内置角色 `ROLE_PART_TIME_PURCHASER`（`tenant_id=0`、`is_built_in=1`），只授权「我的询价任务」菜单和下载 / 上传按钮，数据范围固定为仅本人。询价任务相关接口只返回采购判断优先级需要的客户摘要：询盘等级、新老客户、所属业务员、报价截止；客户名称只对正式采购返回，兼职采购（内置角色 `ROLE_PTBUYER`）不返回——这是业务上的取舍：长期合作的老客户询盘要优先找货，正式采购需要知道是哪个客户。客户联系方式、原始询盘内容与附件对所有采购都不返回。摘要统一由 `InquiryLookups.briefs` 组装，是否隐藏名称只在这一处判断。

### 8. 菜单与权限

「询盘管理」下的菜单改为：客户询盘（`/inquiry/customer-inquiries`）、分配工作台（`/inquiry/sourcing-board`）、我的询价任务（`/inquiry/my-tasks`）、历史询价（`/inquiry/price-history`），旧「询盘单列表」菜单下线。按钮：`inquiry:task:assign`（分配、改派、追加、按规则分配）、`inquiry:rule:edit`（分配规则）、`inquiry:import:proxy`（代他人导入）。

### 9. AI 解析输出扩充

`scripts/ai-orchestrator` 的 JSON Schema 增加 `lifecycle`、`replacementModel`、`difficulty`、`inquiryScript`、`searchKeywords`（按「精确型号 → 品牌+型号 → 品牌中文+品名 → 纯规格」顺序），话术生成规则沿用知识库现有询价模版。回调契约字段只增不改，后端对缺失字段容错（旧格式回调仍能确认）。货源直达链接不由 AI 生成 URL，而是前端按关键词拼接淘宝、1688、闲鱼的搜索地址，避免模型产出错误链接。

### 10. 手动录入复用确认页

手动录入不是另一套流程：「待解析 / 解析失败」直接打开同一个确认页，只是没有 AI 预填；打开时不改状态，确认接口接受这两个状态并直接把询盘推进到「询价中 / 可报价」，避免业务员只是点开看看、什么都没填，询盘就卡在「待确认」。确认页的每一行在型号输入完成（失焦）时调用同一个历史询价查询接口；确认接口不区分来源，只多记一个 `parse_mode`（AI / 手动）便于统计 AI 使用率。

### 11. 新老客户在下一个变更才真正生效

「已成交」由报价变更（`add-quotation-pricing`）推进，本变更上线后到报价变更上线前，所有询盘都会被标为新客户。这是预期行为；报价变更上线时不回补历史询盘的标记（快照语义）。

### 12. 状态联动的事务边界

- 确认解析：写明细、生成任务、更新客户询盘状态与计数，一个事务。
- 提交回价 / 导入确认：写询价记录、更新明细回价状态与选定价格、更新任务状态、重算客户询盘进度并可能进入「可报价」，一个事务；客户询盘行加行锁（`SELECT ... FOR UPDATE`），避免多人比价同时提交时进度计数错乱。两条实现约束（并发测试中发现）：锁必须在该事务写任何数据之前拿到，否则两人各自先写询价记录再争锁会死锁；这些事务用「读已提交」隔离级别，否则后拿到锁的一方沿用拿锁前建立的快照，统计不到前一方刚提交的回价。
- 取消客户询盘：任务置为已取消，已提交的询价记录不动（历史询价保留）。

### 原型反馈第二轮的取舍

- **字典承载可配置的选项**：来源渠道、货况、货期都放进系统字典（平台内置、各租户共享），字典值是整数码值；业务表只存码值，名称展示时取字典（含停用项，历史数据仍能显示）。货况码值 1（全新原装）仍是默认选价的依据，写在常量里。货期原来是文本，改为码值后可以统计和在报价单里统一翻译，代价是采购不能写「45 天」这类特殊货期——这是用户明确选择的「只能从字典里选」。
- **货源信息在接口层控制**：渠道、店铺在 `PriceHistoryServiceImpl.toVoMap` 这一处按权限置空，所有输出价格记录的接口（确认页历史价、详情选定价、改选列表、历史询价）都经过它，避免遗漏；采购自己的任务页（MyQuoteVO）不受影响。
- **权限只按按钮授权判断，不认角色**：运行时只看当前账号的角色是否勾选了「查看货源信息」（`inquiry:supplier:view`），不判断角色编码或名称。迁移只给内置角色（租户管理员、兼职采购）预置这个按钮；租户自建的采购、业务员等角色是各租户自己建的，迁移不碰，由管理员自行勾选。代码里唯一按角色编码判断的是内置角色 `ROLE_PTBUYER`（分配工作台标「兼职」）。
- **兼职工作台单独成页**：菜单挂在询盘管理下，只授予兼职采购；首页跳转规则是通用的（没有工作台权限就去菜单里第一个有权限的页面），不为兼职采购写特殊分支。

## Risks / Trade-offs

- [历史价复用的价格过旧] → 确认页和选价处都显示距今天数，业务员可改为重新询价；后续可在系统设置加「超过 N 天提示」
- [导入解析误判] → 预览必须人工确认才入库；问题行不会被静默丢弃；保留原文件可回查
- [多人比价的重复劳动] → 追加分配是采购负责人的显式操作，默认一个任务一个人
- [移除旧询盘单页面影响正在用的人] → 现阶段只有测试数据；上线前在本变更中把商机入口、工作台引用全部改接新模型
- [兼职采购账号外泄风险] → 接口层统一不返回客户信息；兼职采购菜单与接口权限都只限询价任务

2. 后端与 AI 编排服务同时发布（回调字段只增不减，先发后端也兼容）
3. 前端替换询盘管理页面
4. 回滚：前后端回退到上一版本即可，新表无数据依赖；`inquiry_order*` 表本次未删除

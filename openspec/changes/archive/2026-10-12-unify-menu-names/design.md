## Context

菜单名称存在两处：
- 菜单资源表（`resource.name`），侧边栏、角色授权页、菜单管理页都从这里读；
- 前端的路由文案（`locales/zh-CN/menu.ts`）。

单据名称则分散在前端页面文字、后端返回的提示与报错、导出文件、单据类型枚举的显示名称和操作日志里。

粗略统计，旧名称在前端约 120 个文件、后端约 300 个文件、主规格约 100 处出现。其中不少是代码注释，或同一个词的其他含义，例如：
- 「商品资料」：商品详情里那一类资料的名字；
- 「单据编号」：指编号本身；
- 「采购单号」：字段名。

## Goals / Non-Goals

**Goals：**
- 用户能看到的所有地方，统一使用新名称：侧边栏、页面、提示、导出、新的操作日志。
- 命名规则写进导航规格，以后新增菜单时有据可查。

**Non-Goals：**
- 不改访问地址、权限码、单据编号前缀与类型代码、数据库表名、Java 与 TypeScript 的标识符。
- 不重写已有的操作日志文字。
- 不重画已有原型。

## Decisions

1. **只改显示文字，不改标识。** 地址和权限码不变，书签、角色授权、租户套餐都不受影响，迁移只需要 `UPDATE resource SET name = ...`，不用重新授权。代码里的 `PurchaseOrder`、`receipts` 等标识保持原样。

2. **逐词人工替换，不做全局批量替换。** 下面几个词替换时要注意：
   - 「入库单」「出库单」：已有「采购入库单」「销售出库单」的写法，盲目替换会变成「采购采购入库单」。先排除已带前缀的写法，再替换。
   - 「商品资料」：只有作为分组名时改为「商品管理」；作为资料类别（商品详情的「商品资料」页签、资料包）的地方不改。
   - 「单据编号」：只有指设置页、权限按钮名称时改为「编号规则」；指编号本身的地方不改。
   - 「采购单」：改为「采购订单」，字段名同步改（如「采购单号」改为「采购订单号」）。
   - 「对账单」：只替换货代运费对账的含义；其他对账含义（如果有）不改。
   - 「付款记录」：单据叫「付款单」；PY 编号与列表不变。

   每个词替换后，用 `grep` 复核剩下的旧词都属于「不改」的含义。

3. **代码注释顺带改，不单独列任务。** 文件里本来就要改用户文字的，注释也一起改，避免新旧名称混在一起；只有注释用到旧名称的文件不专门去改。

4. **后端报错文字一并改，契约测试跟着改。** 报错文字是用户能看到的，按规则要和单据名一致。断言了报错文字的契约测试，在同一次提交里更新。

5. **其他主规格直接替换叫法。** 导航和单据编号两份规格的改动走变更规格。其余主规格里的旧名称只是叫法，行为不变，在实现时直接替换主规格文字，和代码同一次提交，不另写变更规格。

6. **迁移按资源 ID 更新名称。** 用 `WHERE id = ...` 精确更新菜单与按钮名称。按钮名里含旧名称的（如「单据编号编辑」）一并改；字典里单据类型、操作日志模块的显示名称同理。

## Risks / Trade-offs

- **漏改**：旧名称出现的地方很多，可能有个别提示漏掉。上线后通过 `grep` 清单复核，发现漏改的按同一规则补上。
- **历史操作日志仍是旧名称**：用户查日志时会同时看到新旧两种名称。这是有意保留的，历史记录不改写。
- **已有原型与新名称不一致**：原型是设计记录，不影响使用；以后改到某个页面的原型时再顺带更新。
- **使用习惯**：已经在用的同事要重新适应。侧边栏的位置不变，只是名称变了，影响不大。

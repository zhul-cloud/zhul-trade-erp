## Context

动机见 proposal.md。现状：

- 售后退款单（TK）由财务在退款管理直接登记，冲减订单收入，可以转客户余额（`finance/customer-refund`、`finance/customer-credit`）。
- 费用单（FE）按订单分摊计入订单成本（`finance/expense`、`finance/order-cost`）。
- 闲置库存有两个来源：到货差异、订单部分取消（`stock_hold.source_type` 1、2）。
- 订单出运数量由销售出库与出运单驱动（`LogisticsQty.shipped`）。
- 单据编号类型在 `DocumentType` 枚举里登记；系统设置是 `sys_config` 的键值。

## Goals / Non-Goals

**Goals:**
- 一张售后单串起跟进、退货、退款、费用，结案时能看到这次售后花了多少。
- 退货的货有入库记录和去向，去向决定原订单成本，口径可追溯。
- 退款由业务员提出、财务执行，预留审批。

**Non-Goals:**
- S1–S5 响应时限与逾期提醒、售后补发订单、客户等级权益、复盘统计（第二期）。
- 退回供应商与应付 / 付款打通（第二期），本期只登记金额冲成本。
- 去向处理后的撤回（处理错由后续版本支持作废）。

## Decisions

### 1. 新模块 `aftersales`

包 `com.zhul.erp.modules.aftersales`，放售后单、退货单、退款申请三组实体与服务；退款执行仍调用 `finance` 的退款单服务，闲置库存仍由 `warehouse` 生成（新增 `AfterSalesHolds` 或扩展 `PartialCancelHolds` 的通用方法）。

- 备选：退货放 warehouse、申请放 finance。三者都挂在售后单上、状态互相约束（结案校验），放一起更好维护；页面仍按菜单分在各自分组。

### 2. 数据模型

| 表 | 说明 |
|----|------|
| `after_sales` | 售后单：编号 AS、客户、订单（可空）、等级、现象、诉求、原始描述与收到时间、原因、方案（逗号分隔的字典编码）、负责人、下一步、下次更新时间、状态、结案原因与结果、结案时间、撤销原因 |
| `after_sales_item` | 售后型号行：订单型号行（可空）、型号、品牌、数量 |
| `after_sales_log` | 跟进时间线：类型（跟进、等级变更、状态变更、退货、退款、费用）、内容、附件、操作人 |
| `sales_return` | 退货单：编号 TH、售后单、订单、快递、状态（1-待入库、2-待处理、3-已处理、4-已作废）、收货日期、验收人 |
| `sales_return_item` | 退货行：订单型号行、型号、退货数量、实收、合格 |
| `sales_return_disposition` | 去向：退货行、去向（1-退回供应商、2-转闲置、3-报废）、数量、供应商、快递、运费（CNY）、供应商退款（CNY）、冲减成本（CNY）、闲置库存 ID、说明 |
| `fin_refund_request` | 退款申请：编号 RA、售后单、订单、币种、金额、原因、建议去向、收款信息、说明、状态（1-待审批、2-待财务处理、3-已执行、4-已驳回、5-已撤回）、审批人与时间、处理人与时间、驳回原因、退款单 ID |

改动：`fin_customer_refund` 加 `after_sales_id`、`refund_request_id`；`fin_expense` 加 `after_sales_id`；`stock_hold` 加 `return_id`，`source_type` 增加 3-售后退货。所有金额 DECIMAL(18,2)，原币与人民币分列。

### 3. 退货数量上限与并发

可退数量 = 订单型号已出运数量 − 其他有效退货单（非作废）的退货数量。发起与修改退货单时锁订单行（`FOR UPDATE`），防止并发超退。

### 4. 去向冲减订单成本

`OrderCostCalc.Item` 增加两个按型号行汇总的金额：`returnCredit`（退回供应商的退款 + 转闲置的冲减成本，正数表示冲减）与 `returnFreight`（退回运费）。型号行实际成本 = 原各项 + 退回运费 − 售后退货冲减。转闲置的冲减成本在处理时按当时的原采购成本计算并落库（`sales_return_disposition.cost_cny`），之后不随采购订单变化重算，保证可追溯。

原采购成本 = 该型号行的有效采购订单行按合格入库数量加权的 `net_price_cny`；没有合格入库时按采购订单行数量加权；没有采购订单时取订单型号行的 `cost_price`；HALF_UP 两位。

### 5. 退款申请与退款单

申请金额上限 = 订单已到账（PI 转成的取 PI，含手续费差额不含待处理多收，口径同退款单）− 有效售后退款 − 其他待审批 / 待财务处理的申请。执行时调用现有登记退款的服务（新增参数 `afterSalesId`、`refundRequestId`），同一事务内把申请置为已执行；退款单作废时（`CustomerRefundService.voidRefund`）把关联申请改回待财务处理。

审批开关：`sys_config` 新增 `finance.refund-request.approval`（布尔，默认 false，分组「业务」），提交时读取。

### 6. 权限

- 菜单「售后管理」`/sales/after-sales`：授予有「销售订单」菜单的角色；
- 菜单「退货入库」`/warehouse/returns`：授予有「采购入库」或「采购订单」菜单的角色（仓库验收、采购员处理去向）；
- 按钮「退货验收」`warehouse:return:receive`（授予有采购入库菜单的角色）、「退货去向处理」`purchase:return:dispose`（授予有采购订单菜单的角色）、「审批退款申请」`finance:refund-request:approve`（只授予租户管理员，其他由管理员分配）。
- 数据范围：售后单按负责人或订单业务员落在当前用户可见范围内；退货与申请随售后单。

### 7. 事务边界

每个操作一个本地事务，由对应 Service 声明：
- 发起 / 修改退货：锁订单 → 校验上限 → 写退货单与跟进记录；
- 验收：锁退货单 → 写实收合格 → 状态；
- 去向：锁退货单 → 写去向（转闲置时同一事务生成闲置库存）→ 状态 → 跟进记录；
- 执行退款申请：锁申请 → 生成退款单（含余额流水）→ 申请状态 → 跟进记录；
- 结案：锁售后单 → 校验退货与申请都已处理完 → 状态。

### 8. 编号

`DocumentType` 增加 AS、TH、RA（内部单据，不带租户前缀）。编号规则页按现有方式列出。

## Risks / Trade-offs

- [退回供应商的钱实际没收到，成本已冲减] → 本期明确「登记金额 = 供应商已同意的退款或抵扣」，第二期与应付打通后用实际到账核对。
- [退货去向处理后不能撤回] → 处理前确认框写明对订单成本的影响；后续版本加作废。
- [售后单负责人可以是任意用户，数据范围外的人也能被指派] → 被指派人能看到自己负责的售后单（数据范围按负责人或订单业务员任一满足）。

## Migration Plan

1. 迁移（版本取最新序号）：新建 7 张表；`fin_customer_refund`、`fin_expense`、`stock_hold` 加字段；字典「售后问题等级」「售后原因」「售后方案」；菜单 2 个、按钮 3 个与角色、套餐授权；`sys_config` 新增审批开关。
2. 回退：新表与新字段不影响旧版本；回退 SQL 写在迁移文件末尾（删菜单、按钮、字典、配置、新表与新字段）。回退前确认没有售后单、退货单与退款申请，或已导出留档。

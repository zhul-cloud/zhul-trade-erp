## Context

动机见 proposal.md。现状中影响方案的事实：

- 任务生成后直接是「待分配」，开启自动分配时马上按规则分配（`SourcingTaskServiceImpl.createTasks`）。
- 采购人员等于「角色带我的询价菜单的账号」（`SourcingTaskServiceImpl.purchasers`），而业务员要用这个菜单才能询价。
- 型号只要有一条已提交的无货记录就算无货（`SourcingProgress.refreshItems`），只有询价中的任务能退回（`MyTaskServiceImpl.returnTask`）。
- 超时从 `first_assigned_at` 算，退回后不清空；等待时长从退回时间或创建时间算。
- 回价联动已有约定：读已提交事务内先锁询盘单（`SourcingProgress.lock`）。
- 角色由租户自建，业务员、采购没有固定编码，只有兼职采购是内置角色；兼职不能看公司历史价（`V1.2.18`）。
- 项目已启用 `@Scheduled`，已有按固定间隔扫描的先例（`AiTaskTimeoutWatchdog`）。

## Goals / Non-Goals

**Goals:**

- 采购负责人的待分配池里只有确实要分配的任务。
- 按型号转交时，无货和已查记录不丢失，也不会被下一次进度重算覆盖。

**Non-Goals:**

- 不做通用的多层流转引擎。兼职和 AI 仍在待分配之后处理，AI 询价不在这次范围内。
- 不做业务员之间互相接单，也不做站内消息推送。
- 不修改已有任务（上线时已在待分配或询价中的任务保持原状）。

## Decisions

### 1. 用新任务状态表示业务阶段，而不是单独建池子

新增状态 `6-待业务处理`（5 已被工作台「待审核」页签占用），字段 `sales_deadline` 记录流转时间。任务归属、编号、型号关联都不变。

没有采用「只靠时间过滤、不改状态」：规则自动分配需要明确的进入时点，查询条件也会散落到各处。

### 2. 用标记而不是状态表示业务员自询

认领后状态就是现有的 `2-询价中`，这样「我的询价」、回价、撤回逻辑都能复用。任务增加 `sales_handling`（1-业务员自询中），退回时清零；分配记录增加方式 `6-业务员自询`，用于统计和熟悉度排除。

「已回价」页签的「业务员自询」标记从分配方式取，而不是 `sales_handling`，这样任务退回后由采购完成时不会被误标。

### 3. 用询价轮次解决「无货被重算覆盖」

`inquiry_item.quote_round` 和 `sourcing_quote.quote_round` 都默认 0。提交或审核通过时，回价记下当时型号的轮次；转交时型号轮次加一。

进度重算规则变为：**本轮没有已提交的记录就是待询价**；本轮有结果后，再按现有规则在全部已提交记录里选成本价。这样可以同时满足规格里的三种结果：找到新价、再次无货、新一轮无货但保留旧价。

没有采用的方案：

- 把旧记录标记为已转交并排除：选成本价时会丢掉旧价，「比价后没有更好的结果」就无法实现。
- 用转交时间比较提交时间：同一秒发生时会出错，草稿后提交也难判断。

询价记录不受影响，仍包含所有已提交记录。

### 3a. 用转出记录表统计工作量

新增表 `sourcing_item_handoff`（型号、任务、转出人、转出时轮次、原因、时间）。按型号退回时，每个交出的型号写一条。「按人员」统计用它算转出，并把这些型号从转出人的有价、无货、待回价里排除。

没有从回价记录反推：还没录过价就交出的型号没有回价记录，推不出来。也没有用分配记录的有效标记：多人比价和改派也会让记录失效，无法区分。旧数据没有转出记录，所以转出为 0，数字和原来一致。

### 4. 扩展现有退回，而不是新增流程

`POST /my-tasks/{id}/return` 增加 `itemIds`（要额外交出的无货或有价型号）。待询价的型号总是交出，已报给客户的型号用现有 `quotationLocks` 拒绝。业务员界面的文案是「转采购继续找」，采购和兼职是「退回」，接口相同。

退回后的询盘回退逻辑与「撤回回价」相同，抽成公共方法。

有待审核回价时一律拒绝退回。审核中的记录交不交出会产生多种组合，这样做规则最简单。代价是兼职要等审核，已写入 Risks。

退回时清空 `first_assigned_at`（没有其他处理人时），并写入 `pool_entered_at`。这也改变了采购退回后的计时方式，是规格明确要求的。

### 5. 接手人看到的范围

有上一轮记录的型号（`quote_round > 0`）才显示其他人的记录，这样不改变现有多人比价「各自录入」的方式。价格由后端按 `isPartTime` 不返回，不靠前端隐藏。

不需要找的型号不设为只读。多人比价本来就允许补充报价，额外报价只会增加选择；只读还需要多维护一个型号标记。

### 6. 候选人改用新权限

新增按钮资源「可接询价任务」（`inquiry:sourcing:accept`），`purchasers()` 改为按它查角色。

迁移授权规则：有「我的询价」菜单、且**没有**客户询盘菜单的角色，加上内置的兼职采购。这是根据 `V1.2.26` 的约定（能看客户询盘的角色就是业务员）推断的，同时做业务和采购的角色需要租户管理员手动调整。

没有采用「在代码里判断是不是业务员角色」：角色是租户自建的。

### 7. 超时流转用定时任务，每分钟扫描

新增定时任务，查询 `status=6 AND sales_deadline <= now`，逐个任务在独立事务内处理，切换到任务所属租户后执行。用带状态条件的更新（`WHERE status=6`），认领和流转同时发生时只有一方成功；未来多实例部署也不会重复处理。

转采购和超时流转走同一个方法 `moveToPool`，规则自动分配放在这个方法里。

### 8. 事务边界

| 操作 | 同一事务内 |
|------|------|
| 认领、转采购 | 任务状态、分配记录 |
| 超时流转 | 单个任务的状态和规则分配，一个失败不影响其他任务 |
| 按型号退回 | 先锁询盘单；型号轮次和状态、转出记录、分配记录、任务、询盘状态 |

不新增金额计算，不跨到报价模块写数据。

### 9. 设置

新增按租户的系统设置 `inquiry.sourcing.sales-window-minutes`（默认 120）和 `inquiry.sourcing.sales-window-urgent-minutes`（默认 30）。沿用 `SourcingSettings` 的读取方式；负数按 0 处理。

## Risks / Trade-offs

- [所有询盘都多等最长 2 小时] → 紧急任务 30 分钟；业务员可以马上转采购；租户可以设为 0。上线后按实际反应速度调整。
- [权限迁移按菜单推断，可能授错] → 上线前列出授权结果，请管理员核对。漏授时候选人会变少，表现明显，容易发现。
- [采购负责人看不到业务员自询的进度] → 这是确认过的取舍。询价统计按月和按人员显示数量，业务员自询超时只提醒业务员本人。
- [业务员自询不审核，价格直接进入询价记录和成本] → 这是确认过的取舍，分配记录能查出来源。
- [兼职有待审核回价时不能退回] → 提示原因；需要依赖负责人及时审核。
- [定时任务停止时任务卡在待业务处理] → 负责人仍可手动转采购；定时任务出错写 ERROR 日志。
- [已回价的任务被退回，询盘从可报价回到询价中，业务员可能正在做报价] → 退回前列出受影响的草稿报价单，和撤回回价一致。
- [按人员对比时，业务员和采购的询价难度不同，只看数量可能不公平] → 同时显示有价率和转出；统计只作参考，不直接等于绩效。
- [修改 `refreshItems` 影响所有回价] → 这是核心逻辑，存量数据轮次都是 0，算出来应与现在相同；用测试覆盖。

## Migration Plan

**上线前：**

1. 执行数据库迁移：任务表增加 `sales_deadline`、`pool_entered_at`、`sales_handling`，型号表和回价表增加 `quote_round`，新增 `sourcing_item_handoff` 表，新增资源和角色授权，新增设置模板。
2. 核对「可接询价任务」的授权结果。

**上线后：**

3. 收回业务员角色的「询价分配」菜单。这一步不做，业务员仍能在工作台分配任务。
4. 上线时已在待分配的任务不变，仍由采购负责人分配。

**回退：** 字段只增不改，旧版本能正常启动，但旧版本不认识状态 6。回退前先执行 `UPDATE sourcing_task SET status = 1 WHERE status = 6`，并把 `sales_handling = 1` 的任务留在询价中，并把 `purchasers()` 依赖的菜单授权恢复为旧状态（迁移没有删除菜单授权，无需操作）。回退后，转交过的型号在下一次重算时可能恢复为无货。

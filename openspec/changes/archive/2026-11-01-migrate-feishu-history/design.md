## Context

- 源数据：`~/Downloads/历史数据/` 下 14 个飞书导出文件，其中 9 张业务表、5 张月度报表（只用于核对）。单据之间的引用基本完整：采购、发货、结汇、核算引用的销售单号 100% 能找到，询盘引用的客户与商机 100% 能找到。主要问题：
  - 订单、询盘的型号是多行自由文本：订单 264/627 条是多行，询盘 1435/3800 条是多行；
  - 询价的「进价」76% 不是纯数字，单价写在文本里；
  - 销售订单几乎都没填询盘单号；
  - 商机只有联系人，没有客户编码：入选的 1609 条中，按联系人能匹配到旧客户的只有 179 条；
  - 供应商库只导出了 6 条，询价、采购单引用的约 2100 个编码只能从询价的「供应商名称」还原：带「店名」的 1726 个，公司 47 个，个人供货商 336 个；
  - 附件只有文件名：询盘中型号为空或写「见附件」的有 222 条，订单 15 条。
- 新系统的型号热度（`ProductHeatMapper`）：询盘次数按 `inquiry_item.product_id` 计数，成交次数要经 `sales_order_item.inquiry_item_id` 关联回询盘行。没进商品主数据的型号，热度记在候选商品池（平台级，`product_candidate` + `product_candidate_source`）。
- 订单成本（`finance/order-cost`）由采购入库、付款、运费分摊、结汇、对账推算。旧系统没有入库与对账数据，按新规则推算对不上旧《成本核算》。
- 单据编号由 `document_sequence`（租户 + 单据类型 + 业务日期 + 流水）生成；`fin_fx_settlement` 已有 `migrated` 标记，迁移生成的结汇不参与先进先出与估算汇率。
- 素材库按「品牌 + 型号」归并（`media_item.asset_key`），分类已有客户来图、供方实拍、供方发货、验货记录。
- 演练租户 1007 已完成数据初始化，有阿里国际站、中国制造网两个事业部，开始核算月份为 2026-10。
- 先例：`scripts/product-migration`（干跑 → 生成 → 核对 → 软删除回滚）。

## Goals / Non-Goals

**Goals:**
- 清洗可以反复跑，人工复核结论能沉淀；导入可以干跑、可以重复执行、可以按批次回滚。
- 型号、品牌、商品匹配、候选入池、编号生成与日常业务走同一套代码，不另写一套规则。
- 迁移后新系统的经营统计、销售统计（商机数除外）、利润统计与旧报表逐月一致。

**Non-Goals:**
- 不迁移报价单、PI：旧系统没有，也不反推。
- 不让迁移订单在新系统里继续走流程（入库、对账、补收款）。在途订单在冻结日之前要在旧系统做完，或者切换后在新系统里新建。
- 不做通用的导入功能，只针对这一份旧系统数据。
- 不回写飞书。

## Decisions

### 1. 分两段：离线清洗用 Node 脚本，导入用后端任务

```
飞书导出 xlsx ─┐
飞书附件(只读) ─┼─► scripts/history-migration（Node）
               │    读表 → 规范化 → AI 拆分(缓存) → 合并去重 → 配对 → 分摊
               │    产出 out/bundle/*.json + out/review.xlsx（复核报告）
人工复核结论 ───┘    review/decisions.json（下次清洗沿用）
                           │
                           ▼
              后端 HistoryMigrationService（平台账号，指定租户）
              干跑 / 正式执行 / 回滚；按阶段分事务；复用各模块服务
                           │
                           ▼
              scripts/history-migration/verify（按月对比旧报表）
```

- **为什么清洗放在离线**：AI 调用多、耗时长、要反复调整规则，放在后端会拖慢应用、也不好迭代。清洗结果是普通 JSON，可以检查、可以对比差异。
- **为什么导入放在后端**：型号归一化、品牌别名、商品匹配、候选入池、编号序列、客户查重比较键都在后端服务里，用 SQL 再写一遍必然出现差异。商品迁移那次之所以能生成 SQL，是因为它只涉及一张主表。
- 备选：全部用后端实现，或全部用脚本生成 SQL。不选，原因如上。

### 2. 清洗结果的形状

每条记录带 `src`（源文件、行号、旧编号、内容哈希），以及清洗后的字段。外键用**旧编号**表示，比如订单引用 `customer: "C00729"`、型号行引用 `inquiryLine: "XP2026101010700#2"`。新 ID 只在导入时通过迁移对照得到，所以清洗不依赖数据库。合并、跳过、人工处理的记录也写进结果，`disposition` 字段注明结果和原因，复核报告就从这里生成。

### 3. AI 拆分：用本机 Claude Code 订阅（`claude -p`），不配接口密钥

- 调用方式：清洗脚本分批调用 Claude Code 的非交互模式 `claude -p --output-format json`，用的是本机已登录的订阅账号，不需要 `ANTHROPIC_API_KEY`。附件解析时只放开读文件这一项工具（`--allowedTools Read`），把附件的本地路径交给它读。
- 模型：文本拆分与进价抽取用 Haiku（每批 20～30 条记录一次调用）；附件（图片、PDF）和低置信度复核用 Sonnet（一次一个附件）。PI/INV 表格用程序直接读，不经过 AI。
- 已试通（2026-10-24）：多行型号文本拆分正确；一张「型号见附件」的询盘图片识别出 17 个施耐德型号，与原图逐个核对完全正确。单次调用的耗时：文本约 3 秒，图片约 12 秒。
- 输出固定结构：型号行数组，每行含品牌、型号、数量、货况、单价、置信度、依据片段。
- 缓存键 = 记录内容哈希 + 提示词版本。提示词改了才整体重跑，否则只跑内容变化的记录，冻结日只需补跑新增部分。
- 订阅有用量额度（按时间窗口限制）：脚本可以断点续传，遇到额度用完就停下，额度恢复后从断点继续，已完成的结果都在缓存里。并发 3～4 个。
- 品牌先用旧记录上的品牌字段（如「Siemens (西门子)」）对应到品牌主数据，作为 AI 的提示；最终的品牌识别以后端导入时的规则为准。
- 质量把关：随机抽 100 条和人工对照，型号行召回率和准确率都达到 95% 以上才进入正式清洗；没达到就调整提示词。
- 备选：如果订阅额度不够用，可以改用接口密钥（同样的提示词，只是调用方式不同）。

### 4. 记录与附件读取：借用浏览器里的飞书登录状态

不建飞书自建应用、不配凭证。脚本通过 ego 浏览器，在已登录飞书的页面里调用飞书网页端自己用的只读接口（2026-10-23 已试通）：

- 多维表格：知识库节点 `PAJzwD6YAiEwsxkxwc3c2ZxdnUg` 对应多维表格 `GBYVbckxgaKlGXsog07ciezvnHx`。询盘表 `tblIvCdp4JXZdvBN`，销售订单表 `tblLrmy9RRI9dfZ0`，其他表从多维表格的表清单里取。
- 字段定义：`GET /space/api/v1/bitable/{base}/clientvars?tableID=…`，返回的 `table` 是 gzip + base64，其中 `fieldMap` 给出字段 ID、名称和类型。
- 全部记录：`GET /space/api/v1/bitable/{base}/records?tableID=…&offset=N&limit=1000`，按 1000 条一页取完（询盘 3803 条、订单 629 条，都已取全）。附件单元格里带 `attachmentToken`、文件名、类型和大小。
- 附件：`GET /space/api/box/stream/download/all/{attachmentToken}/?mount_point=bitable_image&mount_node_token={base}&extra={"bitablePerm":{"tableId":…,"rev":…}}`。下载下来的文件大小与记录里的一致。

附件规模：询盘 1252 条记录有附件，共 1924 个，约 1.65 GB（图片 1461 个、PDF 279 个、表格 171 个）；订单 423 条记录有附件，共 454 个，约 94 MB（PDF 207 个、图片 184 个、表格 63 个）。询价、发货两张表待统计。

全部下载：图片同时用于型号解析和素材归档，PDF 和表格用于解析型号与 PI 单价。视频、压缩包不下载。文件缓存在 `out/attachments/`（加入 `.gitignore`），迁移结束后删除。下载失败的列入复核报告，不影响其余记录。

**字段值仍以导出的 Excel 为准**（实现时发现）：飞书原始记录里没有公式和引用字段的值（如询盘的「业务员」「客户名称」、核算的「销售成本」），这些是网页端算出来的，接口拿不到。所以冻结日仍要导出一次 Excel。飞书接口负责：附件、按单号对上记录、发现导出之后新增或修改的记录（非公式字段与 Excel 逐字段比对一致，只有导出后改过的几条不同），以及两张没导出过 Excel 的表——询价和采购单「供应商」字段关联的完整供应商库（`tblfbh3CaIj5fguI`），以及成本核算「退款单号」关联的退款表（`tblr1GyD3KsLPLSW`）。

- 风险：这些是飞书网页端的内部接口，不是公开接口，飞书改版就可能失效。对策是演练期间先把记录和附件全部取到本地缓存，冻结日只补新增部分；万一失效，就退回到人工导出 Excel，附件改为按需人工下载。
- 不选飞书自建应用：需要管理员审批并逐个授权表格，用户觉得太麻烦；这次的数据量用浏览器方式完全够用。

### 5. 客户与商机合并

- 比较键与客户查重一致：名称键、邮箱键、电话与 WhatsApp 键，另加「联系人小写去空格 + 国家」。
- 自动合并：邮箱、电话、WhatsApp 任一相同；或联系人与国家都相同且没有相互矛盾的联系方式。
- 疑似重复：只有联系人相同、国家不同或缺失。列入复核报告，人工结论写回 `decisions.json`。
- 国家：中文名对应到系统国家清单，内置一份别名表处理脏值（如「印度尼i西亚」对应印度尼西亚、「HK」对应香港）；对不上的为空，列入报告。

### 5a. 实现中发现的数据问题与处理

- **不可信的商机引用**：商机 SJ202511291241（Northwind Group）被 494 个不同客户的询盘引用（旧系统批量回填时填错）。一个商机被多个不同客户的询盘引用时，这些引用既不作为合并依据，也不让该商机因此入选，并列入复核报告。按此规则，新客户约 2139 个（旧客户 705 个，其余来自入选商机），疑似重复 23 组。
- **退款核算单**：11 张核算单没有关联订单（收入为 0，成本含退款），由退款表对回原订单后生成退款单。
- **金额的小数**：个别交易服务费有三位小数（如 10.455），以实收为准，手续费 = 总金额 − 实收；核算单的采购金额引用了多条采购单（显示为「¥7,360.00,¥7,360.00」）时，值都相同视为重复显示，取一个。
- **订单销售日期只到月份**：配对与编号用订单的创建日期作为销售日期。

### 6. 订单行配对询盘行

分三轮，每轮只在还没配上的行之间进行：

1. 同一客户 + 同一归一化型号 + 询盘日期 ≤ 销售日期，取最近的一条；
2. 同一业务员 + 同一归一化型号 + 销售日期前 180 天内，取最近的一条；
3. 归一化型号做前缀匹配（如去掉末尾的版本后缀），只作为建议列入报告，不自动关联。

一条询盘行可以被多张订单配对（客户复购）。归一化规则在清洗时用后端规则的同等实现预估配对结果，导入时以后端归一化结果为准重新校验；两边不一致的列入报告。

### 7. 金额与汇率

- 订单原币与人民币都保存；汇率取结汇汇率（6 位小数），没有结汇记录的取销售日期当天的系统汇率。人民币订单汇率为 1。
- 行金额分摊：以单价有来源的优先（PI/INV 附件）；否则按采购成本比例；都没有就按数量比例。分摊时中间值保持完整精度，最终 HALF_UP 保留 2 位，尾差放在金额最大的行。
- 采购单多行时同样分摊，比例取询价单价，没有询价单价按数量。
- 结汇单金额取实收（与新系统「结汇按实收口径」一致），汇率取原结汇汇率；到账的人民币金额按结汇汇率计算。

### 8. 订单成本用历史核算快照

新增 `sales_order_cost_snapshot` 表（订单 ID、收入、退款、采购成本、运费、附加费、交易服务费、实际成本、毛利、毛利率、结算状态、来源核算单旧号）。订单成本服务遇到迁移订单时直接读快照并按行金额分摊，不走推算。利润统计、经营统计、销售统计都经过订单成本服务取数，所以只改这一处。

- 备选：补造入库、对账、付款记录，让推算结果等于旧值。不选：要伪造大量下游单据，而且部分旧订单本身就对不上（成本核算里的附加费、运费在旧系统里是手工填的）。

### 9. 迁移标记与只读

- 业务表增加 `migrated tinyint(2) NOT NULL DEFAULT 0 COMMENT '历史迁移（0-否、1-是）'`（`fin_fx_settlement` 已有，沿用）。涉及：opportunity、customer_inquiry、sourcing_task、sourcing_quote、sales_order、purchase_order、supplier_shipment、logistics_shipment、payment_receipt、fin_customer_refund、fin_expense、fin_other_income、fin_payment。客户、供应商不加，迁移后可以正常编辑。
- 各模块的修改、作废、取消、删除服务入口统一调用一个检查：发现迁移数据就抛出业务异常「历史迁移数据不能修改」。前端读 `migrated` 字段，显示标记并隐藏操作入口。
- 商机例外：允许重新打开，重新打开时清除 `migrated`。

### 10. 迁移对照与批次

- `migration_batch`：批次号、租户、清洗结果的版本哈希、运行方式（干跑 / 正式）、状态（运行中、成功、失败、已回滚）、各阶段数量、开始结束时间、操作人。
- `migration_id_map`：租户、批次、源表、旧编号、目标表、目标 ID、状态（有效、已回滚）；唯一键为（租户、源表、旧编号、有效）。
- 重复执行：先查对照表，有记录就跳过；源数据内容哈希变化的列入报告，不覆盖。
- 回滚：按批次倒序软删除目标记录，移除候选来源（来源条数与可信度重新计算）和素材条目，对照标为已回滚。

### 11. 编号

导入时以单据业务日期调用现有编号服务，取号后更新 `document_sequence`。同一天的单据按旧系统的创建时间排序后依次取号，保证顺序与旧系统一致。冻结日当天的单据迁入后，序列已经推进，之后新建的单据接着往下编号。

### 12. 人员

按姓名在目标租户找用户。找不到就新建：用户名为姓名拼音，状态停用，不建登录账号。在采购员字段出现次数多于业务员字段的，岗位定为采购员，其余定为业务员；部门放在阿里国际站事业部对应的业务部或采购部。

### 13. 事业部

演练租户和福唯的正式租户都把旧数据全部归入「阿里国际站事业部」：旧业务都来自阿里国际站，这与「已有数据归属」规则一致。早于开始核算月份的月份，公共费用由该事业部承担（现有规则），全公司口径不受影响。

### 14. 核对

`verify` 脚本从数据库读取统计结果，与 5 张旧报表逐月、逐人、逐客户比较，再逐单比较订单收入和毛利与《成本核算》。输出差异表。在差异为零（商机数除外）之前，不进入正式执行。

## Risks / Trade-offs

- [AI 拆分出错，型号热度失真] → 抽样把关到 95% 以上；低置信度的列入复核；保留原文，以后可以重新拆。
- [客户合并错误，成交配不上，或者把两个人合成一个] → 只对强证据自动合并；疑似重复由人工确认；回滚按批次进行，改完结论可以重跑。
- [商机只迁 1609 条，商机数和转化率对不上旧报表] → 核对报告单独列出这一项的差异和原因，不当作迁移错误。如果以后需要对齐，可以把跳过的 1257 条以「无效」商机补迁。
- [候选池一次进来几千条，审核压力大] → 按可信度排序审核；「已成交」「采购问到有货」的优先。
- [快照让迁移订单的成本不再随后续操作变化] → 这些订单是只读的历史存档，本来就不再变化。
- [冻结日数据量大、耗时长] → AI 结果提前缓存；演练时记录各阶段耗时，据此安排冻结窗口。
- [飞书附件链接或权限变化，导致下载失败] → 演练阶段先把所需附件全部下载缓存；冻结日只补新增记录的附件。
- [「未登记客户（历史迁移）」占位客户混在客户列表里] → 每个业务员一个，名称带标记，状态启用但备注说明来源；以后可以在客户页按名称筛出。

## Migration Plan

1. **准备**：在 ego 浏览器里保持飞书登录；在租户 1007 确认已完成数据初始化。
2. **开发**：Flyway 新增迁移对照、批次、快照表和各表的 `migrated` 字段（附反向 SQL）；后端导入任务与只读检查；前端标记；清洗脚本与核对脚本。
3. **演练（租户 1007，可多轮）**：清洗 → 人工复核 → 干跑 → 正式执行 → 核对 → 回滚 → 调整后再来一轮，直到核对差异为零（商机数除外），并记录耗时。
4. **冻结日**：旧系统停止录入 → 全量重新导出（含附件）→ 清洗（只补跑变化部分）→ 复核增量 → 对福唯的正式租户干跑并正式执行 → 核对 → 通知大家切换。
5. **回滚**：正式执行后发现问题，按批次回滚；旧系统在核对通过前保持只读可查。
6. **收尾**：删除附件缓存；在飞书停用自建应用；迁移代码保留到下一个版本，再决定是否移除。

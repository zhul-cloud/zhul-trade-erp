## Context

- 文件已经统一存储（`unified-oss-storage`）。各来源的文件记录在：
  - `biz_attachment`：所属类型为 SHIPMENT、RECEIPT、SHOOT、SOURCING_QUOTE 的附件；
  - `customer_inquiry_attachment`：客户询盘附件；
  - `product_media`、`product_document`：共享商品库，租户 0。
- 现有实拍数据在 `shoot_task`（每个入库行一条）和 `media_asset`（素材 → 附件，类型分为 1 拆箱、2 验货、3 实物图）。开发库里租户 1005 有：已完成 1 条、待拍摄 10 条、已跳过 2 条。
- 需求热度已有 `ProductHeatMapper`（按租户统计询盘次数、成交次数）。
- 共享商品库的商品有品牌、系列、品类，型号归一化规则见 product/product；素材按「品牌 + 型号」去空格、不区分大小写归并（与 `ReceivingSupport.assetKey` 相同）。

## Goals / Non-Goals

**Goals:**
- 素材只做汇总，不复制文件；来源单据仍是文件的唯一归属，删除或作废后随之消失。
- 查一个型号的全部素材，以及列出有素材的型号，都只查一张索引表。
- 两个标记按「本公司 × 素材」保存，共享商品库的素材也能有本公司自己的标记。

**Non-Goals:**
- 不做全文检索、以图搜图。
- 不做素材的文件夹整理和手工归类。
- 不改各单据原有的附件显示与权限。

## Decisions

### 1. 素材索引表 `media_item`，一条素材 × 一个型号一行

字段如下：

| 字段 | 说明 |
| --- | --- |
| `tenant_id` | 租户 |
| `asset_key` | 品牌 + 型号的归并键 |
| `brand`、`model` | 显示用 |
| `category` | 类别，1-11，对应规格中的表 |
| `source_table`、`source_id` | 指向具体的文件记录：`biz_attachment`、`customer_inquiry_attachment`、`product_media`、`product_document` |
| `kind` | 1-图片、2-视频、3-文件 |
| `can_send`、`for_listing` | 两个标记 |
| `flag_by`、`flag_time` | 最后一次修改标记的人和时间 |
| `deleted_at` | 软删除时间 |
| 审计四列 | 创建时间、创建人、更新时间、更新人 |

- 唯一键：`(tenant_id, source_table, source_id, asset_key)`。
- 索引：`(tenant_id, asset_key)`，以及 `(tenant_id, category)`。

**文件信息不冗余存储**。展示时按 `source_table` 分批查原记录，取存储方式、文件键、文件名、大小、处理状态。原因是视频转码、历史迁移都会改动文件键，冗余一份就要处处同步。

**共享商品库的素材不预先建索引**。打开型号时，按商品实时读取它的图片和资料；本公司给它改了标记时，才在本公司的 `media_item` 里补一行，作为覆盖。列表页统计「有无营销图」等数字时只用索引表，官方素材单独显示数量。

**备选**：每次查询时直接合并各来源表（UNION）。被否决：各来源表的型号信息分散在单据行、标注表和任务上，联查超过 3 张表，违反编码规范，列表页也无法分页和排序。

### 2. 附件的型号标注 `biz_attachment_model`

字段：`attachment_id`、`tenant_id`、`asset_key`、`brand`、`model`。用于 SHIPMENT、RECEIPT（包括不良品）、PACKING 三类附件。

- 前端在保存单据时，随附件 ID 一起提交每个附件的型号列表；不传时默认为单据的全部型号。
- 后端校验标注的型号都在这张单据里。

**索引的维护**：在 `AttachmentService.attach/sync/remove/reassign` 之后调用 `MediaIndexer.syncAttachment(ownerType, ownerId)`，用当前附件和标注重建这张单据的索引行：新增的补上，消失的软删除，已有的标记保留。

其他来源的写入时机：

| 类别 | 何时进入素材库 | 型号从哪来 |
| --- | --- | --- |
| 营销实拍 | 挂到实拍任务时 | 实拍任务的型号 |
| 网络图片 | 上传时 | 上传时指定的型号 |
| 供方实拍 | 回价挂上附件时 | 询价任务行的型号 |
| 客户来图 | 确认解析结果时，以及追加型号确认时 | 询盘单当时的全部型号，重建这张询盘的索引 |

### 3. 新增附件所属类型

| 所属类型 | 内容 | 存储环节 | 数量上限 |
| --- | --- | --- | --- |
| `PACKING` | 打包发货 | `StorageArea.PACKING`（`packing/{年月}`） | 每张出库单 20 个 |
| `NETWORK` | 网络图片 | `StorageArea.MEDIA`，上传时带型号，直接放进型号目录 | 每个型号 30 张 |
| `RECEIPT_DEFECT` | 不良品照片 | `StorageArea.RECEIPT` | — |

- `NETWORK` 的归属是素材库里的一个型号，没有单据。`owner_id` 存索引行的 ID，型号写在标注表。
- 不良品照片和验收照片分开记录。把 RECEIPT 的附件拆成两种所属类型，就能用「上传入口决定类别」，而不必再加一个字段。

### 4. 两个标记与下载控制

- 标记的默认值在写入索引时，按类别给出。
- 下载链接的接口校验 `can_send = 1`，否则拒绝。预览链接不受这个限制。
- 素材库的预览和下载链接由素材库接口签发：校验的是素材库菜单权限，而不是原单据的菜单权限，这样业务员也能看到仓库拍的照片。这是有意放宽的。仅内部的素材只能预览。

### 5. 参考素材的查找

1. 由型号的 `asset_key` 找到共享商品库里的商品，得到品牌、系列和品类；找不到时只按品牌查找。
2. 按层查商品库里的候选商品，再与本公司 `media_item` 中「有可发客户的图片或视频」的型号求交集。官方图片也算在内。
3. 同一层按 `ProductHeatMapper` 的询盘次数、成交次数排序，最多 20 个。

每一层是两次查询加内存中求交集，不跨三张以上的表联查。

### 6. 下载

- 前端逐个取下载链接（`download=true`），用 `<a>` 依次触发，间隔 300 毫秒，最多 50 个。
- 浏览器第一次会询问「是否允许下载多个文件」。这是浏览器自身的保护，用户允许一次即可。
- 不在服务器端打包 zip：文件在 OSS 上，服务器打包要先下载再上传，延续上一个变更「统一使用 OSS 链接」的决定。

### 7. 实拍任务改为营销拍摄

- `shoot_task` 表沿用，含义改为营销拍摄任务；`media_asset` 不再写入，数据转到 `media_item`，表保留，以后的版本再删除。
- 生成条件：这个型号在本公司没有「营销实拍」类别的素材，并且没有待拍摄的任务。在验收入库的同一事务里判断，同一次入库按型号去重。
- 完成条件：营销图不少于 6 张。

### 8. 历史数据转换（Flyway SQL，V1.3.3）

1. `media_asset` 中实物图（类型 3）对应的附件：在 `media_item` 里写成「营销实拍」，可发客户、未用于发品。
2. 拆箱和验货视频（类型 1、2）对应的附件：所属类型改为 RECEIPT，`owner_id` 改为任务的来源入库单；标注表写入该型号；`media_item` 写成验货记录。
3. 待拍摄的任务：
   - 型号已有营销实拍的，置为已跳过，原因「已有营销图」；
   - 同型号有多条的，保留 ID 最小的一条，其余置为已跳过，原因「合并到 {保留任务的 ID}」。
4. 已有的 SHIPMENT、RECEIPT 附件：按发货单、入库单的全部型号写入标注表和 `media_item`；SOURCING_QUOTE 附件按任务行型号写入。
5. 客户询盘附件：按询盘的全部型号写入。

全部是 `INSERT … SELECT` 和 `UPDATE`。分组去重放在子查询里，每条语句联查的表不超过 3 张。

### 9. 实施顺序

`unified-oss-storage` 修改了 file-attachment 的「业务附件」等要求，本变更也给 file-attachment 增加要求。归档时，要先归档 `unified-oss-storage`，再归档本变更。

## Risks / Trade-offs

- **[索引与来源不同步]**：例如某处删除附件时漏调了索引同步。
  → 缓解：所有附件的增删都经过 `AttachmentService`，集中在这里调用；另外提供一个「按单据重建索引」的内部方法，供修复时使用；集成测试覆盖增、改、删、作废。
- **[客户来图标注全部型号太宽]**：一张铭牌照片会出现在这张询盘的所有型号下面。
  → 接受：默认仅内部可见，只用于识别型号；以后有需要再加手工调整。
- **[业务员能看到仓库的验货照片和视频]**：这是素材库的目的。
  → 不可以发给客户的类别（到货异常、供方发货等）默认仅内部可见，只能预览。
- **[批量下载被浏览器拦截]**：首次需要用户允许，页面上给出提示。

## Migration Plan

1. 先归档 `unified-oss-storage`（至少完成它的规格合并）。
2. 发布迁移 V1.3.3：建表、补菜单和权限、转换历史数据。
3. 发布前后端。
4. 抽查转换结果：已完成的实拍任务的营销图、待拍摄任务的合并情况。
5. 回退：本次只新增表、新增附件所属类型；历史数据转换只修改了 `shoot_task` 的状态和 SHOOT 视频附件的归属。回退需要一个反向 SQL，在 tasks 里一并准备。

## 1. 功能概述

### 1.1 功能目标

外贸业务流程的第一步是询盘（询盘 → 报价 → 客户确认 → 合同签订 → ...），本模块承接团队现有的"烛龙询盘助手"AI 能力（自动解析原始询盘、联网核验型号、按品牌+品类拆单、生成中英文询价话术），落地为 zhul-erp 里正式的询盘管理模块。

模块分两条主线：

- **客户询盘**：记录客户原始诉求全貌。业务员录入原始内容（文本/Excel/图片），触发 AI 异步解析，解析完成后业务员在预览页确认拆单结果，确认后正式生成询盘单。
- **询盘单**：AI 按品牌+品类拆出的可分配工作单元。拆单刚完成时仍是中性的客户诉求分组，尚未指定对接人；经过**分配**动作后才成为某个采购员手头要去问供应商的工作项，支持同时问多家供应商并列比价。

两条主线关联但独立：询盘单既可以由客户询盘 AI 拆单产生，也支持业务员/采购员跳过 AI、直接手动创建（简单询盘无需走完整解析流程）。

### 1.2 使用角色

| 角色 | 说明 |
|------|------|
| 业务员 | 录入客户原始询盘、确认 AI 拆单结果、跟进客户询盘的报价与成交状态 |
| 采购员 | 被分配到具体询盘单后，对接供应商、录入报价、比价 |
| 业务/采购主管 | 将拆单后的询盘单分配给具体采购员（分配权限的具体角色留待实现阶段结合项目现有角色权限体系确定） |

### 1.3 入口路径

| 场景 | 路径 |
|------|------|
| 客户询盘列表 | `/inquiry/customer-inquiries` |
| 客户询盘详情（含解析状态、拆单预览确认） | `/inquiry/customer-inquiries/:id` |
| 新建客户询盘 | `/inquiry/customer-inquiries` 页面内弹窗 |
| 询盘单列表 | `/inquiry/orders` |
| 询盘单详情（含分配、供应商报价对比） | `/inquiry/orders/:id` |
| 手动新建询盘单（跳过 AI） | `/inquiry/orders` 页面内弹窗 |

## 3. 状态流转

### 3.1 客户询盘 × 询盘单 关系概览

```
customer_inquiry（客户询盘，1条）
      │  AI 拆单确认后生成
      ▼
inquiry_order（询盘单，N条，也可脱离客户询盘手动创建）
      │
      ▼
inquiry_order_item（明细，N条）
```

### 3.2 客户询盘状态枚举

| 状态值 | 含义 | 触发方 |
|--------|------|--------|
| 待解析 | 已提交，尚未创建 AI 任务，等待业务员手动发起解析 | 系统（提交后自动进入，不自动触发解析） |
| 解析中 | 业务员已点击"开始解析"，AI 任务已创建并处理中 | 业务员（点击"开始解析"） |
| 待确认 | AI 处理完成，等待业务员在预览页确认拆单结果 | 系统 |
| 解析失败 | AI 处理失败，需人工介入（引导走询盘单手动创建） | 系统 |
| 已确认 | 业务员已确认拆单，`inquiry_order` 记录已生成 | 业务员 |
| 待报价 | 等待汇总供应商报价，准备回复客户 | 业务员 |
| 报价中 | 正在向供应商询价（关联询盘单进入询价流程） | 业务员 |
| 已报价 | 报价已发给客户 | 业务员 |
| 已成交 | 客户确认下单 | 业务员 |
| 已取消 | 询盘取消或客户撤回 | 业务员 |

### 3.3 询盘单状态枚举

| 状态值 | 含义 | 触发方 |
|--------|------|--------|
| 待分配 | 询盘单已生成（AI拆单确认后，或手动创建后），尚未指定采购员 | 系统 |
| 已分配 | 已指定 `assignee_id`，采购员开始处理 | 分配人 |
| 已发供应商 | 采购员已将询价发给至少一家供应商 | 采购员 |
| 已收报价 | 已收到供应商报价 | 采购员 |
| 已报客户 | 报价已同步给业务员/客户 | 采购员 |
| 已成交 | 该询盘单对应的采购已成交 | 采购员 |
| 已取消 | 该询盘单取消 | 采购员/业务员 |

> 询盘单状态由人工显式推进，不依据 `inquiry_order_supplier` 各供应商的独立回复状态自动聚合计算（3~4家供应商部分回复时，"算不算已收报价"由采购员自行判断）。

## 5. 页面流程

### 5.1 客户询盘录入与 AI 解析确认流程

```
P01 列表页点击"新建客户询盘"
      │
      ▼
P02 弹窗：选择录入方式（文本/Excel/图片）+ 选择客户（可内联新建 M03）
      │
      ▼
提交 → 创建 customer_inquiry（status=待解析），不自动触发解析
      │
      ▼
P03 详情页展示"待解析"态：只读展示原始内容/附件 + "开始AI解析"按钮
      │  业务员核对无误后点击"开始AI解析"
      ▼
创建 ai_task（status=排队中）→ 同步调用 AI 编排服务 POST /skills/inquiry-parse-and-split/run
customer_inquiry.status → 解析中
（业务员可离开，去做其他事）
      │
      │  AI 编排服务处理完成，webhook 回调 zhul-erp
      ▼
ai_task.status → 已完成，output 写入三层结构 JSON
customer_inquiry.status → 待确认
（工作台"待办事项"出现"N条询盘待确认"提醒，见 Open Question）
      │
      ▼
P03 详情页展示拆单预览（按品牌+品类分组的卡片列表，逐条明细可编辑：
    调整分组归属 / 修正型号 / 修正数量单位，低置信度条目高亮）
      │
   ┌──┴──┐
 确认拆单   （编辑后）确认拆单
   │
   ▼
POST 确认接口，创建 inquiry_order（status=待分配）× N + inquiry_order_item
customer_inquiry.status → 已确认
      │
      ▼
P03 详情页切换为"已确认"态：展示已生成的询盘单列表（跳转 P05）
```

**解析失败分支**：`ai_task.status=失败` 时，`customer_inquiry.status → 解析失败`，P03 展示失败原因 + "手动创建询盘单"按钮（跳转 P06，预填客户询盘关联）。

### 5.2 询盘单分配与供应商询价流程

```

      │
      ▼

inquiry_order_supplier 记录生成（status=待发送）

      │
      ▼

      → 该供应商 status=已回复

（已发供应商→已收报价→已报客户→已成交/已取消）
```

### 6.3 P03 客户询盘详情

页面按 `customer_inquiry.status` 展示四种主要形态：

#### 6.3.1 「待解析」态

- 页面顶部展示原始内容/附件预览（只读）
- 中部展示提示文案"AI 尚未开始解析，确认原始内容无误后可发起解析" + 醒目的"开始AI解析"按钮（primary）
- 点击"开始AI解析"后按钮 loading，接口创建 `ai_task`（status=排队中）并触发 AI 编排服务调用成功后，页面自动切换到"解析中"态

#### 6.3.2 「解析中」态

- 页面顶部展示原始内容/附件预览（只读）
- 中部大面积 loading 区域，文案"AI 正在解析询盘内容，预计需要几分钟，你可以先去处理其他事情"
- 无需用户停留等待，可直接离开（列表页/工作台待办会提示完成）

#### 6.3.3 「待确认」态（拆单预览）

- 顶部统计条：共 N 条明细 | 确认 X | 已纠正 Y | 待核实 Z | 未识别 W
- 按品牌+品类分组的卡片列表，每组一张卡片：
  - 组头：品牌 · 品类（可下拉切换到其他已有分组，用于手动调整某条明细的归属）
  - 组内表格：原始型号 / 确认型号（可编辑） / 置信度标签 / 数量 / 单位 / 描述 / 操作（移除、移到其他组）
  - 组内低置信度行（待核实/未识别）行底色浅黄/浅红高亮
- 底部操作栏："取消询盘"（危险色，需二次确认，status→已取消） + "确认拆单"（primary）
- 置信度标签配色：确认=绿 / 已纠正=蓝 / 待核实=黄 / 未识别=红（与 `inquiry-parser` skill 原定义保持一致）

#### 6.3.4 「已确认」及之后各态

- 顶部展示询盘基本信息（只读）
- 关联询盘单列表（表格：询盘单编号/品牌/品类/型号数/采购员/状态，点击行跳转 P05）
- 允许业务员手动推进 `customer_inquiry.status`（待报价→报价中→已报价→已成交/已取消），通过顶部状态下拉或对应操作按钮

#### 6.3.5 「解析失败」态

- 展示失败原因（`ai_task.error_message`）
- 展示"手动创建询盘单"按钮，跳转 P06 并预填 `customer_inquiry_id`

### 6.4 P04 询盘单列表

#### 6.4.1 页面结构

### 6.5 P05 询盘单详情

#### 6.5.1 页面结构

## 7. 异常与边界处理

| 场景 | 处理方式 | 提示文案 |
|------|----------|----------|
| AI 处理超时（无回调） | 前端轮询兜底或设置超时阈值，超时后允许业务员手动标记"处理超时"转人工 | "AI 解析超时，可选择手动创建询盘单" |
| 拆单预览中把所有明细都移出某个分组 | 该分组随确认动作一并被丢弃，不生成空询盘单 | 组内为空时该组卡片显示"本组已无明细，确认后不会生成询盘单" |
| 拆单预览页面刷新/意外关闭 | 预览数据来自 `ai_task.output`，刷新后重新拉取仍可继续编辑（编辑内容如未提交确认不持久化，刷新后编辑丢失） | 编辑区域旁提示"未提交确认前，页面刷新会丢失本次修改" |
| 询盘单已分配后再次分配给其他人 | 允许，视为"重新分配"，�covers 原 assignee | 分配记录变更，不保留历史（如需分配历史留待后续版本） |
| 供应商报价货币非常规 ISO 4217 代码 | 前端下拉限定常见币种（CNY/USD/EUR/GBP/JPY等），不支持自由文本 | — |
| 汇率未维护（币种非本位币且无汇率） | 报价状态可先保存为"待报价"，本位币金额留空，不阻塞录入，提交报价单流程时再校验 | "该币种汇率未填写，本位币金额暂不计算" |
| 手动创建询盘单未关联客户询盘 | 允许，`customer_inquiry_id` 为空，P05 详情页不展示"关联客户询盘"入口 | — |
| 客户/供应商快速创建时名称已存在 | 后端校验唯一性（同租户内），提示后可选择使用已有记录 | "该名称已存在，是否使用已有客户/供应商？" |
| 明细数量或单价为 0 | 允许保存（如"数量待定"场景），报价对比表格该单元格显示"待定" | — |
| 电商询价渠道的店铺名称与已有正式供应商同名 | 允许并存，不做唯一性校验（电商询价渠道不落 `supplier` 主数据，与 `supplier.name` 不在同一命名空间内） | — |
| 电商询价渠道"转为正式供应商"时店铺名称已存在于 `supplier` 中 | 复用 M04 已有的"名称已存在"校验逻辑，提示后可选择关联已有供应商而不新建 | "该名称已存在，是否关联已有供应商？" |
| 询盘单下所有供应商均"未回复"超过回复截止日期 | 不自动变更状态，仅在列表页/详情页展示"已超期"提示标签 | "已超过回复截止日期" |

## 8. 默认假设

1. **AI 编排服务已独立部署**：本 PRD 假设 AI 编排服务（复用现有"烛龙询盘助手" skill）作为外部依赖已可用，通过 webhook 回调 zhul-erp；AI 编排服务自身的实现、部署、鉴权不在本 PRD 范围（见 `openspec/changes/add-inquiry-management/design.md`）。
2. **不接入 PDF 解析报告**：原"烛龙询盘助手"的 `report-generator`（PDF报告生成）本次不接入，P03 不展示 PDF 下载入口。
3. **询盘单状态不自动聚合**：多供应商场景下，询盘单整体状态由人工手动推进，不根据各供应商独立回复状态自动计算（见 3.3 状态流转说明）。
4. **分配权限待实现阶段确定**：谁有权限执行"分配采购员"动作（业务主管/任意登录用户/仅特定角色），本 PRD 不做限定，交由实现阶段结合项目现有角色权限体系（`role`/`resource`）确定，默认先对所有登录用户开放。
5. **不做分配历史留痕**：询盘单重新分配后不保留历史分配记录（谁在什么时候被分配过），如需审计追溯留待后续版本。
6. **报价单/销售订单衔接留待后续**：询盘单确认成交后，如何流转到报价单（quotation）/销售订单（sales_order）模块，不在本 PRD 范围，两个模块尚未设计。
7. **工作台待办事项联动**：客户询盘"待确认"、询盘单"待分配"/"我的待处理"是否接入工作台首页的"待办事项"卡片，建议接入但具体实现细节留待实现阶段确定（不阻塞本模块本身的验收）。
8. **多租户与金额精度**：所有涉及金额的字段遵循 `.claude/rules/finance-rules.md`（HALF_UP 四舍五入、汇率保留6位小数、金额保留2位小数）；所有业务表遵循项目多租户隔离规范（`tenant_id` + 软删除）。

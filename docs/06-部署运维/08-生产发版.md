# 生产发版

生产服务器的发版全部由 GitHub Actions 完成（`.github/workflows/release.yml`），不在本机构建镜像，也不在服务器上编译代码。

```
release/X.Y.Z 通过 PR 合并到 main
  → 在 main 的合并提交上打版本标签 vX.Y.Z
  → GitHub 构建 backend、frontend、ai-orchestrator 三个镜像，推送到 ghcr.io/zhul-cloud/zhul-erp-*:vX.Y.Z
  → 登录生产服务器执行部署脚本：拉取镜像、切换 :prod 标签、更新 compose 文件、重启、等待健康检查
```

**合并到 main 就等于上线**，构建完成后自动部署，中间不需要人工确认。

## 版本号

- 取分支名：`release/1.3.0` 第一次合并打 `v1.3.0`。
- 同一个分支再次合并，补丁号自动加一：`v1.3.1`、`v1.3.2`……
- 只有本仓库 `release/X.Y.Z` 分支合并到 `main` 的 PR 才会发版；其他分支、fork 的 PR、未合并就关闭的 PR 都不会触发。

## 服务器上的文件

| 路径 | 内容 |
| --- | --- |
| `/opt/zhul-trade-erp/.env` | 生产配置与密钥，只在服务器上，不进仓库 |
| `/opt/zhul-trade-erp/docker-compose.yaml`、`docker-compose.prod.yaml` | 每次部署从对应版本标签下载，不要在服务器上直接改 |
| `/opt/zhul-trade-erp/storage/mysql`、`storage/redis` | 持久化数据 |
| `/opt/zhul-trade-erp/deploy.sh` | 部署脚本，来自仓库 `scripts/deploy/prod-deploy.sh` |
| `/opt/zhul-trade-erp/releases.log` | 每次部署的版本、结果与上一版 |

`docker-compose.prod.yaml` 固定使用 `zhul-erp-*:prod` 镜像，部署脚本把 `:prod` 指向本次版本的镜像。服务器上保留最近 3 个版本的镜像。

## 一次性配置

### 1. 服务器：安装部署脚本和受限部署密钥

部署脚本更新后也要重新执行这一步的第一条命令。

```bash
install -m 700 -o root -g root prod-deploy.sh /opt/zhul-trade-erp/deploy.sh
```

单独生成一把部署专用的密钥（不要复用个人登录密钥），把公钥按下面的格式追加到服务器 `/root/.ssh/authorized_keys`。`command=` 和 `restrict` 让这把密钥只能执行部署脚本，不能开 shell、转发端口或执行其他命令：

```
command="/opt/zhul-trade-erp/deploy.sh",restrict ssh-ed25519 AAAA... github-actions-deploy
```

### 2. GitHub：填写部署配置

在仓库 Settings → Secrets and variables → Actions 中添加：

| 类型 | 名称 | 内容 |
| --- | --- | --- |
| Secret | `DEPLOY_SSH_KEY` | 部署密钥的**私钥**全文 |
| Variable | `DEPLOY_HOST` | 生产服务器地址 |
| Variable | `DEPLOY_KNOWN_HOSTS` | 服务器主机公钥，在可信网络中执行 `ssh-keyscan -t ed25519 <服务器地址>` 得到 |

### 3. 镜像可见性

三个镜像推送时会关联到本仓库，并继承仓库的公开可见性，服务器不登录就能拉取，不需要额外设置。如果部署时报镜像拉取失败（例如组织设置把新建的包默认设为私有），到组织的 Packages 页面把 `zhul-erp-backend`、`zhul-erp-frontend`、`zhul-erp-ai-orchestrator` 改为 Public（Package settings → Change visibility），再在 Actions 里对这次运行点 Re-run failed jobs。

镜像里只有程序和运行环境，不含任何密钥；密钥只在服务器 `.env` 中。

## 重新部署与回滚

Actions → 生产发版 → Run workflow，填一个已有的版本号（如 `v1.3.0`）。这只会重新部署这个版本，不会打标签，也不会重新构建。上一版是哪个，看 `releases.log` 或部署日志里的「上一版」。

也可以在服务器上直接执行 `/opt/zhul-trade-erp/deploy.sh v1.3.0`。

## 部署失败时

- **`.env` 缺少配置项**：新版本的 `.env.example` 加了配置，而服务器 `.env` 里还没有。部署会在拉取镜像前停下，并列出缺少的配置项名称；补齐后重新部署。
- **健康检查失败或超时**：此时 `:prod` 已经指向新版本。先在服务器上用 `docker logs <容器名>` 查原因，需要恢复服务就按上面的方法回滚到上一版。
- 仓库是公开的，Actions 日志所有人都能看到，所以部署日志只输出状态，不输出容器日志和配置内容。

## 第一次部署之后

全新的生产库没有可登录的账号，按 [生产环境首次账号](06-生产环境首次账号.md) 初始化第一个平台管理员。

# 分支与版本规范

本项目按完整的 Git Flow 管理分支，版本号遵循语义化版本。所有参与开发的人员都按本文操作。

合并到 `main` 前的检查、部署、回滚见 [生产发版](08-生产发版.md)。

## 一句话规则

- 日常开发都进 `develop`。
- 发版从 `develop` 拉 `release/X.Y.Z`，线上紧急修复从 `main` 拉 `hotfix/X.Y.Z`。
- **`release/*`、`hotfix/*` 合并到 `main` 就是生产上线**，中间没有人工确认；合并后必须再合回 `develop`。

## 分支

| 分支 | 从哪拉出 | 合并到 | 用途 | 生命周期 |
| --- | --- | --- | --- | --- |
| `main` | 无 | 无 | 生产代码，只接受 `release/*`、`hotfix/*` | 长期 |
| `develop` | 无 | 无 | 日常开发集成 | 长期 |
| `feat/<说明>` | `develop` | `develop` | 新功能 | 合并后自动删除 |
| `fix/<说明>` | `develop` | `develop` | 普通问题修复 | 合并后自动删除 |
| `docs/<说明>`、`chore/<说明>`、`test/<说明>`、`ci/<说明>` | `develop` | `develop` | 文档、杂项、测试、持续集成 | 合并后自动删除 |
| `release/X.Y.Z` | `develop` | `main`，再合回 `develop` | 发版收尾 | 合并到 `main` 后自动删除 |
| `hotfix/X.Y.Z` | `main` | `main`，再合回 `develop` | 线上紧急修复 | 合并到 `main` 后自动删除 |

```text
feat/xxx       ──→ develop
develop        ──→ release/1.4.0 ──→ main（打 v1.4.0，上线）
release/1.4.0  ──→ develop
main           ──→ hotfix/1.4.1  ──→ main（打 v1.4.1，上线）
hotfix/1.4.1   ──→ develop
```

仓库已开启合并后自动删除来源分支，不用手动删除远程分支。本地分支用下面的命令清理：

```bash
git fetch --prune
git branch -d <分支名>
```

命名要求：

- `<说明>` 用小写英文和连字符，如 `feat/inquiry-edit`、`fix/user-delete`。
- `release/`、`hotfix/` 后面必须是完整的三段版本号，如 `release/1.4.0`。`release/1.4`、`release/foo` 这样的名字合并后会让发版流程报错停止。
- 不要新建其他长期分支。

## 版本号

格式是 `主版本.次版本.修订号`，发版标签加 `v`，如 `v1.4.0`。

| 这次发布包含什么 | 改哪一段 | 例子 |
| --- | --- | --- |
| 只有问题修复 | 修订号加一 | `v1.4.0` → `v1.4.1` |
| 有新功能 | 次版本号加一，修订号归零 | `v1.4.1` → `v1.5.0` |
| 有不兼容的改动 | 主版本号加一，后两段归零 | `v1.5.0` → `v2.0.0` |

- 标签由发版流程自动打，不要手动打。版本号直接取分支名：`release/1.4.0` 打 `v1.4.0`，`hotfix/1.4.1` 打 `v1.4.1`。
- 同一个版本号只能发一次。标签已存在时发版流程报错停止，不会部署，要用新的版本号开分支。

版本号写在三个文件里，接口文档和登录页页脚会自动读取，不用另外修改：

| 文件 | `develop` 上 | `release/*`、`hotfix/*` 上 |
| --- | --- | --- |
| `zhul-erp-backend/pom.xml` | `X.Y.Z-SNAPSHOT` | `X.Y.Z` |
| `zhul-erp-frontend/package.json` | `X.Y.Z` | `X.Y.Z` |
| `zhul-erp-frontend/package-lock.json`（开头两处） | `X.Y.Z` | `X.Y.Z` |

其中 `X.Y.Z` 在 `develop` 上表示下一个要发布的版本。

## 日常开发

一项需求从开始到合并，按下面的顺序做。具体要求以各步链接的原文为准。

1. **写变更提案。** 用 OpenSpec 写提案，说明影响范围，见 [参与贡献](../../README.md#-参与贡献)。
2. **确认原型。** 涉及 UI 的改动先用 OpenPencil 出原型，经确认后才能开发页面，见 [AGENTS.md](../../AGENTS.md) 和 [前端 UI 设计规范](../../.claude/context/ui-design-patterns.md)。不涉及 UI 的跳过这一步。
3. **开发。** 从 `develop` 拉分支，按 [编码规范](../../.claude/rules/coding.md) 写代码；财务相关改动还要遵循 [财务计算规则](../../.claude/rules/finance-rules.md)。
4. **测试。** 补齐测试，确保后端 `mvn test`、前端 `npm run lint` 与 `npx antd lint ./src` 全部通过。覆盖率要求见 [编码规范](../../.claude/rules/coding.md)。
5. **发 PR 到 `develop`。** 有新增或改名的 `.env` 配置项、有数据库迁移时，按 [AGENTS.md](../../AGENTS.md) 的「分支与发版」写进 PR 说明。

分支操作：

```bash
git switch develop && git pull
git switch -c feat/xxx
# 开发、提交
git push -u origin feat/xxx
gh pr create --base develop
```

提交信息遵循 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/)，如 `feat(sales): 销售订单可上传附件`。

不要把功能分支直接合并到 `main`：不会触发发版，还会让 `main` 和线上版本不一致。

## 发版

以 `1.4.0` 为例。

1. **拉发版分支。** 这个版本从此不再加新功能，新功能继续进 `develop`，随下一版发布。

   ```bash
   git switch develop && git pull
   git switch -c release/1.4.0
   ```

2. **改版本号。** 把 `pom.xml` 改成 `1.4.0`（去掉 `-SNAPSHOT`），确认另外两个文件也是 `1.4.0`，提交并推送。

3. **测试和收尾。** 这个分支上只修测试发现的问题，不加功能。

4. **发 PR 到 `main`。** 先按 [合并到 main 前的检查](08-生产发版.md#合并到-main-前的检查) 确认配置项和数据库迁移。

   ```bash
   gh pr create --base main --head release/1.4.0 --title "发版：v1.4.0"
   ```

5. **合并并确认上线。** 用合并提交方式合并，不要压缩或变基。到 Actions 页面确认「生产发版」运行成功。

   ```bash
   gh pr merge <PR 编号> --merge
   ```

6. **合回 `develop`，升下一版。** 这一步没有自动化，必须手动做，漏了会让收尾时的修复在下一版丢失。发版分支此时已自动删除，版本记录保存在 `v1.4.0` 标签里，所以从 `main` 拉一个临时分支来合回：

   ```bash
   git switch main && git pull
   git switch -c chore/back-merge-1.4.0
   # 把版本升到下一版并提交（如后端 1.5.0-SNAPSHOT、前端 1.5.0）
   git push -u origin chore/back-merge-1.4.0
   gh pr create --base develop --title "chore: 合回 v1.4.0，版本升到 1.5.0"
   ```

   如果有版本号冲突，保留下一版的版本号。

## 线上紧急修复

只用于不能等下一次发版的线上问题。普通问题走 `fix/*`。以修复 `v1.4.0` 为例。

1. **从 `main` 拉分支。** 不要从 `develop` 拉，否则会带上还没发布的功能。

   ```bash
   git switch main && git pull
   git switch -c hotfix/1.4.1
   ```

2. **改版本号并修复。** 三个文件都改成 `1.4.1`，只改和这个问题有关的代码。

3. **发 PR 到 `main`，合并上线。** 检查和确认方式与发版相同。

4. **合回 `develop`。** `hotfix/1.4.1` 此时已自动删除，从 `main` 拉 `chore/back-merge-1.4.1`，发 PR 到 `develop`。如果有版本号冲突，保留 `develop` 的版本号。如果此时有进行中的 `release/*` 分支，也要合进去，否则这个修复不会进入即将发布的版本。

## 常见问题

**合并后 Actions 里没有「生产发版」运行。** 看分支是否为 `release/*` 或 `hotfix/*`。其他分支合并到 `main` 不会触发发版。

**发版流程报错“标签已存在”。** 这个版本号已经发过了。线上版本不变。从最新的 `main` 或 `develop` 用新的版本号重新开分支。

**发版流程报错“分支名不是 release/X.Y.Z 或 hotfix/X.Y.Z”。** 分支名不符合要求，线上版本不变。用正确的名字新建分支，重新发 PR。

**部署失败或要回滚。** 见 [生产发版](08-生产发版.md) 的「部署失败时」和「重新部署与回滚」。回滚只切换线上版本，修复仍然要走 `hotfix/*`。

## 过渡说明

本规范于 2026-10-31 启用，`main` 上要等 `v1.4.0` 发布后才生效。

- **`v1.4.0` 发布前：** `main` 上的发版流程还是旧规则，`hotfix/*` 合并后不会发版。这期间如果要发紧急修复，要把 `.github/workflows/release.yml` 的改动一起带进 hotfix 分支。
- **旧分支：** `release/1.1.0`、`release/1.2.0`、`release/1.3.0` 是历史分支，不再使用。`v1.4.0` 发布前，`main` 上的旧规则仍然有效，把它们合并到 `main` **会触发发版和部署**，不要这样做。

## 1. 功能概述

### 1.1 功能目标

为租户管理员提供角色的创建、配置、权限分配和生命周期管理能力。通过 RBAC（基于角色的访问控制）模型，将菜单/按钮资源权限与用户解耦，通过角色统一授权，降低权限管理复杂度。

### 1.2 使用角色

| 角色 | 操作范围 | 说明 |
|------|----------|------|
| 租户管理员（super_admin） | 全部操作 | 可增删改任意角色及权限 |
| 系统管理员（sys_admin） | 全部操作（不含修改管理员角色） | 由租户管理员授权 |

### 1.3 入口路径

顶部导航 → 系统管理 → 角色管理
路由：`/system/roles`

## 2. 数据字段定义

### 2.1 角色表（role）

| 字段名 | 字段标识 | 类型 | 必填 | 说明 |
|--------|----------|------|------|------|
| 角色ID | id | BIGINT | 是 | 主键，系统自动生成 |
| 租户ID | tenant_id | BIGINT | 是 | 所属租户，多租户隔离 |
| 角色名称 | role_name | VARCHAR(64) | 是 | 租户内唯一，最长64字符 |
| 角色编码 | role_code | VARCHAR(64) | 是 | 系统生成，格式：ROLE_{大写字母}，全局唯一 |
| 数据权限范围 | data_scope | TINYINT | 是 | 1-全部数据 2-自定义部门 3-仅本人数据，默认3 |
| 自定义部门IDs | scope_dept_ids | VARCHAR(1024) | 否 | data_scope=2时填写，逗号分隔的部门ID |
| 备注 | remark | VARCHAR(256) | 否 | 角色用途说明 |
| 状态 | status | TINYINT | 是 | 1-启用 0-禁用，默认1 |
| 是否系统内置 | is_system | TINYINT | 是 | 1-系统内置不可删除 0-自定义 |
| 创建人 | created_by | BIGINT | 是 | 操作人 user_id |
| 创建时间 | created_at | DATETIME | 是 | UTC时间 |
| 更新时间 | updated_at | DATETIME | 是 | UTC时间 |
| 删除时间 | deleted_at | DATETIME | 否 | 软删除标记，NULL表示未删除 |

### 2.2 角色-资源关联（role_resource）

| 字段名 | 字段标识 | 类型 | 必填 | 说明 |
|--------|----------|------|------|------|
| ID | id | BIGINT | 是 | 主键 |
| 角色ID | role_id | BIGINT | 是 | 关联 role |
| 资源ID | resource_id | BIGINT | 是 | 关联 resource |
| 创建时间 | created_at | DATETIME | 是 | UTC时间 |

### 2.3 新增/编辑角色表单字段

| 字段名 | 字段标识 | 控件类型 | 必填 | 说明 |
|--------|----------|----------|------|------|
| 角色名称 | role_name | Input | 是 | 2-64字符，租户内唯一 |
| 角色编码 | role_code | Input（只读） | 是 | 系统自动生成，不可修改 |
| 数据权限范围 | data_scope | RadioGroup | 是 | 三选一，默认仅本人数据 |
| 自定义部门 | scope_dept_ids | TreeSelect（多选） | 条件必填 | data_scope=2时展示并必填 |
| 备注 | remark | Textarea | 否 | 最长256字符 |
| 状态 | status | Switch | 是 | 默认启用 |

**搜索栏：**
- 角色名称：Input，模糊匹配（LIKE）

- 状态：Select，选项：全部 / 启用 / 禁用

**表格列说明：**
- 角色名称：点击打开分配权限抽屉（P-ROL-04）

**特殊显示规则：**

**校验规则：**

### 5.3 P-ROL-03 编辑角色抽屉

**标题：** "编辑角色 - {role_name}"

布局与新增一致，差异：
- 角色编码只读展示已有值（不可修改）
- 表单回填当前角色数据
- 系统内置角色（is_system=1）：角色名称仍可修改，其余字段同常规

**提交逻辑（PUT /api/system/roles/{id}）：**
1. 更新 role 基础字段
2. 若 data_scope 从非2改为2，或修改了 scope_dept_ids，一并更新
3. 清除该角色权限缓存
4. 显示"角色信息已更新"

**交互逻辑：**
- 打开时调用 `GET /api/system/resources/tree` 获取全量资源树，同时调用 `GET /api/system/roles/{id}/resources` 获取当前角色已有权限，回显勾选状态
- 勾选父节点（目录/菜单）：联动全选子节点
- 取消父节点：联动取消全部子节点
- 子节点部分选中：父节点显示 indeterminate（半选）状态
- 搜索过滤：仅显示匹配的节点及其父节点路径，关键字高亮
- 底部实时统计已选节点数量

**保存逻辑（PUT /api/system/roles/{id}/resources）：**
- 请求体：`{ "resource_ids": [1, 2, 3, ...] }`
- 后端全量替换 role_resource（DELETE旧关联 + INSERT新关联，同一事务）
- 清除 Redis 中该角色的权限缓存（Key: `role:perm:{role_id}`）
- 成功提示："权限保存成功，修改已实时生效"

**情况A：角色已关联用户，不可删除**

```
+--------------------------------------------+

+--------------------------------------------+
| 角色「销售员」已分配给 25 名用户：          |
|                                            |

|                                            |
| 请先在用户管理中移除这些用户的该角色，      |
| 再执行删除操作。                           |
+--------------------------------------------+
|                              [我知道了]    |
+--------------------------------------------+
```

**情况B：角色无关联用户，可删除**

```
+--------------------------------------------+
| 确认删除角色                               |
+--------------------------------------------+
| 确认删除角色「报价员」？                    |
|                                            |
| ! 此操作不可恢复，该角色配置的所有菜单      |
|   权限将同时清除。                         |
+--------------------------------------------+
|                    [取消]  [确认删除]      |
+--------------------------------------------+
```

**删除逻辑（DELETE /api/system/roles/{id}）：**
1. 后端查询 account_role 是否存在该 role_id 的记录
2. 存在则返回400，携带关联用户信息，前端展示情况A弹窗
3. 不存在则执行：软删除 role（设置 deleted_at）+ 物理删除 role_resource 关联记录
4. 清除权限缓存，列表刷新，显示"角色已删除"

### 5.6 P-ROL-06 禁用/启用确认弹窗

**禁用：**
- 内容：确认禁用角色「{role_name}」？禁用后，已分配该角色的用户将失去此角色的所有菜单权限，下次请求时生效。
- 操作按钮：[取消] [确认禁用]（红色）

**启用：**
- 内容：确认启用角色「{role_name}」？启用后，已分配该角色的用户将恢复此角色权限。
- 操作按钮：[取消] [确认启用]（蓝色）

**提交逻辑：**
- 禁用：`PUT /api/system/roles/{id}/disable`，更新 status=0，清除权限缓存
- 启用：`PUT /api/system/roles/{id}/enable`，更新 status=1，清除权限缓存

## 6. 异常与边界处理

| 场景 | 处理方式 | 用户提示 |
|------|----------|----------|
| 角色名称租户内重复 | blur实时校验 + 提交时后端再次校验 | "该角色名称已存在，请更换" |
| 删除有关联用户的角色 | 后端返回400，前端展示情况A弹窗 | 显示关联用户列表，确认按钮不可点击 |
| 删除系统内置角色 | 前端置灰删除按钮 | hover提示"系统内置角色不可删除" |
| 分配权限时资源树为空 | 检查资源表 | "暂无可分配的菜单资源，请先在菜单管理中配置" |
| 选择自定义部门但未选部门 | 前端必填校验 | "请至少选择一个自定义部门" |
| 权限保存含无效资源ID | 后端过滤无效ID并提示 | "部分资源不存在，已忽略，其余权限已保存" |
| 并发修改同一角色权限 | 最后写入覆盖，操作日志记录双方变更 | "权限已被其他管理员修改，请刷新确认" |
| 禁用角色时有X名关联用户 | 允许操作，弹窗提示影响范围 | "该角色已分配给 X 名用户，禁用后其权限将受影响" |
| 接口超时 | 按钮恢复可点击，显示错误 | "操作超时，请重试" |
| 权限缓存清除失败 | 记录告警日志，不阻断主流程（缓存TTL到期自动失效） | 对用户透明，后台记录 |

## 7. 默认假设

1. 角色编码由后端系统自动生成，管理员不可手动修改。
2. 系统内置角色（is_system=1）不可删除，但可编辑名称、备注和权限。
3. 禁用角色后，权限鉴权在下次请求时生效（非实时踢出当前 Session）。
4. 权限缓存存储于 Redis，Key 格式：`role:perm:{role_id}`，TTL 30分钟，保存时主动清除。
5. 分配权限的资源树只展示**状态为启用**的资源节点。
6. 用户同时拥有多个角色时，菜单权限取所有角色权限的并集。
7. 数据权限（data_scope）与菜单权限独立管理，由查询业务层实现数据过滤。
8. 角色列表按 is_system DESC, created_at DESC 排序，内置角色始终置顶。
9. role_resource 关联表在角色删除时物理删除，角色权限变更时全量替换。
10. 权限相关变更全部写入审计日志（audit_log），记录操作人、时间、变更内容快照，保留180天。

# 业务边界与接口契约补查

基线：`09da3dc3c790c8c1b729cad8d195a66944d7546e`，分支 `docs/erp-audit`。本轮对照原 54 项台账补查实际表单 → 请求 DTO → Service → Mapper/更新 SQL；以下两项为新增问题，不重复 BUS-003～010 或 UI-012。两项均须请求交错才触发，暂定 **P2**。

## BUS-011 · P2 · 报销提交未与费用来源互斥，可将刚作废的费用纳入待付款报销单

**状态：确认静态调用链；已通过真实 Java Service 的内存交错契约验证。未作真实 MySQL 并发或付款实测。**

- **触发条件 → 实际 / 期望：** 员工提交一笔有凭证的垫付费用；提交请求已读取待报销金额、尚未插入报销明细时，另一个有权操作的请求作废这张费用单并提交。随后报销提交仍成功，将已作废的费用及旧金额快照写入「待付款」报销单。期望提交与来源作废/金额变更使用同一互斥边界；来源失效时提交失败，或报销先成功时来源作废被拒绝。
- **页面与 API 可达性：** [报销页提交](../../zhul-erp-frontend/src/pages/finance/reimbursements/index.tsx#L227) 只传 `sourceType/sourceId`；[Controller.submit](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/controller/ReimbursementController.java#L76) 进入真实提交方法。用户没有传入/伪造旧金额；旧金额由后端本次读取产生。
- **证据链：** [collect 的费用查询](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/ReimbursementService.java#L183) 筛选有效、本人垫付费用，但使用普通 `selectList`；[submit](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/ReimbursementService.java#L280) 在 L283 形成 `pending` 快照，在 L301 汇总快照金额，L317/L330 插入报销单和来源明细，期间没有锁定或重新检查费用来源。[voidExpense](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/ExpenseService.java#L156) 虽通过 [lock](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/ExpenseService.java#L420) 对费用 `FOR UPDATE`，但 [locked/activeLine](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/ExpenseService.java#L244) 只在作废时查询是否已有有效报销明细；此时提交端尚未插入，故允许作废。
- **现有保护为何不足：** 两端显式使用 `READ_COMMITTED`；费用行锁不阻止另一事务的普通快照读，提交端也不获取该行锁。[明细表唯一键](../../zhul-erp-backend/src/main/resources/db/migration/V1.2.59__reimbursement_expense.sql#L36) 仅防止同来源同时进入多个有效报销单，不能约束来源仍有效；该表未建立来源外键。[pay](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/ReimbursementService.java#L380) 检查报销单待付款状态，按其 `totalAmount` 生成付款（L419），未重新验证费用来源。普通顺序操作已有保护：费用先作废再发起新的提交，会被拒绝；本项仅针对两请求交错。
- **业务影响：** 已从费用账取消的金额仍进入财务待付款队列，费用账与报销负债口径不一致，可能导致按无效来源报销。未实测财务登记已付或真实转账，不能将内存探针写为已发生资金损失；本轮仅对费用单来源确认，不将其他四类来源一并宣称复现。
- **修复方向：** 提交时按稳定顺序锁定所选来源行，再校验有效性、金额、垫付人与凭证，并在同一事务插入报销明细；所有来源修改/作废采用相同锁协议。保留现有防重复来源唯一键。不要仅在当前普通读之后再追加一次无锁查询。
- **验收方法：** 两个独立事务设置屏障：A 读取有效费用 100 元后暂停，B 作废并提交，A 继续提交；必须有一方被拒绝，不能同时得到已作废费用与有效报销明细。反向顺序亦须成立；另测改金额、撤回后重提、重复提交以及五类来源各自的锁顺序。
- **本轮实测：** 真实 `ReimbursementService.pending()/submit()` 先读取有效费用 100 元；在获取报销编号的确定性暂停点执行真实 `ExpenseService.voidExpense()`，内存存储状态变为 `FE_VOID`；恢复后仍插入 `amount=100.00/releaseSeq=0` 的有效报销明细。随后重新提交同一已作废来源，既有校验正确拒绝。SQL 查询与事务提交由内存 mapper 模拟，未连接数据库。

## BUS-012 · P2 · 其他收入编辑与作废交错，旧编辑实体可把已作废记录恢复有效

**状态：确认静态调用链；已通过真实 Java Service 交错契约及实际 MyBatis SQL 生成验证。未作真实 MySQL 并发实测。**

- **触发条件 → 实际 / 期望：** 两个有编辑权限的财务请求处理同一有效收入。A 的编辑请求已读取有效记录，尚未执行更新；B 将收入作废并提交；A 继续保存。实际 A 把旧实体的 `status=VALID`、空 `voidReason` 连同新金额写回，收入重新有效且作废原因消失。期望作废后的编辑被拒绝，或通过同一行锁串行执行；普通编辑不能隐式恢复收入。
- **页面与 API 可达性：** [其他收入页](../../zhul-erp-frontend/src/pages/finance/other-incomes/index.tsx#L319) 为有效记录提供修改、作废；[保存表单](../../zhul-erp-frontend/src/pages/finance/other-incomes/index.tsx#L87) 只发日期、类别、金额、说明、附件和事业部，没有要求用户提交 `status`。[Controller](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/controller/OtherIncomeController.java#L57) 分别进入 update/voidIncome，均为正常编辑权限路径。
- **证据链：** [update](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/OtherIncomeService.java#L66) 先 `require(id)`、检查内存状态，再 `mapper.updateById(x)`；[voidIncome](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/OtherIncomeService.java#L86) 也先普通读取，置 VOID 后 `updateById(x)`。[require](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/OtherIncomeService.java#L140) 使用无锁 `selectById`；[实体](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/entity/OtherIncomeDO.java#L17) 无版本字段，状态和作废原因均随非空实体更新；[Mapper](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/repository/OtherIncomeMapper.java#L8) 直接继承 BaseMapper，无状态条件更新；[MyBatis 配置](../../zhul-erp-backend/src/main/java/com/zhul/erp/framework/config/MybatisPlusConfig.java#L16) 没有乐观锁拦截器。
- **实际 SQL 核验：** 使用项目当前 MyBatis 依赖注册真实 `OtherIncomeMapper`，不建立数据库连接；给最小旧实体 `id/status/voidReason` 生成的 BoundSql 为：

  ```sql
  UPDATE fin_other_income
  SET status=?, void_reason=?, update_time=?, update_by=?
  WHERE id=?
  ```

  `WHERE` 只有主键，没有「仍有效」或版本条件；实际完整旧实体还会写入金额等字段。两端虽有 `@Transactional`，默认隔离级别并不会把普通 `SELECT` 变为 `FOR UPDATE`；在常见 READ_COMMITTED/REPEATABLE_READ 下，B 可在 A 普通读取后、A 更新前完成作废。这里不把事务注解误当作防丢失更新。
- **业务影响：** 已作废收入无显式恢复操作即重新进入有效收入与按月经营统计，作废原因被清空，操作日志仍留有作废事件，形成账面状态与审计记录不一致。金额 100→120 的用例是内存验证，不代表实际经营报表已运行或资金已到账。
- **修复方向：** 编辑和作废统一获取同一收入行锁后校验状态；或采用带旧状态/版本条件的更新，检查影响行数并返回冲突。普通编辑仅更新允许编辑的业务字段，不把读取时的状态和作废原因无条件写回。
- **验收方法：** A 读有效记录后暂停，B 作废并提交，A 保存；最终必须仍作废或 A 返回冲突。反向时序、两次作废及修改金额同时作废均须验证；确保有效收入合计不重新纳入已作废记录。顺序测试「已作废后再开始编辑」也应保持拒绝。
- **本轮实测：** 真实 update 读有效金额 100，拦截其 mapper 更新前执行真实 voidIncome；内存状态先变 VOID，再被旧编辑写回 VALID，`voidReason=""`、金额 120。负对照先将记录置 VOID 再开始 update，既有状态校验正确拒绝。SQL 生成测试另行确认 `updateById` 的无条件状态写入，未执行 SQL。

## 本轮验证与复核边界

临时 `AuditBoundaryInterleavingTest` 共 **3 个 JUnit 用例，3 成功、0 失败、0 错误、0 跳过**：两个 Service 交错用例（各含顺序拒绝负对照）及一个实际 Mapper SQL 生成用例。执行入口为离线 Maven 定向 `-Dtest=AuditBoundaryInterleavingTest -Djacoco.skip=true test`，临时 POM 将全部编译输出重定向至独立 `target/erp-audit-boundary-20261101`；未重跑前轮 1143 个现有用例。初次临时测试把字典 VO 写成 DO 导致测试源码编译失败，修正 fixture 后的最终三例全部通过；该编译错误不是产品问题。

测试执行当前源码的真实 Service 方法；mapper、编号、附件、字典和日志等依赖均为内存 mock，暂停点确定性模拟上述合法事务交错。未启动 Spring、事务代理、服务器、MySQL/Redis、Docker 或外部 SDK；没有真实付款、真实账号、凭据或业务数据。因此「交错业务逻辑可接受错误状态」已实测，而数据库连接隔离、锁等待与实际并发调度仍属源码推断，需要修复时以双真实事务补验。本轮已核查相关锁、事务注解、表约束和实际更新 SQL，没有声称这些 mock 用例等同数据库端到端复现。

## 排除项与未覆盖项

- **字段清空已有保护：** [客户](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/masterdata/entity/CustomerDO.java#L66) 的定金比例、账期、信用额度及 [供应商](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/masterdata/entity/SupplierDO.java#L39) 的注册资本、成立日期均有 ALWAYS 策略；表单空值、DTO、完整实体赋值链已核对，不再按通用 `updateById` 忽略 null 误报。费用和其他收入事业部清空另有显式 `set(..., null)`，见 [费用](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/ExpenseService.java#L143)、[收入](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/OtherIncomeService.java#L76)。
- **供应商软删除/批量删除：** 当前 [供应商 spec](../../openspec/specs/master-data/supplier/spec.md#L36) 明确允许软删除并保留历史询盘/报价引用，[批量删除](../../openspec/specs/master-data/supplier/spec.md#L166) 跳过已删除/不存在记录。旧 PRD 的一律引用阻止与当前规范不同，不能仅据旧文档将现行为列为缺陷；本轮未证明仍存在独立业务损害。
- **报销非并发保护：** [撤回](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/ReimbursementService.java#L341) 与付款锁定报销单；重复来源有唯一键；[撤销已付](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/ReimbursementService.java#L442) 的支付字段清空由 [实体 ALWAYS](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/entity/ReimbursementDO.java#L31) 支持，未认定为清空失败。现实现为「员工提交、财务登记已付」，不把未实现的多级审批当 BUG。
- **商机与运营：** 追读商机关闭/重开、首次进入有效阶段标记、报价触发和统计口径，以及资料/营销任务写入、发品任务生成/取消/恢复/发布保护；未取得足以新增问题的强证据。发品的页签可重叠、已生成任务在资料退回待核后保持，均有现行 spec 依据；不将它们当状态错误。本轮没有对这些模块完成全量组合或真实 UI 验证，也不据此保证无其他缺陷。

本轮临时测试源码、临时 POM、独立编译目录与日志已清理；保留既有 `target` 内容、原有测试源码（含 tracked AuditFill）、其他代理的临时资源及全部报告。产品源码未修改。

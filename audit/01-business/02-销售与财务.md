# 销售、退款与应付一致性审查

基线：`09da3dc3c790c8c1b729cad8d195a66944d7546e`。已增加隔离 MySQL/Redis 上的真实 Spring、MockMvc、JWT 和 SQL 验证；各项状态分别标注，详见 [隔离测试记录](../06-verification/01-后端隔离测试.md)。

## BUS-002 · P1 · 按订单读取退款绕过租户与订单数据范围

**状态：确认（静态调用链）；跨租户 API 请求尚未实测。**

- **触发条件 → 实际 / 期望：** 租户 A 中有销售订单菜单权限的用户调用 `GET /api/v1/finance/refunds/order/{soId}`，传租户 B 的订单 ID；接口直接返回 B 的有效退款信息。期望在读取退款前校验订单属于当前租户，并对仅有销售菜单权限的用户执行订单负责人数据范围校验。
- **证据链：** [Controller 的 VIEW 与 order 路由](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/controller/CustomerRefundController.java#L30) 允许退款菜单 **或** 销售订单菜单；[ofOrder](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/CustomerRefundService.java#L150) 只按 `so_id/status/deleted_at` 查询，没有调用 `requireOrder`。`toVos` 继续按这些记录关联订单、客户并输出退款金额、汇率、人民币金额、原因、日期、备注等。[MyBatis 配置](../../zhul-erp-backend/src/main/java/com/zhul/erp/framework/config/MybatisPlusConfig.java#L16) 仅配置分页，无自动租户过滤来补救此查询。
- **业务影响：** 普通销售角色可以越权枚举同租户其他负责人的退款，也可读取其他租户的退款财务信息；主键不需要由当前用户先获得详情授权。
- **边界：** [附件 owned 查询](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/attachment/service/AttachmentService.java#L367) 有当前租户过滤。因此本项确认财务字段泄露，不声称可下载其他租户附件。
- **修复方向：** 查询显式限定当前租户；销售侧入口先校验订单可见性，财务侧按既定财务授权读取。避免仅因有菜单就放开任意订单 ID。
- **验收方法：** 两个租户分别建有效退款；A 的普通销售调用 B 的订单退款必须拒绝/不可见。再以 A 内不同 owner 的订单测试 SELF/部门范围；财务授权用户应仍能按合法范围查看。

## BUS-003 · P1 · PI 取消重转订单后已退款不占用新订单额度

**状态：已复现（隔离 MySQL、真实 Spring/MockMvc/JWT/SQL）。**

- **触发条件 → 实际 / 期望：** PI 到账 USD 100，转 SO-A；在尚未完成的 SO-A 登记退款 USD 60；取消 SO-A 后用同一 PI 再转 SO-B。SO-B 可退额度再次变为 USD 100，可登记累计 USD 160 的退款。期望同一笔到账跨订单版本共享剩余额度，本例只剩 USD 40。
- **证据链：** [退款额度计算](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/CustomerRefundService.java#L167) 对 PI 订单取 `pi.received_amount`，却只扣 `so_id = 当前订单` 的有效退款；[登记退款](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/CustomerRefundService.java#L75) 据此校验并写单。[取消销售订单](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/sales/service/impl/SalesOrderServiceImpl.java#L459) 只禁止已取消和已完成订单，无收款/退款阻止条件，并在 L489 将 PI 恢复 SENT；采购需求的 [取消处理](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/purchase/support/RequirementLifecycle.java#L281) 只关闭草稿需求/标记已下单需求，不拒绝取消。随后 [convert](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/sales/service/impl/SalesOrderServiceImpl.java#L132) 在无有效订单时新建 SO，沿用该 PI ID；旧退款仍留在 SO-A。
- **业务影响：** 重复退款上限可超过真实到账，且新 SO 的成本利润不扣旧 SO 的退款。无需并发即可触发；对外付款虽仍需人工执行，但系统校验会错误放行。
- **修复方向：** 把可退余额绑定到稳定的收款归属（PI/到账记录），覆盖取消前后全部关联订单；明确退款历史在订单重转后的成本与经营统计归属。在同一额度锁下检查并写退款。
- **验收方法：** 按上述 100/60 场景真实走取消和重转，断言 SO-B 可退 40，退 40 成功、再退 0.01 拒绝；检查退款清单与利润。另覆盖手动订单、退款作废、取消后直接登记退款规则。
- **已有测试边界：** [OperatingReportContractTest](../../zhul-erp-backend/src/test/java/com/zhul/erp/modules/finance/OperatingReportContractTest.java#L94) 测了同一 SO 的超额退款与取消订单拒绝退款，未覆盖同 PI 重转后余额。
- **2026-11-01 实测：** 原 PI 到账 100；SO-A 退 60；取消并重转 SO-B 后接口返回可退 100，再退 100 成功。直接查询两订单有效退款合计 160。临时审计探针断言的是错误行为确实存在，不表示业务规则通过。

## BUS-004 · P1 · 已生成应付的采购订单换币后，应付保留旧币种

**状态：已复现（隔离 MySQL、真实 Spring/MockMvc/JWT/SQL）。**

- **触发条件 → 实际 / 期望：** 已确认采购订单为 CNY 100（应付已生成），编辑币种为 USD、金额仍为 100。采购订单变为 USD 100，但原应付仍标 CNY 100，同时其汇率/人民币额按新 USD 汇率重算。期望无付款时原币字段一致更新，有付款/抵扣/退款后禁止直接改币种或走受控调整。
- **证据链：** [采购订单 save](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/purchase/service/impl/PurchaseOrderServiceImpl.java#L519) 接受已下单单据，L530–535 更新币种与汇率，L636 同步应付；[应付同步](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/PayableSyncService.java#L67) 仅新建应付时传币种，已有应付只更新汇率（L91），未更新 `currencyCode`；`apply` 按新汇率重算人民币金额。这里也未阻止已有付款后改币。[前端币种选择](../../zhul-erp-frontend/src/pages/purchase/orders/detail.tsx#L775) 在编辑表单未按已下单/已付款禁用；不是只能伪造请求的不可达分支。
- **业务影响：** 采购订单、应付与付款核销对同一数字使用不同币种；列表可能把旧币付款当成新币付款，未付款也会向财务显示错误币种。已付金额被不经换算地继续用于新金额比较，导致少付/误结清风险。
- **修复方向：** 对已发生资金往来的单据锁定币种；未发生资金往来时，原币、汇率、本位币与应付计划整体一致更新。不要只补一行 `setCurrencyCode` 后继续把历史实付款当新币。
- **验收方法：** 先确认未付款 CNY 单后换 USD，检查 PO/AP 三金额一致；分别有部分付款、欠款抵扣、退款时再换币必须按确定规则拒绝或调整，历史付款币种与金额不被改写。
- **2026-11-01 实测：** 真实采购订单确认后编辑为 USD 100；PO 响应为 USD，但同来源应付 SQL 查询仍为 CNY 100，`amount_cny=715`、汇率 7.15，证实同一应付原币与本位币口径冲突。

## BUS-008 · P1 · 作废部分结汇后恢复了旧已结汇额，分摊与到账余额不一致

**状态：已复现（隔离 MySQL、真实 Spring/MockMvc/JWT/SQL）；本轮深审新增。**

- **触发条件 → 实际 / 期望：** 未认领 USD 100 到账，结汇 USD 50 / CNY 350，再作废这张唯一结汇单。有效结汇分摊已为 0，但到账 `settled_amount` 仍为 50；期望归零，恢复待结汇余额 100。
- **证据链：** [voidSettlement](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/FxSettlementService.java#L190) 先在内存中从已锁到账扣减 settled amount，软删分摊，尚未保存到账；L207–209 将这些对象加入 `LinkedHashSet`，又加入 `lockOpen` 查出的数据库旧版本对象。部分结汇的到账仍在 OPEN 查询中。[PaymentReceiptDO](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/sales/entity/PaymentReceiptDO.java#L17) 使用 Lombok `@Data`，全字段 equals/hashCode 使同 ID、金额不同的新旧对象同时入集合；[refresh](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/FxSettlementService.java#L239) 逐对象更新同一 ID，后写的旧对象覆盖了已扣减数值。
- **实测结果：** MockMvc 创建未认领到账 100、结汇 50、作废成功；SQL 断言同 receipt 的有效 allocation 行数为 **0**，但 settled amount 为 **50**。同一临时探针两轮执行均命中。
- **业务影响：** 原结汇已作废但仍占用待结汇额度，已结汇状态与有效分摊不一致；到账人民币重算使用错误剩余额度，利润和经营统计的收入换算也可能受影响。后续到账作废仍可能被“已结汇”阻止。
- **修复方向：** 按主键去重合并到账集合，并保留内存中已扣减的权威版本，或在统一行锁下从有效分摊重算 settled amount；避免用全字段集合对实体做主键去重。
- **验收方法：** 覆盖单笔部分结汇作废、多个结汇只作废最新、整笔结清后作废和包含其他 OPEN 到账的池子；始终断言 `receipt.settled_amount = 有效 allocations.amount 合计`，待结汇余额与人民币金额守恒。现有 [FxSettlementContractTest](../../zhul-erp-backend/src/test/java/com/zhul/erp/modules/finance/FxSettlementContractTest.java#L117) 作废场景的被撤销到账此前已全部结清，未覆盖本项部分结汇。

## BUS-009 · P1 · 欠款已抵扣另一应付后，作废原付款仍保留目标“已付”

**状态：已复现（隔离 MySQL、真实 Spring/MockMvc/JWT/SQL）；本轮资金依赖链深审新增。**

- **触发条件 → 实际 / 期望：** 原采购应付100先付款100，取消采购形成供应商欠款100；用该欠款全额抵扣同供应商另一采购应付100。随后作废最初的付款，接口允许。期望先撤销依赖该欠款的后继抵扣，或在同一受控事务中正确冲回依赖链，不能凭空保留已付金额。
- **证据链：** [付款作废](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/PaymentService.java#L326) 锁原付款涉及的应付，并检查作废/报销状态，但未检查由这笔付款形成的欠款是否已被其他有效付款抵扣；它只软删原付款自己的 allocations 并刷新该批应付。后继抵扣的 [allocation](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/PaymentService.java#L196) 仍保留 `fromCredit=1/creditPayableId`；[totals](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/finance/service/PayableSyncService.java#L222) 继续给目标加已付、给来源减已付。
- **实测结果：** 完整走付款100→采购取消→欠款抵扣100→原付款作废；SQL 得来源应付 `paid_amount=-100`，目标应付 `paid_amount=100/status=PAID`。当前有效实际付款已为0，目标应付仍可被当作结清。
- **业务影响：** 资金与核销不守恒，目标采购可能少付而系统显示结清；来源出现负已付，使后续退款/抵扣与经营核算难以解释。单纯给来源 `max(0)` 会掩盖丢失的资金来源，不能修复目标核销。
- **修复方向：** 作废前按 `creditPayableId` 找到有效后继抵扣，明确先后撤销顺序，锁定完整依赖集合；拒绝带有效依赖的直接作废，或提供有审计记录的联动冲回。供应商退款等消耗该欠款的后继单据也需同样验证。
- **验收方法：** 本例原付款作废必须拒绝或连带冲回目标；先撤销抵扣再撤销原付款可成功。另覆盖部分抵扣、多个目标、同源退款、抵扣单作废和并发原付款作废/抵扣，断言每张应付已付及所有有效现金/抵扣来源守恒。

## 覆盖范围与验证限制

检查 PI 转订单/取消、手动订单、到账登记/认领/作废、客户退款、付款登记/供应商退款/作废、应付同步、结汇分摊与作废、费用/报销的主要锁与状态约束、订单成本归集。资金并发主要沿实际行锁链检查；付款按应付 ID 排序加锁、结汇与到账作废对到账行互斥等现有保护不记作缺陷。

只对上述有具体证据的问题作结论；未审完每个报表组合和每种报销来源，不对财务总账、会计凭证锁定、税务申报或规划中的信用证模块宣称覆盖。这些上下文规划不能当成“已实现但缺功能”的 BUG。

第一阶段的 Python 内存检查仅验证公式。深化阶段已在专用 MySQL/Redis 跑真实业务复现及收款、结汇、应付、仓储和报表契约，隔离、测试计数和未覆盖范围见 [验证记录](../06-verification/01-后端隔离测试.md)；不能将某个正常契约通过推广为模块没有其他缺陷。

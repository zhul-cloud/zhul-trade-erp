# AI 任务可靠性与运行诊断

基线：`09da3dc3c790c8c1b729cad8d195a66944d7546e`，分支 `docs/erp-audit`。本轮只读核验生产实现并执行无网络、无数据库、无 CLI 的内存 mock；不修改产品，不留测试脚本或运行产物。

## AI-001 · P1 · 受理、回调与超时扫描无条件更新，终态可回退且与询盘状态分叉

**状态：确认（静态调用链）；更新语义内存模拟通过，未运行 Java / SQL 并发复现。**

- **触发条件 → 实际 / 期望：** 存在以下合法线程交错：①成功回调先落库，异步 202 受理结果随后被 Java 处理，任务从 COMPLETED 被改回 PROCESSING；②超时扫描先查到处理中任务，成功回调落库，再由扫描按旧快照把任务写为 FAILED；③扫描先将任务及询盘置失败，晚到成功回调又把任务写为 COMPLETED，但询盘已非 PARSING，仍保留解析失败。期望状态更新遵循统一终态/迟到结果策略，任务与业务记录不矛盾。
- **证据链：** [doSubmit](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiTaskServiceImpl.java#L106) 接到 accepted 后无条件调用 `markStatus(PROCESSING)`；[handleCallback](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiTaskServiceImpl.java#L131) 只检查任务存在/未删除，不检查旧状态，随后写终态并分发；[markStatus](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiTaskServiceImpl.java#L157) 最终仅 `updateById`，无旧状态条件。[超时扫描](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiTaskTimeoutWatchdog.java#L41) 在 SELECT 中过滤 QUEUED/PROCESSING，随后逐项 `updateById`，更新时不复核状态。[编排受理](../../scripts/ai-orchestrator/server.py#L712) 先发送 202 再启动处理，但并不保证 Java 的 future 受理处理一定早于另一个 HTTP 回调请求落库。
- **业务影响：** 通用任务可显示处理中/失败，而业务询盘已待确认；也可任务显示完成而询盘保持解析失败。晚到付费结果无法正常进入确认流程，用户可能手动重试并再次消耗额度。
- **反证与边界：** [询盘成功/失败处理](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/inquiry/customerinquiry/service/impl/CustomerInquiryServiceImpl.java#L700) 明确要求当前询盘为 PARSING；[追加解析](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/inquiry/customerinquiry/service/impl/CustomerInquiryServiceImpl.java#L997) 也只接受 APPEND_PARSING。因此不能据此声称“顺序重复回调必定重写已确认询盘”。上述保护反而使任务与业务终态可能分叉。已存在的 afterCommit 提交修复解决“任务尚未提交导致回调查不到”，不是本项仍存在的受理/回调终态竞争；[现有测试](../../zhul-erp-backend/src/test/java/com/zhul/erp/modules/aitask/service/AiTaskServiceImplTest.java#L114) 已覆盖该旧修复，不重复列为缺陷。
- **修复方向：** PROCESSING 只允许从 QUEUED 条件更新；超时转换需以未终结状态为更新条件，并仅在抢占成功后分发。回调制定明确的幂等与超时后补偿策略，使用同一状态机处理任务与业务副作用，不能靠再次无条件覆盖终态恢复。
- **验收方法：** 用可控 future 和 mapper 屏障模拟上述三种交错，断言终态不被 accepted 或旧扫描覆盖；相同成功回调重发不重复执行业务副作用；迟到成功是拒绝、人工接纳还是恢复需有确定结果，任务与询盘展示一致。

## AI-002 · P1 · 结果回调一次失败后被吞掉，已完成 AI 结果没有可靠投递路径

**状态：已用源函数内存 mock 复现；真实服务之间的投递故障未实测。**

- **触发条件 → 实际 / 期望：** 模型已返回结果，`send_callback` 投递时遇到一次瞬时连接失败、超时或 HTTP 错误。函数仅打印并返回，调用方结束；没有待投递队列、重试或持久化结果。期望重投同一结果，或至少提供可恢复的投递记录，避免要求重新执行模型。
- **证据链：** [send_callback](../../scripts/ai-orchestrator/server.py#L521) 只调用一次 `urlopen(timeout=10)`，捕获所有异常后只 print；[process_job](../../scripts/ai-orchestrator/server.py#L561) 在成功生成 output 后调用它并退出；任务在 [daemon 线程](../../scripts/ai-orchestrator/server.py#L725) 中处理。Java 的 [超时兜底](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiTaskTimeoutWatchdog.java#L41) 只会改失败并分发，无法取回已算出的 output，也不会重新投递结果。
- **内存验证：** 用 AST 仅提取生产 `send_callback`，注入 fake Request/urlopen，后者固定抛 `OSError`。断言：调用次数 **1**，异常被吞、返回值 **None**、记录一条失败日志；未执行真实 HTTP。调用方捕获不到异常，因此没有外层补偿重试。
- **业务影响：** 一次短暂回调失败即可使已花费时间/额度的解析或翻译结果失联，直到 watchdog 报超时；再次业务重试会重新调用模型，无法复用原结果。本项不是在建议自动重复执行付费任务。
- **修复方向：** 将结果投递与模型计算分离，保存可重试的结果/outbox，按有界退避重投同一 task ID；后端按任务和结果幂等接收。只增加内存重试仍不能解决进程重启后的丢失。
- **验收方法：** fake 回调前两次失败第三次成功，确认模型只计算一次、同一结果最终被接收一次；再模拟投递期间进程恢复，确认待投递结果仍可恢复。永久失败需可定位并重投，日志不包含凭据和完整敏感输入。

## AI-004 · P2 · 串行诊断的总超时预算超过 Java 的 30 秒请求期限

**状态：条件性时序确认；AST 源函数配模拟时钟验证通过，未检查真实登录状态或外部服务耗时。**

- **触发条件 → 实际 / 期望：** `/status` 的两个 CLI 检查各接近 20 秒，或 `/test` 的两个模型检查耗时合计超过 30 秒。Python 仍在按各项预算工作，Java 已先超时返回不可用。期望整次诊断在 HTTP 总预算内返回部分/完整结果，并区分超时与未登录。
- **证据链：** [QUICK_TIMEOUT_SECONDS](../../scripts/ai-orchestrator/server.py#L80) 为 20 秒；[/status](../../scripts/ai-orchestrator/server.py#L685) 调 `login_status(20)`；[login_status](../../scripts/ai-orchestrator/subscription.py#L133) 顺序执行 Codex、Claude 两次 `subprocess.run(timeout=timeout)`，每次失败后仍执行下一次。订阅模式 [/test](../../scripts/ai-orchestrator/server.py#L602) 也走两个 CLI，即使用户只测试其中一家。API 模式 [test_connection](../../scripts/ai-orchestrator/server.py#L610) 顺序查解析、翻译模型，每次 [_retrieve_model](../../scripts/ai-orchestrator/server.py#L588) 可用 20 秒。Java 的 [SYNC_TIMEOUT](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiOrchestratorClientImpl.java#L42) 为 30 秒，[/status](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiOrchestratorClientImpl.java#L118) 与 [post](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiOrchestratorClientImpl.java#L136) 都使用它。
- **内存验证：** AST 提取 `login_status`，fake subprocess 每次按参数增加模拟时钟并抛 TimeoutExpired，观察调用顺序 Codex→Claude、总预算 **40 秒**；再提取 `test_connection`，两个 fake `_retrieve_model` 各模拟 20 秒并报 APIError，仍完成两项，总计 **40 秒 > 30 秒**。实际等待为 0，没有启动 CLI、导入/调用 AI SDK 或发网络请求。API SDK 自身若有重试可能更久，本结论不依赖该假设。
- **业务影响：** 慢响应时设置页的测试和订阅可用性诊断误报不可用；非平台租户的 [resolveForCurrentTenant](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiConfigServiceImpl.java#L120) 依赖此登录状态，可能因此拒绝提交实际任务。
- **反证与边界：** Java [loginStatus](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiConfigServiceImpl.java#L262) 捕获服务错误返回 null，平台展示为 unknown，并非必定误写成 logged_out。本轮没有证据证明任何真实账号未登录；只有耗时条件成立才触发本项。
- **修复方向：** 给整次诊断设置统一 deadline，子检查使用剩余预算；需要时并行检查、仅测试所选订阅服务商，并保持 Python 总预算短于 Java 期限。返回分项超时原因，而非将诊断超时等同未登录。
- **验收方法：** 以可控延迟 fake 验证两项慢响应、首项超时、仅一家登录和选定服务商测试；端到端请求在统一总期限内给出准确的部分结果，非平台租户不会因无关 CLI 检查阻塞而错误拒绝。

## 本轮验证边界

第一阶段仅静态阅读现有 Java 单元测试及 Python 诊断/鉴权测试，没有把“已有测试文件”当成运行通过；当时未运行服务器或测试库。该阶段 Python mock 仅解析 AST 并编译选定函数，Java 状态流转仅按源赋值/条件提取语义模拟。AI-001 的 Java 并发至今仍未做真实 SQL 竞争复现，不能称为 Java 单元测试或数据库竞争已复现。整个审查未读取真实 `.env`、凭据或真实附件。

深化阶段补充：已在无网络缓存镜像中执行现有 Python 全套 **53/53 通过**（真实 Anthropic SDK MockTransport、图片/PDF、订阅进程与鉴权），并运行下述源函数 fake SDK 探针。Java 财务/仓储另已执行专用隔离库真实测试；各类证据不可混同，环境和计数见 [后端隔离测试](../06-verification/01-后端隔离测试.md)。

## AI-005 · P1 · Claude 续传按单请求计时，整任务可超过 watchdog 期限而继续运行

**状态：确认（生产 Python 函数配 fake SDK/模拟时钟实测）；未进行真实云调用或实际长等待。**

- **触发条件 → 实际 / 期望：** Claude 多轮返回 pause_turn，每轮耗时均未超过单请求 timeout，但累计超过 Java watchdog 的20分钟；Python 仍会继续续传并最终回调成功，期间 Java 已可能判失败并让用户重试。期望整任务有统一 deadline，或后端超时策略与有效运行租约一致，避免已判失败的任务继续计费工作。
- **证据链：** [TIMEOUT_SECONDS](../../scripts/ai-orchestrator/server.py#L76) 默认为900秒；[call_api](../../scripts/ai-orchestrator/server.py#L304) 的 API 路由进入 [_call_claude](../../scripts/ai-orchestrator/server.py#L317)，900秒传给 Anthropic client。L337 起循环 `range(MAX_CONTINUATIONS + 1)`，上限5次续传意味着最多6轮请求；每轮直接 `messages.stream/get_final_message`，没有整任务 elapsed/deadline 检查或接收 Java 取消信号。[Java watchdog](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/aitask/service/impl/AiTaskTimeoutWatchdog.java#L37) 默认20分钟，按任务 create_time 扫描并仅更改数据库/分发失败，不取消编排端运行。
- **安全实测：** 在 `--network none --read-only` 的审计容器中导入真实当前 server 模块，调用实际 `call_parse`，只将 Anthropic client 替换为 fake stream。前5轮 pause_turn，第6轮 end_turn 并返回合法解析JSON；每轮模拟250秒、单轮均小于900秒。结果：源函数成功返回，**6 × 250 = 1500秒 > watchdog默认1200秒**，调用次数6；实际网络、模型费用和 sleep 均为0。模拟时钟用于记录各轮时间，没有改动生产函数；不是说真实任务已运行1500秒。
- **业务影响：** 有条件出现已被后端判为失败的任务继续运行并晚到成功；结合 AI-001，询盘可保持失败而任务变完成。用户按失败提示重试会与仍运行的旧请求重叠，可能重复耗时/费用。网络队列、上传、SDK内部重试等可能加长总耗时，但本项成立不依赖它们。
- **反证与边界：** 订阅分支 [call_subscription](../../scripts/ai-orchestrator/server.py#L307) 确实把900秒传给工作进程超时机制；这里确认的是 API Claude 多轮续传缺少总期限，不能将结论无差别扩大成“所有订阅任务都无超时”。未模拟真实云端计费与 Java/Python同时运行1500秒的端到端场景。
- **修复方向：** 给任务设绝对 deadline，排队、附件下载、每轮SDK调用及续传使用剩余预算；需要续租时显式报告运行中，而非仅依据 create_time 判死。后端超时应能发取消/失效信号，回调统一处理取消后结果，避免无条件恢复已失败任务。
- **验收方法：** 用 fake clock覆盖单轮慢响应、5次续传、排队时间和期限边界；在总期限前可正常完成，超过期限不再发下一轮请求，失败/取消与业务状态一致。另测订阅分支维持现有进程终止语义，回调不重复触发业务。

## AI-007 · P2 · 个人订阅方式同时只能执行一个任务，其他任务立即失败

**状态：确认（2026-11-06 用户反馈；`test_subscription` 并发用例在修复前代码上复现）。**

- **触发条件 → 实际 / 期望：**
  - 一个订阅任务（如询盘解析）还没结束时，又提交了别的订阅任务，后提交的任务立即回调失败（「个人订阅正在处理其他任务，请稍后重试」），用户只能手动重试。
  - 多家公司获授权共用平台订阅后，这种情况更常见。
  - 期望与 API Key 方式一致：每个任务各自执行，不因别的任务在跑而失败。
- **证据链：** [`subscription.py`](../../scripts/ai-orchestrator/subscription.py) 原有进程内的 `threading.BoundedSemaphore(1)`；`call_subscription` 拿不到这个锁就直接报错。API 方式由 [`server.py`](../../scripts/ai-orchestrator/server.py) 为每个任务起一个线程，没有并发上限。规格 [model-providers](../../openspec/specs/ai-platform/model-providers/spec.md)「订阅任务隔离与完整结果」原写作「单实例串行执行」。
- **当初为何限制：**
  - [设计](../../openspec/changes/archive/2026-10-28-ai-subscription-modes/design.md)与[第二次设计](../../openspec/changes/archive/2026-10-29-ai-provider-profiles-and-subscription-access/design.md)只写「一次只执行一个订阅任务，忙碌即失败」「开放给多家公司后更容易遇到忙碌失败 → 维持现状」，没有给出技术上必须串行的理由，属于保守取舍。
  - 每个任务本来就使用独立的临时目录、进程组和隔离环境，不共享会话；官方 Codex / Claude Code CLI 也支持同一登录同时运行多个会话。
- **影响与取舍：** 去掉限制后，同时执行的任务越多，订阅额度消耗越快，容器内存也随 CLI 进程数增加。额度用完时任务按现有「订阅 CLI 调用失败」回调失败，不回退到 API。

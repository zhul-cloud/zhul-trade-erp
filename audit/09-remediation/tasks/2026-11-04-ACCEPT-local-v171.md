## 验收方式（用户 2026-11-04 确认）

用户提出在本地库验收，数据不够可用生产数据，敏感数据替换掉即可，并建议直接用现成的备份。

- **数据**：生产 2026-11-04 03:00 的自动备份，下载后核对 sha256，改库名导入为 `zhul_erp_accept`，导入后立即脱敏：删除登录令牌与旧邮箱备份表；所有登录密码改为本机测试密码（只存在已忽略的 `storage/test-accounts.md`）；客户、联系人、收发货方、供应商、收付款方、员工的姓名、邮箱、电话、地址、银行账号改为占位值；询价原文、AI 任务输出、操作日志内容清空；第三方 API Key 清空。
- **数据改动**：验收中新建了测试公司（租户 1001–1005）、测试角色、两条附件、一条退款记录，合并掉一个客户，并临时启停了几名用户与租户 1000。全部只在本机验收库内。被脚本误改的名称和状态已从备份核对后还原（角色 111 名称、字典项 1 名称、两名用户的状态）。
- **清理**：原始备份 `.sql.gz` 与改名后的 `.sql` 已删除；`v1.7.1` 工作树、临时前端代理配置 `config/config.local.ts`、端口转发与延迟代理、本机后端与前端进程均已停止或删除。只保留已脱敏的 `zhul_erp_accept` 库，便于复验。

**边界**：这是用生产版本和生产数据的脱敏副本做的验收，**不是在生产环境上验证**。按[整改流程「证据与验收边界」](../README.md#证据与验收边界)，隔离数据库与目标环境的证据不能相互替代。能否据此关闭，由用户作为验收人决定。

脚本逐项登录真实账号调用接口，并直接查库核对数据是否改变。临时脚本，不进仓库；持久回归仍以各任务记录里的契约测试为准。

**脚本自身的问题**（已改正，不算产品问题）：头两轮把用户状态 2 当成「禁用」，实际 2 是「已删除」，导致两名测试用户被删除（由此发现 SEC-012）；查库客户端未指定字符集，把一个角色名写成了「???」；SEC-010 一开始把「租户改平台字典项」当成应拒绝，但按[SEC-011 任务记录](2026-11-03-SEC-011-tenant-isolation.md)这是 PRD 允许、有意保留的行为，后改为不判。

### 新发现 SEC-012 的修复

`updateUserStatus` 只接受 0（停用）、1（启用），其他值抛出「用户状态只能是启用或停用」；`UserService` 新增常量 `STATUS_DISABLED = 0`。前端只传 0 或 1，不受影响。

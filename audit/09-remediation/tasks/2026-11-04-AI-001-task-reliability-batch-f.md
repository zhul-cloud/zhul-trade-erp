## 规则决定（用户 2026-11-04 确认）

- **迟到的结果**：任务已被后端超时扫描判为失败后，AI 的成功结果才到，直接丢弃。任务与询盘都保持失败，只记日志；用量照记。没有选「询盘未处理就采用」，因为那样解析、追加、翻译、背调等每类技能都要各自实现「失败后恢复」。
- **回调重投**：在内存里有限次重投（5、15、45 秒）。没有选「写入磁盘待投递」，因为那要给编排服务容器加数据卷，生产部署也要跟着调整。代价是：重投期间编排服务进程重启，结果会丢失，最后由后端超时扫描判失败。

- **回归**：
  - 后端：`*Ai*Test`、`*Inquiry*Test`、`BackgroundEntryTenantContractTest`、`TenantIsolationContractTest` 共 193 个用例，0 失败。旧单元测试从按 `updateById` 断言改为按条件更新断言。
  - 编排服务：全量 `python -m unittest` 84 个用例通过，3 个仅 Linux 运行的跳过。
- **不算缺陷见证的用例**：`test_recoverable_errors_retry_within_deadline` 在修复前也失败，但那是因为原来由 SDK 自己重试、假 SDK 不重试，不说明原来不重试。它只用来守住改为自己重试之后的行为。
- **本机已知问题，与本批无关**：`HttpTokenTest.test_missing_or_wrong_token_rejected` 在 Windows 本机修复前后都偶发「连接被中止」，5 次里约 1 次。CI 跑在 Linux 上。
- **已知取舍**：
  - 回调重投只在内存里。
  - 期限只管编排服务自己。后端超时扫描仍按 `create_time` 判定，不会通知编排服务取消，靠的是编排服务的期限（900 秒）比后端短（20 分钟）。这个前提已写进 README 和 `.env.example` 的说明。
  - `/status` 检查超时时仍按「未登录」返回给后端，后端的约定没改。

## UI-003｜P1｜我的询价切换任务直接丢失未保存回价

- **证据状态：静态确认。**
- **触发：**在任务 A 填写价格、店铺或备注，尚未点击“保存草稿/提交回价”，点击左侧任务 B，再返回 A；搜索结果排除 A、切换“已回价”等导致活动任务改变时同样可能发生。
- **实际：**任务按钮直接 `setActiveId(t.id)`；effect 立即加载 B，并用 `setState(next)` 替换整份录价状态。`dirtyRef` 仅避免列表刷新时覆盖同一任务详情，没有切任务确认或自动保存。A 的输入从未经过 save API，返回后无法恢复。
- **期望：**未保存时提示保存/放弃/取消切换，或明确自动保存草稿；跨任务保留草稿也须按任务隔离。
- **证据：**[任务切换](../../zhul-erp-frontend/src/pages/inquiry/my-tasks/index.tsx#L738)、[详情重建并替换编辑状态](../../zhul-erp-frontend/src/pages/inquiry/my-tasks/index.tsx#L225)、[dirtyRef 仅保护同任务刷新](../../zhul-erp-frontend/src/pages/inquiry/my-tasks/index.tsx#L279)、[真正的保存请求](../../zhul-erp-frontend/src/pages/inquiry/my-tasks/index.tsx#L388)。没有将“已自动保存到后端”的状态误判为丢值。
- **影响：**采购员/兼职采购多任务并行询价，供应商原话、金额和附件关联等录入可能丢失。
- **建议：**所有改变活动任务的入口走统一离开守卫，保存成功后再切换；处理列表刷新、搜索、待处理/已回价切换和站内离开。
- **验收：**A 修改价格/备注后点 B、搜索及切页签均可取消离开；选保存后返回 A 保持；保存失败时不能静默离开；选择放弃仅影响 A，不误提交到 B。

## UI-004｜P2｜报价单和 PI 的未保存保护遗漏站内导航

- **证据状态：静态确认 + PI与报价两分支均经根代理BrowserOS真实SPA导航/隔离后端复现。**
- **触发：**在可编辑报价单或 PI 中修改价格、数量、折扣、条款，未保存时点击侧边栏菜单或其他站内 `Link`；之后返回原单。
- **实际：**两页根据 dirty 注册 `beforeunload`，只覆盖关闭/刷新/整页跳转。应用外壳菜单用 Umi `Link`，SPA 导航不会卸载浏览器文档，因而不会触发该事件。组件卸载后输入丢失。
- **期望：**浏览器离开和 SPA 站内导航都受同一 dirty 守卫保护，取消后保留编辑状态。
- **证据：**[报价单 dirty 与 beforeunload](../../zhul-erp-frontend/src/pages/quotation/detail.tsx#L430)、[PI 同类逻辑](../../zhul-erp-frontend/src/pages/sales/pi/detail.tsx#L440)、[外壳菜单 Link](../../zhul-erp-frontend/src/app.tsx#L180)。现有[商品详情 history.block](../../zhul-erp-frontend/src/pages/product/products/detail.tsx#L323)说明项目已有站内拦截实践，可作为适配参考，不能直接据此断言所有页面都已受保护。
- **真实浏览器追加：**根代理分别在隔离PI草稿和报价草稿填写专用审查备注，两页均明确出现“有未保存的修改”、保存按钮可用；点击真实侧栏“工作台”直接进入dashboard，没有确认。再打开各自原单据，备注为空、页面显示已保存且保存按钮disabled。两个分支分别完成，不以同类源码推断替代实测；完整过程由根代理浏览器专项记录。
- **影响：**报价与 PI 草稿/修订版本的未保存业务值。不是已发送单据被后端修改，也不是后端持久化丢失。
- **建议：**复用统一未保存守卫；实际保存成功、显式放弃、跳到同单版本等分别定义解除条件，避免保存后仍重复阻挡。
- **验收：**菜单、面包屑、浏览器后退/前进、版本切换、刷新/关页均覆盖；取消导航保持值；保存后导航不提示；失败保存仍保持 dirty。

## UI-012｜P1｜角色列表启停重置数据权限并清空自定义部门

- **证据状态：前端真实 React 组件实测 + 后端代理报告的真实 MockMvc/SQL 隔离实测；源码交叉确认。**
- **触发：**已有角色的数据范围为全部、仅本人或自定义部门，在角色列表点击“禁用/启用”，没有进入编辑数据权限。
- **实际：**`handleToggleStatus` 只发送 `{name,status}`；后端 `SaveRoleRequest.permissionScope` 缺省为 0，更新接口把它当显式值保存；随后无条件调用 `assignRoleDepts`，后者先删除角色部门关联，再因 `deptIds=null` 返回。角色启停同时改坏数据权限，之后再次启用不会恢复。
- **期望：**状态更新只修改状态；未传的数据范围和自定义部门保持不变。对完整保存与局部更新应明确契约，不让 DTO 默认值覆盖既有配置。
- **证据：**[前端启停载荷](../../zhul-erp-frontend/src/pages/system/role/index.tsx#L270)、[service 使用同一个 PUT](../../zhul-erp-frontend/src/pages/system/role/service.ts#L80)、[请求默认值](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/dto/SaveRoleRequest.java#L13)、[后端更新和删除关联](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/RoleServiceImpl.java#L140)。后端代理在独立 schema 用真实请求与 SQL 验证：原 scope=2、role_org=1 行，发送仅 `{name,status}` 后 scope=0、role_org=0 行，详见[隔离验证](../06-verification/01-后端隔离测试.md)。
- **前端实测：**真实 RolePage/ProTable 载入自定义范围角色，点击“禁用”，mock service 观察到精确 `{name:'审查自定义角色',status:0}`，没有 permissionScope 或 deptIds；没有用重写事件函数代替组件。
- **影响：**全部/自定义范围角色的用户可见范围退化：DataScopeResolver 对 scope0 实际按 SELF 处理，自定义跨部门数据因此不再可见；原 scope3→0 虽也改了存储值，其当前有效范围仍为 SELF。不是“所有角色都变成零数据”，也不是仅按钮文字错误。
- **建议：**优先采用独立状态接口或真正可区分缺省/显式 0 的局部更新；部门关联仅在明确提交相应范围变更时替换。前端不能靠重复传旧表格值替代后端契约修复。
- **验收：**scope=1/2/3 分别启停两次，范围不变；scope=2 的部门 ID 集合完整保留；显式编辑范围/清空部门仍按规则执行；真实请求和持久化结果均断言。

## UI-013｜P2｜角色 scope0 的显示、回填与后端语义不一致

- **证据状态：真实 RolePage + ProComponents DrawerForm + antd Radio 的 JSDOM 实测。**
- **触发：**角色原 `permissionScope=0`（列表映射为“无”），点击编辑，只改名称或备注后保存。
- **实际：**编辑 initialValues 使用 `editingRole.permissionScope || 3`，把合法 0 回填为 3；表单选项也只有 1/2/3。用户没有主动调整数据权限，保存却提交 scope=3。
- **期望：**界面显示、回填和后端解释一致；若0是旧值/缺省值，应明确归一化或迁移策略，不能一处显示“无”、另一处显示“仅本人”。
- **证据：**[合法 0 的显示映射](../../zhul-erp-frontend/src/pages/system/role/index.tsx#L63)、[编辑默认值](../../zhul-erp-frontend/src/pages/system/role/index.tsx#L551)、[提交表单值](../../zhul-erp-frontend/src/pages/system/role/index.tsx#L244)。真实测试载入 scope=0 角色，点击实际编辑入口，DOM 中“仅本人数据（默认）”radio 已 checked；没有 mock DrawerForm 或 Radio。
- **影响：**管理员会被错误的权限标签误导，编辑无关字段会改写范围编码。进一步核实[DataScopeResolver](../../zhul-erp-backend/src/main/java/com/zhul/erp/framework/security/DataScopeResolver.java#L83)：0和3当前都落入SELF，因此**不能据此称实际扩大授权**；该补查已将本项由P1降P2。UI-012清空自定义部门仍为独立P1。
- **建议：**先定清0是合法“无”还是旧值/缺省，统一显示与后端执行；需要保留时用 `??` 表达缺省，需要归一化时明确迁移，增加编辑无关字段的回归用例。
- **验收：**scope=0 打开编辑正确表示且保存不变；1/2/3 同样无变化；显式更改权限才改变请求范围。

## UI-014｜P1｜角色权限尚未加载就能保存，可能清空或串用上一角色权限

- **证据状态：真实 RolePage/DrawerForm/Tree 的 JSDOM 实测 + 后端替换式保存源码确认。**
- **触发：**点击角色的“分配权限”，在菜单树/当前权限请求未完成时点击“保存权限”；或先打开角色 A 再打开 B，B 的请求较慢。
- **实际：**`openAssign` 在 await 前先打开抽屉，未清空旧 checkedKeys/rawMenuTree，也无 loading 状态；保存按钮始终可用，直接把当前 checkedKeys 传给当前 permRole。首次打开是空数组，后续可能为上一角色的数组。后端 `assignRoleMenus` 先删除该角色现有菜单再重建，空载荷不是无操作。
- **期望：**当前角色的权限已成功加载并可编辑后才允许保存；失败保持明确错误，不使用旧角色数据。
- **证据：**[打开后才异步加载](../../zhul-erp-frontend/src/pages/system/role/index.tsx#L224)、[保存按钮与载荷](../../zhul-erp-frontend/src/pages/system/role/index.tsx#L665)、[后端替换现有授权](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/MenuServiceImpl.java#L255)。实测延迟 `getRoleMenuIds` Promise，真实抽屉已出现“保存权限”；点击后 service 实际收到 `assignRoleMenus('R14',[])`，随后才完成原权限响应。
- **影响：**管理员操作可撤销整角色菜单/按钮权限，或误赋上一角色已选权限；不绕过服务端可分配范围校验，风险来自当前授权范围内的误配置。
- **建议：**按角色 ID 跟踪加载状态与请求序号；打开时清编辑态，loading/failed 禁用保存；成功后建立基线，提交阶段也校验对应角色及加载完成。
- **验收：**延迟、失败、快速 A→B 切换时保存均不可用或只提交 B 的完整新值；请求迟到不能覆盖 B；首次空权限角色也需加载成功后才允许明确保存空集。

## UI-037｜P3｜编辑角色的部门数据晚返回时，关闭后又弹出编辑抽屉

> 2026-11-03 整改中新发现（Claude，批次 C 后续），不属于 2026-11-01 审查基线。

- **证据状态：真实 RolePage + DrawerForm 的 JSDOM 实测（修复前代码可复现）。**
- **触发：**先点「自定义部门」角色 A 的「编辑」，A 的部门请求较慢；再点角色 B 的「编辑」，B 的抽屉打开后关闭；A 的部门数据此时返回。
- **实际：**`openEdit` 在 await 前就设置了编辑角色，返回后无条件 `setEditingDeptIds` 并 `setDrawerOpen(true)`。抽屉在用户关闭后又自行弹出，标题是角色 B，部门初始值却是 A 的；若把 B 的范围改成自定义部门，会带入 A 的部门。部门加载失败时抽屉静默不开，没有提示。
- **期望：**只有最后一次点击的编辑请求生效；点「新增」或换角色后，迟到的回包不再打开抽屉；加载失败给出提示。
- **证据：**[openEdit](../../zhul-erp-frontend/src/pages/system/role/index.tsx)（修复前版本见 `develop` `ec3e24bf`）。
- **影响：**管理员可能在不知情时把别的角色的部门存进当前角色；当前抽屉已打开时表单初始值只在挂载时读取，界面不变，因此主要在关闭后重新弹出时出错，定为 P3。
- **验收：**A 慢、B 快或 B 无需加载时，关闭 B 后 A 返回不再弹出；只显示和提交最后打开角色的数据；加载失败有提示。

# 错误恢复、字典与列表一致性待整改

## UI-006｜P2｜错误页“重试”不能恢复成功页面

- **证据状态：静态确认；单据模板已追加真实 React 组件 JSDOM 实测。未做本项浏览器网络故障实测。**
- **触发：**单据模板首次取类型/版本失败，网络恢复后点重试；或运营商品详情的商品基础信息首次 GET 失败后点重试。
- **实际：**单据模板 `refresh()` 重发接口，但 `loadTypes/loadVersions/refresh` 均不清空 `error`，成功仍命中 `if(error) return ErrorHint`。运营商品详情错误页只调用 `content.load`，商品基础信息的 `productApi.get(id)` effect 不会重跑，外层 `error` 也不会清空。两处都需要整页刷新才能走出错误态。
- **期望：**重试重新执行对应失败资源、清错误并显示加载，成功后恢复完整页面；独立资源可单独恢复。
- **证据：**[单据模板加载与 refresh](../../zhul-erp-frontend/src/pages/system/document-template/index.tsx#L191)、[模板错误页](../../zhul-erp-frontend/src/pages/system/document-template/index.tsx#L304)、[运营商品基础信息加载与错误页](../../zhul-erp-frontend/src/pages/operations/products/detail.tsx#L156)。
- **影响：**业务设置/单据模板，运营管理/营销商品详情；暂时网络错误会变为本次 SPA 生命周期内不可恢复的错误页。
- **建议：**统一可重试的加载函数，开始请求清 error，重试涵盖失败资源；禁止错误页绑定无关资源的 reload。
- **验收：**分别让模板 types、versions、商品 get、content 失败一次，再成功，点一次重试即可恢复；连续失败显示最新原因，不能无限空白或永久旧错误。

深审追加：挂载真实 DocumentTemplatePage 和 ErrorHint，mock types 首次 reject“temporary failure”、第二次 resolve，versions 正常返回；点击真实“重试”按钮后 types 调用数变为 2，但 DOM 仍显示旧错误且主页面不存在，实测确认永久错误态。实拍抽屉另发现错误页的 onRetry 直接绑定 onClose（`warehouse/shoots/index.tsx:395`），其“重试”实际关闭抽屉，应随同错误恢复体验整改；本分支仅静态确认。

## UI-007｜P3｜租户和套餐列表缺少三项固定审计字段

- **证据状态：静态确认；性质为仓库 UI 规范偏差，不是后端数据未记录。**
- **触发：**打开租户管理或套餐管理分页列表，想核对最近修改人和时间。
- **实际：**两个可编辑分页业务列表只渲染“创建时间”，然后直接进入操作列，没有“创建人、更新时间、更新人”。前端 service 类型已经具备四字段，无需推测数据库缺字段。
- **期望：**按仓库明确规范，在业务字段后、操作列前固定显示“创建时间→创建人→更新时间→更新人”。
- **证据：**[租户 columns 尾部](../../zhul-erp-frontend/src/pages/tenant/list/index.tsx#L357)、[套餐 columns 尾部](../../zhul-erp-frontend/src/pages/tenant/package/index.tsx#L248)、[租户字段契约](../../zhul-erp-frontend/src/pages/tenant/list/service.ts#L3)、[套餐字段契约](../../zhul-erp-frontend/src/pages/tenant/package/service.ts#L3)、[统一规范](../../.claude/context/ui-design-patterns.md#列表页统一规范2026-09-22-确立)。这是分页、可增改的业务表，非日志/树排序例外。
- **影响：**平台管理员列表审计与排错效率；不应与 P1 数据丢失同优先级处理。
- **建议：**复用现有审计列工厂或补齐列，按 `formatDateTime` 显示，核实接口实际 JSON 值；不借此重排人工排序的树和字母列表。
- **验收：**两列表四列完整、顺序一致、空值合理；窄屏横向滚动仍可访问；修改后更新时间/更新人可核对。

## UI-008｜P2｜字典修改后业务下拉仍使用页面生命周期内旧缓存

- **证据状态：静态确认 + 真实 loadDict 函数内存 mock 实测。未调用真实服务。**
- **触发：**先打开商机/询盘等页面，使 `useDictOptions('crm_source_channel')` 取数；通过侧栏进入字典管理，修改、禁用或新增该字典项；再通过站内导航返回业务页。
- **实际：**`utils/dict.ts` 的模块级 Map 缓存成功 Promise，没有 TTL 或失效接口；字典维护只重载自己的列表，不通知这些缓存。新挂载的业务 hook 仍取旧 Promise。文字字典、付款方式、行业另有同类成功缓存，默认值/启用状态也可能一直不更新，直到整页刷新。
- **期望：**同一应用中修改字典后，相关下拉及显示名按约定刷新，停用项不能作为新录入可选项继续出现。
- **证据：**[整数字典缓存](../../zhul-erp-frontend/src/utils/dict.ts#L33)、[文字字典缓存](../../zhul-erp-frontend/src/utils/dict.ts#L101)、[字典保存后仅 loadItems](../../zhul-erp-frontend/src/pages/system/dict/index.tsx#L206)、[删除后同类行为](../../zhul-erp-frontend/src/pages/system/dict/index.tsx#L243)、[商机页面实际消费](../../zhul-erp-frontend/src/pages/crm/opportunity/index.tsx#L49)。
- **影响：**来源渠道、询盘等级、税率/货况/货期、单据条款、付款方式、行业等实际采用这些 hook 的页面。单纯整页刷新后可恢复；不是跨账户缓存泄漏结论，登录成功本身会整页跳转。
- **建议：**提供按字典类型失效与订阅机制，在成功变更后失效；或使用带版本/合理 TTL 的共享请求层，区分历史显示与新录入的启用项。
- **验收：**在同一浏览器文档中预热→改名/停用/新增→返回，展示与可选项更新；文字字典与付款方式同测；失败请求仍允许重试。

内存实测：读取真实 `utils/dict.ts`，只在内存附加测试导出 `loadDict`，用已有 TypeScript 编译并在 VM mock request。首调返回“旧渠道”，mock 服务改为“新渠道”后第二次调用实际仍返回“旧渠道”，request 调用总数为 1。无网络、无文件写入、未存测试产物。

## UI-009｜P2｜商品新建向导只加载前 100 个一级品类

- **证据状态：静态确认；边界条件为当前可见启用一级品类超过 100 个，未确认实际租户数据达到该数量。**
- **触发：**平台或租户可见的启用一级品类超过 100 个，使用商品新建向导选择排在后面的品类。
- **实际：**向导只请求 `categoryApi.page({page:1,pageSize:100,status:1})` 并存 `records`，忽略 `total`，没有后续分页/搜索/补载入口。第二步只遍历这份数组，因而第 101 个及之后的一级品类及其子类不能通过向导选择。
- **期望：**所有可见启用一级品类都可选；已有不分页的 `categoryApi.options(1)` 或树接口可评估复用。
- **证据：**[固定第一页请求](../../zhul-erp-frontend/src/pages/product/products/new.tsx#L181)、[唯一一级品类渲染](../../zhul-erp-frontend/src/pages/product/products/new.tsx#L750)、[service 已有完整 options](../../zhul-erp-frontend/src/pages/product/service.ts#L214)、[后端一级品类分页与完整选项](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/product/service/impl/CategoryServiceImpl.java#L56)。
- **影响：**品类规模较大的商品建档场景；数据量未达到条件时不触发，不能据此称现有生产用户已经受阻。
- **建议：**使用完整选项或可搜索分页选择器，保留租户行业范围过滤，不通过一次超大 pageSize 隐藏问题。
- **验收：**mock 101+ 个一级品类并包含子品类，第 101 个可搜索和选择，提交 categoryId 正确；停用品类与不可见行业不出现。

## UI-015｜P2｜销售统计下钻丢失业务员/事业部维度，列表与统计数对不上

- **证据状态：真实 SalesStatsPage + antd Select/Table 的 JSDOM 实测，service 与后端 Query 源码对照。**
- **触发：**在销售统计按某业务员、事业部筛选，点击订单数、销售收入或毛利；按业务员分组点击某行同理。
- **实际：**`go(path,row)` 只将日期写进 URL，没有携带当前 ownerId/unit，也没有从 OWNER 行 key 补业务员条件。订单列表的初始化只读日期，且 Filters 没有 ownerId/businessUnitId；利润页只读 businessUnitId，ownerId 初始化为空。下钻展示更宽的数据，与用户点击的统计值无关。
- **期望：**保留日期、业务员、事业部以及当前行对应维度；目标页按完整上下文请求并展示筛选条件，受权限范围约束。
- **证据：**[统计请求含维度](../../zhul-erp-frontend/src/pages/sales/stats/index.tsx#L44)、[下钻只拼日期](../../zhul-erp-frontend/src/pages/sales/stats/index.tsx#L78)、[订单目标页初始筛选](../../zhul-erp-frontend/src/pages/sales/orders/index.tsx#L44)、[利润目标页初始化](../../zhul-erp-frontend/src/pages/finance/profit-stats/index.tsx#L29)、[后端订单 Query 已有 ownerId](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/sales/dto/SalesOrderPageQuery.java#L23)。事业部订单下钻还需协调后端 Query 支持，不能只加 URL 参数。

- **影响：**经理/跨事业部用户核对统计、查单和解释业绩；不据此认定越过后端数据权限。
- **建议：**集中定义统计下钻上下文，与目标 Query 契约逐字段对齐；缺少相应查看权限时明确提示，不静默跳更宽列表。
- **验收：**月份、业务员、事业部、汇总行分别下钻，目标请求条件与来源一致，订单数/收入/毛利可核对；只获本人权限的用户也不能扩大后端范围。

## UI-016｜P2｜客户当地时间的跨日时差被折回，早晚方向显示错误

- **证据状态：真实原函数的内存 VM 实测 + 客户详情渲染链静态确认；未做本项浏览器实测。**
- **触发：**客户使用与北京时间相差超过12小时的时区，如美国西海岸；打开客户详情的“客户当地时间”。
- **实际：**`localTimeInfo` 只格式化两个 HH:mm 相减，再把差值折回 ±12 小时，丢掉日期与真实UTC offset。当地钟面时间正确，旁边“比北京早/晚X小时”可能方向相反。固定时点 `2026-01-15T12:00:00Z`，北京20:00、洛杉矶04:00；真实Intl offset为UTC+08、UTC-08，实际晚16小时，但函数返回 `diffHours=8`，详情显示“比北京早8小时”。
- **期望：**用同一瞬间两个时区的UTC offset求差并保留真实跨日关系；当天/前一天的业务表达应明确，不能以最短钟面差替代时区差。
- **证据：**[只相减钟面并折回](../../zhul-erp-frontend/src/pages/customer/time.ts#L38)、[详情按正负渲染早晚](../../zhul-erp-frontend/src/pages/customer/detail.tsx#L91)。VM直接transpileModule读取真实time.ts并调用导出函数，同时调用同文件utcOffsetLabel核对；输出洛杉矶`{time:'04:00',diffHours:8}`，未重写被测函数。
- **影响：**跨日客户的联络时机判断与排期；工作时间标签按当地钟面计算，本项不声称该标签也错误。
- **建议：**保留具体时区日期/offset，避免把差压回±12；明确夏令时取同一个at值，小时差可含半小时/45分钟。
- **验收：**覆盖北京、洛杉矶、纽约、跨国际日期变更线、半小时时区和夏令时前后；当地时钟、相对北京早晚和跨日说明都与同一瞬间的Intl结果一致。

## UI-017｜P2｜关闭后旧详情回包覆盖新出库单，完成打包提交旧单

**证据状态：真实 PackDrawer / BoxEditor / AntD 组件在 JSDOM 复现；service 使用内存 mock。后端接收路径静态确认，未发真实打包请求。**

- **触发 → 实际 / 期望：** 打开待打包单 A（id1），详情请求较慢；关闭抽屉后打开 B（id2），B 详情先返回；A 后返回。实际 B 内容被替换成 A，点击“完成打包”调用 `outboundApi.pack(1, A的箱子, …)`，虽然组件当前 `id` 仍为 2。期望关闭或切换后，旧请求不得再修改当前抽屉；提交目标必须与本次打开的单据一致。
- **可达链：** [列表打包入口](../../zhul-erp-frontend/src/pages/warehouse/outbounds/index.tsx#L126) 设置 `packing`；[同一个 PackDrawer](../../zhul-erp-frontend/src/pages/warehouse/outbounds/index.tsx#L347) 始终挂载，关闭只把 id 置空。Drawer 的 `destroyOnHidden` 销毁内部内容，不会卸载外层函数组件的 effect。[详情 effect](../../zhul-erp-frontend/src/pages/warehouse/outbounds/dialogs.tsx#L80) 没有取消或请求序号检查，任何回包都会 `setOb/setPhotos/setBoxes`；[submit](../../zhul-erp-frontend/src/pages/warehouse/outbounds/dialogs.tsx#L111) 使用 `ob.id`，不是当前 prop 的 id。
- **接口对应：** [真实 service 的 pack](../../zhul-erp-frontend/src/pages/logistics/service.ts#L303) 将该 id 放进 `PUT /api/v1/logistics/outbounds/{id}/pack`，并转换箱内行字段；[后端 pack](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/logistics/service/OutboundService.java#L254) 允许待打包或已打包单据，按 URL id 锁定和替换装箱记录。A 仍可见且状态允许时，后端没有理由知道用户本次打开的是 B；这是前端会话目标串用，未认定为后端权限绕过。
- **影响与边界：** 用户可能误操作刚关闭的 A，B 没有完成打包；若 A 已打包则可能覆盖其装箱数据。标题、型号也会变成 A，细心用户可能察觉，因此不描述为“仍显示 B 却隐蔽写 A”。必须存在回包乱序；一般同步快速点击不必然复现。
- **同型静态分支：** [实拍任务详情](../../zhul-erp-frontend/src/pages/warehouse/shoots/index.tsx#L291)、[货代账单详情](../../zhul-erp-frontend/src/pages/logistics/statements/index.tsx#L150)、[只读出库详情](../../zhul-erp-frontend/src/pages/warehouse/outbounds/dialogs.tsx#L452) 也未隔离旧回包。本轮仅对 PackDrawer 做真实组件复现；这些分支应一并检查，不能声称已逐个实测或都已错写。
- **建议：** 在 effect 清理时废弃响应或取消请求，以本次打开序号核验异步结果；保存、上传及其他异步写回也绑定同一单据会话。提交前校验当前单据身份，避免仅比较标题或只禁用首次加载按钮。
- **验收：** 保留“当前 B 正常返回 → pack id2”的对照；再测 A 慢、关闭、B 快、A 最后返回，始终只能显示和提交 B；补测 A 失败回包、关闭后回包、同一 id 重开以及保存/上传中切换，旧结果不污染新会话。

## UI-018｜P2｜事业部信息晚到会清空正在填写的费用草稿

**证据状态：真实 ExpensePage、真实 useBusinessUnits hook 与 AntD 输入组件在 JSDOM 复现；仅网络和无关外壳组件使用 mock。**

- **触发 → 实际 / 期望：** 首次进入费用页，事业部信息请求尚未完成；立即打开“新建费用单”并输入名称。随后响应带 `myUnitId: 7`。实际已输入名称被清空，订单选项重新请求；未点击保存。期望异步补齐默认事业部时保留用户已填写内容，或在基础信息就绪前明确阻止开始填写。
- **原因：** [useBusinessUnits](../../zhul-erp-frontend/src/utils/businessUnit.tsx#L63) 初值为 EMPTY（没有 myUnitId），完成请求后更新 info。[ExpenseDrawer 初始化 effect](../../zhul-erp-frontend/src/pages/finance/expenses/index.tsx#L110) 把 `bu.myUnitId` 与 `open/editing` 一起列为依赖；事业部到达后再次执行全表单回填，重设名称、金额、付款方式、备注、附件、分摊等，而非仅补默认事业部。[依赖与选项重载](../../zhul-erp-frontend/src/pages/finance/expenses/index.tsx#L140) 可直接对应本次第二次 soItems 调用。
- **真实组件结果：** 在真实页面点击新建后输入 `AUDIT-DRAFT-NAME`，先断言输入存在，再 resolve 事业部 mock 响应；等待后名称实际为 `''`，`expenseApi.soItems` 共调用 2 次，`expenseApi.create` 没有调用。名称丢失已实测；其他字段受同 effect 重置是静态确认，没有声称逐字段都测过。
- **影响与条件：** 对首次信息尚未到达、且用户主部门有事业部的用户可触发；若响应先于打开抽屉、缓存已完成或 myUnitId 未变化，则不满足本次条件。新建可丢草稿；编辑模式也可能重新回填原记录，丢掉已改内容，但编辑分支本轮未实测。没有发生数据库数据删除。
- **建议：** 单独管理“打开/切换记录时初始化”和“异步补默认事业部”；只给尚未编辑的事业部字段补默认值，不重置整张表单。也可在所需基础信息加载期间禁用新建，但应显示可理解的状态。
- **验收：** 延迟事业部请求，先输入名称、金额、备注并选择付款方式，再返回事业部，所有用户输入保留；补测已有记录编辑、无事业部、请求失败重试、响应已缓存，以及关闭后再次新建，默认值正确且不会带入上次草稿。

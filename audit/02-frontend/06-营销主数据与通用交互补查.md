## UI-019 · P2 · AI 测试结果未绑定配置，修改模型或切换服务商后仍显示旧的通过状态

**证据状态：真实 AiSettingsPage、AntD Form/AutoComplete/App 的 JSDOM 组件实测；service 使用受控 Promise。未调用模型或验证真实凭据。**

- **可达触发与实际：** ①Claude 配置测试通过后，直接把解析模型改为一个未测试的名称；模型输入已改变，页面仍显示“测试通过”“解析模型可用”，测试接口仅调用1次。②发起 Claude 测试，返回前改选 OpenAI；选择操作虽立即清空结果，但迟到的 Claude 成功响应再次写入，页面按当前服务商显示“OpenAI 已确认身份”。③当前保存的选择仍是 Claude，表单选中 OpenAI 后测试成功但不保存；顶部同时显示“AI 已就绪 / 测试通过”和“Claude · API Key”，而分项结果描述 OpenAI。三种情形均已独立执行，不靠相似代码推断。
- **期望：** 测试结果对应发起请求时的服务商、方式和模型/Key等配置快照；相关输入变化或服务商切换后，旧结果失效。顶部描述已保存配置时，不套用未保存草稿或其他服务商的测试结果。
- **原因与位置：** [select 清空状态但不失效旧请求](../../zhul-erp-frontend/src/pages/system/ai-settings/index.tsx#L405)；[runTest await 后直接 setTestResult](../../zhul-erp-frontend/src/pages/system/ai-settings/index.tsx#L429)，没有配置版本/请求归属检查。[onValuesChange](../../zhul-erp-frontend/src/pages/system/ai-settings/index.tsx#L1179) 只在 apiKey 改动时清除结果，parseModel/translateModel 等不清除。[顶部状态使用 testResult](../../zhul-erp-frontend/src/pages/system/ai-settings/index.tsx#L547)，但 [服务商元信息取已保存 config.provider](../../zhul-erp-frontend/src/pages/system/ai-settings/index.tsx#L533)，分项文案又取当前表单 meta，因而同一卡片混用不同配置。
- **已有保护与边界：** 切换服务商、撤销修改、正常保存会主动清一次测试状态；改 Key 也会清。问题是这些操作没有阻止先前请求随后重新写入，而且修改模型未清。保存仍由 [toPayload](../../zhul-erp-frontend/src/pages/system/ai-settings/aiConfig.ts#L36) 按当前表单构建，未证明 Key 被发给错误服务商、实际 AI 任务配置被串写或后端鉴权失效。本项不要求“测试通过才允许保存”，只是要求结果归属和展示准确；与 UI-002 请求重放、AI-004 诊断期限不同。
- **影响：** 管理员可能把未测试的模型或另一份配置误认为已验证；当前实际生效配置与绿色状态无法可靠对应，干扰配置排错。
- **整改与验收：** 用配置指纹/版本和请求序号校验返回归属；测试依赖字段变化即标为未测试。区分当前生效配置与草稿测试的状态。覆盖正常不切换对照、测试期间切换/撤销/改模型、迟到成功与失败、测试草稿后不保存，确保旧响应不能恢复已作废状态。

## UI-020 · P2 · 迟到的模型列表缓存被用于另一服务商

**证据状态：同一真实 AI 设置组件内，延迟模型列表 Promise 实测。**

- **可达触发：** Claude 下首次展开模型输入，模型列表请求尚未返回时改选 OpenAI；待 Claude 响应返回后，展开 OpenAI 的模型下拉。
- **实际：** 下拉出现 fixture 中仅由 Claude 请求返回的 `claude-delayed-wrong-provider`，底部却写“OpenAI 返回的模型”。整个过程 getAiModels 仅调用1次，其载荷 provider 为 claude；没有为 OpenAI 获取列表。
- **期望：** 列表按服务商/连接方式/相关账号配置缓存；切换后拒绝旧请求结果，当前服务商可以重新加载自己的列表。
- **证据链：** [fetchModels](../../zhul-erp-frontend/src/pages/system/ai-settings/index.tsx#L413) 用全局 models/modelsLoading 拦截重取，await 后无归属判断直接 setModels；[select](../../zhul-erp-frontend/src/pages/system/ai-settings/index.tsx#L405) 只清 models，不失效旧请求；[onOpenChange](../../zhul-erp-frontend/src/pages/system/ai-settings/index.tsx#L931) 再调用 fetchModels 时，旧列表已使 models 为真；[列表来源文案](../../zhul-erp-frontend/src/pages/system/ai-settings/index.tsx#L954) 使用当前 meta.consoleName。
- **边界与反证：** 正常不切换的 Claude 对照已实际获取正确列表并成功测试。模型字段允许手填推荐/其他模型；没有认定列表内每一项都会被自动保存或实际请求错误服务商。此项与 UI-019 的测试结果生命周期分开：只修 testResult 的失效不能修复 models 缓存与 modelsLoading 的归属。
- **整改与验收：** 按请求发起配置隔离缓存/加载状态，切换时使旧列表请求失效，返回时再次检查配置归属。覆盖 A慢→切B、B先回/A后回、切回A、请求失败、同服务商更换账号配置；下拉来源标签、请求provider和可见模型保持一致。

## UI-021 · P2 · 取消候选导入后迟到预览复活，界面可确认却提交空文件

**证据状态：真实 ImportDrawer、AntD Upload/Drawer/Table/Button 的 JSDOM 实测；文件内容和API均为 fixture。**

- **可达触发：** 在“添加候选”选择一个 Markdown 文件，解析尚未结束时点击“取消”；旧预览随后返回，再打开“添加候选”。父页面持续挂载抽屉，仅切 open，见[真实调用位置](../../zhul-erp-frontend/src/pages/product/candidates/index.tsx#L1249)。
- **实际：** 重新打开后显示已取消的 `cancelled-A.md` 和“确认导入1个”；点击确认时，真实事件函数向 importConfirm 提交的却是 **[]**。这是预览与待提交文件不同步，不是将旧文件成功导入。
- **原因与位置：** [pick](../../zhul-erp-frontend/src/pages/product/candidates/ImportDrawer.tsx#L85) 先 setFiles，再 await 预览；[close/reset](../../zhul-erp-frontend/src/pages/product/candidates/ImportDrawer.tsx#L58) 清 files/previews，却不使请求失效。迟到响应只重新填 previews；[确认按钮](../../zhul-erp-frontend/src/pages/product/candidates/ImportDrawer.tsx#L237) 只按预览的可写项计数启用，[confirm](../../zhul-erp-frontend/src/pages/product/candidates/ImportDrawer.tsx#L97) 则读取已被 reset 清空的 files。
- **已有保护与边界：** 上传区在 loading 时禁用，候选状态也会区分可写/跳过，但取消按钮仍可达。服务端 [CandidateImportRequest.files 的 @NotEmpty](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/product/candidate/dto/CandidateImportRequest.java#L15) 会拒绝空文件，且确认时重新解析；因此不能称为旧候选误导入、越权或业务数据损坏。组件测试的 confirm mock 只用于观察提交载荷，没有替代后端验证作成功导入结论。
- **影响：** 用户已取消的预览重现，按钮承诺可导入但实际请求被拒绝，必须重新选择；错误态来自前端会话归属而非文件本身。
- **整改与验收：** 取消/重新选择/关闭时失效当前预览请求，返回时检查抽屉会话和文件集版本；确认按钮还需检查预览与待提交文件集一致。覆盖解析中取消、关闭重开、重新选B后A迟到、解析失败再选、正常预览确认，保证旧会话不能恢复已丢弃状态。

## UI-017 的运营列表补充链：新筛选下被旧响应覆盖

本节归入[UI-017 跨记录/请求的异步归属问题](05-供应链与财务交互补查.md)，不新编号。运营素材列表的后果是筛选与结果不一致，**没有实测或声称媒体错单写入**。

- 在真实 MediaLibraryPage 中先延迟“全部”请求，再点击“有营销实拍”。第二次请求 hasMarketing=true 并先返回 `CURRENT-FILTER`，页面正常显示它；随后第一次“全部”请求返回 `OLD-UNFILTERED`，列表被覆盖为旧结果，而“有营销实拍”仍为选中样式。真实请求参数、真实 Segmented 和真实 Table 均参与验证，没有复制 load 函数自测。
- [load](../../zhul-erp-frontend/src/pages/operations/media/index.tsx#L58) 每次响应直接写 rows/total，没有请求序号；[筛选切换](../../zhul-erp-frontend/src/pages/operations/media/index.tsx#L188) 可以在表格加载时操作。因此网络快慢会使当前筛选与列表记录不一致；不依赖实际存在媒体数据的生产环境。
- 共享 ProductSelect 的对照显示[已有 seq 保护](../../zhul-erp-frontend/src/pages/product/components/ProductSelect.tsx#L41)能拒绝“新请求已发起后才回来的旧结果”，不能机械断言全部选择器都没有保护；但[空查询分支](../../zhul-erp-frontend/src/pages/product/components/ProductSelect.tsx#L34)只清 options、不递增 seq。实际先搜A、请求pending时清空输入，旧A结果返回后仍出现在空输入下。仅用于[商品关系选择器](../../zhul-erp-frontend/src/pages/product/products/cards/RelationCard.tsx#L94)的当前可达调用已核对，不按注释扩大到询盘/报价，也不另增加主题数。
- 后续修复应让列表/选择器结果绑定筛选版本，清空查询也使旧请求失效；测试正常查询、连续筛选、清空、慢响应及失败返回的最终展示。

## UI-022 · P2 · 列表操作只绑定鼠标点击，键盘 Tab 跳过修改/作废等入口

**证据状态：主审亲自在 BrowserOS 对真实费用页执行原生 Tab 与鼠标对照，页面使用第二轮 mock 数据；其他列表为本执行者静态核对。不是实际后端或全站键盘验收。**

- **真实可达触发：** 费用页布局检查覆盖1280和1024宽；原生键盘与鼠标对照实际只在 **1024×768** 执行。fixture显示两条有效、未锁定费用，主审先将焦点放到“查询”按钮，再连续使用真实 Tab。
- **实际与对照：** 主审记录的焦点顺序为表格滚动DIV→分页LI（第1页）→每页条数INPUT→BODY，跳过两行“修改/作废”共4个入口。正常查询按钮、表格滚动和分页控件可进入焦点，排除了页面整体不能接收Tab的解释。随后原生鼠标点击“修改”，成功打开“修改费用单 FE101”对话框，回填名称和金额268.5正常；未保存、未作废。这验证了操作存在且鼠标可用，但无法按相同顺序用键盘抵达。
- **DOM与原因：** 主审直接读取操作单元格a的href/role均为null，JavaScript读取的element.tabIndex值为0；本次没有单独读取getAttribute('tabindex')。没有显式tabIndex的结论来自[费用操作源码](../../zhul-erp-frontend/src/pages/finance/expenses/index.tsx#L769)：只有 `<a onClick>`，无href/tabIndex/onKeyDown，缺少原生按钮/链接的键盘行为。**不能误写为tabIndex=-1，也不能据该IDL值认定它实际进入Tab顺序**。
- **期望与影响：** 有权限且可见的列表操作应可通过键盘抵达并以原生按键触发，焦点清晰。当前依赖键盘或辅助输入的用户无法完成这些行操作；不是后端拒绝权限或记录不可修改。

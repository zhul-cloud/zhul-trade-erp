## UI-001｜P1｜多选上传的附件被后完成的上传覆盖

- **证据状态：静态确认 + 真实 React/antd Upload 组件的 JSDOM 实测；未做本项浏览器实测。**
- **触发：**在复用 `AttachmentWall` 的单据中，一次选择两份或更多附件；等待上传结束再保存。
- **实际：**`UploadTile` 开启 `multiple`，在每次 `beforeUpload` 中独立启动异步上传。同批文件持有同一轮渲染的 `onUploaded`，而父组件回调为 `onChange([...value, a])`。各回调基于相同旧 `value` 构造新数组，后完成者覆盖先完成者。已有附件仍在，新上传的多份中可能只留下最后完成的一份。文件上传成功不等于附件 ID 已保留在表单中。
- **期望：**每个成功上传的附件都累加到最新列表，删除、关闭表单等并发操作也不被迟到回调覆盖；批量选择需按剩余数量限制。
- **证据：**[并发上传入口](../../zhul-erp-frontend/src/pages/warehouse/components.tsx#L330)、[捕获旧 value 的回调](../../zhul-erp-frontend/src/pages/warehouse/components.tsx#L413)、[采购回价同类实现](../../zhul-erp-frontend/src/pages/inquiry/my-tasks/QuoteAttachments.tsx#L38)、[附件上传 service](../../zhul-erp-frontend/src/pages/warehouse/service.ts#L349)。费用/收入保存都将当前列表映射为附件 ID，例如[其他收入](../../zhul-erp-frontend/src/pages/finance/other-incomes/index.tsx#L105)、[采购发货](../../zhul-erp-frontend/src/pages/purchase/shipments/ShipmentDrawer.tsx#L167)。这是可达的完整上传→表单→提交链，非孤立组件推测。
- **影响：**采购询价回价、采购发货、采购入库及不良凭证、付款/供应商退款、费用、报销、客户退款、其他收入等复用入口。业务记录会遗漏凭证，用户需重新核对并添加。
- **建议：**在状态拥有者处使用函数式追加或维护最新列表引用；复用组件接收明确的 `onAdd`/`onRemove`，而非让异步回调覆盖整份旧数组。统一处理上传中状态、数量上限和关闭后回调。
- **验收：**原有 1 份附件，单次选择 3 份，按 3→1→2 顺序完成后应恰有 4 个不同 ID；上传期间删除原附件不得复活；保存请求包含全部有效附件 ID；单据再次打开仍一致。

模拟说明：Node 内存中按组件原表达式创建同一个 `value=[]` 的两个完成回调，依次传 `{id:101}`、`{id:102}`，实际结果为 `[102]`，期望 `[101,102]`。这验证闭包覆盖机制，不替代真实浏览器及附件服务测试。

深审追加：用 testing-library/JSDOM 挂载真实 `AttachmentWall`、`UploadTile`、antd `Upload`，仅 mock 上传/预览 service 与主题/外壳，不重写上传状态逻辑。通过真实文件 input 一次选择两份 File，分别控制两个 Promise 完成，实际 DOM 状态 `[101]→[102]`；原有附件 10 上传中被用户删除后，迟到上传完成又变为 `[10,11]`，证明删除项会复活。逐份选择并等待完成的对照用例保留 `[101,102]`。3 例均执行通过（断言为缺陷见证，不代表已修复），细节见[自动化验证](../06-verification/02-前端自动化验证.md)。

## UI-002｜P1｜令牌刷新后的请求重放绕过业务错误校验

- **证据状态：静态确认 + 真实拦截函数的内存 mock 实测。未调用真实后端。**
- **触发：**任一写操作因 access token 过期返回业务 `code=401`，刷新成功后，重放请求又返回 HTTP 200、业务 `code=403` 或其他非零业务码。
- **实际：**响应拦截器用裸 `axios` 重放并直接返回，该实例没有当前 Umi 请求的业务码拦截器。重放响应不再经过下方 `code !== 0` 分支。大量 service 直接 `.then(r => r.data)`，业务失败可作为 resolved 结果进入成功路径。若重放发生 HTTP 错误，当前 catch 又将其统一当令牌失效处理，可能无故退出登录。刷新失败分支也在跳转后返回原 401 响应，没有 reject。
- **期望：**首次请求和重放请求采用相同业务码校验；非认证类业务错误应按真实原因 reject；认证失败终止原请求的成功链。
- **证据：**[401 与裸 axios 重放](../../zhul-erp-frontend/src/requestErrorConfig.ts#L185)、[重放异常与原响应返回](../../zhul-erp-frontend/src/requestErrorConfig.ts#L204)、[后端认证/权限失败使用 HTTP 200](../../zhul-erp-backend/src/main/java/com/zhul/erp/framework/security/SecurityConfig.java#L60)、[其他收入 service 直接解包](../../zhul-erp-frontend/src/pages/finance/other-incomes/service.ts#L10)、[收入保存后的成功提示](../../zhul-erp-frontend/src/pages/finance/other-incomes/index.tsx#L113)。例如更新收入接口重放收到 `403,data=null` 时，页面不会因返回数据为空而自然报错，可继续提示“已保存”并关闭。
- **影响：**全站 Umi 请求，包括财务单据、主数据、系统维护。仅在过期后重放窗口触发，普通有效 token 的业务失败仍会被当前拦截器正确拒绝。
- **建议：**提取统一响应校验函数同时应用于首次与重放响应；限制刷新重试次数；重放 HTTP 错误按原错误传播；刷新失败跳转后抛认证异常，确保不继续成功流程。
- **验收：**mock 首次 401→刷新 0→重放 403 时必须 reject 且不显示成功、不退出有效新登录；重放 500 保留错误；重放 0 仅成功一次；刷新失败不执行调用方成功回调；并发 401 仍只刷新一次。

实测方法与结果：使用仓库已有 `node_modules/typescript` 读取并在内存 `transpileModule` 编译真实 `src/requestErrorConfig.ts`，用 Node `vm.runInNewContext` 加载，mock `axios`、auth refresh、tokenStore、antd 和 window；直接调用 `errorConfig.responseInterceptors[0][0]`。输入首次 `code=401`、刷新成功、重放 `code=403`，输出 `resolved=true, code=403, replays=1, redirect=null`。全程无网络、无真实令牌、无新测试文件和产物；没有运行完整 Umi/浏览器栈。

# 身份、会话与对象权限待整改

基线 `09da3dc3c790c8c1b729cad8d195a66944d7546e`；2026-11-01。本文由入口、权限计算、服务和数据库条件交叉追踪确认，**没有执行账号接管、读取真实令牌、跨租户破坏或附件窃取测试**。全部待整改，P1 表示应优先处理，不表示已知生产入侵。

## SEC-001 · P1 · 登录日志将在线访问凭据返回给同租户普通登录用户

**证据与原因**：`LogController.listLoginLogs` 没有菜单或按钮权限限制，全局过滤仅要求登录。[控制器](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/controller/LogController.java#L64)、[全局过滤](../../zhul-erp-backend/src/main/java/com/zhul/erp/framework/security/SecurityConfig.java#L61)。登录成功时将实际 access token 传给 `recordLoginLog`，并非独立的会话展示编号；日志 JSON 写入 `token_id`，查询 VO 在会话在线时原样设置 `tokenId`。[登录记录调用](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/auth/service/impl/AuthServiceImpl.java#L201)、[存储](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/LogServiceImpl.java#L334)、[返回](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/LogServiceImpl.java#L437)。认证过滤器正是将该凭据与 Redis 会话记录配合使用。[认证](../../zhul-erp-backend/src/main/java/com/zhul/erp/framework/security/JwtAuthenticationFilter.java#L35)。

**成立范围**：有同租户其他在线账号记录时，日志接口可返回仍有效的认证凭据。查询存在租户过滤，不能据此称为匿名读取或直接跨租户读取。强制下线按钮有权限注解，也不能抵消查询响应泄露。

**影响**：原本只应展示登录活动的接口扩大为凭据披露面，日志存储本身也持有可用登录凭据。即使增加日志页面权限，管理员日志列表仍不应返回可直接用于认证的值。

**整改方向**：日志与前端只使用不可用于认证的会话标识；后台会话管理内部映射并校验操作对象归属；查询/导出补齐日志查看权限，响应模型从类型上移除 access token。评估历史存储及既有会话的处置范围。

**验收**：普通账号不可查询管理日志；授权日志响应、导出及日志持久化内容均不包含访问凭据；会话管理仍能按独立 ID 正常撤销指定会话，并拒绝越权目标。使用独立 fixture 验证，禁止把真实令牌写入测试报告。

## SEC-002 · P1 · 用户管理写操作缺少目标租户约束

**证据与原因**：启停、编辑、删除、管理员重置密码具有各自功能权限，但 `UserServiceImpl` 的查询/更新只使用传入 `userId` 或其关联 `accountId`，未校验目标租户。同步账号状态、邮箱也仅按 `userId`。[启停](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/UserServiceImpl.java#L144)、[编辑](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/UserServiceImpl.java#L205)、[删除](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/UserServiceImpl.java#L248)、[重置密码](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/UserServiceImpl.java#L263)。[MyBatis 配置](../../zhul-erp-backend/src/main/java/com/zhul/erp/framework/config/MybatisPlusConfig.java#L19) 只安装分页拦截器，没有为这些 SQL 自动追加租户条件。

**成立范围**：调用者持有相应用户管理操作权限，并指定非本租户目标。列表过滤和 UI 按钮隐藏不能替代写接口的目标校验。本文不提供实际账号、目标 ID 或调用脚本。

**影响**：租户内的用户管理权可作用于其他租户对象，破坏账号状态、资料和认证信息的隔离。

**整改方向**：先通过统一的“本租户可管理用户”查询取得目标，再以目标租户和 ID 联合更新；同步账号更新复用相同边界。明确平台管理员、自身账号和受保护管理员的管理规则；校验提交的角色、部门、岗位引用是否在允许范围。

**验收**：租户 A/B fixture 中，A 的普通用户管理员对 B 的编辑、启停、删除、重置均被拒绝且数据库无变化；A 内被授权的操作成功；平台跨租户管理仅走明确的平台能力。复核事务内用户表与账号表同步，不以影响行数为零当作成功。

## SEC-003 · P1 · 角色、部门及角色授权缺少对象归属校验

**证据与原因**：

- `RoleServiceImpl.updateRole` 直接按角色 ID 读取/更新；部门分配、删除和部门查询按角色编码操作，未要求角色属于当前租户。[角色修改](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/RoleServiceImpl.java#L140)、[关联部门](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/RoleServiceImpl.java#L170)。
- `MenuServiceImpl.assignRoleMenus` 检查调用者可分配哪些资源，却不检查**目标角色**归属；随后直接按 `roleCode` 删除并重建权限关系。[授权逻辑](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/MenuServiceImpl.java#L257)。
- `DeptServiceImpl.updateDept/updateStatus/deleteDept` 按部门 ID 读取；更换上级时也未校验上级部门租户。名称重复和子节点检查使用当前租户查询，不能为已经读取的外部目标补上归属约束。[编辑](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/DeptServiceImpl.java#L110)、[启停](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/DeptServiceImpl.java#L181)、[删除](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/DeptServiceImpl.java#L209)。

**成立范围与影响**：相应功能授权不等于可维护所有租户的角色或组织。目标 ID/编码属于其他租户时，缺少服务端阻断；共享角色还需要明确“可引用”与“可修改”边界。`MenuServiceImpl` 的全局菜单 CRUD 有平台身份校验，本条**不认定**普通租户可创建全局菜单；资源子集校验是现有有效保护，但没有覆盖目标对象。

**整改方向**：统一角色/部门的可管理对象解析，对共享角色只读；授权变更先校验目标角色，再校验可授予资源。部门父节点、负责人和角色自定义部门引用均校验租户归属。与 [UI-012～014](../02-frontend/02-表单草稿与页面切换.md) 的前端误写问题分别修复：前端正常请求也可能误写，不能用本条后端归属修复代替。

**验收**：不同租户及平台共享角色的读写矩阵；任何越界操作在删除旧关联前拒绝，旧权限/部门关系保持原样；合法本租户分配及平台维护流程正常。

## SEC-004 · P1 · 禁用、删除或管理员重置密码未撤销已有会话

**证据与原因**：用户启停/删除只更新数据库状态，管理员重置只更新密码哈希，均未删除访问/刷新会话。`JwtAuthenticationFilter` 每次请求仅验证 JWT 与 Redis 会话存在性，不读取账号启用状态；`EffectivePermissionResolver` 读取账号及角色资源时同样没有过滤账号禁用/删除状态。[用户变更](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/UserServiceImpl.java#L144)、[认证过滤](../../zhul-erp-backend/src/main/java/com/zhul/erp/framework/security/JwtAuthenticationFilter.java#L35)、[权限计算](../../zhul-erp-backend/src/main/java/com/zhul/erp/framework/security/EffectivePermissionResolver.java#L52)。

**成立范围**：目标在变更前已有有效会话，且相应 Redis 会话仍在。源码中 access token 时长为 7200 秒，因此禁用/删除后可能继续访问至既有 token 到期；不是“永久有效”。`refresh` 会检查账号启用状态，**禁用/删除后不能据本条断言刷新也成功**。管理员重置密码不改变启用状态，需同时核对刷新会话的失效策略。[刷新时检查](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/auth/service/impl/AuthServiceImpl.java#L252)。

**影响**：管理员认为已经停用或收回的账号仍能使用未到期凭据，安全操作不能即时生效。已有手动强制下线实现能撤销 access/refresh 会话，可作为统一会话撤销的参考，但当前用户变更没有调用该路径。

**整改方向**：禁用、删除及密码重置调用按账号撤销所有会话的内部服务；认证/授权增加状态有效性约束或会话版本检查。明确正常修改密码与管理员重置是否允许保留当前会话，确保策略与 UI 一致。

**验收**：独立账号正常登录后依次验证停用、删除、管理员重置；旧 access/refresh 按策略立即失效；重新启用不恢复已撤销会话。事务失败不能呈现“已停用”却仍留下可用会话的成功结果。

## SEC-005 · P1 · 附件链接未继承所属单据的数据可见范围

**证据与原因**：`AttachmentController.url` 先 `service.require(id)`，再按附件类型检查菜单，随后直接签发链接。[入口](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/attachment/controller/AttachmentController.java#L65)。`AttachmentService.require` 检查存在、未删除、当前租户；`link` 直接调用文件存储，没有根据 `ownerType/ownerId` 校验所属业务对象。[附件服务](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/attachment/service/AttachmentService.java#L343)。相比之下销售订单 `visible` 明确检查负责人数据范围。[订单可见性](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/sales/service/impl/SalesOrderServiceImpl.java#L1549)。

**成立范围与影响**：同租户、拥有该类菜单但仅能查看本人数据的账号，若取得其他负责人单据附件 ID，附件 URL 接口未复用单据的数据范围限制。现有租户检查有效，不能称为可任意读取其他租户附件；链接有签名/有效期也不能替代签发前的业务授权。

**整改方向**：按附件所属对象复用对应的可见性策略，区分未挂接附件的上传者与已挂接单据；查询链接、预览、下载、上传时指定 ownerId 的授权保持一致。公共商品素材与私有业务附件按已有业务规则区分，不统一粗暴封锁。

**验收**：同租户本人/他人/部门范围、跨租户、未挂接、已删除附件的矩阵；能看业务对象的人正常预览下载，看不到对象的人不能得到签名 URL。测试只使用无敏感内容的 fixture 文件。

## SEC-006 · P2 · 登录幂等缓存先于身份验证，且未绑定账号

**证据与原因**：登录方法最前面使用客户端提供的 `idempotencyKey` 读取缓存；命中直接返回缓存 `LoginResponse`，随后才是用户名、账号状态、密码校验。[缓存命中分支](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/auth/service/impl/AuthServiceImpl.java#L85)。缓存键未包含账号或已验证请求身份，成功响应缓存 10 秒。[缓存写入](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/auth/service/impl/AuthServiceImpl.java#L215)。

**成立条件**：短时间内复用了相同幂等键，或该键被其他调用者知晓。前端使用随机键能降低碰撞概率；没有证据说明键易猜、已经泄露或可无条件绕过认证，因此列为**条件性风险**，不列作已发生登录绕过。

**整改方向**：先完成必要身份验证，再复用成功结果；使幂等状态绑定已验证账号与请求语义，且不把客户端自报的幂等键当成取得认证响应的唯一条件。处理响应丢失重试时同时保持 Cookie/会话语义一致。

**验收**：相同账号合法重试保持幂等；不同账号、错误密码、已禁用账号与缓存键复用组合均不能获得缓存中的其他身份成功响应；过期及并发重复不产生多余有效会话。

## SEC-007 · P1 · 恢复租户会同时重新启用此前单独停用的用户

**证据与原因**：`TenantServiceImpl.updateStatus` 修改租户状态后，对该租户所有非删除账号和用户统一写入同一个状态，没有保存停用原因，也不区分租户停用前已经单独禁用的员工。[级联更新](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/tenant/service/impl/TenantServiceImpl.java#L203)。登录依据 `account.status` 判断账号是否可用，[登录状态判断](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/auth/service/impl/AuthServiceImpl.java#L108)。这是一条防御性源码确认，未用真实停用员工账号进行登录测试。

**触发与影响**：某员工因离职或单独限制已被禁用；平台将整个租户停用，再恢复启用。恢复操作把该员工也设为启用，覆盖了独立的账号停用决定。已删除账号被现有 `STATUS_DELETED` 条件排除，不会因此恢复；“普通租户可自行停用其他租户”也不成立，该服务有平台身份检查。

**整改方向**：租户状态与用户自身状态分别保存，登录/鉴权要求两者都有效；租户恢复只解除租户级限制，不改写员工状态。避免简单记录一份旧状态后全量回放而覆盖停用期间管理员的新决定。

**验收**：同租户预设启用、单独禁用、已删除三类 fixture 用户；租户停用期间均不能获得可用会话，恢复后仅原本允许且没有新增限制的用户恢复访问。覆盖停用期间修改员工状态、重复启停和事务失败。现有会话撤销另按 SEC-004 验证。

## 复核边界与排除项

本节为防御性源码审查，不含利用代码和生产验证。权限审查执行子任务被工具安全检查中断后停止，由主审接替只读调用链复核；未绕过检查继续账号接管式测试。后续应在专用环境按上述预期授权矩阵建立回归。

- [全量声明矩阵](01-接口权限矩阵.md) 的 86 个无 `PreAuthorize` 声明不等于 86 个漏洞。公共健康信息、登录入口、独立校验回调及有服务端兜底的接口应分别判断。
- 租户管理服务存在 `requirePlatform`，不能仅凭控制器注解缺失认定普通租户可管理租户；全局菜单写操作同样有平台限定。
- 系统账号密码使用 BCrypt；这里没有认定系统密码明文存储。租户第三方 API Key 的加密存储是项目允许的设计，不能以“入库”本身列为漏洞。
- 业务退款的数据隔离缺口见 [BUS-002](../01-business/02-销售与财务.md)，通用 AI 任务的附件信任边界见 [AI-003](../04-ai-and-operations/02-AI附件入口与权限.md)，不在本文重复计数。

## SEC-011 · P1 · 没有自动租户过滤，租户隔离全靠逐条手写条件

> 2026-11-03 整改中新发现（Claude，批次 B 方案讨论），不属于 2026-11-01 审查基线；是 SEC-002、SEC-003、SEC-009、SEC-010、BUS-002 的共同根因。

**证据与原因**：[编码规范「多租户规范」](../../.claude/rules/coding.md)要求「Repository 层查询必须自动注入 tenant_id 过滤（MyBatis 拦截器或 JPA @Filter）」，但 [MybatisPlusConfig](../../zhul-erp-backend/src/main/java/com/zhul/erp/framework/config/MybatisPlusConfig.java) 只安装分页拦截器（修复前版本见 `develop` `f705aaee`）。161 张表中 144 张有 `tenant_id`，代码里约 281 处手写租户条件；按 ID 读写（`selectById` 281 处、`updateById` 336 处）没有统一的归属校验，审查发现的越权多出在这类调用。另有 162 处读平台（tenant 0）共享数据（商品库、品类品牌、字典、配置等），简单套用 MyBatis-Plus 租户拦截器会把它们改成只看本租户。

**影响**：逐条修只能修掉已发现的漏写，新写的查询照样可能漏；规范与实现不一致，评审时容易误以为有自动过滤。

**整改方向（用户 2026-11-03 选定方案 C）**：分类租户拦截器——私有表 `= 当前租户`；平台共享只读表查询 `IN (0, 当前租户)`、写只限本租户；共享可写表（字典，PRD 允许租户维护全局项）读写都 `IN (0, 当前租户)`；本来跨租户的入口（登录、找回密码、权限计算、平台租户管理、迁移、后台任务）显式放进平台范围；没有租户上下文直接报错。按模块逐步启用，每个模块启用前演练 SQL 改写，并全量回归。

**验收**：所有带 `tenant_id` 的表都已分类且纳入拦截器；跨租户读写矩阵（私有、共享只读、共享可写）测试通过；编码规范改为与实现一致。

## SEC-012 · P3 · 用户启停接口不校验状态值，可借它删除用户或写入非法状态

> 2026-11-04 本机验收中新发现（Claude），不属于 2026-11-01 审查基线。

**证据与原因**：`PUT /api/v1/system/users/{userId}/status` 的 `status` 直接写入 `user_basic.status` 与 `account.status`，[UserServiceImpl.updateUserStatus](../../zhul-erp-backend/src/main/java/com/zhul/erp/modules/system/service/impl/UserServiceImpl.java) 只排除已删除的用户，不校验取值。用户状态的取值为 0-禁用、1-启用、2-已删除（`V1.3.26__user_status_deleted.sql`）。本机验收时传入 2，用户随即变为已删除，再调启停接口返回「用户不存在」，无法恢复。

**触发与影响**：只有「用户启停」按钮权限（`system:user:status`）、没有删除权限的人，可以传 2 删除同租户用户，绕过删除接口（`system:user:delete`）的权限码与删除流程。传 9 等非法值时，账号既不能登录，也不按停用统计。前端只会传 0 或 1，正常使用不受影响。仍受租户隔离约束，不能跨租户。

**整改方向**：启停接口只接受 0、1，其他值拒绝；删除仍只走删除接口。

**验收**：传 2、9、-1、空值均被拒绝，用户与登录账号状态不变；传 0、1 正常停用、启用并同步到登录账号。
